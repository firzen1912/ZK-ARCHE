## 2. Executive synthesis

1. **ZK-ARCHE should not treat a future SAPIC source as automatically semantics-preserving across generated backends.** On 2026-09-12, Tamarin issue #931 demonstrated that enabling `translation-state-optimisation` can change reachability semantics for a stateful lock example. On 2026-09-14, issue #932 separately showed SAPIC inferred typing can make a matching lock/unlock pair stop matching. For ZK-ARCHE's state-heavy replay, authorization, trust-mutation, retained-authority, and lineage models, translation itself must therefore become a qualified evidence boundary.
2. **Privacy/equivalence results need backend-commit and formula-feature gating, not merely a version string.** Tamarin issue #933 documented a specific soundness bug in guarded conversion of negated equivalence; PR #934 added a regression test and was merged to `develop` on 2026-09-18. The current latest public release remains 1.12.0 from March 2026, so a future ZK-ARCHE Tamarin privacy run must pin a build that demonstrably includes the needed fix and must retain a regression corpus for the exact equivalence constructs it uses.
3. **A stored proof artifact is not durable evidence unless it can be replayed/revalidated.** Open Tamarin issue #881 shows a case where a proof emitted by `--prove --output` is accepted during generation but later reload can become incomplete because normalization differs. A future Tamarin evidence bundle should therefore retain exact model/tool hashes, command flags, raw output, emitted proof, and an independent reload/revalidation result.
4. **These upstream Tamarin/SAPIC findings do not invalidate current ZK-ARCHE ProVerif evidence.** Exact-current ZK-ARCHE has direct `.pv` models, synchronized Rust/C mirrors, and a local exact-HEAD ProVerif qualification script. There is no current Tamarin/SAPIC model in the repository. ProVerif's official documentation independently supports trace and privacy/equivalence properties, making it a useful independent backend rather than evidence that SAPIC translation is correct.
5. R-004 remains `reproduce`. No roadmap/spec/code/ADR/assurance/debt claim advances today. The decision-changing next step is a small formal-toolchain qualification corpus before ZK-ARCHE adopts SAPIC/Tamarin as a claim-bearing backend.

### D20260919-F01 — SAPIC state translation is itself a security-evidence boundary

- **Novelty:** new.
- **Backlog owner:** R-004; adjacent TD-003.
- **Sources:** Tamarin issue #931, `[SAPIC] translation-state-optimisation changes proof semantics and is not sound`; Tamarin issue #932, `[SAPIC] inferred type annotations break matching lock/unlock pairs`; official Tamarin repository/release material.
- **Primary links:** https://github.com/tamarin-prover/tamarin-prover/issues/931 ; https://github.com/tamarin-prover/tamarin-prover/issues/932 ; https://github.com/tamarin-prover/tamarin-prover/releases
- **Source type / venue:** official upstream Tamarin issue tracker and official release page.
- **Publication/revision dates:** #931 opened 2026-09-12; #932 opened 2026-09-14; latest public Tamarin release 1.12.0 published March 2026.
- **Verified claim:** #931 provides a minimal SAPIC process where a second lock is unreachable without `translation-state-optimisation` but is reported reachable when that translation optimization is enabled, with a well-formedness warning. #932 demonstrates that current SAPIC type inference can annotate `lock` and `unlock` differently so a syntactically matching pair no longer matches. Tamarin's official repository explicitly supports process-calculus input translated to multiset-rewrite rules and includes non-monotonic-state examples.
- **Existing engineering owner:** R-004 / TD-003; no current SAPIC/Tamarin implementation owner is promoted.
- **Repository fact:** ZK-ARCHE currently models lifecycle/state directly in ProVerif `.pv` files and has no SAPIC/Tamarin source. R-004 nevertheless explicitly allows a pinned SAPIC+/ProVerif/Tamarin environment or mechanically synchronized model source as a future assurance direction.
- **Problem addressed:** a single higher-level formal source can reduce model drift only if its translation is semantics-preserving for the constructs ZK-ARCHE relies on. Replay continuity, trust mutation, lineage replacement, revocation, authorization generation, and retained authority are precisely the kind of stateful semantics where a translator defect could create a false proof or false attack.
- **Strongest distinct engineering idea:** make the translator/configuration part of the formal trusted-computing/evidence boundary. Before using SAPIC for claim-bearing ZK-ARCHE results, pin exact Tamarin commit/build, Maude version, translator flags and typing mode; prohibit unresolved `translation-state-optimisation` in qualification; retain generated backend model text/hashes; and run a small state-semantic regression corpus whose expected reachability is known independently.
- **Evidence maturity:** upstream software defect reports with minimal reproductions; not yet locally reproduced in ZK-ARCHE.
- **Limitations / uncertainty:** these issues do not imply all SAPIC/Tamarin translations are unsound. #931 is option/construct specific, #932 concerns inferred typing around lock/unlock, and ZK-ARCHE currently does not use SAPIC/Tamarin. Local reproduction against a pinned candidate toolchain is still required.
- **ZK-ARCHE inference:** a future "single source → multiple formal backends" architecture should be treated as a hypothesis to qualify, not as automatic model equivalence. Direct-backend models or generated-model review remain useful independent oracles until translation semantics are demonstrated for the ZK-ARCHE construct subset.
- **Wire / RAM / CPU / flash / dependency / trust / privacy impact:** no protocol wire/MCU resource impact. This adds development-time toolchain dependencies, retained generated artifacts, and regression runtime. It reduces assurance risk by making translation assumptions explicit.
- **Rust/C / vector/profile compatibility impact:** no Rust/C wire change. Representable formal counterexamples should still become Rust/C negative tests. Generated formal models should be hash-bound to the same spec/implementation anchor and exact repository HEAD.
- **Required next evidence:** locally reproduce #931/#932 on a pinned candidate Tamarin build; define the exact SAPIC construct subset ZK-ARCHE would permit; create stateful regression witnesses for lock/state mutation, replay epoch, trust replacement, and rollback/continuity; retain generated backend artifacts; compare semantic verdicts with direct ProVerif or hand-written Tamarin models where feasible.
- **Recommended disposition:** reproduce.

- **Publication/revision dates:** #933 opened 2026-09-14; #934 merged into Tamarin `develop` on 2026-09-18; latest public release 1.12.0 predates that fix.
- **Verified claim:** #933 demonstrates that a specific negated-equivalence formula was converted to the wrong guarded formula, causing logically true forms to be falsified in the supplied example. The issue is labeled critical/prover and is closed by #934. PR #934 says it fixes #933, adds a regression test, and was merged to `develop` on 2026-09-18. For each anonymity/unlinkability/equivalence theorem, record exact backend commit/build and formula constructs used, and retain micro-regressions covering those constructs. ### D20260919-F03 — Retained Tamarin proof artifacts require replay/revalidation, not generation-only success

- **Novelty:** refines.
- **Backlog owner:** R-004.
- **Source:** Tamarin issue #881, `In certain cases proofs emitted with --prove cannot be revalidated`.
- **Primary link:** https://github.com/tamarin-prover/tamarin-prover/issues/881
- **Source type / venue:** official upstream Tamarin issue tracker.
- **Publication/revision date:** opened 2026-07-07; still open when verified 2026-09-19.
- **Verified claim:** the issue documents a reproducible case where Tamarin emits a proof with `--prove --output`, the generated file can be re-run with proving, but a later ordinary reload reports a previously verified lemma as `analysis incomplete`. The report attributes the mismatch to different normalization of stored goals between in-memory proof construction and reload/parsing.
- **Existing engineering owner:** R-004 / TD-003 formal evidence provenance.
- **Repository fact:** ZK-ARCHE's current ProVerif formal gate already captures exact repository HEAD, exact model Git blob, ProVerif version, expected/observed query counts, result, and raw log. Retained formal-run documents also preserve scoped historical evidence. That architecture is a strong base, but it does not yet define Tamarin emitted-proof replay because Tamarin is not currently part of the gate.
- **Problem addressed:** a proof artifact that cannot be independently reloaded and checked is weaker durable evidence than a replayable artifact bound to exact tool/model state.
- **Strongest distinct engineering idea:** for any future Tamarin lane, require two separate success conditions: `generation/verdict PASS` and `replay/revalidation PASS`. Retain the source model hash, generated/translated model hash if applicable, exact binary commit/version, Maude version, all CLI/feature flags, raw output, emitted proof, and replay output. A replay mismatch is a qualification failure/evidence defect, not a warning to suppress.
- **Evidence maturity:** upstream reproducible software issue; ZK-ARCHE has not locally reproduced it.
- **Limitations / uncertainty:** #881 concerns certain proof shapes/normalization behavior; it does not mean every emitted Tamarin proof is unreplayable. Direct batch verdicts and stored interactive proof artifacts are related but distinct evidence surfaces.
- **ZK-ARCHE inference:** exact-head binding is necessary but not sufficient for durable multi-tool formal evidence. Re-execution/revalidation should be part of the artifact contract whenever the tool exposes a checkable proof representation.
- **Wire / RAM / CPU / flash / dependency / trust / privacy impact:** no protocol/target impact. Formal qualification runtime/storage increases modestly; evidence auditability increases substantially.
- **Rust/C / vector/profile compatibility impact:** none directly. Counterexamples found during replay/revalidation should still be converted to deterministic Rust/C negative tests when representable.
- **Required next evidence:** reproduce #881 on the chosen Tamarin candidate; define a replayable artifact manifest; test replay after clean-process reload; document how unreplayable output is classified; retain a small known-good and known-bad proof-replay corpus.

## 6. Cross-source synthesis

The decision-changing conclusion is not that ZK-ARCHE should avoid formal verification or avoid Tamarin. Tamarin remains specifically attractive for multiset-rewrite/stateful protocol analysis, while ProVerif remains a strong independent symbolic backend for trace and privacy/equivalence properties. The new upstream evidence changes the **trust boundary**: translation configuration, formula-feature support, exact patch level, and proof replay must be qualified artifacts rather than implicit assumptions.

For ZK-ARCHE, the safer progression is:

```text
current direct ProVerif models + exact-HEAD evidence
                  ↓
define canonical property/attacker matrix
                  ↓
introduce bounded Tamarin/SAPIC prototype
                  ↓
qualify translator + feature subset + exact build
                  ↓
retain generated models + proof/replay evidence
                  ↓
reconcile cross-backend verdicts and abstractions
                  ↓
only then broaden formal/privacy claims
```

This preserves the value of a future mechanically synchronized source without mistaking source synchronization for semantic equivalence between tools.
