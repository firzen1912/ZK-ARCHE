## 2. Executive synthesis

1. *Additional Messages in LAKE* `draft-selma-lake-additional-messages-00` (2026-11-02, **individual Internet-Draft**, not a normative ZK-ARCHE feature) proposes a profile-bounded handshake extension beyond the ordinary four messages. Per-index exporter-derived AEAD keys/nonces and exact-byte retransmission are mandatory within **that proposal**, as is waiting until final expected message before session completion.
2. The security-critical comparison is that regenerating a different plaintext with the same derived `(K_n,IV_n)` can violate AEAD nonce uniqueness; unacknowledged final flights and delayed session abort complicate authorized effect commitment. ZK-ARCHE's existing terminal `AUTH_3` consume-before-verification policy must not be silently reinterpreted as LAKE dedup semantics.
3. ACE WG `draft-ietf-ace-coap-est-oscore-12` (2026-11-02) describes secure certificate re-enrollment over existing OSCORE context **without new EDHOC**, and deliberately avoids EST payload transport in EDHOC EAD because new EDHOC may be absent. This supports keeping ZK-ARCHE explicit ENROLL authority/freshness/PoP independent of a live protected channel.
4. The ACE draft discourages server-generated private keys and ties local key generation to secure client entropy. A transport-protected remote key cannot automatically satisfy ZK-ARCHE local-sovereign key custody or R-005 entropy-readiness evidence.
5. **No local Rust/C/protocol/model/MCU execution** occurred. Both statuses remain `reproduce`, no protocol, credential, CA, OSCORE/LAKE or profile adoption occurred.

### D20261109-F01 — Single-use encrypted post-handshake flights require distinct dedup, completion and authorization gates

- **Novelty / backlog owner:** new external comparator/refines R-009 (P0); R-010 cross-reference only.
- **Source / date / type / primary link:** Selander & Preuß Mattsson, *Additional Messages in Lightweight Authenticated Key Exchange*, individual IETF Internet-Draft `draft-selma-lake-additional-messages-00`, **2026-11-02**: https://datatracker.ietf.org/doc/html/draft-selma-lake-additional-messages-00 (sections 3–6).
- **Verified source-supported claim:** For RFC 9528 methods, optional additional `message_n` starts at `n=5`, requires `message_4`, is consecutively numbered, alternates directions in lockstep, and is profile-bounded. `K_n` and `IV_n` use dedicated LAKE exporter labels and the CBOR-encoded `n` context; recipient infers `n` from state. A given `(K_n,IV_n)` encrypts **at most one plaintext**; retry MUST resend identical ciphertext. Processing and EAD failures abort the extended session; expected last flight defines completion. Invoking `LAKE_KeyUpdate` before completion is forbidden. The proposal calls out loss of last-flight acknowledgement, and exporter-label access by less-trusted code permits message forgery. Exporter labels remain `TBD`.
- **Existing engineering owner / repository anchor:** R-009, TD-003/TD-004; `spec/auth-terminal-flight-disposition.md`, `spec/replay-continuity.md`, `rust/test-vectors/state/auth-terminal-flight-v1.txt`.
- **Bottleneck:** Optional confirmation/attestation round trips could accidentally reuse an AEAD nonce with newly randomized payload, advance an authorization decision before authenticated completion, mutate key-generation state while an exchange is incomplete, or consume attacker-injected duplicates as new messages.
- **Strongest distinct idea:** Define a bounded *optional extra-flight state oracle* with `(session,direction,index,key_epoch)` identity, immutable first-send payload and ciphertext, exact duplicate response cache, expected-flight counter, failure cleanup and an independent current-authorization/effect-commit frontier. Inject same-ciphertext duplicate, different-plaintext same-index retransmit, reordered/cross-session message, dropped last flight, forged success, premature key update, restart/cached-ciphertext loss, and stale grant. Compare against existing mandatory AUTH_3 consume-before-verification semantics; **do not transplant** LAKE rules into ZK-ARCHE wire.
- **Evidence maturity:** `concept` source; repository `software` classifier/vector anchors exist but **this scenario was not reproduced**.
- **Limitations / uncertainty:** Draft is individual working text, has unallocated `TBD` exporter labels, and does not guarantee acknowledgement of final flight. No ZK-ARCHE exporter design, cryptographic proof, or interoperability follows from it.
- **ZK-ARCHE inference:** Protected success is not itself a grant, ENROLL authority, replay recovery, or permission to release DATA. Authorization and durable effect-frontier checks remain separate.
- **Impact — wire/CPU/RAM/flash/dependency/trust/privacy:** Baseline **none**. Optional extra flights add bytes/latency and AEAD CPU, session/ciphertext-cache RAM and potential durable-index flash; scoped exporter access is a trust boundary; retry behavior may leak linkability or permit DoS. Concrete values unmeasured.
- **Rust/C/vector/profile compatibility:** No current wire/vector changes. Future two-lane positive/negative corpus must pin selected profile, exact exporter label/context/nonce/epoch and key schedule, dedup semantics, cache limits, buffer bounds; require human versioned profile/wire decision before adoption.
- **Required next evidence:** Exact-HEAD locally reproducible Rust/C state/effect fixture and crash/rollback timing, then MCU resource measurements and independent crypto/domain-separation review if extension is proposed.
- **Recommended disposition:** reproduce, no promotion.
- **Weekly finding candidate:** yes.

### D20261109-F02 — Re-enrollment over an existing secure channel is still an explicit trust mutation

- **Novelty / owner:** refines R-008; cross-references R-005 and R-013. Do **not** assert that content newly appeared in revision -12.
- **Source / date / type / primary link:** IETF ACE Working Group, *Protecting EST Payloads with OSCORE*, `draft-ietf-ace-coap-est-oscore-12`, Standards Track Internet-Draft, **2026-11-02**: https://datatracker.ietf.org/doc/draft-ietf-ace-coap-est-oscore/12/ (sections 3,4,6).
- **Verified source-supported claim:** EST certificate payloads can be protected using OSCORE, typically from preceding EDHOC, but **re-enrollment does not require a new EDHOC handshake**. EST payloads are not carried in EDHOC EAD because that handshake may not occur. Client/server credential and DH proof-of-possession checks are distinct from protected transport. Server-generated private keys introduce theft risk; the draft discourages them and prohibits them for EDHOC clients with suitable CSPRNG, while giving limited exceptions for pre-shared OSCORE/no secure client RNG. Certain CSR channel-binding modes rely on application policy, not automatic credential-authority semantics.
- **Existing owner / repository anchors:** R-008, TD-002/TD-004; `spec/enroll-lifecycle-state-machine.md`, `spec/enrollment-grant-issuance.md`, `spec/authorization-generation-lifecycle.md`; `rust/crates/proto/src/enrollment_grant.rs`, `c/src/proto/enrollment_grant.c`.
- **Bottleneck:** A valid secure session may outlive commissioner authority or local policy. Restart/re-enrollment can accidentally inherit stale authorization, skip subject key possession, reapply an operation ID, or transfer private-key custody to an unauthorized actor.
- **Strongest distinct idea:** Compare four optional enrollment transports: fresh AUTH, resumed/long-lived protected association, pre-shared protected context and local P2P-assisted commissioning. For each, apply exact same local ENROLL authority/epoch, subject-PoP, audience/scope, unused operation ID, no-rollback and durable transaction classifier. Include valid-channel/stale-grant, revoked commissioner, wrong audience, missing PoP, RNG-unready client, remote-generated private-key exception, interrupted commit and duplicate after restart. Ensure every denial causes **no new trust mutation**.
- **Evidence maturity:** `concept` external WG draft; repository has `software` matched classifiers but no new execution or complete protected enrollment exchange.
- **Limitations:** The comparator is certificate/CA-centric; neither EST, PKI, OSCORE nor a cloud service becomes mandatory for infrastructure-independent ZK-ARCHE. Draft does not solve offline P2P authorization, physical RNG quality or rollback-resistant flash.
- **ZK-ARCHE inference:** Separate a protected data carrier, authenticated peer, locally authorized commissioner, subject key possession, and durable enrollment mutation. Normal AUTH remains NO-LEARNING.
- **Impact — wire/CPU/RAM/flash/dependency/trust/privacy:** Mandatory baseline **none**; optional profile may incur certificate/CoAP encoding, asymmetric CPU, state buffers, flash, secure storage, entropy and metadata/linkability costs. Locally generated keys minimize unnecessary remote key-custody trust. Not measured.
- **Rust/C/vector/profile compatibility:** No wire change. Future matching Rust/C ENROLL decision matrix and negative vector corpus must preserve existing grants/nonces on rejection, require current generation, and include target-specific CSPRNG readiness/secure-key storage evidence.
- **Required next evidence:** Pin revisions; run paired Rust/C local exact-HEAD current-versus-stale ENROLL/PoP/rollback/no-mutation tests, physically measure entropy and flash where relevant, and explicitly review any server-generated-key exception.
- **Recommended disposition:** reproduce, retain as design comparator only.

## 6. Cross-source synthesis

The LAKE proposal extends a *handshake* until the last authenticated message and requires stateful, single-use key/nonce plus immutable retries. The ACE EST/OSCORE WG draft places credential *lifecycle enrollment* on a protected channel reusable without the original handshake. Their responsibilities are distinct and not interchangeable. ZK-ARCHE should independently gate (1) optional confirmation/handshake completion, (2) current local ENROLL permission and subject PoP, (3) replay/crash continuity, and (4) durable effects. Do not convert EAD or receipt into trust mutation, adopt exporter labels, or infer current grants from an existing connection.
