# ZK-ARCHE Research — 2026-08-17

## Executive synthesis

Today’s repo-first review found no new implementation, vector, roadmap, or assurance changes after the 2026-08-16 research commit. That makes the highest-value work a deeper audit of three already-open questions rather than another broad scan.

Four findings are actionable:

1. **CFRG’s current Sigma-protocol draft maps directly onto ZK-ARCHE’s custom CDS OR-composed role-membership proof.** ZK-ARCHE’s Rust proof constructs simulated branches, one real branch, and a Fiat–Shamir master challenge whose branch challenges sum to the master challenge. The CFRG draft explicitly treats OR composition, simulator behavior, canonical serialization, CSPRNG requirements, constant-time behavior, protocol identifiers, and composition security as first-class concerns. This gives TD-001 a concrete pre-review checklist and justifies a new bounded research item focused on proving that the existing construction is specified, constant-time, domain-separated, and cross-language reproducible.
2. **ESP32-S3 RNG and eFuse-backed HMAC behavior materially changes what “MCU benchmark” must mean.** Espressif documents that true-random operation requires an enabled entropy source for continuous use and recommends a DRBG when permanent entropy cannot remain enabled. It also exposes an HMAC accelerator whose secret key can remain inaccessible outside cryptographic hardware. Therefore R-005 should measure entropy-source state, DRBG reseeding, secure-key placement, and acceleration configuration—not only latency/RAM/flash.
3. **Current hybrid PQ/T KEM drafts put hard lower bounds on packet pressure.** CFRG’s concrete MLKEM768-X25519 construction defines a 1,216-byte encapsulation key and 1,120-byte ciphertext before ZK-ARCHE framing, identity, proof, transcript, or transport overhead. The TLS working-group hybrid profile likewise standardizes X25519MLKEM768 as a large fixed-length group. This strongly supports keeping PQ hybrids outside `iot-core` UDP and benchmarking them first on edge/gateway or explicitly fragmented/stream profiles.
4. **BBS remains promising but not mature enough for promotion into the constrained baseline.** The active BBS core draft uses BLS12-381, 48-byte G1 point encodings, pairing operations, and two defined ciphersuites; related blind-signature and per-verifier-linkability drafts are currently expired. This supports continuing R-002 as research/benchmark work rather than replacing the current small Ristretto/Schnorr-style role proof.

No source reviewed today justifies changing ZK-ARCHE’s mandatory cryptographic suite, wire format, profile definitions, or maturity claims.

### 1. CFRG Sigma Protocols gives TD-001 a direct review framework for the current role proof

- **Source:** `draft-irtf-cfrg-sigma-protocols-02`, *Interactive Sigma Proofs*
- **Primary link:** https://datatracker.ietf.org/doc/html/draft-irtf-cfrg-sigma-protocols-02
- **Source type / venue:** IRTF CFRG Internet-Draft, active RG document
- **Publication date:** 2026-03-02
- **Verified claim:** the draft defines Sigma-protocol interfaces over prime-order groups, explicitly identifies OR composition as a standard composition technique, requires simulator outputs for composition, requires canonical serialization/deserialization, requires a CSPRNG for non-zero scalar sampling, warns that composition must preserve security properties, and requires constant-time group/field operations when private witnesses influence control flow or memory access. It also calls for unique protocol and instance identifiers.
- **Problem addressed:** ZK-ARCHE’s role proof is a custom non-interactive CDS OR composition and TD-001 currently states only that external review is needed. The repository has working Rust/C vectors, but the review target is not yet decomposed into explicit proof-system properties.
- **Strongest distinct engineering idea:** turn TD-001 into a property-driven proof review: statement definition, witness relation, simulator correctness, completeness, special soundness/extractability assumptions, honest-verifier/statistical ZK assumptions after Fiat–Shamir, canonical branch serialization, unique protocol/instance identifiers, challenge-domain separation, allowed-role ordering/canonicalization, zero/identity rejection, scalar sampling, constant-time witness handling, and negative-vector coverage.
- **Evidence maturity:** concept
- **Limitations / uncertainty:** the CFRG draft does not specify ZK-ARCHE’s exact CDS role construction or Ristretto255 ciphersuite. It is a review framework, not proof that ZK-ARCHE’s construction is secure.
- **ZK-ARCHE inference:** before external review, produce a machine-readable/Markdown proof contract mapping every value in `RoleSetBinding`, every transcript field, each simulated branch, the real branch, and the sum-of-challenges equation to a mathematical statement. Then compare Rust and C serialization and deterministic vectors against that contract. This should precede any claim that the role proof is externally reviewable or specification-grade.
- **Wire / RAM / CPU / dependency impact:** no immediate runtime change. The likely cost is test/spec/review work. Any future canonicalization change could alter vectors and therefore requires checkpoint review.
- **Rust/C / vector compatibility impact:** compatible at research stage. A discovered discrepancy in ordering, domain separation, or scalar handling may require versioned vector changes in both lanes.
- **Recommended disposition:** reproduce

### 2. ESP32-S3 entropy and hardware-key behavior must be part of R-005, not hidden platform assumptions

- **Sources:** Espressif ESP-IDF documentation for ESP32-S3 Random Number Generation and HMAC
- **Primary links:** https://docs.espressif.com/projects/esp-idf/en/latest/esp32s3/api-reference/system/random.html and https://docs.espressif.com/projects/esp-idf/en/latest/esp32s3/api-reference/peripherals/hmac.html
- **Source type / venue:** official vendor platform documentation
- **Publication/release date:** current documentation checked 2026-08-17
- **Verified claim:** Espressif states that the ESP32-S3 internal RNG state is not large enough to provide an unlimited stream of true random numbers and that a continuous entropy source must be enabled when true random numbers are required. When that cannot remain enabled, Espressif recommends seeding a strong software DRBG from hardware entropy. The ESP32-S3 HMAC peripheral can use SHA-256 HMAC keys stored in eFuse blocks and can make those keys inaccessible to ordinary software resources.
- **Problem addressed:** ZK-ARCHE’s roadmap requires per-target RNG and secure-storage evidence, while current Rust code uses `OsRng` abstractly. An MCU port cannot inherit Linux `OsRng` assurance by analogy.
- **Strongest distinct engineering idea:** define a target RNG/key-storage profile as part of the benchmark artifact: boot entropy source, runtime entropy availability, DRBG algorithm/state/reseed policy, failure behavior, concurrency, health/fault behavior, key origin, eFuse/flash storage mode, debug/JTAG posture, and whether hardware acceleration changes timing or key-exposure boundaries.
- **Evidence maturity:** hardware
- **Limitations / uncertainty:** vendor documentation establishes hardware behavior, not ZK-ARCHE integration quality. eFuse HMAC is not a drop-in replacement for every ZK-ARCHE private scalar operation.
- **ZK-ARCHE inference:** R-005 benchmark reports should distinguish protocol cost from platform security configuration. Two ESP32-S3 measurements with different entropy/secure-boot/eFuse settings are not equivalent assurance results even if packet latency is identical.
- **Wire / RAM / CPU / dependency impact:** DRBG state adds RAM and reseed logic; hardware HMAC may reduce software key exposure and CPU cost for HMAC-specific operations but does not accelerate Ristretto scalar multiplication. Secure storage choices affect provisioning and recovery semantics.
- **Rust/C / vector compatibility impact:** no wire impact. Deterministic vectors must remain independent of production RNG source; platform ports should prove that deterministic test mode cannot leak into production configuration.
- **Recommended disposition:** benchmark

### 3. Hybrid ML-KEM/X25519 sizes reinforce an edge-only default for PQ/T work

- **Sources:** `draft-irtf-cfrg-concrete-hybrid-kems-03`, *Concrete Hybrid PQ/T Key Encapsulation Mechanisms*; `draft-ietf-tls-ecdhe-mlkem-05`, *Post-quantum hybrid ECDHE-MLKEM Key Agreement for TLSv1.3*
- **Primary links:** https://datatracker.ietf.org/doc/html/draft-irtf-cfrg-concrete-hybrid-kems-03 and https://datatracker.ietf.org/doc/html/draft-ietf-tls-ecdhe-mlkem-05
- **Source type / venue:** IRTF CFRG and IETF TLS working-group Internet-Drafts
- **Publication dates:** 2026-03-02 and 2026-05-26
- **Verified claim:** CFRG’s concrete `MLKEM768-X25519` hybrid defines `Nek = 1216` bytes and `Nct = 1120` bytes, with a 32-byte shared secret. The TLS draft defines X25519MLKEM768, P-256/ML-KEM-768, and P-384/ML-KEM-1024 hybrid groups and explicitly notes that its security analysis relies on the TLS 1.3 transcript and must not simply be assumed to transfer to other protocols.
- **Problem addressed:** R-003 needs exact size and composition evidence before any PQ hybrid enters ZK-ARCHE. The current roadmap already says oversized extensions require an explicit TCP, fragmentation, or gateway-only profile.
- **Strongest distinct engineering idea:** use the concrete 1,216-byte key + 1,120-byte ciphertext as the **minimum PQ/T transport budget**, then add ZK-ARCHE framing, negotiation, authentication proof, transcript fields, retry/retransmission behavior, and MTU loss model. Treat hybrid composition/KDF/transcript binding as a protocol-specific proof obligation rather than copying TLS identifiers.
- **Evidence maturity:** concept
- **Limitations / uncertainty:** both sources are drafts; ZK-ARCHE may choose a different hybrid construction later. Exact embedded CPU/RAM/flash measurements remain absent.
- **ZK-ARCHE inference:** `iot-core` should retain the classical compact baseline unless a future measured profile proves that fragmentation/stream transport and memory budgets are acceptable. The near-term PQ experiment belongs on Linux-edge/accelerated-edge first, with ESP32/STM32 work limited to measurement unless results are unexpectedly favorable.
- **Wire / RAM / CPU / dependency impact:** the hybrid public material alone exceeds a typical small single-datagram target before ZK-ARCHE overhead. ML-KEM also adds code, scratch RAM, hashing, and side-channel implementation requirements.
- **Rust/C / vector compatibility impact:** no current impact. A future PQ suite must receive new suite IDs, negotiation/downgrade vectors, fixed-length parser tests, hybrid KDF vectors, MTU/fragmentation tests, and synchronized Rust/C support or an explicitly edge-only lane.
- **Recommended disposition:** benchmark

### 4. BBS should remain a comparator, not a baseline migration target

- **Sources:** `draft-irtf-cfrg-bbs-signatures-10`, *The BBS Signature Scheme*; current CFRG document status for BBS extensions
- **Primary links:** https://datatracker.ietf.org/doc/html/draft-irtf-cfrg-bbs-signatures-10 , https://datatracker.ietf.org/doc/draft-irtf-cfrg-bbs-blind-signatures/ , https://datatracker.ietf.org/doc/draft-irtf-cfrg-bbs-per-verifier-linkability/
- **Source type / venue:** IRTF CFRG Internet-Drafts/document status
- **Publication date:** core BBS revision 2026-01-08; related extension status checked 2026-08-17
- **Verified claim:** BBS provides multi-message signatures with selective disclosure and unlinkable zero-knowledge proofs. The current core draft defines BLS12-381 ciphersuites, 32-byte scalar encodings, 48-byte G1 point encodings, pairings, and extensive vectors. The blind-signature and per-verifier-linkability extension drafts are currently expired, although tracked as CFRG work.
- **Problem addressed:** R-002 asks whether a reviewed anonymous/selective-disclosure credential should eventually replace or complement ZK-ARCHE’s bounded role-membership proof.
- **Strongest distinct engineering idea:** compare **privacy property gained per byte/CPU/dependency** rather than comparing only cryptographic elegance. BBS has materially stronger credential semantics, but it also introduces pairing-friendly-curve arithmetic and a different credential lifecycle.
- **Evidence maturity:** concept
- **Limitations / uncertainty:** draft status may change; no ZK-ARCHE-specific MCU benchmark was found today. The presence of standardized vectors does not imply suitability for STM32/ESP32-class baseline use.
- **ZK-ARCHE inference:** keep BBS in `iot-edge`/research evaluation. Benchmark proof/signature sizes, pairing verification, flash/code footprint, RAM, credential issuance/revocation, verifier-linkability needs, and privacy benefit against the existing CDS role proof before proposing an ADR.
- **Wire / RAM / CPU / dependency impact:** expected to be materially larger and more computationally/dependency intensive than the current Ristretto/Schnorr-style baseline; exact ZK-ARCHE target measurements are still required.
- **Rust/C / vector compatibility impact:** none while comparator-only. Any adoption should be suite-isolated with independent vectors rather than replacing existing role-proof vectors in place.
- **Recommended disposition:** benchmark

## Cross-source synthesis

The strongest cross-source conclusion is that **ZK-ARCHE’s next maturity gain comes from making proof and platform assumptions measurable, not from adding another primitive**.

CFRG’s Sigma work is especially relevant because it describes the same proof family ZK-ARCHE is already using: prime-order-group Sigma proofs, OR composition, simulation, Fiat–Shamir conversion, canonical serialization, randomness, and constant-time obligations. This does not validate the current role proof, but it makes the external-review target far less vague.

The ESP32-S3 material reinforces the same principle at the hardware boundary. “Runs on ESP32-S3” is not sufficient evidence unless the benchmark states how entropy, DRBG state, key storage, secure boot/debug policy, and acceleration are configured.

PQ/T and BBS both remain valuable research directions, but today’s primary-source evidence strengthens the case for isolation rather than promotion: PQ/T has immediate packet-size pressure, while BBS has a substantially heavier pairing-based implementation surface. Neither should displace the constrained interoperability floor without measured evidence.
