## 1. Executive synthesis

1. **The new ZK-ARCHE TLS exporter context is better modeled as a custom exporter construction than as RFC 9266's generic `tls-exporter` channel-binding type.** RFC 9266 fixes the standard channel binding to label `EXPORTER-Channel-Binding`, empty context, 32-byte output, and warns applications not to reuse that binding for more than one authentication-mechanism instance on a TLS connection. Current ZK-ARCHE instead deliberately includes `auth_instance_id`, application, ALPN, deployment, endpoint IDs, protocol/suite/profile, and transcript hash in a canonical digest. That is a sound direction for per-AUTH disambiguation, but the specification must name it accurately and test it as a distinct application exporter binding rather than claiming RFC-9266-equivalent semantics.
2. **RFC 5705 directly supports binding exporter output to upper-layer identifiers, algorithms/parameters, session identity, and lifetime, which matches the new context surface.** However, label and context have different roles: the label disambiguates exporter purpose, while the context is per-association application data. Future normative text should therefore freeze a dedicated ZK-ARCHE exporter label and canonical context encoding, not move variable per-session fields into the label.
3. **The concrete API still lacks an explicit exporter-generation/currentness input.** TLS 1.3 ordinary `KeyUpdate` leaves the standard exporter secret unchanged; the July 2026 Extended Key Update draft introduces fresh exporter secrets, application notification, and epoch-aware exporter interfaces for post-compromise recovery. ZK-ARCHE should keep its 32-byte canonical context digest stable as application context while separately deriving/validating whether the TLS exporter secret generation is the current accepted binding generation.
4. **No wire, code, spec, roadmap, debt status, profile, or maturity change is made today.** Findings refine R-010/R-009 and TD-004/TD-003 evidence requirements. Promotion requires explicit human review and Rust/C deterministic/negative evidence.

## 4. Findings

### D20260910-F01 — Use a dedicated ZK-ARCHE application exporter binding, not the fixed RFC 9266 channel-binding value

- **Novelty:** refines
- **Sources:** RFC 5705, *Keying Material Exporters for Transport Layer Security (TLS)*; RFC 9266, *Channel Bindings for TLS 1.3*; RFC 9846, *The Transport Layer Security (TLS) Protocol Version 1.3*
- **Primary links:** https://www.rfc-editor.org/rfc/rfc5705.html ; https://www.rfc-editor.org/rfc/rfc9266.html ; https://www.rfc-editor.org/rfc/rfc9846.html
- **Source type / venue:** IETF Standards Track RFCs
- **Publication / release date:** March 2010 / July 2022 / June 2026
- **Verified claim:** RFC 5705 defines exporter output as scoped by TLS session, label, and application context and explicitly gives endpoint identity, algorithms/parameters, session identifiers, and lifetime as examples of upper-layer context that applications may need to bind. RFC 9266 defines a specific generic TLS 1.3 channel-binding type using label `EXPORTER-Channel-Binding`, zero-length context, and 32-byte output; it further states that applications must not use that same channel-binding value for more than one authentication-mechanism instance on a TLS connection. RFC 9846 retains the exporter interface and recommends that new exporter uses provide a context.
- **Existing owner:** R-010 / TD-004 / TLS binding surface
- **Repository fact:** the new ZK-ARCHE C context API hashes a rich per-AUTH tuple including `auth_instance_id`, application/ALPN/deployment identifiers, endpoint roles, negotiated ZK-ARCHE protocol/suite/profile, and transcript hash. Its test corpus already proves different AUTH-instance IDs and reversed endpoint roles produce different digests.
- **Problem addressed:** avoid two opposite specification errors: (a) reusing one generic RFC-9266 binding value across multiple ZK-ARCHE AUTH instances, or (b) inaccurately calling a custom context-sensitive application exporter the RFC-9266 `tls-exporter` channel-binding type.
- **Strongest distinct engineering idea:** specify one dedicated ZK-ARCHE exporter purpose label and feed the canonical 32-byte context digest as the per-association `context_value`. Keep `auth_instance_id` and other variable binding inputs inside the canonical context encoding. Treat RFC 9266 as a channel-binding comparator/security requirement source, not as the byte-level definition of the ZK-ARCHE custom exporter unless ZK-ARCHE deliberately adopts its fixed label/empty-context construction.
- **Evidence maturity:** externally-reviewed standards plus software implementation/test evidence
- **Limitations / uncertainty:** the exact exporter label is not being normatively allocated here. RFC 5705 label-registration requirements must be handled deliberately if ZK-ARCHE moves beyond private experimentation. The current report does not prove the canonical digest encoding is collision-free under malformed/ambiguous input encodings; that remains a vector/parser review question.
- **ZK-ARCHE inference:** add future deterministic cross-language tests proving same TLS secret + different AUTH instance, endpoint-role ordering, application/ALPN/deployment/profile, or transcript context yields different EKM; same exact context re-derives identical EKM; context omission or ambiguity fails closed. Keep one normalized application-exporter abstraction across TLS libraries.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** wire-neutral if exporter context is local binding material. CPU/RAM impact is one bounded canonicalization/hash plus TLS exporter call. No new online trust dependency. Privacy improves by avoiding accidental cross-AUTH binding reuse; raw context fields need not be exposed on wire if already authenticated/known locally.
- **Rust/C / vector compatibility impact:** requires a Rust peer implementation/corpus matching the new C digest and eventually shared EKM fixtures using a deterministic exporter-secret test harness. Existing protocol wire vectors need not change unless the binding is later serialized or negotiated.
- **Required next evidence:** normative custom-label/context construction; Rust implementation parity; malformed/duplicate/empty-field canonicalization vectors; cross-AUTH/cross-role/cross-application negative EKM fixtures; explicit decision on label registration/private-use naming.
- **Recommended disposition:** reproduce

### D20260910-F02 — Keep exporter-context identity separate from exporter-secret generation/currentness

- **Novelty:** refines
- **Sources:** RFC 9846 TLS 1.3; `draft-ietf-tls-extended-key-update-13`, *Extended Key Update for Transport Layer Security (TLS) 1.3*
- **Primary links:** https://www.rfc-editor.org/rfc/rfc9846.html ; https://datatracker.ietf.org/doc/draft-ietf-tls-extended-key-update/
- **Source type / venue:** IETF Standards Track RFC + active TLS WG Internet-Draft
- **Publication / release date:** RFC 9846 — June 2026; Extended Key Update -13 — 4 July 2026
- **Verified claim:** ordinary TLS 1.3 exporters derive from the connection exporter secret, and ordinary traffic `KeyUpdate` does not refresh that exporter secret. Extended Key Update -13 explicitly introduces fresh exporter secrets for its post-compromise-recovery path, notifies applications when a new exporter epoch becomes active, allows epoch-aware exporter use, and warns that old/new exporter secrets may need bounded overlap (especially for DTLS reordering). Its TLS epoch identifier is a local logical counter and can differ between peers.
- **Existing owner:** R-010 / R-009 / TD-003 / TD-004
- **Repository fact:** `auth_tls_exporter_context_v1_t` has no exporter-secret generation/epoch/currentness field. That is not necessarily a defect in the context object: the context describes ZK-ARCHE application identity/instance semantics, while TLS secret generation is lower-layer channel lifecycle state. Current association/binding architecture already prefers normalized security facts over transport identity.
- **Problem addressed:** prevent a context digest from being mistaken for proof that the EKM came from the currently accepted TLS secret generation, especially in long-lived sessions, resumption/recovery, DTLS reordering, or any future post-compromise-recovery profile.
- **Strongest distinct engineering idea:** preserve a two-axis model: `zk_context_digest` identifies the exact ZK-ARCHE AUTH/application context; `exporter_generation_current` (or equivalent adapter fact) establishes that the TLS exporter secret used for EKM is the currently accepted generation. On generation transition, association policy should explicitly rebind/revalidate or fall back to full AUTH according to profile policy. Never compare peer local integer epoch counters as if they were globally synchronized identities.
- **Evidence maturity:** externally-reviewed TLS baseline plus active WG draft; ZK-ARCHE integration remains software/spec research
- **Limitations / uncertainty:** Extended Key Update is still an Internet-Draft and must not become a mandatory ZK-ARCHE dependency. Standard TLS 1.3 without EKU has one ordinary exporter-secret generation for the connection, so a generation API can normalize to a stable baseline state there. Exact recovery semantics require separate threat-model review.
- **ZK-ARCHE inference:** extend future binding qualification with fixtures for ordinary `KeyUpdate` (context/EKM generation behavior remains according to standard exporter semantics), resumption/new TLS connection, optional EKU epoch transition, stale prior exporter generation, DTLS old-generation overlap, and mismatched local epoch numbering. The Common Contract should consume a boolean/currentness relation rather than TLS-specific epoch integers.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** no mandatory wire change. Optional epoch-aware adapters need bounded previous/current exporter-secret metadata and transition state. Trust remains local; TLS/DTLS supplies channel evidence but does not confer ZK-ARCHE authorization. Privacy impact is favorable if generation IDs remain local and are not exposed as stable correlators.
- **Rust/C / vector compatibility impact:** add shared normalized binding-state vectors independent of TLS library API, plus adapter tests mapping concrete TLS exporter lifecycle into those facts. Existing canonical context digest should remain stable unless its own semantic fields change.
- **Required next evidence:** exact adapter state machine for standard TLS 1.3 and optional EKU-capable TLS/DTLS; stale/current generation negative corpus; resumption/new-connection tests; Rust/C parity; explicit no-authorization-from-channel-binding checks.
- **Recommended disposition:** reproduce

## 5. Cross-source synthesis

The new implementation is converging on the right separation if ZK-ARCHE keeps three distinct objects:

```text
TLS/DTLS secure-channel secret state
        +
ZK-ARCHE dedicated exporter purpose label
        +
canonical per-AUTH application context digest
        ↓
exported binding material
        ↓
normalized binding-valid/current fact
        ↓
association admission
```

RFC 5705 supports putting endpoint/session/application semantics in exporter context. RFC 9266 shows why a fixed generic channel-binding value cannot simply be reused across multiple authentication instances. RFC 9846 and Extended Key Update show why application context identity and lower-layer exporter-secret generation are different lifecycle dimensions. The concrete ZK-ARCHE context API addresses the first dimension; future evidence should now prove the second without leaking TLS-specific epoch numbering into the Common Contract.
