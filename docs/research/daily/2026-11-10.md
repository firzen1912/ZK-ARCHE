## 2. Executive synthesis

1. **This is a newly mapped authoritative comparator, not a new November 2026 RFC.** RFC 9770 is a **June 2025 Standards Track RFC**. The source and its threat examples were absent from the current research index/backlog. Current November searches found no more recent publication that supersedes its specifically relevant ACE revocation-notification design. Do not characterize the source as newly published.
2. **Transport update cursor is not a security epoch.** RFC 9770's bounded history and modulo cursor can become insufficient to recover dropped updates. ZK-ARCHE's authenticated, authority-scoped `view_epoch` and exact `base_epoch` check must remain independent. Missing history requires an authoritative FULL/sufficient authenticated chain, never a guessed or modulo-derived recovery.
3. **Credential-handle canonicalization belongs to security correctness.** RFC 9770 documents a valid-token-but-wrong-hash attack using nonprotected wrappers. ZK-ARCHE should test semantic-equivalent inputs and noncanonical wrappers across issuer/authority, value, reference, alias and cache paths before relying on a revocation handle or a credential-mapping hash.
4. **Revocation tombstone retention is an authorization question, not merely a cache optimization.** RFC 9770 retains revoked token hashes under defined conditions, with explicitly conditional memory-limit behavior. ZK-ARCHE's v1 `REVOKE`-only, lineage-scoped semantics cannot import ACE token-expiry unrevocation or cache eviction without separate review and safety evidence.
5. **No promotion:** This run executed no Rust/C tests, formal models, MCU hardware measurements or canonicalization fixtures. R-012 and R-013 remain `reproduce`; no mandatory CoAP, OAuth, authorization server, token hash or online service is adopted.

## 5. Findings

### D20261110-F01 — Bounded diff history and modulo cursor must never substitute for authoritative epoch continuity

- **Novelty / backlog:** `refines` R-012; already published standard newly integrated into research evidence.
- **Primary source:** IETF RFC 9770, *Notification of Revoked Access Tokens in the Authentication and Authorization for Constrained Environments (ACE) Framework*, **June 2025**, Standards Track RFC, §§6.2–6.2.1, 8–11, 14.3–14.5: https://www.rfc-editor.org/rfc/rfc9770.html .
- **Verified claim:** RFC 9770 supports a bounded `MAX_N` history of per-requester diffs and optional `MAX_DIFF_BATCH` pagination; its `index` rolls over modulo `MAX_INDEX+1`. The RFC cautions that deleted old updates cannot be recovered via diff queries and recommends regular FULL queries as a complement to notifications/diffs. Lost notifications can therefore leave a resource server unaware of a relevant revocation.
- **Existing owner/anchors:** R-012, zk214/zk225/zk230, TD-004/TD-002; `spec/revocation-update-ingestion.md` §§3–9, `spec/revocation-view-representation.md` §§2,5; `rust/test-vectors/state/revocation-reconciliation-v1.txt`.
- **Bottleneck:** A transport sequence/cursor can be recent yet represent only a suffix of a history. On wrap, reset or mixed-authority delivery, comparing cursor integers alone could wrongly mark stale local revocation state as current. ZK-ARCHE currently has structural negative vectors for base mismatch but not authenticated distribution, multi-batch cursor rollover and restart loss.
- **Distinct engineering idea:** A two-layer decision oracle: `transport_cursor` is a non-authoritative retrieval hint; only authenticated `(authority, view_epoch, base_epoch, representation_identity)` can change local revocation state. Inject missed >history-window updates, cursor wrap/reuse, batch truncation, lost `more` page, duplicate/out-of-order notifications, stale FULL, wrong-authority snapshot, and offline reconnect. Require an independently authenticated complete FULL (or complete authenticated chain) when continuity cannot be proven. Preserve exact old state pending atomic commit; dependent permissions stay stale/denied when profile freshness fails.
- **Evidence maturity:** external **externally-reviewed** standards specification; ZK-ARCHE matching execution **not reproduced**. Published IETF semantics are not a security proof of ZK-ARCHE.
- **Limitations:** RFC 9770 presumes ACE/authorization-server Token Revocation List and CoAP distribution; exact ACE cursor and retention algorithms are **not** ZK-ARCHE wire proposals. A bounded FULL may be too large for `iot-core`; authoritative partitioning/compression needs its own evidence.
- **Inference for ZK-ARCHE:** Reconciliation `view_epoch` must not be derived from a mod-wrapping cursor, cache age, observation counter, TLS session, or mere response success. A permanently disconnected peer obeys its own freshness limit rather than inferring that no notification means no revocation.
- **Wire/CPU/RAM/flash/dependency/trust/privacy impact:** mandatory wire/profile/dependency **none**. Optional distribution experiments cost extra notification/fetch bytes, bounded cache/scratch and flash writes; full fetch frequency trades bandwidth/energy versus stale-authorization window; endpoint/poll cadence can leak relationship and activity metadata. Numbers unmeasured.
- **Rust/C/vector/profile compatibility:** add matched negative corpus with authenticated mock FULL/DIFF/cursor metadata, exact epoch/authority checks, and equal accept/reject/unchanged-state oracles. No current vectors or profile semantics change; explicit no-counter-rollback MCU evidence remains outstanding.
- **Required next evidence:** execute local exact-HEAD Rust/C gap/wrap/restart/pagination/freshness tests and constrained payload/persistent write counts; separately model authorization effect frontier during ingestion. **Disposition:** `reproduce`; weekly candidate **yes**.

### D20261110-F02 — Cryptographically valid but noncanonically wrapped credentials can evade hash-based revocation matching

- **Novelty / backlog:** `refines` R-013; R-012 dependent matching/identity cross-reference.
- **Primary source:** IETF RFC 9770, **June 2025**, Standards Track, §§3–4.4 and §§14.6–14.7: https://www.rfc-editor.org/rfc/rfc9770.html .
- **Verified claim:** RFC 9770 demonstrates that modifying unprotected COSE headers or token-enclosing CBOR tags can leave cryptographic validation of a token intact while changing the hash input used to identify it for revocation; the verifier may then miss the later issuer-side revocation. For JWT delivery through alternative JSON/CBOR representations, RFC 9770 specifies dual hashes under defined circumstances. These are attacks/comparators concerning **ACE tokens**, not demonstrated ZK-ARCHE defects.
- **Existing owner/anchors:** R-013, TD-004, zk207/zk217/zk225; `spec/revocation-view-representation.md` (holder/lineage references), `spec/revocation-update-ingestion.md` (authority binding), `spec/authorization-generation-lifecycle.md`; R-013's local credential/reference/alias/cache attribution contract.
- **Bottleneck:** Revocation by a digest or opaque alias fails if the issuer, holder and verifier identify the same security principal using different bytes/authority namespaces. Authentication success alone cannot prove matching revocation-handle provenance.
- **Distinct engineering idea:** Construct a shared *semantic-identity / byte-representation mutation* test harness: same cryptographically valid credential under canonical form, permuted/extra unauthenticated wrapper, alternate transport encoding, stale local alias, raw value, reference and cached result, across two issuers with identical display labels. Compare (a) accepted canonical attribution, (b) explicit rejection of unsupported/noncanonical form, (c) **no** alternative-reference path that bypasses current revocation, and (d) fail-closed when multiple authority-qualified interpretations remain. Any future canonical credential-ID derivation must be explicitly domain-separated by version, authority and credential class and reviewed; **do not silently select JWT dual-hashing for ZK-ARCHE**.
- **Evidence maturity:** external **externally-reviewed** normative attack analysis; ZK-ARCHE software-only classification and existing vectors are contextual, not execution of the proposed cross-representation attack.
- **Limitations:** ZK-ARCHE does not currently mandate CWT/JWT/COSE or ACE token hashes; no actual code path was shown vulnerable and no canonical identifier change is authorized. A variant that changes *authenticated* payload semantics must be rejected by cryptography itself, distinct from an unauthenticated-wrapper mismatch.
- **ZK-ARCHE inference:** Credential identifier/canonicalization and revocation naming must be decided with the full authority-qualified trust record, not an untrusted display field, transport wrapper or TLS/CoAP request path.
- **Wire/CPU/RAM/flash/dependency/trust/privacy impact:** no mandatory wire/dependency change. A future reviewed canonical-ID strategy may add bounded parsing/hashing CPU and minimal reference bookkeeping; redundant alias/hash indexes increase flash/RAM and correlation risk. Security benefit hinges on preventing cross-authority confusion rather than increasing the count of accepted aliases. Quantities unmeasured.
- **Rust/C/vector/profile compatibility:** add accepted-reference and reject-mutation fixtures for canonical/alternate wrappers, alias/proof/authority mismatch, and token-like expiry/revocation interplay, comparing **same local decision and no trust mutation**. Do not alter existing Ristretto proof vectors or profile IDs.
- **Required next evidence:** pin canonical reference/identity semantics through explicit human review, then execute paired Rust/C representation mutation + revocation propagation fixtures on the same pinned HEAD, including issuer collision and cached selector variants. **Disposition:** `reproduce`; weekly candidate **yes**.

### D20261110-F03 — Revocation tombstone retention cannot be replaced by opportunistic cache deletion

- **Novelty / backlog:** `refines` R-012; R-009 durable rollback/epoch retirement cross-reference.
- **Primary source:** IETF RFC 9770, **June 2025**, Standards Track, §11.1 and §§14.2, 14.5: https://www.rfc-editor.org/rfc/rfc9770.html ; contextual ACE RFC 9200, **August 2022**, §5.10.3: https://www.rfc-editor.org/rfc/rfc9200.html .
- **Verified claim:** RFC 9770 instructs a resource server not to immediately discard the revoked token hash when expunging its token, to prevent re-accepting a known revoked token. It defines conditions for later deletion based on observation/expiration knowledge, and an explicit conditional memory-pressure oldest-first rule accompanied by sequence-number considerations. ACE tokens can expire, and RFC 9770's TRL removes hashes on token expiry. That last behavior is **not** equivalent to ZK-ARCHE v1 lineage revocation.
- **Existing owner/anchors:** R-012, R-009, zk213/zk214/zk239, TD-002/TD-004; `spec/revocation-view-representation.md` §§2,5 (only `REVOKE`, no implicit `UNREVOKE`); `spec/revocation-update-ingestion.md` §§4,5,8,9 and `spec/authorization-generation-lifecycle.md` §§3–7; `rust/test-vectors/state/revocation-view-v1.txt` contains an unknown `UNREVOKE` negative.
- **Bottleneck:** Under constrained RAM/flash and post-crash recovery, reclaiming a revoked record or accepting a truncated FULL may appear to restore free storage yet can also permit an old credential/lineage to become eligible again.
- **Distinct engineering idea:** Classify *tombstone disposal* separately from *revocation-view cache eviction*: a bounded profile must prove a closed credential/lineage lifetime, locally authoritative replacement generation, or other reviewed irreversible exclusion before reclaiming any deny-state. Test full tombstone cache, duplicate/reordered REVOKE, expiration claim without a trusted clock, truncated/oversized FULL, interrupted write and restored older snapshot; denial under insufficient storage must not evict a deny record while continuing to authorize its lineage. Separate unrelated new lineage reauthorization by authorized ENROLL from deletion of an old revocation entry.
- **Evidence maturity:** external **externally-reviewed** RFC behavioral comparator; exact ZK-ARCHE persistence/expiration/MCU test not performed.
- **Limitations:** RFC 9770's bounded-memory and expirability rules are deliberately token-specific; copying them would violate the current draft's `REVOKE`-only/no implicit repair property. No assumption that ZK-ARCHE supports sequence numbers, token introspection or trusted time on every constrained device.
- **ZK-ARCHE inference:** Treat unresolved tombstone compaction as a separate authorization-proof obligation for future local storage policy, not as a reason to weaken current fail-closed reconciliation or force an online revocation authority.
- **Wire/CPU/RAM/flash/dependency/trust/privacy impact:** no baseline wire change. Tombstone retention consumes bounded flash/RAM and persistent writes; compact generations/lineages might reduce storage only with proof of non-resurrection. Fail-closed over-capacity may reduce availability. Stable hashed identifiers/tombstones expose linkability if disclosed; no numeric budgets or MCU flash measurements available.
- **Rust/C/vector/profile compatibility:** add cache-pressure/expiry/compaction/rollback tests with exact retained deny decisions and Rust/C parity; existing `UNREVOKE` reject vector stays authoritative. Do not introduce ACE-specific `removed` semantics in v1.
- **Required next evidence:** explicit human approval of any tombstone collection criterion, paired exact-HEAD Rust/C deletion/restoration/crash tests and physical wear/performance qualification; **reproduce**, weekly candidate **yes**.

## 6. Cross-source synthesis

RFC 9770 and RFC 9200 concern a **central ACE authorization-server revocation list of expirable access tokens**. Their strongest portable lessons are that (1) change-notification transport state is not equivalent to current authorization state, (2) cryptographic acceptance of an object does not guarantee that all participants derive the same revocation identifier, and (3) a local cache cannot drop revocation denial information without a separate safe lifetime/monotonicity argument. ZK-ARCHE already defines stricter local authority, REVOKE-only lineage and fail-closed DIFF rules; the missing work is *executable* cross-layer Rust/C + crash/MCU evidence, not copying ACE's protocol or its token expiry semantics. Neither source establishes deployment-level freshness, revocation immediacy, unlinkability or cryptographic proof security for ZK-ARCHE.
