## 2. Executive synthesis

1. **RNG availability is a platform lifecycle state, not a property conferred by calling `OsRng` or `randombytes_buf`.** Current ESP32-S3 documentation says hardware output is true-random only while an entropy source is active; after the second-stage bootloader hands control to the application, output can be only pseudo-random until RF or the internal entropy source is enabled again. ZK-ARCHE therefore needs measured `UNREADY/READY/FAULT` behavior at boot, wake, and runtime transitions before constrained-target key/proof/session randomness can be qualified.
2. **Entropy health failures need a fail-closed operation boundary.** NIST SP 800-90B requires start-up and continuous entropy-source health tests, while current STM32 HAL documentation exposes seed/clock error state and explicitly notes that seed-error recovery is not guaranteed. Current ZK-ARCHE Rust and C RNG helpers return random values through APIs with no explicit recoverable RNG-error result. Before field-readiness claims, fault injection must prove that a failed/unready target RNG cannot commit a proof nonce, key, session state, replay state, or outbound protocol message.
3. **The actual entropy backend is part of the benchmark identity.** ZK-ARCHE Rust currently uses `rand 0.8` `OsRng`; C uses libsodium `randombytes_buf`. Rand delegates `OsRng` to `getrandom`, while libsodium documents custom RNG replacement for embedded platforms. A Rust-vs-C benchmark is therefore not assurance-equivalent unless it records the exact target backend, source state, DRBG/reseed policy, and failure semantics in both lanes.
4. **NIST SP 800-90C gives the right decomposition for the evidence artifact:** distinguish entropy source, DRBG/RBG construction, reseed behavior, and consuming protocol operation. The project should measure each layer rather than collapsing all of them into “RNG works.”
5. **No status promotion is justified.** R-005 remains `benchmark`; its existing backlog contract already names entropy-source state, DRBG/reseed, RNG-failure behavior, storage, and target context, so `backlog.md` does not need a semantic rewrite today. The new evidence belongs in the dated report and future exact-head hardware benchmark artifacts.

### D20260924-F01 — Entropy readiness is a lifecycle state across ESP32-S3 boot and runtime

- **Novelty:** refines
- **Backlog owner:** R-005
- **Source:** Espressif ESP-IDF ESP32-S3 Random Number Generation documentation, v6.0.3/current
- **Primary link:** https://docs.espressif.com/projects/esp-idf/en/v6.0.3/esp32s3/api-reference/system/random.html
- **Source type / venue:** official vendor platform documentation
- **Publication or release date:** current vendor documentation checked 2026-09-24
- **Verified claim:** ESP32-S3 hardware RNG output is described as true-random while RF is enabled, the internal SAR-ADC entropy source is explicitly enabled, or the second-stage bootloader is running. The bootloader enables entropy and disables it before entering the application. Without those conditions, the output should be treated as pseudo-random. Espressif further notes that the internal RNG state is not large enough for an unlimited true-random stream and recommends a strong software DRBG seeded from hardware entropy when a continuous entropy source cannot remain active.
- **Existing engineering owner:** R-005 / constrained-target assurance and IoT-profile evidence
- **Repository fact:** Rust production crypto calls `OsRng` directly; C calls libsodium `randombytes_buf`. Neither implementation layer records whether an ESP32-S3 physical entropy source is currently active.
- **Problem addressed:** “RNG API returned bytes” is insufficient evidence for boot/wake/runtime phases where physical entropy availability changes.
- **Strongest distinct engineering idea:** qualify a target-local entropy lifecycle with at least `UNREADY`, `READY`, and `FAULT/DEGRADED` states, and bind every key/proof/session randomness operation to a measured READY precondition. Measure transitions at cold boot, bootloader→application handoff, RF enable/disable, deep sleep/wake, warm reset, and entropy-source enable/disable.
- **Evidence maturity:** constrained-hardware
- **Limitations / uncertainty:** vendor documentation defines platform behavior, not ZK-ARCHE integration correctness. The exact DRBG construction, if one is used, still requires independent implementation/configuration review. ESP32-S3 results must not be generalized to STM32-class targets.
- **ZK-ARCHE inference:** constrained profiles should not claim secure production randomness until exact-head tests demonstrate that no private scalar, proof nonce, session identifier, HPKE/KEM ephemeral value, resumption secret, or other security-critical random input can be generated during an unqualified entropy state.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** no wire-format change. A readiness state and DRBG context consume small RAM/flash; temporary entropy-source activation may affect ADC/RF coexistence, energy, and startup latency. A DRBG adds reseed logic and implementation dependency.
- **Rust/C / vector compatibility impact:** deterministic vectors stay unchanged. Production target adapters in both lanes must expose equivalent READY/failure semantics; target tests should prove deterministic test RNGs cannot be selected in production profiles.
- **Required next evidence:** ESP32-S3 cold/warm boot and sleep/wake traces; entropy-source state logs; first-ready latency; sustained generation/reseed measurements; negative tests attempting every security-critical random-consuming operation before readiness and after forced loss of readiness.
- **Recommended disposition:** benchmark

### D20260924-F02 — Entropy health and seed failures require fail-closed operation atomicity

- **Novelty:** new
- **Backlog owner:** R-005
- **Sources:** NIST SP 800-90B, NIST SP 800-90C, current ST STM32 RNG HAL documentation
- **Primary links:** https://csrc.nist.gov/pubs/sp/800/90/b/final ; https://csrc.nist.gov/pubs/sp/800/90/c/final ; https://dev.st.com/stm32cube-docs/stm32c5xx-hal-drivers/2.0.0/en/docs/drivers/hal_drivers/rng/hal_rng_how_to_use.html
- **Source type / venue:** NIST standards guidance and official vendor HAL documentation
- **Publication or release date:** SP 800-90B January 2018 (planning note updated 2025; NIST page updated 2026); SP 800-90C final September 25, 2025; current ST documentation checked 2026-09-24
- **Verified claim:** SP 800-90B requires start-up and continuous health tests as components of an entropy source. SP 800-90C separates entropy sources from DRBG mechanisms/RBG constructions and defines classes according to how entropy is supplied. Current STM32 HAL documentation exposes RNG seed/clock error detection and seed-error recovery; the vendor explicitly notes that recovery is not guaranteed.
- **Existing engineering owner:** R-005; TD-002/target evidence boundary where applicable
- **Repository fact:** current Rust helpers `random_scalar()`/`random_bytes_32()` return values rather than a recoverable RNG error; current C `auth_random_*` helpers return `void`. The protocol layer therefore has no explicit target-RNG health/failure result in these helper signatures.
- **Problem addressed:** an MCU entropy peripheral can enter a seed/clock/health failure state. Treating that as an invisible implementation detail risks continuing a cryptographic operation after the randomness precondition has failed.
- **Strongest distinct engineering idea:** define a fault-injection qualification contract before changing code: force `NOT_READY`, health-test failure, seed error, timeout, and reseed failure at each random-consumption point, and require an all-or-nothing outcome—no proof/session/key material committed, no replay/authorization state advanced, and no success wire message emitted. Recovery, if supported, is a new attempt after a successful health/reseed transition rather than continuation of partially committed state.
- **Evidence maturity:** concept + constrained-hardware vendor evidence
- **Limitations / uncertainty:** NIST 800-90B/90C specify RBG/entropy-source assurance constructs, not ZK-ARCHE protocol error semantics. STM32C5/U5 HAL documentation is representative of current STM32 RNG error handling; the exact selected STM32 benchmark part (for example an H5-class board) still needs its own reference manual, errata, and HAL-version qualification.
- **ZK-ARCHE inference:** future MCU adapters should surface entropy readiness/health to the protocol implementation or provide a formally defined fail-stop boundary below it. Silent substitution with a weaker pseudo-random source after hardware failure should be prohibited for production profiles.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** no new wire field is required. Fault state and health counters add minimal RAM; health tests/reseeding add startup/runtime latency and energy. External error normalization should preserve R-015 privacy requirements rather than creating an attacker-visible “RNG failed” oracle.
- **Rust/C / vector compatibility impact:** add deterministic fault-injection adapters and cross-language negative fixtures for fail-before-output/fail-before-state-commit behavior. Existing positive wire vectors need not change.
- **Required next evidence:** exact-board STM32 + ESP32-S3 error injection; seed/clock/health fault traces; recovery attempts; proof that partial AUTH/ENROLL/P2P operations leave no accepted state; Rust/C semantic parity; power-loss during recovery; local/exact-head benchmark artifact with toolchain/HAL versions.
- **Recommended disposition:** reproduce / benchmark
- **Weekly finding candidate:** yes

### D20260924-F03 — RNG backend provenance is part of Rust/C benchmark equivalence

- **Novelty:** refines
- **Backlog owner:** R-005
- **Sources:** Rand 0.8.5 crate documentation; libsodium random-data/custom-RNG documentation
- **Primary links:** https://docs.rs/crate/rand/0.8.5 ; https://doc.libsodium.org/generating_random_data ; https://doc.libsodium.org/doc/advanced/custom_rng
- **Source type / venue:** official library documentation
- **Publication or release date:** Rand 0.8.5 release documentation; current libsodium documentation checked 2026-09-24
- **Verified claim:** Rand 0.8 documents `OsRng` as backed by the `getrandom` dependency and notes only partial `no_std` support unless the appropriate features/backend are provided. Libsodium documents that mainstream systems use OS RNG facilities and that embedded/nonstandard platforms can replace `randombytes_*` through a custom implementation installed before `sodium_init()`.
- **Existing engineering owner:** R-005 / Rust-C target portability evidence
- **Repository fact:** the Rust workspace pins `rand = "0.8"` with default dependency behavior and the protocol crypto uses `OsRng`; C uses libsodium `randombytes_buf`. The current repository does not contain evidence proving that these two generic interfaces resolve to equivalently qualified entropy/DRBG backends on ESP32-S3 and STM32-class builds.
- **Problem addressed:** two binaries can execute identical ZK-ARCHE wire logic while relying on materially different entropy sources, reseed rules, failure behavior, threading/locking, and secure-storage assumptions.
- **Strongest distinct engineering idea:** make the RNG backend part of the benchmark manifest identity: language/library version, backend implementation, hardware entropy peripheral, conditioning/DRBG algorithm, initialization/readiness rule, reseed trigger, health/fault behavior, concurrency policy, sleep/reset behavior, and failure propagation. Compare protocol performance only after those security semantics are documented.
- **Evidence maturity:** software
- **Limitations / uncertainty:** library documentation establishes extension points, not which backend a future MCU port will choose. No bare-metal build was produced by this research run, so this finding does not claim that the current Rust or C implementation already compiles on a specific board.
- **ZK-ARCHE inference:** target parity should mean equivalent security semantics, not identical RNG APIs. Rust and C may use different mechanisms, but the same benchmark profile should demonstrate equivalent readiness, entropy/reseed, failure, rollback/restart, and deterministic-test isolation properties.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** no wire impact. Backend selection can materially change code size, RAM, system-call/HAL cost, energy, concurrency behavior, and dependency surface.
- **Rust/C / vector compatibility impact:** deterministic cryptographic vectors remain portable. Add target-manifest and negative-test parity; keep deterministic vector RNG and production RNG as explicitly separate build/runtime capabilities.
- **Required next evidence:** one ESP32-S3 and one STM32-class exact-head build per language lane (or explicitly documented unsupported lane), pinned backend/toolchain/library versions, entropy readiness/reseed traces, error injection, RAM/flash/latency/energy measurements, and a parity matrix.

## 6. Cross-source synthesis

The combined evidence sharpens R-005 from “measure randomness behavior” into a four-layer assurance boundary:

```text
physical entropy source / health
            ↓
conditioning + DRBG/RBG construction
            ↓
Rust/C target RNG backend
            ↓
ZK-ARCHE random-consuming operation
```

Each layer needs its own provenance and failure semantics. The strongest decision rule is **no cryptographic/protocol success may depend on randomness obtained while the target entropy/RBG contract is unready or failed**. On ESP32-S3, readiness changes with boot/runtime entropy-source state; on STM32-class devices, hardware reports seed/clock failures and recovery can fail; NIST separates health-tested entropy sources from DRBG/RBG construction; and Rust/libsodium expose platform-dependent backends rather than proving embedded entropy quality by themselves.

This is not a request to standardize a single RNG implementation across platforms. The correct Common Contract is semantic: sufficient entropy provenance, explicit readiness/reseed/failure behavior, no silent downgrade, deterministic test RNG isolation, and fail-closed protocol-state behavior. Platform adapters may satisfy that contract differently.
