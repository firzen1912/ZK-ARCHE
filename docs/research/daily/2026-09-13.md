## 2. Executive synthesis

1. **NO-LEARNING AUTH is now well represented at the decision boundary, but authorized trust mutation is still a stateful protocol problem.** Tamarin's multiset-rewrite semantics and the stateful-protocol literature are designed to model mutable/non-monotonic security state. For ZK-ARCHE, the next formal step should not be another boolean/event refinement of normal AUTH; it should be an explicit trust-store transition model for ENROLL/re-registration/rekey-like mutation, including authorization, predecessor state, commit, and rollback/replay behavior.
2. **The June 2026 cBRSKI draft provides a concrete constrained-device trust-replacement invariant worth reproducing.** During re-enrollment, the client authenticates under the current trust anchor, validates the new identity against the successor trust anchor, and only then stores the new anchor/identity; if validation fails, it must not update either. This maps directly to ZK-ARCHE's lifecycle atomicity rule and strengthens R-013/R-008 without importing BRSKI's PKI architecture.
3. **Externally observable error normalization must be threat-model-specific rather than equivalent to internal reason normalization.** EDHOC keeps detailed internal/state-machine errors but warns that unprotected error messages and metadata can reveal sensitive information; it also allows suppressing errors for DoS reasons and treats forged errors cautiously. ZK-ARCHE's new unknown-code normalization is good interoperability hygiene, but privacy assurance still requires a separate mapping from internal reasons to externally observable classes, including silence/size/timing/retry behavior.
4. **No backlog status transition is justified today.** R-004, R-013, and R-015 remain `reproduce`: the external evidence sharpens the next model/spec/test targets but does not provide a fresh exact-model proof, a complete trust-mutation protocol, physical persistence evidence, or measured observable-failure equivalence.
5. No wire format, suite, profile, roadmap, ADR, technical-debt status, hardware-readiness claim, or release posture changes in this report.

### D20260913-F01 — Authorized trust mutation needs an explicit stateful formal model

- **Novelty:** refines
- **Backlog owner:** R-004 / R-013
- **Sources:** Tamarin Prover official documentation; Kremer & Künnemann, *Automated analysis of security protocols with global state*
- **Primary links:** https://tamarin-prover.com/ ; https://doi.org/10.3233/JCS-160556
- **Source type / venue:** official formal-methods project; peer-reviewed Journal of Computer Security paper
- **Publication / release date:** stateful-protocol paper first published August 3, 2016; Tamarin documentation current as reviewed 2026-09-13
- **Verified claim:** Tamarin models protocol state machines through multiset rewrite rules and can express trace properties over the resulting labeled transition system. The stateful-protocol literature specifically motivates this approach for security APIs/key servers/protocols with global non-monotonic state such as databases and registers, where monotonic Horn-clause abstractions are insufficient or awkward.
- **Existing engineering owner:** R-004 / R-013 / TD-003
- **Repository fact:** the current dedicated association-admission ProVerif model proves only a wire-neutral postcondition over supplied facts. It represents `TrustMutationRequested` as a rejected path, but does not model an authorized ENROLL/re-registration mutation, mutable trust-store contents, predecessor/successor trust generations, persistent commit, or rollback.
- **Problem addressed:** extending the current NO-LEARNING theorem into a meaningful statement about *where learning is allowed* without accidentally proving only that normal AUTH rejects a mutation flag.
- **Strongest distinct engineering idea:** introduce a separate stateful trust-mutation model with explicit facts/rules for `TrustState(peer, generation, authority)`, authorized mutation intent, commissioner/grant authority, predecessor validity, one-time operation identity, successor validation, durable-commit event, and invalidation of predecessor state. Keep normal AUTH as a non-mutating consumer of the resulting trust state.
- **Evidence maturity:** formal-methods basis externally reviewed; ZK-ARCHE mapping remains concept/formal research
- **Limitations / uncertainty:** choosing Tamarin/SAPIC+ does not prove implementation refinement, storage atomicity, or computational cryptography. ProVerif can still remain useful for monotonic AUTH correspondence; the finding is about the mutable-trust subproblem, not replacing all current models.
- **ZK-ARCHE inference:** the next formal milestone for R-013 should be an authorized mutation theorem such as “a newly trusted successor state exists only after a valid explicit mutation authority and commit event,” plus “normal AUTH cannot produce that commit event.” This is stronger and more useful than adding more pre-existing-trust booleans to association admission.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** no immediate wire cost; modeling may reveal a need for explicit mutation operation IDs/generations. Runtime impact depends on the chosen persistence mechanism and remains outside formal proof.
- **Rust/C / vector compatibility impact:** future vectors should distinguish normal AUTH rejection, authorized ENROLL mutation, replayed mutation, stale predecessor, rollback-suspected storage, partial successor validation, and exactly-one durable successor commit. Both languages should consume the same state-transition corpus.
- **Required next evidence:** define the normative explicit trust-mutation state machine first; encode a stateful model; retain exact model/tool version and results; map successful/failed model traces to Rust/C deterministic state-transition vectors.

### D20260913-F02 — Verify successor trust before committing any trust-anchor/identity replacement

- **Novelty:** new/refines
- **Backlog owner:** R-013 / R-008 / R-009
- **Source:** `draft-ietf-anima-constrained-voucher-31`, *Constrained Bootstrapping Remote Secure Key Infrastructure (cBRSKI)*
- **Primary link:** https://datatracker.ietf.org/doc/draft-ietf-anima-constrained-voucher/31/
- **Source type / venue:** IETF ANIMA Working Group Internet-Draft, Standards Track work in progress
- **Publication / release date:** June 2026; expires December 10, 2026
- **Verified claim:** cBRSKI defines constrained-device re-enrollment in which the client authenticates to the currently trusted domain, obtains a successor identity, retrieves successor trust anchors when needed, verifies that the new identity chains to the successor anchors, and only on success stores the new anchors/identity and stops using the predecessor identity. If the verification fails, it must not update either the identity or the trust-anchor database. The draft also explicitly limits the number of stored CA certificates in constrained pledges to avoid memory exhaustion.
- **Existing engineering owner:** R-013 / R-008 / R-009 / TD-002 / TD-004
- **Repository fact:** ZK-ARCHE's lifecycle contract already requires atomic or recoverable multi-component transitions and says a successor must not become usable while predecessor invalidation remains durably older. The ENROLL grant classifier now separates commissioner authentication, authorization freshness, generation provenance/currentness, replay, possession, scope, revocation, lineage, and rollback, but it does not yet define the complete durable trust-mutation transaction.
- **Problem addressed:** partially committed trust replacement can create split-brain authority, revive predecessor trust after rollback, or leave a new identity installed without its corresponding successor trust context.
- **Strongest distinct engineering idea:** define trust mutation as a two-phase semantic transaction: `validate successor under authorized mutation context -> commit successor trust+identity+predecessor invalidation as one recoverable security transition`. Any failure before commit leaves predecessor state authoritative; any uncertain/partial recovered commit fails closed under lifecycle freshness rules.
- **Evidence maturity:** active IETF WG draft; ZK-ARCHE mapping remains concept/spec research
- **Limitations / uncertainty:** cBRSKI uses certificates, MASA/registrar roles, and domain PKI; ZK-ARCHE should not inherit those infrastructure assumptions. The reusable lesson is transactional trust replacement and constrained storage discipline.
- **ZK-ARCHE inference:** a future ENROLL/re-registration trust mutation should bind the exact successor key/credential commitment, authorization generation, policy/revocation/lineage state, and mutation operation ID before durable commit. The commit should simultaneously make the successor usable and make the predecessor non-authoritative, or recover into `STALE_OR_UNKNOWN`/`ROLLBACK_SUSPECTED`.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** potentially wire-neutral if mutation evidence is already carried by an ENROLL/grant flow; persistent storage needs may increase because predecessor/successor metadata and recovery markers can coexist temporarily. Constrained targets need an explicit upper bound on retained trust records and atomicity metadata.
- **Rust/C / vector compatibility impact:** add shared transaction vectors for successor-valid/commit, successor-invalid/no-change, interrupted-before-commit, interrupted-during-commit, rollback-to-predecessor, repeated operation ID, and constrained trust-store capacity exhaustion.
- **Required next evidence:** normative trust-mutation commit state machine; host fault-injection tests; Rust/C decision and persistence parity; physical ESP32-S3/STM32-class power-loss/rollback measurements for a selected backend.

### D20260913-F03 — Internal reason precision and external observable-failure privacy are separate contracts

- **Novelty:** refines
- **Backlog owner:** R-015 / R-011
- **Source:** RFC 9528, *Ephemeral Diffie-Hellman Over COSE (EDHOC)*
- **Primary link:** https://www.rfc-editor.org/rfc/rfc9528.html
- **Source type / venue:** IETF Standards Track RFC
- **Publication / release date:** March 2024
- **Verified claim:** EDHOC defines structured fatal error codes, but allows errors to be skipped for cases such as missing sessions or DoS concerns; it warns that error messages are unprotected and privacy-sensitive, that unauthenticated data must not trigger harmful actions, and that forged errors may justify continuing rather than automatically tearing down state. It also notes that unknown-credential errors can help interoperability while allowing an adversary to induce larger credential transmissions.
- **Existing engineering owner:** R-015 / R-011 / TD-004
- **Repository fact:** the current ZK-ARCHE wire-error corpus normalizes unknown numeric codes to `UNSPECIFIED`, while `spec/error-and-observable-failure-state-matrix.md` correctly states that `ERROR` versus silence is privacy-relevant and that no observational equivalence follows from normalization.
- **Problem addressed:** conflating registry normalization with privacy normalization. Mapping an unknown code to `UNSPECIFIED` solves decoder interoperability; it does not make known failure classes, response presence, packet size, timing, retry behavior, or post-error state indistinguishable.
- **Strongest distinct engineering idea:** maintain three layers: rich internal reason -> protocol state consequence -> externally observable response class. The privacy contract should operate on the third layer and may coalesce reasons, suppress responses, pad/normalize size, or constrain retry behavior according to attacker model, while retaining rich local audit reasons.
- **Evidence maturity:** externally reviewed standard; ZK-ARCHE mapping remains software/spec research
- **Limitations / uncertainty:** EDHOC's error registry and handshake state are not ZK-ARCHE's. Exact normalization choices require ZK-ARCHE timing/resource measurements and must account for DoS cost.
- **ZK-ARCHE inference:** R-015 should test observational classes rather than only numeric error equality: known-vs-unknown peer/credential, authorization denied, revocation stale/revoked, replay, malformed input, terminal state consumed, and unknown session should be evaluated for response/no-response, size bucket, timing distribution, retry semantics, and state retention.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** padding/dummy work can increase wire bytes and CPU; silence can improve privacy/amplification posture but reduce diagnostics; external class normalization is likely implementation/profile policy rather than a new mandatory cryptographic primitive.
- **Rust/C / vector compatibility impact:** keep existing numeric normalization corpus, but add a separate observable-failure corpus describing external response class/state consequence rather than reusing internal reason codes as privacy evidence.
- **Required next evidence:** attacker-model-specific observable-failure matrix, Rust/C response-class corpus, timing/size measurements, and DoS-cost evaluation for any dummy-work/padding/suppression rule.

## 6. Cross-source synthesis

The three findings reinforce one architectural rule: **security-state mutation, decision reasoning, and external observability must remain separate layers**.

Normal AUTH can consume pre-existing trust but must not mutate it. Explicit ENROLL/re-registration may mutate trust, but only through a separately authorized, replay-safe, verify-then-commit transition whose persistence semantics are recoverable and independently evidenced. Formal assurance should therefore model mutable trust where mutation actually occurs rather than stretching a monotonic admission abstraction beyond its scope.

Likewise, a rich internal reason taxonomy is useful for deterministic Rust/C behavior and auditability, but privacy claims concern what an adversary can observe. Numeric normalization alone is not sufficient evidence for unlinkability or oracle resistance.
