## 2. Executive synthesis

1. The original CryptoProver research and its Verus-equipped `dalek-lite` source give a concrete **proof-inheritance candidate**, not a verification of ZK-ARCHE. The fork descends from Signal's `curve25519-dalek` 4.1.3 tag but removes backends other than `serial/u64`; it proves only selected functions.
2. Current ZK-ARCHE Rust pins crates.io `curve25519-dalek` **4.1.3**; matching the version string is insufficient to transfer a proof across source forks, feature resolution, backend selection, theorem preconditions, and build artifacts. C uses a separate libsodium implementation with no implied inheritance.
3. The repository's CDS proof still takes a secret-dependent true-branch index. In both Rust and C, that branch receives different random-draw and group-operation schedules from simulated branches. The total random-byte requirement is fixed for a fixed role-set size, but its **per-index schedule is not**. A primitive functional-correctness proof does not establish witness-index privacy, noninterference, side-channel resistance, or OR-composition security.
4. New Aeneas/Lean work makes a **code-to-mathematical-specification refinement proof** plausible as an optional experiment for bounded Rust helpers, but does not replace computational Sigma/Fiat–Shamir analysis, Rust/C conformance or independent TD-001 review.
5. Keep R-007 **P0 / reproduce**. Only evidence requirements were refined. No suite, wire, implementation, specification, roadmap, maturity or production/security claim changes.

## 5. Findings

### D20261013-F01 — Version resemblance is not proof inheritance

- **Novelty / owner:** new/refines; R-007, TD-001, zk207/zk209/zk241.
- **Sources / dates / types:** Sun et al., *An AI Approach to Verified Production Cryptographic Libraries*, original research preprint, **2026-08-02**, https://arxiv.org/abs/2608.00965 ; Beneficial AI Foundation `dalek-lite` README and proof taxonomy, original project source inspected **2026-10-13** (no stable publication date), https://github.com/Beneficial-AI-Foundation/dalek-lite and https://github.com/Beneficial-AI-Foundation/dalek-lite/blob/main/spec-taxonomy.toml .
- **Source-supported claim:** The paper reports Verus-checked proof synthesis relative to explicit API specifications and a fixed trusted set of arithmetic/field assumptions. The project README states its fork is based on Signal's `signal-curve25519-4.1.3` tag, removes backends other than `serial/u64`, and carries proofs for a **selection** of functions. Its taxonomy distinguishes proven versus assumed assertions and documents probabilistic/field/encoding trust categories.
- **Repository fact / bottleneck:** ZK-ARCHE instead resolves crates.io `curve25519-dalek 4.1.3` at the Rust lockfile checksum; its CDS code depends on Ristretto group operations, scalar arithmetic and canonical decoding. Neither equivalence to the forked source and backend nor proof coverage of the called functions is established. The C lane uses libsodium.
- **Distinct engineering idea:** Build a **property-specific cryptographic proof-inheritance ledger**: source commit and dependency checksum; source-code function identity; enabled features and selected field backend; compiler/target/options; exact theorem, preconditions, invariants, axioms and unchecked/admitted functions; called API path; artifact hash; and an explicit `covered / conditional / uncovered` verdict. Fail closed on any mismatch. Do not swap dependencies to “gain verification” without a separate human-approved engineering decision.
- **Evidence maturity:** external **formal** source proof (scoped to its own checked fork and assumptions); ZK-ARCHE inheritance remains **concept**.
- **Limitations:** Paper claims do not prove independent algorithm security, uniform randomness, constant-time execution, witness privacy, or equivalence of ZK-ARCHE's executable dependency. Functions outside the verified subset and backend variants are unproved here; the fork's disabled tests are not production qualification.
- **ZK-ARCHE inference:** A reusable proof can at most discharge the *exact mathematical implementation sub-obligation* whose source/configuration and preconditions match; it cannot discharge CDS OR soundness/ZK, transcript composition, hidden-role noninterference, C parity or TD-001 review.
- **Wire / CPU / RAM / flash / dependency / trust / privacy impact:** no wire change; analysis-only cost and retained proof artifacts. Any later backend replacement would need measured MCU CPU/RAM/flash and dependency/constant-time review. Trust depends on explicit axioms and proof-to-binary provenance; privacy is **not** upgraded.
- **Rust/C / vectors / profile impact:** Rust function-level audit candidate only; C is uncovered. Preserve existing known-answer vectors, canonical parse negatives and current profile/suite semantics.
- **Required next evidence:** pin proof repository commit and report hashes; map each called Dalek function plus transitive dependencies to actual checked theorem/precondition, compare against crates.io source/backend/target; run a local exact-head reproduction or label uncovered explicitly. Record separate C/library obligations.

### D20261013-F02 — Rust functional proofs cannot certify OR-proof role privacy

- **Novelty / owner:** refines; R-007 and R-004/TD-003 cross-link.
- **Sources / dates / types:** Ho et al., *Scaling Verification of Cryptographic Software with Aeneas, Rust, and Lean*, research preprint **2026-09-14**, https://arxiv.org/abs/2609.15648 ; Aeneas official cryptographic-verification guide and codebase, official tool documentation inspected **2026-10-13**, https://github.com/AeneasVerif/aeneas/blob/main/documentation/crypto-verification.md and https://github.com/AeneasVerif/aeneas .
- **Source-supported claim:** The paper reports translating production Rust into Lean through Aeneas and mechanically checking functional correctness, memory safety and panic freedom for a scoped SymCrypt Rust corpus. The authors' guide explicitly layers mathematical standard → Lean specification → optional auxiliary specification → Aeneas-generated implementation model. The tool currently supports a **subset of safe Rust** and documents limitations for unsafe, concurrency and selected generic/loop patterns.
- **Repository fact / bottleneck:** ZK-ARCHE's Rust role prover has a witness-index-dependent loop, while the C counterpart performs the analogous branch-specific operations. Existing symbolic models abstract proof arithmetic. Functional statement equality alone will not cover leakage or computational OR composition.
- **Distinct engineering idea:** Pilot a bounded **code/spec correspondence proof** for the public verification equations and canonical challenge inputs; separately require an independent computational CDS OR/security proof and per-role witness-index noninterference evidence. Treat each as an orthogonal claim, not as three labels for the same passing test.
- **Evidence maturity:** external **formal** demonstration; ZK-ARCHE-specific correctness/leakage remains **concept**.
- **Limitations:** No Aeneas extraction of this repository was run; external SymCrypt results do not prove current Dalek/FFI dependencies, embedded targets, the randomized prover distribution or timing/power noninterference. Proof translation to an intermediate model requires explicit soundness assumptions.
- **ZK-ARCHE inference:** For a fixed `n`, total scalar draw count is `64 + 128(n-1)` bytes in the C sampling contract, but the **position and type** of operations vary with the secret role index. Tests must compare role-class timing, allocation, RNG-call schedule, target power and compiler-generated control flow; constant total entropy consumption is insufficient.
- **Wire / CPU / RAM / flash / dependency / trust / privacy impact:** no wire alteration. Offline verification may be costly; a later changed implementation could change execution time and footprint, so measure before promotion. A correct public verifier is not a proof of private prover execution.
- **Rust/C / vectors / profile impact:** keep canonical Rust/C positive and malformed point/scalar/role-set vectors; introduce a language-neutral property coverage matrix with `functional-correctness`, `computational-OR-security`, `Fiat-Shamir-context-binding`, `witness-noninterference`, and `physical-side-channel` as distinct obligations. No mandatory-profile change.
- **Required next evidence:** select a tiny exact-head proof function for source→spec extraction (or explicitly reject the approach if unsupported); retain versioned tool/source/formal artifacts; reproduce per-role branch and RNG schedule on Rust/C; obtain compiler-specific and physical-target leakage measurements plus external cryptographic review.
