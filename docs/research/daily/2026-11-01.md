## 2. Executive synthesis

1. **Current standards anchor changed:** The current HPKE WG draft is -06 dated October 29, 2026 (the previous R-014 report pinned -05). It intends to obsolete RFC 9180 **if approved**; it is not an RFC. The new draft does not specify Auth/AuthPSK sender-key modes, but explicitly says it does not deprecate their existing RFC 9180 use. For this optional one-shot hint comparator, pin the *actual* revision, KEM/KDF/AEAD/mode, recipient-key epoch, and every normative vector's provenance. Do not silently reinterpret RFC 9180 interoperability as -06 conformance or claim a -05-to--06 algorithm change without an audited textual diff.
2. **HPKE decryption alone is not freshness:** The -06 text explicitly excludes replay protection, downgrade prevention, sender authentication in Base mode, and plaintext-length privacy. In particular, reusing an encapsulation can reproduce the same exported secret; the draft forbids deriving AEAD key/nonce pairs from such exports without a fresh per-use input. R-014 currently proposes a one-shot ciphertext hint, not a reply-key export, so the immediate evidence requirement is to ensure ciphertext success only selects a local candidate and does not open trust, bypass AUTH replay, or reset retry eligibility.
3. **A retry challenge proves only limited reachability:** DTLS 1.3's cookie exchange limits source spoofing but does not stop attackers at valid addresses, and its cookie is handshake-scoped; CoAP Echo may validate only the nearest proxy. R-014 therefore needs distinct per-source amplification, pre-auth CPU, and pending-state budgets, plus explicit NAT/proxy/rotation and retry-oracle tests. The CoAP-specific 136-byte example is not a ZK-ARCHE packet limit.
4. **Decision:** R-014 stays P1/prototype. Only its research evidence contract is refined; no cryptographic primitive, wire field, cookie policy, profile, roadmap, specification, code, vector, or release claim is promoted.

### D20261101-F01 — Revision-pinned HPKE -06 prototype boundary

- **Novelty:** refines the -05 evidence from 2026-10-07.
- **Backlog owner / engineering owner:** R-014; roadmap zk220; specification maturity TD-004.
- **Source / date / type:** *Hybrid Public Key Encryption*, draft-ietf-hpke-hpke-06, HPKE WG Standards-Track Internet-Draft dated **2026-10-29**, current IETF revision; https://datatracker.ietf.org/doc/draft-ietf-hpke-hpke/06/ . Comparator: https://datatracker.ietf.org/doc/html/draft-ietf-hpke-hpke-05 , **2026-09-26**. The draft remains work in progress.
- **Verified source fact:** -06 is the newer WG revision and proposes obsoleting RFC 9180 if approved. It specifies Base/PSK mode APIs, not RFC 9180 Auth/AuthPSK; it explicitly says those existing modes are not deprecated. It specifies a single-shot Seal/Open interface and leaves wire framing/recipient-key identification to the application. Existing common-function compatibility is an intention, not evidence that ZK-ARCHE already interoperates.
- **Bottleneck / repository fact:** R-014 references -05 while there is no promoted encrypted-hint format, key epoch, or full Rust/C HPKE vector. The stable 24-byte v2 outer header does not allocate an HPKE hint extension. Existing registry-attribution rules forbid any hint or database handle from becoming identity/authorization.
- **Distinct engineering idea:** versioned experimental *test manifest*, not a new production wire allocation: pin precise draft revision and HPKE mode/KEM/KDF/AEAD, recipient public-key identifier plus rotation generation, canonical info/AAD and ciphertext framing, fail-closed unknown/retired-key behavior and pure prefilter semantics. Do not infer migration from an updated draft number alone.
- **Evidence maturity:** concept for ZK-ARCHE; official IETF standards-development comparator, not implementation or security qualification.
- **Limitations:** Not a verified -05→-06 cryptographic algorithm delta; no implementation or device measurements. Draft may change.
- **ZK-ARCHE inference:** retain Base-only as a potential non-authenticating envelope, not a sender PoP or trusted registry lookup result. Preserve existing authentication and trust attribution.
- **Wire / CPU / RAM / flash / dependency / trust / privacy impact:** For DHKEM(X25519) with a 16-byte AEAD tag, a one-shot H-byte plaintext needs an HPKE cryptographic envelope of H+48 bytes (32-byte encapsulation plus ciphertext H+16) before framing, epoch, key ID, retry and padding: H=16→64 bytes, H=32→80 bytes. Additional KEM decapsulation CPU, buffering and dependency burden are unknown. Does not reduce trust-validation cost; ciphertext length and key-ID choice may leak metadata.
- **Rust/C/vector/profile impact:** pinned algorithm IDs, canonical info/AAD and key-generation fields, shared full/short/malformed ciphertexts, unsupported legacy Auth-mode and wrong-recipient-key negative cases; optional experiment only, no iot-core mandatory burden.

### D20261101-F02 — HPKE ciphertext/secret replay is not an AUTH replay or authorization check

- **Novelty:** refines the existing envelope-only threat model with an explicit replay/export acceptance oracle.
- **Backlog owner / engineering owner:** R-014; R-009 replay/AEAD lineage cross-reference.
- **Source / date / type:** draft-ietf-hpke-hpke-06, 2026-10-29, HPKE WG Internet-Draft, Sections 5.3, 9.1 and 9.8; https://datatracker.ietf.org/doc/draft-ietf-hpke-hpke/06/ .
- **Verified source fact:** HPKE has no inherent replay protection or Base-mode sender authentication; replaying encapsulation can reproduce exported secrets. The draft prohibits deriving an AEAD (key,nonce) from an exported secret absent fresh per-derivation input and its revised bidirectional example uses a recipient-generated nonce.
- **Bottleneck / repository fact:** spec/implementation-requirements.md prohibits candidate-hint authority, and spec/privacy-considerations.md explicitly does not claim private lookup. The present Rust AUTH path has an independent replay check prior to its registry scan; this does not itself measure whether a new optional HPKE prefilter would preserve replay precedence.
- **Distinct engineering idea:** explicit three-stage oracle: (a) valid hint ciphertext only produces an opaque candidate set; (b) duplicate/replayed ciphertext cannot alter retry or authentication state except under separately approved idempotency; (c) only fresh verified transcript/proof plus current authoritative mapping can admit a session or protected operation. Separately reject any response-key export construction that lacks fresh recipient input.
- **Evidence maturity:** concept for ZK-ARCHE (IETF source specifies the cryptographic limitation).
- **Limitations:** No identified ZK-ARCHE response-key export implementation, practical replay exploit, or live prototype. HPKE's one-shot Seal/Open does not itself imply repeat-key/nonce failure; the Export hazard is conditional.
- **ZK-ARCHE inference:** prevent an encrypted lookup accelerator from becoming a replay, authn, or authz shortcut.
- **Wire / CPU / RAM / flash / dependency / trust / privacy impact:** No mandatory wire change. A replay cache or bounded duplicate tracking may consume memory/storage and operations; response-nonce handshake would add bytes/flight if such a response construction were proposed. Fail-closed candidate behavior preserves trust separation; repeated-error timing remains a privacy oracle to measure.
- **Rust/C/vector/profile impact:** compare first-use vs repeated enc/ciphertext, altered info/AAD, stale recipient epoch, malformed tag, duplicate concurrent requests and restart; preserve canonical v2 semantics and profile-specific resource limits.
- **Next evidence / disposition:** deterministic Rust/C negative corpus and transaction-level state snapshots before/after replay; do not assert an implementation vulnerability. **prototype**; weekly candidate **yes**.

### D20261101-F03 — Return-routability is not peer identity, authorization, or complete DoS control

- **Novelty:** refines R-014's existing retry-first rule with an explicit proxy, rebinding, valid-source-flood and resource-amplification boundary.
- **Backlog owner / engineering owner:** R-014; zk219; R-015 privacy cross-reference.
- **Source / date / type:** IETF RFC 9147 *DTLS 1.3*, **2022-04**, Standards Track, Section 5.1; https://www.rfc-editor.org/rfc/rfc9147.html . IETF RFC 9175 *CoAP Echo, Request-Tag, and Token Processing*, **2022-02**, Standards Track, Sections 2.3–2.6; https://www.rfc-editor.org/rfc/rfc9175.html .
- **Verified source fact:** DTLS 1.3 uses a cookie with HelloRetryRequest for return-routability and observes that cookies do not block DoS from legitimate source addresses; cookie secrets may rotate with bounded overlap, and cookie validity is handshake-scoped. It recommends limiting prevalidation response volume to three times bytes received and discusses rebinding/Connection-ID limitations. CoAP Echo can check address reachability, but an origin server behind a proxy may learn only the proxy's reachability. Its illustrative 136-byte initial-response limit is CoAP-specific and cannot be copied into ZK-ARCHE framing.
- **Bottleneck / repository fact:** roadmap zk219 envisages stateless/bounded AUTH_RETRY; spec/security-considerations.md says retry/source-validation/amplification protection is not complete across all transports. Current draft error matrix does not define a fully qualified retry state machine.
- **Distinct engineering idea:** separately capture (1) outbound byte amplification under spoofing, (2) CPU spent on token validation, HPKE decapsulation, PID scans and proofs, (3) peak pending sessions/response cache and cookie-rotation state. Test challenge loss/retransmission and valid-source floods; model proxy vs end-to-end reachability, NAT rebinding, rotated cookie secret, token reuse and response/size timing linkability. Retain independent AUTH peer identity and per-session replay checks.
- **Evidence maturity:** concept for ZK-ARCHE; established IETF standards provide the comparators.
- **Limitations:** A DTLS cookie/CoAP Echo is not a drop-in ZK-ARCHE wire format; address-reachability proves neither cryptographic peer identity nor authority. Threefold threshold is a measurement comparator, not an adopted ZK-ARCHE limit.
- **ZK-ARCHE inference:** before optional HPKE decode or registry scan, require a bounded source validation gate only in exposed datagram profiles where its benefit outweighs cost. Explicitly keep valid-source CPU throttling and privacy equivalence as distinct protections.
- **Wire / CPU / RAM / flash / dependency / trust / privacy impact:** challenge/response adds round trip and bytes; stateless MACs consume CPU/key management and small buffers, bounded state requires RAM and possibly persisted rotation secrets. No required infrastructure; retry token tied to an address may link sessions or fail after rebinding.
- **Rust/C/vector/profile impact:** capture pre/post retry exact byte lengths, operation counts and max resident state with identical attacker replay/duplicate/fragment/rebinding/proxy corpora; never silently apply the rule to already secure TCP/TLS paths or iot-core without measured justification.
- **Next evidence / disposition:** attack-driven local exact-head Rust/C trace and per-profile resource budget; later physical MCU measurements before mandatory claims. **prototype**; weekly candidate **yes**.

## 6. Cross-source synthesis

HPKE -06 defines the cryptographic envelope, not ZK-ARCHE sender authority or replay; DTLS 1.3 and CoAP Echo define source-reachability comparators, not end-to-end identity. Therefore a safe optional pipeline must retain separate *return route → bounded candidate decrypt → authoritative record resolution → authenticated transcript/proof → current authorization* boundaries. No one stage may upgrade an earlier unauthenticated observation. A verified cookie also does not justify unbounded valid-source HPKE or proof work. The novel evidence is the **separate acceptance and resource oracles**, not the mere existence of HPKE or cookies.
