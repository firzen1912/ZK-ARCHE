## 2. Executive synthesis

1. **New concrete registry mismatch:** The draft `spec/tls-exporter-channel-binding.md` fixes `EXPORTER-ZK-ARCHE-v1`, but the authoritative IANA TLS Exporter Labels registry (last updated **2026-10-28**, checked **2026-10-31**) has no such allocation. RFC 5705 `4 requires registration for non-`EXPERIMENTAL` labels; the current IANA registry specifies Expert Review. This is a draft standardization/identifier-allocation gap, **not proof of cryptographic breakage**.
2. **Provider calls are an unqualified security boundary:** rustls uses `context: Option<&[u8]>` and refuses early/unfinished-handshake export; OpenSSL and Mbed TLS expose `use_context` explicitly, and OpenSSL has a distinct early-exporter entry point. Mbed TLS exporter support is a build-time option. Successful local SHA-256 context fixtures cannot establish shared live exporter outputs or fail-closed runtime behavior.
3. **Independent non-TLS reproduction:** Reconstructed 112 canonical context bytes from the checked Rust/C fixture and computed SHA-256 = `a3ba0867ead3c60416f1a68596566f01739b3520b41422a3cda7c039b280c107`, matching the retained local test. RFC 9846's TLS exporter internally hashes that **32-byte supplied context**, so `SHA256(context_digest)` = `43c5b12764b794170161167177819bac489856db65dec05c6ee4ef49f5538c19` is the distinct internal context-hash input, not a published TLS exporter result.
4. R-010 stays P0/`reproduce`; the human decision is registration/label-policy and approved TLS version/profile floor, followed by exact-head two-peer provider/cross-language conformance. Neither source code nor normative specifications nor release posture were changed. R-011 remains independently blocked by its encoding ambiguity.

### D20261031-F01 — IANA exporter-label allocation must precede an interoperable fixed-label claim

- **Novelty / owner:** new concrete registry mismatch; R-010, zk228, `spec/tls-exporter-channel-binding.md` `2, TD-004. It extends rather than repeats the 2026-10-19 exporter-context analysis.
- **Primary sources / dates / types:** RFC 5705 `4 and `6, IETF Standards Track, **March 2010**, https://www.rfc-editor.org/rfc/rfc5705.html ; IANA **TLS Exporter Labels** live registry, last updated **2026-10-28**, checked **2026-10-31**, https://www.iana.org/assignments/tls-parameters/tls-parameters.xhtml#tls-exporter-labels ; RFC 9846 `7.5, IETF Standards Track, **July 2026**, https://www.rfc-editor.org/rfc/rfc9846.html .
- **Source-supported fact:** RFC 5705 permits unregistered private-use labels beginning `EXPERIMENTAL`; other labels require registry allocation. The current IANA registry describes Expert Review and printable `EXPORTER`-prefixed labels, and its complete displayed exporter-label list contains no `EXPORTER-ZK-ARCHE-v1`. RFC 9846 retains the RFC 5705 label-policy reference for TLS 1.3 exporters.
- **Repository fact:** `spec/tls-exporter-channel-binding.md` fixes `label = "EXPORTER-ZK-ARCHE-v1"` with 32 output bytes and a canonically hashed nonempty context, yet `spec/registries.md` governs ZK-ARCHE's *internal* channel-binding IDs, not IANA TLS exporter-label allocation. Neither is promoted.
- **Bottleneck / distinct idea:** make **external IANA label allocation** an explicit human-controlled, independently verifiable promotion gate separate from the internal channel-binding-method ID. Record an explicit choice between eventual registration and **isolated experimental-only** labeling; if an experimental label is chosen, it changes derived exporter bytes and requires versioned fixtures / reviewed migration. Do not silently rename or register identifiers in this research automation.
- **Evidence maturity / limitations:** standards and live registry **externally reviewed** as normative reference; **concept** for ZK-ARCHE application. Registry absence is a checked point-in-time fact, not proof of a collision, exploit, or rejection by TLS implementations. Future registration or policy changes require a fresh lookup.
- **ZK-ARCHE inference / impacts:** output remains 32 bytes if label changes; no additional wire field necessarily follows, but **interoperability is incompatible** across different labels on identical TLS sessions. Local CPU/RAM/flash overhead is negligible for this decision; no new dependency or centralized identity root is proposed. External IANA management does not become device trust authority. No unlinkability claim follows from a registered label.
- **Rust/C / vector / profile impact:** approved label bytes must be pinned identically in Rust/C TLS adapters, negative vectors, profile/registry references and end-to-end Finished tests. A label revision is a binding-method compatibility decision; do not promote AUTH-v3 or mutate existing draft vectors automatically.
- **Required next evidence / disposition / weekly:** human review of label-allocation strategy and IANA state, with a recorded stable/experimental scope and immutable mapping to the chosen profile; then two-peer differing-label and unexpected-label negatives. **Reproduce; weekly candidate yes.**

### D20261031-F02 — Three provider APIs expose different failure and export-boundary surfaces

- **Novelty / owner:** refines R-010 (not a new TLS protocol feature); R-011 is only a dependent transcript-encoding cross-link.
- **Primary sources / types / dates:** RFC 9846 `7.5, Standards Track **July 2026**, https://www.rfc-editor.org/rfc/rfc9846.html ; RFC 9266 `2, Standards Track **July 2022**, https://www.rfc-editor.org/rfc/rfc9266.html ; official rustls `ClientConnection::export_keying_material` API (documentation checked **2026-10-31**, release/date not inferred), https://docs.rs/rustls/latest/rustls/client/struct.ClientConnection.html ; official OpenSSL 3.3 `SSL_export_keying_material` manual (documentation checked **2026-10-31**), https://docs.openssl.org/3.3/man3/SSL_export_keying_material/ ; official Mbed TLS 3.6.6 `mbedtls_ssl_export_keying_material` API/config docs (checked **2026-10-31**), https://mbed-tls.readthedocs.io/projects/api/en/v3.6.6/api/file/ssl_8h/ .
- **Verified source-supported fact:** rustls takes an optional byte-slice context, rejects use before handshake completion and documents that it never uses the early exporter. OpenSSL has a separate `_early` API and a `use_context` switch; Mbed TLS has `use_context` and a conditional exporter build feature. RFC 9846 hashes the *supplied* context internally and reserves early exporters for explicitly specified 0-RTT use. RFC 9266's generic `tls-exporter` is a **different** fixed-label/empty-context channel-binding type, not ZK-ARCHE's per-AUTH label.
- **Repository fact / independent reproduction:** The Rust/C helpers hash 112 deterministic context bytes into `a3ba0867ead3c60416f1a68596566f01739b3520b41422a3cda7c039b280c107` (independently recomputed with Python `hashlib.sha256` from the published sample fields). When this digest is passed to TLS, the internal RFC 9846 context hash is `43c5b12764b794170161167177819bac489856db65dec05c6ee4ef49f5538c19`. Neither hash is a TLS exporter output; a real handshake secret and TLS exporter call are required. The retained TB-N corpus checks only digest relations. AUTH-v3 formal model assumes symbolic channel-binding inputs.
- **Bottleneck / distinct engineering idea:** define a **provider-neutral fail-closed exporter-adapter contract** with declared TLS version, completed-handshake state, negotiated ALPN, per-AUTH pre-binding checkpoint, 32-byte context digest, selected regular-exporter phase, exact label and length, and current TLS session identity. Map rustls `Some(&digest)` vs OpenSSL/Mbed TLS `use_context=1`; prohibit accidental empty/omitted context, 0-RTT early export, wrong result length, unavailable exporter build flag and unsupported TLS version. Do not infer authorization from a valid EKM. Pinned cross-provider acceptance is the promotion evidence; not generic digest equality.
- **Evidence maturity / limitations:** **software** for independently reproduced context SHA-256 and current API signature review; **concept** for ZK-ARCHE live adapter interoperability. No provider code execution, peer agreement, TLS-version negotiation, issuer trust, TLS1.2 EMS qualification or hardware evidence was performed. TLS1.3 absent vs empty context computes identically, but ZK-ARCHE's required **nonempty** canonical context is a separate stricter protocol check; TLS1.2/EMS support, if contemplated, needs an explicit profile/version decision rather than silent fallback. Standard KeyUpdate does not create a new TLS1.3 exporter secret; resumed connections do.
- **Wire / CPU / RAM / flash / dependency / trust / privacy impacts:** no required on-wire change. Adapter choice adds TLS-library/feature dependencies and handshake/session state; per-call canonical SHA-256 and exporter work (unmeasured), plus bounded per-AUTH/connection state. MCU footprint/energy remains unknown; do not make TLS/PKI mandatory for native Common Contract P2P. ALPN and TLS metadata may expose routing/fingerprint information under R-015; no privacy guarantee.
- **Rust/C / vectors / profile compatibility:** shared exact-head test oracle: (1) same TLS1.3 completed handshake/label/Some or use-context digest gives same 32-byte EKM, (2) wrong label, raw encoded context, empty/no context, wrong stage or final-KC self-reference, wrong ALPN/endpoint/profile, and early-exporter substitution reject, (3) distinct AUTH instances on same TLS produce separate bindings, (4) fresh resumed TLS connection requires fresh EKM and ZK-ARCHE AUTH-instance proof, (5) standard KeyUpdate preserves regular exporter in one connection, (6) unsupported TLS version, absent feature, prehandshake state, proxy TLS termination and wrong return/status fail closed, (7) final AUTH-v3 Finished mutation corpus executes only after R-011's canonical critical hash is human selected. Preserve existing synthetic vectors as digest-only evidence, not an interop acceptance oracle.
- **Required next evidence / disposition / weekly:** pin exact SDK/build/provider versions, selected TLS profile/version/fallback rule, and label allocation. Execute live Rust↔C and each-peer cross-provider TLS tests with retained transcripts, EKM comparison and failure traces under local exact-HEAD qualification; later benchmark physical target only if binding profile is selected. **Reproduce; weekly candidate yes.**

## 6. Cross-source synthesis

The IANA check changes **who owns the fixed exporter label**: it is an IETF/IANA-allocated namespace, unlike ZK-ARCHE's local channel-binding method ID. Independently, TLS provider capabilities define whether the correct phase and 32-byte canonical digest actually reach a live regular TLS exporter. These are two separate gates to AUTH-v3 exporter-bound Finished interoperability. Even perfect local SHA-256 agreement cannot pass either gate. The label is not a proof of device trust, and a TLS exporter is not authorization. The unresolved R-011 critical-extension hash makes a full Finished-conformance assertion premature.
