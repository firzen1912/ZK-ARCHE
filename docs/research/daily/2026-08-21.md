# ZK-ARCHE Research — 2026-08-21

## Executive synthesis

The current `dev` branch remains implementation-stable relative to the 2026-08-20 research cycle. No intervening Rust/C implementation, deterministic-vector, formal-model, roadmap, specification, or assurance changes were found. The four controlling debts therefore remain TD-001 independent review of the custom role-membership proof, TD-002 constrained-target measurement, TD-003 reproducible formal evidence, and TD-004 completion of the normative specification.

Three current LAKE/IETF developments sharpen those existing gaps without justifying a new mandatory primitive:

1. **Normal authentication should not silently mutate trust.** The July 2026 EDHOC implementation-considerations draft makes credential-learning policy explicit: under `NO-LEARNING`, a peer trusts a credential only when it already stores that credential, except for deliberately enforced scenario-specific authorization exceptions. This maps closely to ZK-ARCHE's existing rule that normal `AUTH` proves prior enrollment. ZK-ARCHE should treat `NO-LEARNING` as the baseline semantic model for normal AUTH and `p2p-iot-core`, while reserving credential-learning/trust-store mutation for explicit ENROLL/commissioner/grant flows.
2. **Credential references and their local database mappings belong in the threat model.** Formal-analysis discussion of EDHOC-PSK at IETF 125 exposed a subtle identity-agreement risk when two peers associate the same credential identifier with different keys. The meeting explicitly recommended modeling a stateful `ID_CRED -> CRED` database with attacker influence. ZK-ARCHE's current ProVerif skeleton has no stateful registry/credential mapping, while future lookup hints, resumption records, enrollment grants, policy references, and P2P trust records will create exactly this class of identifier-to-security-object mapping. Those mappings should be cryptographically or semantically bound and exercised in negative tests rather than assumed correct.
3. **Registries need compatibility constraints, not only numeric identifiers.** The July 2026 LAKE post-quantum cipher-suite draft adds method-registry and suite-registry compatibility metadata (`Requires DH/NIKE` versus `Supports DH/NIKE`) so a registered method cannot be paired with an incompatible suite. The parallel KEM-authentication draft illustrates why this matters: changing the authentication mechanism can change the number of messages, identity-protection timing, transcript/authentication completion point, and KEM security requirements. ZK-ARCHE's future suite/profile registry should therefore encode semantic prerequisites and compatibility, especially before optional PQ or alternative authentication methods are introduced.

No source reviewed today warrants changing the current Ristretto/HKDF/HMAC baseline, promoting PQ or anonymous credentials into `iot-core`, or modifying roadmap/spec/code automatically.

## Findings

### 1. Make prior-enrollment / NO-LEARNING an explicit trust-store mutation policy

- **Source:** `draft-ietf-lake-edhoc-impl-cons-07`, *Implementation Considerations for Ephemeral Diffie-Hellman Over COSE (EDHOC)*
- **Primary link:** https://www.ietf.org/ietf-ftp/internet-drafts/draft-ietf-lake-edhoc-impl-cons-07.html
- **Source type / venue:** IETF LAKE WG Informational Internet-Draft
- **Publication date:** 2026-07-06
- **Verified claim:** the draft distinguishes `LEARNING` and `NO-LEARNING` trust policies. Under `LEARNING`, a peer may validate, trust, and store a credential that was not already stored. Under `NO-LEARNING`, a peer trusts a credential only if it was already stored when the message arrived, except for deliberately enforced scenario-specific exceptions. The draft gives authorization-token-driven workflows as examples where an explicit exception can justify learning a new credential.
- **Problem addressed:** ZK-ARCHE already says normal AUTH is proof of prior enrollment, but that rule is currently distributed across roadmap prose and implementation behavior rather than expressed as a first-class trust-store mutation policy. Future P2P trust graphs, late enrollment, commissioner grants, lookup hints, or transported credential references could accidentally introduce a path where normal authentication mutates trust merely because a credential verifies cryptographically.
- **Strongest distinct engineering idea:** specify two separate operations: (a) authentication against previously trusted state, which is `NO-LEARNING` and cannot create/expand trust; and (b) explicit trust-state mutation through ENROLL/commissioner/grant procedures, where the authorization evidence, issuer, scope, epoch, validity, replay protection, and audit event are part of the state transition. A successful proof should establish possession/authorization relative to existing policy, not authorize persistence of a new trust anchor by itself.
- **Evidence maturity:** software
- **Limitations / uncertainty:** EDHOC credential validation, EAD, and ACE authorization-token formats are not ZK-ARCHE requirements. ZK-ARCHE P2P deployments may deliberately support local/manual trust establishment, but that should still be modeled as an explicit enrollment/trust operation rather than a side effect of normal AUTH.
- **ZK-ARCHE inference:** the current Rust AUTH behavior is already directionally aligned because it searches enrolled registry entries rather than accepting self-registration. Future zk211/zk212/zk214/zk239 work should preserve that invariant and make authorized learning exceptions explicit and testable. Trust-store writes should produce an auditable reason/authority record and should not be reachable from unauthenticated or merely proof-valid traffic.
- **Wire / RAM / CPU / flash / dependency impact:** no mandatory wire cost for the baseline rule. Explicit enrollment/grant exceptions need bounded authorization fields and persistent audit/epoch state, but normal `iot-core` AUTH can remain unchanged. The separation may reduce attack surface by keeping certificate/credential validation and trust mutation out of the normal fast path.
- **Rust/C / vector compatibility impact:** compatible with current AUTH. Future negative vectors should prove that unknown credentials cannot create trust during normal AUTH, a proof-valid but unenrolled peer remains rejected, unauthorized commissioner/grant attempts do not mutate the registry, and an explicit valid enrollment authorization can create only the scoped trust state it permits.
- **Recommended disposition:** reproduce

### 2. Model credential-reference-to-security-state mappings as adversarial state

- **Source:** IETF 125 LAKE meeting minutes, formal analysis of `draft-ietf-lake-edhoc-psk-06`
- **Primary link:** https://datatracker.ietf.org/doc/minutes-125-lake-202603160600/
- **Source type / venue:** official IETF LAKE WG meeting minutes summarizing formal-analysis results and review discussion
- **Meeting date:** 2026-03-16; minutes updated 2026-03-17
- **Verified claim:** the formal-analysis discussion identified a credential-identifier binding problem: if one peer associates the same credential identifier with one key while the other associates it with another key, protocol transcripts can still agree on the identifier even though the local credential mappings differ. Reviewers explicitly proposed a stateful formal model of the credential database (`ID_CRED -> CRED`) with attacker influence/misconfiguration capability. The subsequent PSK draft update recorded that the identifier-to-PSK relation still needed clarification and that formal-analysis feedback had already driven protocol/test-vector changes.
- **Problem addressed:** ZK-ARCHE's current ProVerif skeleton treats keys/proofs abstractly and does not model its registry or any future credential-reference database. Today, AUTH computes PID candidates from enrolled public keys, which avoids accepting a cleartext externally selected stable device identifier. However, zk220 encrypted lookup hints, zk221 resumption records, zk211 enrollment grants, zk234 policy epochs/release state, and zk239 P2P trust records can all create local identifiers or handles that map to keys, roles, policies, or authorization state.
- **Strongest distinct engineering idea:** treat every security-relevant reference as a tuple binding, not merely a lookup optimization. A credential/trust reference should resolve to the exact public key or commitment, role/policy context, deployment/domain, relevant epoch, suite/profile constraints, and authorization provenance expected by the transcript/state machine. Formal analysis should include misconfigured or attacker-influenced mappings and minimal-compromise scenarios; implementation tests should intentionally swap references between otherwise valid records and require deterministic failure.
- **Evidence maturity:** formal
- **Limitations / uncertainty:** the reported analysis concerns EDHOC-PSK and a PSK identifier, not ZK-ARCHE's current PID construction. The minutes capture formal-analysis discussion rather than a final RFC security theorem. ZK-ARCHE should not copy a PSK-specific fix such as `hash(psk)` blindly; the transferable lesson is that identifier-to-security-object mappings must be included in the model and binding contract.
- **ZK-ARCHE inference:** R-004 should expand from a stateless abstract AUTH model to a stateful registry/trust model. Future lookup hints or ticket IDs must not be treated as authoritative identity by themselves; after lookup, the resolved key/policy state must be transcript- or proof-bound and checked for domain/epoch consistency. This also supplies a concrete model-to-code traceability target for TD-003.
- **Wire / RAM / CPU / flash / dependency impact:** possibly zero wire cost when the binding can be derived from already-transcript-bound state; otherwise compact commitments/epochs may be required. Formal/model complexity increases, and gateways may need bounded metadata per record. The implementation cost is preferable to silently trusting local database consistency as an unstated security assumption.
- **Rust/C / vector compatibility impact:** no current wire change. Add differential negative vectors for swapped credential references, wrong role/policy record, wrong domain/epoch, stale resumption mapping, lookup-hint collision/misbinding, and cross-peer trust-record substitution. The formal model should expose the database relation and attacker/misconfiguration capabilities explicitly.
- **Recommended disposition:** reproduce

### 3. Add semantic method/suite compatibility to registry and PQ benchmarking

- **Sources:** `draft-ietf-lake-pqsuites-00`, *Quantum-Resistant Cipher Suites for LAKE*; `draft-ietf-lake-authkem-edhoc-00`, *KEM-based Authentication for EDHOC*
- **Primary links:** https://datatracker.ietf.org/doc/html/draft-ietf-lake-pqsuites-00 and https://www.ietf.org/archive/id/draft-ietf-lake-authkem-edhoc-00.html
- **Source type / venue:** active IETF LAKE WG Standards-Track Internet-Drafts
- **Publication date:** both 2026-07-06
- **Verified claim:** the PQ cipher-suite draft adds a `Requires DH/NIKE` property to the authentication-method registry and a corresponding `Supports DH/NIKE` property to the cipher-suite registry so that method/suite compatibility is explicit. It replaces the key-exchange DH value with KEM encapsulation/ciphertext material for compatible suites and lists ML-KEM ciphertext sizes of 768 bytes (ML-KEM-512), 1088 bytes (ML-KEM-768), and 1568 bytes (ML-KEM-1024). The separate KEM-authentication draft takes a different route: it defines signature-free KEM authentication, normally uses five handshake messages, delays complete mutual authentication until the final messages, and requires the KEM shared secret to be cryptographically bound to the recipient public key to prevent re-encapsulation/unknown-key-share attacks.
- **Problem addressed:** ZK-ARCHE's registry skeleton enumerates suites and profiles but does not define which authentication/proof/key-establishment methods are compatible with which suite/profile. That is manageable while there is one conservative baseline, but becomes dangerous once optional PQ, anonymous-credential, TLS-bound, or alternative proof methods exist. A numerically valid pair can still be semantically invalid or have different message/state requirements.
- **Strongest distinct engineering idea:** make compatibility metadata part of registry governance. Each future suite should state the key-establishment family it supports, authentication/proof families it supports, required transcript/KDF construction, profile/transport eligibility, message-count/state-machine requirements, and constrained-device status. Negotiation must reject incompatible combinations before expensive cryptographic work. Deterministic vectors should include invalid method/suite/profile combinations as first-class negative cases.
- **Evidence maturity:** concept
- **Limitations / uncertainty:** both documents are active Internet-Drafts and may change. LAKE's COSE method/suite model is not identical to ZK-ARCHE's planned suite decomposition. The quoted ML-KEM sizes are ciphertext sizes only, not full ZK-ARCHE packet budgets, and the KEM-auth method's five-message flow is a design choice rather than a recommendation for ZK-ARCHE.
- **ZK-ARCHE inference:** R-003 should compare at least two PQ design classes—PQ/hybrid key exchange while preserving the existing authentication shape versus a KEM-authentication-style method—before any suite is proposed. R-011 should expand from unknown-value agility to incompatible-but-known-value testing. This strengthens zk224/zk225/zk226 without promoting PQ into `iot-core`.
- **Wire / RAM / CPU / flash / dependency impact:** substantial for PQ profiles. Even an ML-KEM-512 ciphertext alone is 768 bytes before framing/authentication material; larger parameter sets exceed typical small-datagram comfort zones. KEM-authentication can add handshake messages and persistent/static KEM key requirements. Full packet, fragmentation/loss, stack/heap, flash, CPU, and latency measurements remain mandatory.
- **Rust/C / vector compatibility impact:** no current change. Future vectors should cover compatible and incompatible method/suite/profile combinations, wrong recipient-key binding, incomplete-handshake key persistence, downgrade attempts, and exact packet-size/round-trip measurements across Rust and C.
- **Recommended disposition:** benchmark

## Cross-source synthesis

Today's sources converge on a single architectural rule: **the meaning of security state must be explicit at every lookup and mutation boundary**.

- `NO-LEARNING` separates authentication from authorization to mutate trust.
- The EDHOC-PSK formal analysis shows that the local mapping behind a credential reference can invalidate identity agreement even when the on-wire identifier is the same.
- The LAKE PQ work shows that a registered method and registered suite are not necessarily a valid pair; compatibility is itself security metadata.

For ZK-ARCHE, this suggests a future conformance/state matrix spanning **trust-store mutation permission**, **credential/reference resolution**, **method/suite/profile compatibility**, **domain/policy/epoch binding**, and **derived session state**. Normal AUTH should consume pre-existing trusted state; enrollment should be the explicit place that creates or expands it; every security reference should resolve to transcript-consistent state; and negotiation should fail before expensive work when a known combination is semantically incompatible.

The current code already provides one useful baseline: normal Rust AUTH scans enrolled records and verifies proofs rather than accepting unknown-device self-registration. The main gap is to make that invariant normative, cross-language-testable, and present in the formal state model before future lookup, resumption, P2P trust, and PQ extension work expands the state space.
