## 2. Executive synthesis

1. The ACE WG's **2026-10-22** LAKE+OSCORE profile (-12, work in progress) binds a client's authentication credential to a token and derived OSCORE context, but still independently verifies *resource/action* authorization. It specifies distinct invalidation consequences for tokens, credentials and LAKE sessions, plus abort-on-conflicting authorization-server negotiation information.
2. The LAKE WG's **2026-10-04** implementation draft (-08) requires cross-path identity consistency when the same authentication credential is conveyed by ID_CRED and external authorization data. The **2026-10-16** individual credential-hash draft (-02) changes LAKE transcript computations from credential bytes to the suite-hash of those bytes only under explicit signaling; the correct credential/hash and its trusted provenance remain essential.
3. ZK-ARCHE already requires NO-LEARNING normal AUTH, issuer/authority-scoped identity attribution, authorization-generation freshness and distinct authorization decisions. Its current Rust/C P2P delegation classifiers consume **preverified Boolean facts**, not complete OAuth/LAKE token parsing or credential-hash transcript interchange. The next evidence should test integration boundaries, not treat classifier parity as end-to-end proof.
4. The two sources sharpen R-008 and R-001 without justifying a new mandatory OAuth authorization server, X.509, LAKE, COSE, credential-hash mode or on-wire change. No ZK-ARCHE code, physical MCU benchmark or formal proof was executed.

## 5. Findings

### D20261030-F01 — Independent invalidation frontiers across authentication, authorization and protected traffic

- **Novelty / owner:** refines R-008, with R-012 revocation/invalidation and R-013 identity-attribution cross-links; human-owned zk211/zk212/zk230/zk239 / TD-004.
- **Primary source, type, date, URL:** IETF ACE WG, *Lightweight Authenticated Key Exchange (LAKE) and OSCORE Profile of ACE*, Internet-Draft `draft-ietf-ace-edhoc-oscore-profile-12`, **2026-10-22** (work in progress): https://datatracker.ietf.org/doc/html/draft-ietf-ace-edhoc-oscore-profile-12 ; especially §§4.5, 4.6, 4.10–4.14.
- **Verified source fact:** LAKE mutually authenticates client/server while an ACE access token is bound to the client's authentication credential; the resulting OSCORE security context protects requests. After OSCORE verification, the resource server *separately* checks token authorization for the requested resource and action. Token invalidity causes token/associated OSCORE deletion and session purge; client or server credential invalidity cascades into specified token/session/derived-context invalidations; invalidated LAKE sessions invalidate their derived OSCORE contexts. If the authorization server's advertised path/method/suite conflicts with an already-running LAKE exchange, the draft requires abort rather than silent adaptation.
- **Repository fact:** `spec/implementation-requirements.md` differentiates AUTH, authorization and persistent trust mutation; `spec/authorization-generation-lifecycle.md` forbids a valid credential, session or cached grant from repairing stale authority. Rust/C P2P decision helpers evaluate supplied verified facts; they do not demonstrate the full cryptographic-origin→grant→live DATA lifecycle.
- **Bottleneck:** a cryptographically good session or a previously valid grant can accidentally be reused after *one* upstream authority changes. Higher-layer policy metadata received mid-flight may conflict with the already negotiated method/profile and must not silently upgrade authority.
- **Distinct engineering idea / ZK-ARCHE inference:** define a **local-authority dependency/invalidation graph** `{credential attribution, grant, authorization generation, revocation view, session/channel, derived DATA access}`, where edges encode exact scope and authority. In paired Rust/C scheduler-controlled tests, first accept a legitimate protected DATA operation, then separately invalidate (a) the access/grant, (b) the endpoint credential or mapped authority, (c) the authenticated association, (d) the current policy/revocation generation and (e) a conflicting later authority hint; require denial of *new effects* without treating either TLS/OSCORE/LAKE success or a stale token as authorization. A scoped change in domain A must not invalidate unrelated domain B unless explicitly shared; use an explicit in-flight completion policy.
- **Evidence maturity:** IETF WG draft is **concept** comparator for ZK-ARCHE, not executed ZK-ARCHE assurance.
- **Limitations:** ACE assumes a trusted authorization-server/token architecture and OSCORE/LAKE session management. ZK-ARCHE's mandatory P2P Common Contract expressly avoids requiring any always-online authorization service. The draft's delete/purge operations do not directly prescribe ZK-ARCHE's persistence or generation scheme.
- **Wire / CPU / RAM / flash / dependency / trust / privacy impact:** **no required wire change**; likely extra local dependency indexes and generation checks (bounded RAM/CPU) and persistence writes on invalidation (flash/endurance impact unmeasured). An OAuth/OSCORE server or certificate stack is **not** adopted. Explicit scoping protects multi-authority isolation; privacy of unauthorized-error behavior and hints requires R-015 checks.
- **Rust/C/vector/profile compatibility:** preserve existing profile authority floor and classifier APIs until approved engineering change. Proposed shared fixtures: valid grant+protected operation; stale grant with valid channel; revoked credential with live cached session; policy generation switch between classification and emission; changed suite/method/profile from untrusted late hint; scoped domain A/B invalidation; restart/rollback; ordering and reason parity across Rust/C.
- **Next evidence:** pin exact repo spec/checkpoint, build property-to-source and classifier-to-adapter ownership matrix, then run local exact-HEAD Rust/C tests and stateful model/counterexample for at least one previously accepted operation followed by invalidation; physically measure state and durable writes before a constrained claim.
- **Disposition:** R-008 stays `reproduce`; cross-link R-012/R-013, no new R-* item. Weekly finding candidate: **yes**.

### D20261030-F02 — Credential hash versus reference is a transcript and authority decision, not a free privacy optimization

- **Novelty / owner:** refines R-001; R-013 owns canonical local attribution and NO-LEARNING, R-015 owns passive correlatability; human-owned zk217/zk225/zk226 / TD-004.
- **Primary sources, types, dates, URLs:** IETF LAKE WG, *Implementation Considerations for LAKE*, Internet-Draft `draft-ietf-lake-edhoc-impl-cons-08`, **2026-10-04**: https://datatracker.ietf.org/doc/html/draft-ietf-lake-edhoc-impl-cons-08 §§5.3–5.4; Selander et al., *Hashing Authentication Credentials in LAKE*, individual Internet-Draft `draft-selander-lake-cred-hash-02`, **2026-10-16**: https://datatracker.ietf.org/doc/html/draft-selander-lake-cred-hash-02 §§3–6 (individual draft, not IETF endorsement).
- **Verified source facts:** LAKE implementation guidance requires peers receiving the same credential via `ID_CRED` and an EAD-supplied envelope (such as an access token) to confirm they designate the same credential; mismatches abort. The hash-mode draft proposes an explicitly signaled COSE header parameter, replacing CRED with `H(CRED)` in LAKE MAC/signature contexts and transcript hashes, using the selected EDHOC suite's hash. The sender needs the *correct trusted hash*, and the peer verifies it corresponds to the correct credential; the draft does not claim that hashing alone authenticates or authorizes.
- **Repository fact:** `spec/implementation-requirements.md` §4.1 requires one authoritative mapping of credential/reference/key/peer/role/audience; local selectors and opaque hints are non-authoritative. `spec/auth-v3-kc-transcript-encoding.md` separately fixes byte-exact transcript inputs. This repository has draft context-hash helpers and deterministic vectors, **not** an adopted LAKE credential-hash wire mode or complete cross-language credential-envelope transcript parser.
- **Bottleneck:** reference, alias, full credential, and digest can point to mismatched records (especially with reused keys, issuer collisions or stale caches), even if each representation is independently well formed. Switching digest-versus-raw-credential transcript inputs without explicit mode binding would break peer agreement and may obscure authority confusion.
- **Distinct engineering idea / ZK-ARCHE inference:** create a **three-representation comparison** against the same authorized local object: full byte-exact credential, verified opaque reference and verified hash. Separately test correct same-object resolution, two distinct credentials sharing opaque alias, same key under distinct issuer/role records, wrong issuer hash, stale digest after authorized replacement, mode mismatch, changed suite/hash, malformed/noncanonical credential bytes and EAD/ref inconsistency. Require proof of possession and *local policy attribution* independently from any reference/hash equality. Report observed wire, flash, RAM, CPU and latency before considering an optional representation. A public stable digest may itself become a passive correlation handle; do not label it unlinkable.
- **Evidence maturity:** source design is **concept** for ZK-ARCHE; the LAKE WG draft is implementation guidance, the hash proposal is individual work in progress. Neither is a Rust/C ZK-ARCHE test or cryptographic proof.
- **Limitations:** EDHOC transcript inputs and credential model differ from ZK-ARCHE's custom role proof, locally authoritative trust store and non-advertised AUTH-v3; no literal drop-in encoding or improvement is established. Full credential may already be absent on ZK-ARCHE's compact wire, so a digest could *increase* bytes, with unknown CPU/energy. Consistent bytes do not guarantee privacy.
- **Wire / CPU / RAM / flash / dependency / trust / privacy impact:** optional digest mode would carry a suite-sized hash if transmitted, potentially replacing a larger credential but not necessarily outperforming an existing short reference; local credential/hash mapping may cost storage and hash cycles. **No measured savings**. No new CA, cloud, credential issuer, COSE/LAKE dependency. Hash/linkability and lookup timing need R-015/R-014 analysis.
- **Rust/C/vector/profile compatibility:** benchmark only; require pinned cryptographic mode, canonical credential bytes and selected suite, exact `H(CRED)` vector, negative mode/credential substitution, precise accepted-authority mapping, and two-lane transcript parity. Avoid changing existing transcript fields, hash definitions or published wire IDs pending explicit review.
- **Next evidence:** local exact-head shared corpus with byte fixtures and deliberate misbinding; compare existing reference path to proposed hash-only comparator at 1/10/100/1000 records; record CPU/RAM/flash, wire and privacy-visible metadata on STM32/ESP32-S3 where available. Identify whether `H(CRED)` ever improves over existing reference without weak authentication or persistent linkability.
- **Disposition:** R-001 stays `benchmark`; R-013 and R-015 cross-linked without state updates. Weekly finding candidate: **yes**.

## 6. Cross-source synthesis

The three October drafts converge on a single compositional boundary: a credential reference or digest can help *locate or bind* an authenticated object, but it does not authorize an operation, and protected-session success must not outlive credential, grant or policy currentness. ACE's per-resource authorization after OSCORE verification and LAKE's dual-source credential consistency are independent checks; both must pass. ZK-ARCHE can learn from these boundaries while preserving local authority and its mandatory PKI/cloud-free Common Contract. A stable hash, public authorization hint or changed error behavior may increase observability even when identity or authorization correctness improves. No cryptographic equivalence, wire saving or unlinkability benefit is presumed.
