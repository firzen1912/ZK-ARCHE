## 1. Executive synthesis

1. **`usage_counter_continuity_current` is a useful fail-closed Common Contract fact, but it should not eventually collapse all AEAD usage safety into one undifferentiated counter.** The July 6, 2026 OSCORE key-usage-limits draft separates sender-side protected-message count `q`, recipient-side failed-verification count `v`, algorithm-specific limits, and maximum protected message length `l`. Current ZK-ARCHE correctly models only a decision-level continuity fact and does not yet claim concrete AEAD counter semantics. The next LINK/lifecycle design should therefore define which directional counters/limits exist per key and what evidence makes the aggregate continuity fact true.
2. **Exact persistence of every sender-use counter is not the only safe constrained-device design.** The same OSCORE draft describes a conservative estimate of sender usage derived from sequence-number/replay state, explicitly trading earlier key update for less stored counter state. This is highly relevant to ESP32/STM32 flash-endurance and persistence design: ZK-ARCHE can consider a provably conservative monotonic upper bound instead of an exact durable counter, but only if every input to that estimate has rollback/restart continuity strong enough for the claimed profile.
3. **Replay rejection and failed-authentication usage accounting are separate events.** In the OSCORE design, packets identified as replays do not increment the forgery-attempt counter, while packets that reach AEAD verification and fail do. ZK-ARCHE should preserve the same conceptual separation when it eventually defines protected DATA/LINK key-usage limits: replay state, invalid-ciphertext/forgery budget, and sender-use budget should not be inferred from one another.
4. **The new ENROLL generation binding is directionally reinforced by current ELA work, especially exact-session authorization binding.** ELA binds its authorization voucher to the current EDHOC handshake hash, device identifier, and authenticator credential, and a successful authorization response does not excuse later authentication failure. ZK-ARCHE should keep its own infrastructure-independent design, but future ENROLL grant/attempt evidence should remain bound to the exact attempt/session/subject/commissioner context rather than merely to a current policy generation.
5. **No wire, suite, profile-selectability, roadmap, ADR, debt status, or maturity claim changes today.** Existing R-008/R-009/R-012/R-013 and TD-002/TD-003/TD-004 already own these questions; no new backlog row is required.

### D20260905-F01 — Key-usage continuity needs directional AEAD accounting semantics

- **Novelty:** refines
- **Source:** `draft-ietf-core-oscore-key-limits-07`, *Key Usage Limits for OSCORE*
- **Primary link:** https://datatracker.ietf.org/doc/html/draft-ietf-core-oscore-key-limits-07
- **Source type / venue:** IETF CoRE Working Group Internet-Draft
- **Publication / update date:** July 6, 2026
- **Verified claim:** the draft treats sender-key encryption count `q` and recipient-key failed-decryption/verification count `v` as separate quantities with algorithm-dependent limits. It also includes `l`, the maximum protected message length in cipher blocks, in the security analysis. Sender processing increments `count_q` before encryption and stops use of the sender key after the limit is exceeded. Recipient processing does not increment `count_v` for packets already recognized as replays, but does increment it when AEAD decryption/verification fails; after the recipient limit is exceeded, that key is no longer used for verification.
- **Existing owner:** R-009 / TD-003 / TD-004 / CORE-LINK lifecycle
- **Repository fact:** current `dev` now requires `usage_counter_continuity_current` across CORE and P2P decision surfaces, but the fact is intentionally abstract. The local assurance checkpoint explicitly says it does not prove how key-usage counters are persisted or mirrored on real targets.
- **Problem addressed:** a single abstract “usage counter current” fact could later become underspecified if implementations interpret it differently—for example as only a sender nonce counter, only total packets, or only replay sequence state. AEAD security limits can depend on direction, failure count, algorithm, and message size.
- **Strongest distinct engineering idea:** define a future LINK-owned key-usage state as an algorithm/profile-specific tuple such as `(key_epoch, direction, count_or_bound_q, limit_q, count_v, limit_v, l_bound, continuity_generation)` and derive the Common Contract boolean only after validating the required members for that association/profile. Do not expose all of this on wire unless a promoted profile needs it; it can remain local lifecycle state.
- **Evidence maturity:** externally-reviewed work-in-progress comparator; ZK-ARCHE decision surface is software evidence
- **Limitations / uncertainty:** OSCORE's exact values and message-processing rules are protocol-specific. ZK-ARCHE must derive its own limits from its eventual AEAD suites, data framing, forgery model, and traffic patterns rather than copying OSCORE constants.
- **ZK-ARCHE inference:** keep `usage_counter_continuity_current` as a compact Common Contract postcondition, but require a future normative owner to specify the concrete evidence behind it before TD-004 or lifecycle assurance can advance.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** no immediate wire change; concrete directional counters add bounded local state. Failed-verification accounting can affect DoS/key-rotation behavior. Algorithm/message-size limits may constrain profile packet sizes or trigger earlier rekey.
- **Rust/C / vector compatibility impact:** add shared future vectors that independently stale/exhaust sender-use and failed-verification budgets, distinguish replay rejection from AEAD-failure accounting, and verify identical reason precedence when multiple budgets are unsafe.
- **Required next evidence:** suite-specific `q/v/l` derivation for each promoted AEAD; owner/state model; Rust/C decision corpus; persistence/restart mapping; formal abstraction; exhaustion/rekey and malicious-invalid-ciphertext tests.

### D20260905-F02 — Conservative monotonic usage estimates can reduce persistent state

- **Novelty:** new/refines
- **Source:** `draft-ietf-core-oscore-key-limits-07`, Appendix B and sender-context processing
- **Primary link:** https://datatracker.ietf.org/doc/html/draft-ietf-core-oscore-key-limits-07
- **Source type / venue:** IETF CoRE Working Group Internet-Draft
- **Publication / update date:** July 6, 2026
- **Verified claim:** the draft permits a sender to avoid storing an exact `count_q` by computing a conservative estimate from sender sequence numbers and peer/replay-window information. The estimate intentionally overcounts and therefore may force earlier key update, trading efficiency for less dedicated stored counter state.
- **Existing owner:** R-005 / R-009 / TD-002
- **Repository fact:** ZK-ARCHE's September 5 assurance checkpoint explicitly leaves real-target key-usage persistence/mirroring unresolved. The repository already distinguishes replay continuity, restart continuity, and usage-counter continuity rather than assuming one implies another.
- **Problem addressed:** exact durable increment-on-every-use accounting can create flash-write, wear, atomicity, and power-loss costs on constrained MCUs. Persisting every cryptographic use directly may be impractical even when fail-closed counter continuity is required.
- **Strongest distinct engineering idea:** permit two evidence classes for future constrained profiles: (A) exact durable usage counters; or (B) a formally/conservatively derived upper bound from other monotonic state. Class B is valid only if rollback/restart of every contributing input cannot underestimate prior key use. Overestimation is acceptable because it reduces availability/efficiency, not security.
- **Evidence maturity:** concept backed by standards-track-adjacent engineering draft; target evidence absent
- **Limitations / uncertainty:** OSCORE's estimator relies on OSCORE sequence/replay structure and cannot be copied verbatim. ZK-ARCHE must prove its own estimator against its DATA/LINK framing and retransmission semantics. Failed-verification `v` may still require independent state or another safe bound.
- **ZK-ARCHE inference:** this is a promising constrained-target optimization because it preserves the Common Contract security floor without requiring identical storage mechanics across ESP32/STM32/Linux peers.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** potentially lower flash-write frequency and persistent-state cost; possibly earlier rekey and more CPU/wire overhead from conservative overestimation. No mandatory external dependency.
- **Rust/C / vector compatibility impact:** Rust/C need identical accept/fail-closed decisions for the same normalized usage facts even if platform adapters use different persistence strategies. Target-specific estimator tests should include crash, rollback, skipped writes, retransmission, and wrap/exhaustion cases.
- **Required next evidence:** define a ZK-ARCHE-specific monotonic upper-bound candidate; prove it never underestimates usage under restart/retransmission/loss; measure flash writes/endurance and rekey frequency on representative ESP32-S3/STM32 targets; compare against exact-counter persistence.

- **Primary link:** https://datatracker.ietf.org/doc/html/draft-ietf-lake-authz-08
- **Source type / venue:** IETF LAKE Working Group Standards Track Internet-Draft
- **Publication / update date:** July 6, 2026
- **Verified claim:** ELA binds its voucher to the current EDHOC handshake hash `H_12`, the device credential identifier, and the authenticator credential. The enrollment server uses `H_12` as session-related state, and a successful voucher response does not override a later failure to authenticate the device credential; the exchange aborts if credential verification fails.
- **Existing owner:** R-008 / R-013 / `spec/enroll-lifecycle-state-machine.md`
- **Repository fact:** ZK-ARCHE's ENROLL draft now requires authenticated commissioner authorization-generation provenance/currentness and an operation identifier/nonce, then composes issuance with durable mutation. It already keeps authentication, authorization, and trust mutation separate.
- **Problem addressed:** a grant that is merely “from a currently authorized commissioner” can still be misbound if it is transplanted between attempts, subjects, commissioners, or sessions. Parallel authorization also creates a risk that a successful authorization result is mistakenly treated as proof that peer authentication succeeded.
- **Strongest distinct engineering idea:** retain ZK-ARCHE's infrastructure-independent ENROLL model, but make any eventual grant/attempt transcript bind at least the exact operation identifier, subject key/commitment, commissioner identity/credential, selected profile/version, requested/granted scope, deployment/audience, and authenticated authorization generation. Generation currentness is a lifecycle gate; exact attempt binding prevents cross-attempt substitution.

- **Limitations / uncertainty:** ELA assumes an online enrollment server and EDHOC-specific transcript components; ZK-ARCHE explicitly does not want such infrastructure to become mandatory for ordinary authorized P2P operation.
- **ZK-ARCHE inference:** use ELA's exact-session binding discipline, not its infrastructure topology. A positive authorization/grant path must never synthesize missing subject authentication, commissioner authentication, or local generation provenance.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** eventual grant/context encoding may add bounded transcript fields or hashes; no required online service. Stronger binding reduces substitution/misbinding risk with modest local hashing/state cost.
- **Rust/C / vector compatibility impact:** future deterministic ENROLL negative vectors should swap operation IDs, subjects, commissioners, profiles, scopes, and generations independently while preserving otherwise valid signatures/proofs; Rust/C must reject identically.

## 5. Cross-source synthesis

The September 5 repository delta makes lifecycle safety more explicit, but today's sources clarify what future concrete semantics must sit below those high-level facts.

For LINK/DATA key usage, the important decomposition is:

```text
replay continuity
        ≠
sender AEAD-use budget (q)
        ≠
failed-verification/forgery budget (v)
        ≠
maximum protected length assumption (l)
        ≠
restart/persistence continuity
```

A Common Contract boolean can remain useful as a postcondition, but only after the owning layer establishes the profile-specific state behind it. On constrained targets, conservative monotonic upper bounds may reduce flash pressure as long as rollback can never make the estimate smaller than true prior usage.

For ENROLL, the corresponding decomposition is:

```text
commissioner authenticated
        +
authorization generation authentically bound/current
        +
exact attempt/session/subject/commissioner context bound
        +
subject possession succeeds
        +
replay/rollback/lineage state current
        ↓
durable trust mutation
```

Authorization can be processed in parallel with authentication for efficiency, but one does not repair or imply the other.
