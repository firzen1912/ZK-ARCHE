## 2. Executive synthesis

1. **Intentional, verifier-scoped linkability is distinct from unlinkability.** CFRG's updated BBS per-verifier-linkability draft provides a stable pseudonym within a selected context. It is only a possible optional comparison for ZK-ARCHE, not a property of the current Ristretto/SHA-256 role proof or production AUTH.
2. **Freshness signals are not local authorization or replay authority.** The RATS epoch-marker draft explicitly permits signed markers to be delayed/replayed and distinguishes reusable markers from session-bound nonces. Clockless admission must preserve pre-existing authority, revocation and persistent replay semantics.
3. **ML-KEM does not automatically replace authentication-bearing DH.** The new CFRG research-group draft cautions against mechanically replacing implicit DH authentication and clarifies key/ciphertext size requirements; a candidate ML-KEM-768 public key plus ciphertext is 2,272 bytes across objects, exceeding the draft 2,048-byte single-datagram budget if combined in one flight, before framing.
4. These drafts update research evidence contracts only. No standard is promoted by being a November 16 Internet-Draft; no new BBS, Epoch Bell, PQ, CA, online-verifier or cloud dependency is accepted. No executed Rust/C, physical MCU, formal-proof or privacy measurement evidence was produced.

### D20261117-F01 — Intentional per-verifier BBS recognition is a distinct privacy profile, not a free anonymity upgrade

- **Novelty / backlog owner:** refines R-015 P0; R-002 P3 cross-reference (no separate backlog revision).
- **Primary source / publication / type:** IRTF CFRG, BBS per Verifier Linkability, draft-irtf-cfrg-bbs-per-verifier-linkability-05, **2026-11-16**, Informational Internet-Draft, not a published RFC: https://datatracker.ietf.org/doc/draft-irtf-cfrg-bbs-per-verifier-linkability/ . This is a current source revision; the underlying concept is not asserted to have originated in revision -05.
- **Source-supported verified claim:** The draft derives a proof-verifiable pseudonym from issuer-bound prover secret material and a public context_id. Holding the relevant inputs fixed yields the same pseudonym, intentionally allowing recognition within that context; different context values are intended to yield distinct pseudonyms under the draft's assumptions. Issuer contribution to blinded pseudonym secrets supports the defined uniqueness/anti-persona policy but does not prevent metadata correlation, collusion, or compromised-device observations.
- **Exact owner / repository anchor:** R-015, zk215/zk218/zk223, spec/privacy-considerations.md §§3–9, spec/registries.md; R-002 optional BBS research.
- **Problem / bottleneck:** Marketing a selective-disclosure credential as “unlinkable” would hide intentionally stable verifier-scoped pseudonyms and any domain/issuer overlap. Accepting a remote-selected context as trusted identity would also violate ZK-ARCHE's local authority model.
- **Strongest distinct engineering idea:** Evaluate three isolated observer lanes: mandatory existing AUTH with no new pseudonym; optional pseudonym with locally pinned verifier/domain/audience context and controlled same-verifier recognition; and a negative corpus with colluding verifiers, duplicated/reassigned context IDs, overlapping disclosed attributes, role/profile diversity, forged context selection, rollback and revoked/rotated credential lineage. Distinguish intended repeat-recognition from cross-verifier correlatability and from credential-holder authorization.
- **Evidence maturity:** concept for ZK-ARCHE; published active research Internet-Draft and reference vectors are source evidence only, not external cryptographic review of ZK-ARCHE or executed device evidence.
- **Limitations / uncertainty:** Source privacy properties are conditional on signer/prover/verifier behavior and cryptographic assumptions. Cross-layer network metadata, attributes, timing and observer collaboration may defeat separation. No implementation, size or MCU timing measured; BBS does not validate ZK-ARCHE's custom CDS OR construction.
- **ZK-ARCHE inference:** A deliberately linkable optional credential should carry a separately reviewed explicit privacy contract; native NO-LEARNING P2P and current no-general-unlinkability-claim posture must remain the default.
- **Wire / CPU / RAM / flash / dependencies / trust / privacy:** Current baseline costs zero. An optional BBS/pairing lane would increase presentation/issuer state, curve/dependency flash and CPU, working RAM, and potentially stable on-wire correlation; all exact sizes and costs remain unmeasured. Context must not confer authority merely because it matches a transport endpoint.
- **Rust/C / vectors / profile compatibility:** Current suite 0x0001, v2 and draft-v3 reference vectors unchanged. Before any optional adoption require complete BBS proof bytes, pseudonym canonical encoding, same/cross-context accept/reject and collusion tests, Rust/C provider parity, and constrained MCU/gateway comparative benchmarks.
- **Required next evidence / disposition:** Locally pinned simulator and passive/active traffic-capture matrix with repeated/cross-context tests; then external mathematical/implementation review and exact target measurements. **reproduce**.
- **Weekly finding candidate:** yes; intentional linkability is a separate security/privacy choice, not general anonymous authentication.

### D20261117-F02 — Clockless epoch markers are reusable freshness signals, not current grant/epoch authority

- **Novelty / backlog owner:** refines R-012 P1; R-006/R-008 cross-references.
- **Primary source / publication / type:** IETF RATS WG, Epoch Markers, draft-ietf-rats-epoch-markers-09, **2026-11-16**, intended Standards Track Internet-Draft, not an RFC: https://datatracker.ietf.org/doc/html/draft-ietf-rats-epoch-markers-09 .
- **Source-supported verified claim:** An Epoch Bell can distribute cryptographically authenticated shared freshness without a receiver's trusted local clock. A network attacker can replay a valid signed marker or delay its delivery, and propagation latency causes legitimate recipients to have different views. Reusable markers are not session-unique; nonce binding supplies per-session uniqueness where required. The draft distinguishes global versus per-attester tracking, accepted windows, pinned marker types and their storage/latency cost; marker cadence and common Bell identity may create traffic-correlation metadata.
- **Exact owner / repository anchor:** R-012; zk214/zk239; spec/revocation-update-ingestion.md, spec/lifecycle-persistence-freshness.md, spec/authorization-generation-lifecycle.md, spec/replay-continuity.md. R-006 optional attestation and R-008 enrollment are separate.
- **Problem / bottleneck:** A valid/recently received signed marker could be confused with a current local revocation epoch, replay epoch, enrollment authorization or possession proof. Devices without secure time can be tricked by delayed, reordered or cross-authority markers if those state meanings are conflated.
- **Strongest distinct engineering idea:** Compare no-clock nonce/operation-ID freshness and optional locally pinned Bell-assisted freshness using a typed 4-way acceptance ledger: verified marker provenance/window; session nonce/attempt uniqueness; current locally authorized grant and revocation state; durable replay/rollback continuity. A marker may inform the first field only. Test replay, reordered/lossy broadcast, slow links, wrong trust domain, compromised foreign Bell, rollback, missing monotonic state, stale grant and valid marker with revoked subject. Reject state mutation on all failed cases.
- **Evidence maturity:** IETF draft source (concept for ZK-ARCHE); no simulated or physical ZK-ARCHE implementation reproduction.
- **Limitations / uncertainty:** The draft concerns RATS freshness, not ZK-ARCHE's mandatory P2P authority semantics. Off-grid peers may be unable to contact a Bell. Signed shared timing does not give revocation convergence or trusted persistent storage; no actual MCU/LoRa measurements have been made.
- **ZK-ARCHE inference:** Keep authenticated local revocation and authorization generation monotonic, independently derived from authorized lifecycle transitions. A trusted clock, Epoch Bell, CA, online verifier, or gateway must not become a hidden mandatory core-AUTH dependency. A future clockless Bell comparator is research only.
- **Wire / CPU / RAM / flash / dependencies / trust / privacy:** Current wire/dependency cost zero. Optional signed marker verification adds bytes, crypto CPU, key/trust distribution, epoch tracking state and flash writes; buffers grow with accepted window/per-attester tracking. Marker reuse can leak shared timing/Bell correlation. Resource cost and privacy are unmeasured.
- **Rust/C / vectors / profile compatibility:** No change to v2, suite 0x0001, draft AUTH-v3/iot-core or existing vectors. Future paired Rust/C exact-state tests must distinguish authenticated Bell evidence from revocation FULL/DIFF authority, auth-generation transitions, same-session replay and storage rollback; include local exact-head restart and marker-type mismatch vectors.
- **Required next evidence / disposition:** Small deterministic two-peer clockless trace corpus with signed/foreign/replayed/delayed markers, independent nonce, revocation-generation and durable-replay checks, then MCU flash/RAM/CPU/write-budget measurements. **reproduce**.
- **Weekly finding candidate:** yes; freshness source and current authorization are independent authority claims.

### D20261117-F03 — ML-KEM establishment cannot implicitly authenticate DH-based roles and needs a measured flight budget

- **Novelty / backlog owner:** refines R-003 P3, R-005 cross-reference.
- **Primary source / publication / type:** IRTF CFRG, ML-KEM Security Considerations, draft-irtf-cfrg-ml-kem-security-considerations-00, **2026-11-16**, newly CFRG-adopted Informational Internet-Draft (previous individual draft content carried forward), not an RFC: https://datatracker.ietf.org/doc/html/draft-irtf-cfrg-ml-kem-security-considerations-00 ; official CFRG adoption note dated 2026-11-03: https://mailarchive.ietf.org/arch/msg/cfrg/87MkF3BiXirh-xcQOU9AHujFsNk/ .
- **Source-supported verified claim:** A KEM can replace DH-style ephemeral key-establishment roles when the protocol accommodates send/receive ordering and larger objects, but is not a drop-in for implicit ephemeral-static DH authentication, static-static DH, or DH ratchet semantics. ML-KEM-768 has an 1,184-byte public key, 1,088-byte ciphertext, 2,400-byte expanded secret key, and 32-byte shared secret. KEM decapsulation alone does not authorize a credential or prove the intended peer identity.
- **Exact owner / repository anchor:** R-003 / zk224; spec/registries.md §§4–5, spec/iot-profiles.md, rust/test-vectors/profiles/iot-core-v1.profile, spec/zk-arche-protocol.md; R-005 and TD-002 target-measurement cross-reference.
- **Problem / bottleneck:** “Add ML-KEM” without method-by-method authentication/transcript composition can break peer authentication or exhaust constrained datagram/state budgets. FIPS-203 ML-KEM security is not a protocol-level proof of ZK-ARCHE PQ mutual auth, authorization, unlinkability, or compromised-session recovery.
- **Strongest distinct engineering idea:** Gate optional hybrids by a **method × suite × profile × flight** matrix with an authenticated public-key/ciphertext/role/transcript binding check, explicit downgrade-negative fixture, independently reviewed classical/PQ hybrid combiner, and exact sender/receiver ordering. Measure each full flight under loss, fragmentation and DoS before selecting any optional PQ profile.
- **Evidence maturity:** externally reviewed NIST FIPS 203 for ML-KEM primitive, active CFRG draft guidance; concept for ZK-ARCHE integration, no local benchmark.
- **Limitations / uncertainty:** The new group draft continues older individual guidance, so group adoption is the development, not a newly discovered vulnerability. The ML-KEM-768 public-key-plus-ciphertext **sum is 2,272 bytes**, exceeding the draft iot-core maximum of 2,048 **if both must fit in one datagram**. This does not prove that every possible multi-flight integration fragments; headers, proofs and hybrid material only add overhead, and actual flight layout has not been specified. No tested memory/performance figures.
- **ZK-ARCHE inference:** Preserve the conservative current suite 0x0001 and no-PQ-claim boundary. An optional gateway/edge profile may be feasible, but only after method-specific authenticated transcript construction and exact Rust/C physical-target comparison; never silently select a recognized yet incompatible KEM.
- **Wire / CPU / RAM / flash / dependencies / trust / privacy:** No baseline change. Optional ML-KEM-768 adds at least 1,184 pk + 1,088 ct object bytes across the exchange and up to 2,400-byte expanded secret-key storage (before remaining protocol state), crypto CPU/entropy, expanded library flash and possible retransmit/reassembly memory. Actual costs and fragmentation profile remain unmeasured. Trust and privacy must be analyzed separately from PQ confidentiality.
- **Rust/C / vectors / profile compatibility:** Existing v2/0x0001 corpus unchanged; nonselectable draft iot-core manifest remains max_datagram_bytes=2048, replay_epoch_rule=unresolved. Before any adoption: independently verified ML-KEM reference vectors, Rust/C provider pinning, authenticated transcript/hybrid combiner positives and suite/method mismatch negatives, full message bytes, RAM/stack/flash/latency/energy on physical targets.
- **Required next evidence / disposition:** Bounded exact-wire and state/entropy budget for one concrete edge/gateway hybrid candidate, including Rust/C provider versions, classical+KEM transcript composition and wrong-method rejection; human review before any spec/registry change. **benchmark**.
- **Weekly finding candidate:** yes; method-specific cryptographic meaning and constrained resource budgets must gate optional PQ.

## 6. Cross-source synthesis

BBS per-verifier pseudonyms, reusable epoch markers and PQ public keys solve different questions: repeat recognition, freshness timing and key-establishment hardness. None establishes a locally authorized subject, permits trust learning, repairs a revoked grant, provides persistent replay continuity or proves wire/privacy suitability in isolation. All three must be composed under the same locally authoritative protocol/security context and independently qualified. In particular a shared Bell may itself become a cross-domain timing fingerprint, and a stable BBS verifier context intentionally creates a pseudonym; neither should be conflated with absent on-wire names.
