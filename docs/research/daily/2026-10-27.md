## 2. Executive synthesis

1. Recent CFRG AEAD usage-limit guidance models encryption and adversary decryption/forgery work separately, including total exposure across multiple independent keys. A packet replay cache or resumption-reuse counter is not by itself a sufficient AEAD usage-accounting record.
2. CoRE's September OSCORE draft supplies a concrete comparator with sender encryption count, failed-decryption count, pre-decryption replay filtering, and conservative sequence-derived sender-count estimation. This is OSCORE-specific: ZK-ARCHE must first demonstrate the required nonce, sequence, retry and persistence invariants before transferring any accounting shortcut.
3. The July 2026 KUDOS draft distinguishes stateful forward-secret updates from a stateless no-forward-secrecy mode. ZK-ARCHE must not infer forward secrecy merely from a rekey label, successful crypto exchange or an in-memory successor state.

## 5. Findings

### D20261027-F01 — AEAD budgets require q, v, and independent-key accounting

- **Novelty:** refines R-009 by making the failed-decryption/forgery axis, aggregate-key assumptions and safe counter-estimation proof obligation explicit; source is primary but a draft, not an adopted ZK-ARCHE parameter.
- **Backlog owner / existing engineering owner:** R-009; zk213/zk221 and assurance; MCU measurement cross-link R-005.
- **Sources / type / dates / primary links:**
  - Günther, Thomson and Wood, Usage Limits on AEAD Algorithms, CFRG Internet-Draft -13, published 2026-09-03, https://datatracker.ietf.org/doc/html/draft-irtf-cfrg-aead-limits-13.
  - Höglund and Tiloca, Key Usage Limits for OSCORE, CoRE WG Internet-Draft -08, published 2026-09-07, https://datatracker.ietf.org/doc/html/draft-ietf-core-oscore-key-limits-08.
- **Verified source-supported claim:** CFRG specifies algorithm- and construction-dependent confidentiality/integrity bounds using the number of encryptions q, forgery/decryption attempts v, message-size assumptions and multiple independent keys. OSCORE defines separate Sender Context count_q/limit_q and Recipient Context count_v/limit_v: increment q before encryption, count failed decryptions toward v, and exclude packets rejected at its anti-replay check before decryption. Appendix B describes a conservative sequence-based q estimate that may overestimate actual encryption usage.
- **Repository fact / bottleneck:** ZK-ARCHE specifies replay-continuity fail-closed transitions and logical resumption authorization/reuse tests. Those are different state dimensions from actual per-key AEAD calls and forgery attempts. The inspected files do not supply a retained per-suite, per-direction encryption/failure counter and fleet-key budget qualification. That absence in inspected files is not a claim that the entire codebase lacks every counter.
- **Strongest distinct engineering idea:** Make a language-neutral per-suite key-ledger evidence model with distinct (i) sender encryption attempts, (ii) receiver AEAD authentication failures after the applicable early replay filter, (iii) per-key nonce and epoch history, and (iv) multi-key deployment exposure. Require recorded state transitions for limit warn, hard stop, rekey request, failed/aborted rekey, restart and lost state. Treat any sequence-derived q estimator as optional, conditional on a machine-checkable upper-bound invariant for all retransmit, retry, crash and rollback cases.
- **Evidence maturity:** concept for ZK-ARCHE; source guidance is publicly reviewed draft analysis. No ZK-ARCHE replay/AEAD instrumentation or measured limits were executed.
- **Limitations:** CFRG formulas depend on nonce construction, key independence, message-size blocks, offline attacker work and chosen acceptable advantage. OSCORE's SSN estimator and failure counting cannot be copied verbatim into different ZK-ARCHE packet/nonce handling. A hard-stop triggered by attacker forgeries can itself be a denial-of-service vector: availability policy needs a separate bounded response, not silent continuation with exhausted keys.
- **ZK-ARCHE inference:** Before setting numbers, enumerate each actual AEAD use path and key-derivation boundary; determine whether retransmitted bytes reuse a cached ciphertext or invoke fresh encryption; distinguish pre-AEAD duplicate filtering from AEAD failure; derive per-profile q/v budgets and a fleet risk statement. Test simultaneous key generations, per-direction usage, receiver-failure floods, counter restoration and attempted bypass via resumed associations.
- **Wire / CPU / RAM / flash / dependency / trust / privacy impact:** no immediate wire changes. Per-key q/v metadata may consume bounded RAM and durable writes/flash endurance; extra checking adds small unknown CPU; earlier rekey may increase bytes/latency/energy. No additional identity authority or HPKE dependency. Failure timing and rekey triggers may be observable privacy/DoS surfaces.
- **Rust/C/vector/profile compatibility:** additive research vectors should cover wrong-key failures, early-replay rejection vs failed AEAD, exhausted sender/receiver, retransmission, multi-key rollover and counter rollback, with exact same accepted/rejected decisions in Rust and C. Numerical limits and profile commitments require later reviewed spec changes.
- **Required next evidence:** exact algorithms and nonce construction; per-key independent randomness assumptions; concrete q/v/length/deployment bound derivation; common Rust/C fault-injection corpus; bounded target flash-wear and CPU measurements; adversarial attempts to force early exhaustion.
- **Recommended disposition / weekly finding candidate:** reproduce; yes.

### D20261027-F02 — Interrupted rekey is a persistence and forward-secrecy boundary

- **Novelty:** refines persistence/claim gating rather than proposing adoption of KUDOS as a ZK-ARCHE key-update protocol.
- **Backlog owner / existing engineering owner:** R-009, zk213/zk221; formal fidelity cross-link R-004.
- **Source / type / date / primary link:** Höglund and Tiloca, Key Update for OSCORE (KUDOS), CoRE WG Standards-Track Internet-Draft -14, published 2026-07-06, https://datatracker.ietf.org/doc/html/draft-ietf-core-oscore-key-update-14.
- **Verified source-supported claim:** KUDOS distinguishes a stateful forward-secret key-update mode requiring persistent state preservation from a stateless no-forward-secrecy alternative for constrained peers unable to write evolving nonvolatile state. The draft separately addresses reboot/loss of state and key/nonce non-reuse for OSCORE.
- **Repository fact / bottleneck:** spec/replay-continuity.md treats reboot/reconnect/outer-session change as insufficient to create a fresh replay epoch. spec/replay-epoch-recovery.md requires an authenticated successor transition with one logical activation/retirement commit. spec/resumption-lifecycle.md does not allow a ticket to replace local authority. Rust/C transitions fail closed on trusted-state rollback suspicion; docs/assurance/replay-continuity-trusted-rollback-gap-2026-09-11.md identifies a narrower unsynchronized ProVerif branch.
- **Strongest distinct engineering idea:** Define a two-generation crash-cut research matrix spanning old-key send, new-key derivation, authenticated successor confirmation, persistent write, old-key retirement/tombstone, replay epoch activation, and resumption ticket invalidation. Inject power-loss/restart before and after every cut; demand no old (key,nonce) reuse, no uncommitted successor authority, and clear evidence whether the selected device configuration can satisfy a forward-secrecy claim.
- **Evidence maturity:** concept for ZK-ARCHE; existing software decision primitives and documented formal gap, not physical power-cut or forward-secrecy proof evidence.
- **Limitations:** KUDOS is OSCORE-specific and remains an Internet-Draft. Storage durability is necessary for its specified FS mode but not a sufficient cryptographic proof for ZK-ARCHE. Actual flash, secure element, DRBG, erase, anti-rollback and key-derivation semantics require independent design and qualification.
- **ZK-ARCHE inference:** Explicitly separate key-renewal confidentiality, forward secrecy, origin/full-AUTH lineage, authorization generation, revocation view, replay epoch and resumption-reuse budget. A working traffic key must never imply that those independent states are refreshed. Distinguish a safe fail-closed restart from a successful recoverable rekey.
- **Wire / CPU / RAM / flash / dependency / trust / privacy impact:** research-only, no wire or dependency change; proposed qualification incurs simulator/physical cycle time. A future durable scheme consumes flash writes, persistent bytes and energy; rollback-resistant hardware may require a trust/availability tradeoff. Stale epoch identifiers and differing error paths can leak lifecycle timing; quantify before profile adoption.
- **Rust/C/vector/profile compatibility:** build shared staged fault vectors for each crash cut, partial storage commit, inconsistent key/replay counters, already-TRUSTED rollback event, concurrent resumption and revoked predecessor; record exact-head build and model-to-runtime correspondence. Preserve mandatory iot-core and p2p-iot-core security floor.
- **Required next evidence:** defined successor/retirement atomicity invariant; executable Rust/C transition traces; corrected trusted-state rollback formal model with retained counterexample/proof; physical STM32/ESP32-S3 power-loss and flash-endurance manifest; independent forward-secrecy analysis before claim.

## 6. Cross-source synthesis

The sources illuminate two different limits on the same lifecycle: how much cryptographic work one key may safely perform, and which generation remains usable after interrupted renewal. Counting successful AUTH instances or clearing an in-memory replay cache cannot replace encryption/decryption budgets or durable successor authorization. OSCORE accounting and KUDOS storage behaviors are comparators, not proof that ZK-ARCHE has either deficiency or their exact solution. The cost-sensitive order is: first derive the algorithm/nonce-specific invariant, then build exact-head Rust/C negative traces, then measure viable persistence on MCU targets, and only then request a reviewed profile/spec decision.
