## 2. Executive synthesis

1. **Canonical ZK-ARCHE exporter context and exporter-secret generation are independent security dimensions.** Current Rust/C corpus work proves that application, endpoint, profile and AUTH-instance context changes affect the context digest while transport/routing metadata does not. It does not prove that an unchanged context is current after the underlying exporter secret advances.
2. **A long-lived association needs an explicit binding-generation currentness relation.** The July 4, 2026 TLS Extended Key Update draft defines cryptographically independent exporter secrets per completed EKU epoch and notifies applications only after the new epoch becomes active. This makes `binding_valid` insufficiently precise if it can mean only “context digest matches.”
3. **Previous exporter generations may be retained for packet reordering, but retention is not authorization currentness.** The draft permits temporary old/new exporter-secret overlap, especially for DTLS. ZK-ARCHE should distinguish “old generation still processable for bounded transport reordering” from “old generation may authorize a new protected operation.”
4. **Epoch identifiers must remain adapter-local metadata.** The draft explicitly says TLS epoch identifiers are local logical counters that may differ between peers. ZK-ARCHE should normalize a semantic current/previous relation rather than put peer-comparable TLS epoch integers into the Common Contract.
5. No backlog status transition is justified. R-010/R-009 remain `reproduce` until Rust/C vectors exercise exporter-generation advance, bounded previous-generation acceptance, retirement, restart, and DATA/association admission semantics.

## 5. Findings

### D20260917-F01 — Context equality does not establish exporter-generation currentness

- **Novelty:** refines.
- **Backlog owner:** R-010.
- **Source:** `draft-ietf-tls-extended-key-update-13`, “Extended Key Update for Transport Layer Security (TLS) 1.3”.
- **Primary link:** https://datatracker.ietf.org/doc/draft-ietf-tls-extended-key-update/
- **Source type / venue:** IETF TLS WG Internet-Draft, work in progress.
- **Publication/revision date:** 2026-07-04.
- **Verified claim:** ordinary TLS 1.3 keeps its standard exporter secret static for the connection; the draft's EKU-specific interface instead derives a fresh cryptographically independent exporter secret when a completed Extended Key Update activates a new epoch, and applications are notified only after both peers complete the transition.
- **Existing engineering owner:** R-010 / zk217/zk221/zk228; adjacent R-009 lifecycle work.
- **Repository fact:** current C negative-corpus qualification checks whether the canonical ZK-ARCHE context digest changes under AUTH-instance/application/endpoint/profile mutations and remains unchanged for transport/routing metadata. The tested structure does not itself encode an exporter-secret generation.
- **Problem addressed:** a correct context digest can be recomputed under stale exporter material; therefore `context_matches` and `exporter_generation_current` are different predicates.
- **Strongest distinct engineering idea:** model binding evidence as `(canonical_context, exporter-generation relation, exporter-derived proof/material)`, and require both semantic context match and current accepted exporter generation before establishing or retaining association authority.
- **Evidence maturity:** IETF work-in-progress plus current ZK-ARCHE software corpus.
- **Limitations / uncertainty:** Extended Key Update is not an RFC and ZK-ARCHE need not implement it. The finding applies conditionally to transports/providers that can rotate exporter secrets without replacing the whole application association.
- **ZK-ARCHE inference:** `binding_valid` should eventually have a normative decomposition or documented precondition proving it includes generation currentness; context-digest equality alone must not satisfy that claim.
- **Wire / RAM / CPU / flash / dependency / trust / privacy impact:** no mandatory wire change is implied. Adapter state needs a bounded generation/currentness marker; retaining more than one exporter generation costs key material/RAM and increases secret-retention exposure. No new online dependency is required. Privacy impact is low if generation metadata remains local.
- **Rust/C / vector compatibility impact:** add governed cases where canonical context is identical but exporter generation changes; stale-generation binding must fail current-association admission unless a specifically defined bounded previous-generation processing rule applies.
- **Required next evidence:** deterministic Rust/C exporter-generation fixtures, adapter API semantics, association-admission vectors, and exact-head local qualification.
- **Recommended disposition:** reproduce.
- **Weekly finding candidate:** yes.

### D20260917-F02 — Previous exporter retention for reordering is not current authorization authority

- **Novelty:** refines.
- **Backlog owner:** R-009 / R-010.
- **Source:** `draft-ietf-tls-extended-key-update-13`; RFC 9770 as a lifecycle comparator for authorization revocation/currentness.
- **Primary links:** https://datatracker.ietf.org/doc/draft-ietf-tls-extended-key-update/ ; https://www.rfc-editor.org/rfc/rfc9770.html
- **Source type / venue:** IETF TLS WG Internet-Draft; IETF Standards Track RFC.
- **Publication/revision dates:** 2026-07-04; RFC 9770 published 2025-06.
- **Verified claim:** the EKU draft allows applications to retain previous and new exporter secrets temporarily to avoid desynchronization; DTLS may retain the prior exporter until its retention timer/replay acceptance expires. RFC 9770 independently illustrates that possession/availability of old authorization material is not equivalent to current authorization state: revocation information must propagate and additional credential/device revocation may be required.
- **Existing engineering owner:** R-009/R-010; TD-003/TD-004 remain adjacent claim blockers.
- **Repository fact:** current association admission already treats authorization, revocation, lineage, replay, restart, usage-counter continuity, and binding as independent currentness facts rather than allowing one valid domain to repair another.
- **Problem addressed:** a transport may legitimately accept a reordered packet from a previous cryptographic epoch while application policy must refuse to let that previous generation create fresh association/DATA authority.
- **Strongest distinct engineering idea:** define two separate states: `generation_processability` (bounded old/new overlap for transport/reordering) and `generation_authority` (which generation may authorize a new application operation). Old generation processability must not imply current authorization.
- **Evidence maturity:** standards/work-in-progress plus repository software semantics.
- **Limitations / uncertainty:** exact overlap policy is transport- and application-specific. For a strictly ordered TLS adapter, the previous-generation window may be much narrower than for DTLS.
- **ZK-ARCHE inference:** replay windows and exporter-generation retirement should be coupled: once the previous generation is outside its bounded processing window, exporter material and any generation-bound cached evidence should be erased/invalidated; even while retained, new DATA authority should require the current generation unless an explicit reviewed exception exists.
- **Wire / RAM / CPU / flash / dependency / trust / privacy impact:** bounded dual-generation retention increases transient RAM/key-retention cost; flash need not increase if overlap is volatile. CPU impact is limited to generation selection/checking. The trust model becomes clearer by preventing transport tolerance from becoming authorization authority.
- **Rust/C / vector compatibility impact:** vectors should cover reordered previous-generation input, fresh operation under previous generation, generation retirement, replay-window expiry, restart during overlap, and erasure/invalidation postconditions.
- **Required next evidence:** adapter-specific TLS/DTLS corpus plus Rust/C association/DATA admission tests and a stateful formal abstraction for generation transition/retirement.
- **Recommended disposition:** reproduce.
- **Weekly finding candidate:** yes.

### D20260917-F03 — Transport epoch numbers are adapter-local, not Common Contract identities

- **Novelty:** corroborates/refines.
- **Backlog owner:** R-010.
- **Source:** `draft-ietf-tls-extended-key-update-13`; RFC 9266, “Channel Bindings for TLS 1.3”.
- **Primary links:** https://datatracker.ietf.org/doc/draft-ietf-tls-extended-key-update/ ; https://www.rfc-editor.org/rfc/rfc9266.html
- **Source type / venue:** IETF TLS WG Internet-Draft; IETF Standards Track RFC.
- **Publication/revision dates:** 2026-07-04; RFC 9266 published 2022-07.
- **Verified claim:** the EKU draft says a TLS epoch identifier is a local logical counter that may differ between peers. RFC 9266 defines the standardized `tls-exporter` channel binding through exporter-derived material, not through peer-comparable transport epoch numbers.
- **Existing engineering owner:** R-010 / Common Contract transport normalization.
- **Repository fact:** current ZK-ARCHE exporter-context corpus deliberately excludes transport address and routing metadata from authenticated context, consistent with keeping transport mechanics below semantic peer authority.
- **Problem addressed:** importing raw TLS/DTLS epoch integers into cross-peer or cross-transport protocol semantics would couple ZK-ARCHE correctness to adapter-local numbering and could create false equality/inequality assumptions.
- **Strongest distinct engineering idea:** expose a normalized adapter relation such as `current | previous-processable | stale/unavailable`, with opaque adapter-local generation handles used only to retrieve/retire the right exporter material.
- **Evidence maturity:** standards/work-in-progress and software design inference.
- **Limitations / uncertainty:** exact API shape is a ZK-ARCHE design decision, not specified by the external sources.
- **ZK-ARCHE inference:** Common Contract logic should compare semantic currentness, not raw epoch integers; peer-visible binding should remain exporter-derived and context-bound.
- **Wire / RAM / CPU / flash / dependency / trust / privacy impact:** likely no wire impact; tiny adapter state only. Keeping counters local avoids unnecessary fingerprint/correlation surface.
- **Rust/C / vector compatibility impact:** cross-language tests should not require equal local epoch numbers; they should require equal accept/reject semantics for current/stale generation relationships.
- **Required next evidence:** adapter interface fixture with deliberately different local epoch numbers on peers but identical semantic currentness outcome.

## 6. Cross-source synthesis

Current repository changes make the next boundary precise: **channel-binding context, exporter-secret generation, replay processability, and authorization currentness are related but non-substitutable facts.** A binding can have the right ZK-ARCHE context and still be stale because its exporter generation is no longer authoritative. Conversely, a previous generation may remain temporarily processable for DTLS reordering without being allowed to authorize a new protected operation.

The transferable design pattern is therefore a two-layer adapter contract: the transport owns local epoch numbering, key overlap, and packet processability; the Common Contract consumes only a normalized binding-currentness relation and independently checks authorization/revocation/lineage/replay state. This preserves ZK-ARCHE's transport independence and avoids promoting routing or local transport counters into identity/security authority.
