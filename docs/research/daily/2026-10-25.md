## 2. Executive synthesis

1. Two **simultaneously draft-normative** specifications assign **different SHA-256 inputs** to `AUTH-v3.security_context.critical_extensions_hash`. An independent Python `hashlib.sha256` calculation reproduced both empty-set and populated-set digest disagreements. This is a concrete specification interoperability conflict, not a hash collision or a verified exploit.
2. Current Rust and C draft canonical-context helpers and retained fixtures select the **ZKCTX** representation; `spec/critical-extension-set-encoding.md` instead demands a direct count-and-occurrences representation. Rust/C agreement against one shared fixture does not prove an independent implementer following the other document can interoperate.
3. The specifications also differ in permitted critical-bit membership: the direct grammar can encode a noncritical `wire_id`, whereas ZKCTX critical-kind validation requires bit 15 set. The registry/selection rules say unknown noncritical values are only ignorable where policy permits; any extension changing security semantics must be critical unless safely ignorable. This semantic distinction needs an explicit selected-set policy before canonicalization.
4. The latest LAKE EDHOC GREASE draft (-03, dated July 6, 2026) permits **noncritical** GREASE EAD for successful-path extensibility and treats deliberately unknown critical items as negative tests. This corroborates maintaining separate ignore-versus-reject cases; its encoding and allocation are not ZK-ARCHE requirements.
5. R-011 remains P1/`reproduce`, now with an independently reproducible specification-reconciliation test contract. **Only explicit human review** may decide the normative representation; no wire/profile/security, implementation or assurance claim is promoted.

## 5. Findings

### D20261025-F01 — One AUTH-v3 hash destination, two incompatible canonical byte languages

- **Novelty:** contradicts, independently reproduced; R-011, R-010 cross-link.
- **Source / type / date:** RFC 8949 §4.2, *CBOR* (IETF Standards Track, **December 2020**), https://www.rfc-editor.org/rfc/rfc8949.html ; RFC 9052 §§2–3, *COSE Structures and Process* (IETF Standards Track, **August 2022**), https://www.rfc-editor.org/rfc/rfc9052.html .
- **Verified source fact:** RFC 8949 requires application protocols using deterministic encodings to choose exact representation rules and address duplicate keys; RFC 9052 authenticates protected encoded bytes and requires unique protected header labels. These are methodological comparators, **not** prescriptions to use CBOR/COSE or either ZK-ARCHE private format.
- **Repository fact / owner:** `spec/critical-extension-set-encoding.md` §§2–3 and §7 require `u16_le(count) || (u16_le(wire_id)||u16_le(length)||value)*` and empty `0000`. Separately, `spec/auth-v3-context-encoding.md` §§2,5,7 require `"ZKCTX"||01||02||u16_le(count)|| (u16_le(id)||00||u16_le(length)||value)*` and empty `5a4b43545801020000`; both explicitly name `critical_extensions_hash`. `rust/crates/proto/src/auth_v3_context.rs`, `c/src/proto/auth_v3_context.c`, and the current `context-encoding-v1.json` fixture implement the **second** rule only.
- **Independent software calculation** (Python SHA-256 of literal candidate bytes; not execution of Rust/C runtime):
  
  | Case | Direct encoding bytes; SHA-256 | ZKCTX encoding bytes; SHA-256 |
  |---|---|---|
  | No critical extensions | `0000`; `96a296d224f285c67bee93c30f8a309157f0daa35dc5b87e410b78630a09cfc7` | `5a4b43545801020000`; `ef8116870a7dc594749827eae3c9a5346057612b0d93ed3d1f0cea3d6ff0f3ed` |
  | IDs `0x8001`→`aabb`, `0x8004`→`010203` | `020001800200aabb04800300010203`; `d890390d7bf065975212bc1b62b955777781dc7f88f9c66b25423d40d389484e` | `5a4b435458010202000180000200aabb0480000300010203`; `3f4424631680740d286af85cd2eb397e89e32a035eca62b8d9498aa970d4e36c` |
- **Bottleneck / distinct engineering idea:** Pin a **human-approved single normative hash contract** and a versioned migration rule for existing draft vectors. Maintain a two-column **independent-implementer discrimination corpus**: accepted canonical bytes/digest plus explicitly rejected alternate bytes/digest for both empty and populated sets. Then apply the chosen digest in a full draft AUTH-v3 `TH_v3`/directional Finished mismatch test; SHA divergence alone does not exercise Finished.
- **Evidence maturity:** **software** for independent digest calculations and currently existing local source/vector inspection; **concept** for final normative selection and Finished interoperability.
- **Limitations:** No local exact-HEAD Rust/C build/test or full AUTH-v3 Finished execution was performed; both docs are drafts, not evidence that production v3 is vulnerable. The shared ZKCTX fixture demonstrates current draft implementation consistency, not protocol-authoritative superiority.
- **ZK-ARCHE inference / resource impact:** For `n` entries, the ZKCTX hash input is **7+n extra bytes** over direct encoding (7-byte domain/version/kind, 1-byte reserved flag per entry). In the examples, 2 versus 9 bytes (empty) and 15 versus 24 bytes (two entries). The authenticated *digest field remains 32 bytes* regardless of chosen representation: no necessary wire-size increase from the hash itself. Hash input/CPU difference is small but unmeasured on STM32/ESP32-S3; streaming buffers can be bounded; no mandatory library dependency is implied. Trust/interoperability risk is normative ambiguity, not broken SHA-256; metadata privacy has no established delta.
- **Rust/C/vector/profile compatibility:** Require one owner/document hierarchy, a profile/version migration decision, Rust/C golden direct-vs-ZKCTX rejection corpus, canonical empty, sorted pair, mutating critical flag/value/membership, duplicate/zero/reserved/invalid length/trailing bytes, wrong alternative digest and downstream AUTH-v3 Finished negative. Do not alter production v2 or make v3 selectable during research.

### D20261025-F02 — Critical/noncritical selection must precede authenticated encoding

- **Novelty / owner:** refines / R-011; R-015 only for optional GREASE-observable privacy costs.
- **Primary source / type / date:** `draft-ietf-lake-edhoc-grease-03`, IETF LAKE Internet-Draft **work in progress**, **2026-07-06**, https://datatracker.ietf.org/doc/draft-ietf-lake-edhoc-grease/ ; RFC 9052 §3.1, IETF Standards Track, **August 2022**, https://www.rfc-editor.org/rfc/rfc9052.html .
- **Verified external claim:** The LAKE draft reserves EDHOC noncritical GREASE EAD labels for tolerated unknown extension handling; using unknown critical EAD to induce rejection is negative-test territory, not a successful-path GREASE rule. It warns that GREASE choices can fingerprint implementations. COSE critical parameters must be understood when required by an authenticated protected header, providing a **different-protocol** comparator for authenticated critical handling. These do not allocate any ZK-ARCHE number.
- **Repository fact:** Direct extension-set grammar allows serialization of the full `wire_id` with either critical-flag value. ZKCTX critical-kind validation rejects an entry without bit 15. `spec/registries.md` §10 and `spec/negotiation-selection-state-machine.md` §8 require rejecting unknown critical inputs and permit ignoring unknown noncritical inputs only under profile policy. Any selected security-altering extension must be critical unless a reviewed safe-ignorance rule exists.
- **Bottleneck / distinct engineering idea:** Separate **(a) parse extension occurrence; (b) check registry/profile/critical semantics; (c) determine the active authenticated critical-only set; (d) canonicalize only that set; (e) hash; (f) confirm selected-vs-executed equality**. Treat known noncritical-but-security-affecting values as reject or explicit version/profile redesign, not an unauthenticated behavior switch. Keep GREASE test IDs unassigned and non-authoritative, and distinguish ordinary unknown-ignorable vs reserved unknown from known-incompatible values.
- **Maturity / limitations:** Standards-supported comparison and repository analysis = **concept** for an approved ZK-ARCHE semantic rule. No live GREASE recommendation, packet-capture privacy/MTU measurements, or integrated Rust/C selection test executed. EDHOC EAD semantics are not automatically transposable.
- **ZK-ARCHE impact:** Correct inclusion policy protects downgrade/authenticated semantics, without a mandatory new wire field or crypto primitive. A bounded selection table and one pass over entries imply limited CPU/RAM, profile-dependent; flash and energy need hardware measurement. Live GREASE (if proposed later) could enlarge messages, add latency, and increase fingerprintability; no privacy improvement is claimed.
- **Rust/C/vector/profile:** Shared decision matrix for accepted critical, unknown critical (reject), ignorable ordinary unknown noncritical, reserved GREASE-like unknown noncritical, known-but-incompatible, known noncritical with security impact, duplicate, wrong critical flag, swapped selected/implemented set, and policy-dependent selection; capture identical accept/ignore/reject and digest/Finished outcomes. Keep runtime version `0x03` non-advertised.
- **Next evidence / disposition / weekly:** One human-approved selected-set policy, exact-head Rust/C shared matrix and auth-completion negatives; **reproduce / yes**.

## 6. Cross-source synthesis

RFC 8949/9052 support defining *one unambiguous authenticated representation* with duplicate and context constraints; they cannot pick between two custom ZK-ARCHE encodings. The LAKE draft supports ordinary noncritical-unknown tolerance only at eligible extension points, **not** acceptance of unknown critical values or selected-security-semantic downgrade. The exact-current Rust/C fixture consistency and independent SHA-256 reproduction establish an implementer-interoperability contradiction at the **draft specification** boundary. The resulting priority is human normative arbitration before extending R-010 exporter/Finished vectors or R-004 symbolic hash assumptions.
