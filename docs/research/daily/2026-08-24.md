1. RFC 9770 provides a standardized revocation-convergence pattern for constrained and intermittently connected devices, including hashed revocation identifiers, full/diff queries, optional Observe notifications, and an explicit vulnerable window between revocation and local awareness.

## Findings

### 1. Revocation must be a convergence protocol with a measurable stale-authorization window

- **Source:** RFC 9770, *Notification of Revoked Access Tokens in the Authentication and Authorization for Constrained Environments (ACE) Framework*
- **Primary link:** https://datatracker.ietf.org/doc/rfc9770/
- **Source type / venue:** IETF Standards Track RFC
- **Publication date:** June 2025; Datatracker updated 2026-05-20
- **Verified claim:** RFC 9770 defines a Token Revocation List (TRL) for constrained devices where revoked but unexpired authorizations are identified using token hashes. Registered devices can obtain full or differential updates and may subscribe through CoAP Observe. The RFC explicitly addresses intermittently connected devices and states that a resource server can remain vulnerable after revocation until it learns of the change; polling frequency therefore trades communication cost against the maximum vulnerable time window.
- **Problem addressed:** ZK-ARCHE R-012 currently requires invalidation propagation from credentials/policy/key epochs to sessions, resumption, cached authorization, and DATA release state, but it does not yet define how disconnected or intermittently connected peers converge on revocation state or how long stale authorization may remain usable.
- **Strongest distinct engineering idea:** define revocation as a versioned convergence protocol rather than a single local delete operation. Each peer should have a durable `revocation_view` or equivalent epoch/cursor, support a compact full snapshot plus bounded differential updates, and record the maximum permitted stale-authorization window per profile. Push/observe-style notification can be optional; reconnect/poll reconciliation must remain sufficient so no continuously available external infrastructure becomes mandatory.
- **Evidence maturity:** externally-reviewed
- **Limitations / uncertainty:** RFC 9770 is token-oriented ACE/CoAP work, not ZK-ARCHE. Its centralized authorization server is not directly compatible with every P2P deployment. Token hashes can also expose correlation if a global revocation feed is not requester-scoped. ZK-ARCHE would need a trust-graph/issuer-aware equivalent rather than copying the protocol verbatim.
- **ZK-ARCHE inference:** R-012 should test revocation convergence after offline periods, missed notifications, rollback to an old revocation snapshot, duplicate/out-of-order diffs, cursor loss, issuer/epoch mismatch, and stale resumption/DATA-release state. Profiles should state a revocation freshness objective or maximum stale window instead of implying immediate revocation in disconnected systems.
- **Wire / RAM / CPU / flash / dependency impact:** small hash/epoch/cursor state plus bounded revocation-diff storage; periodic network cost depends on polling/reconnect frequency. Flash-write wear and rollback resistance require target measurement. No mandatory always-online service is implied.
- **Rust/C / vector compatibility impact:** compatible research direction. Add deterministic full/diff reconciliation fixtures and negative vectors for stale/rolled-back revocation views before any normative protocol extension.
- **Recommended disposition:** reproduce

### 2. Role proofs should resolve to scoped, expiring authorization state, and membership loss should invalidate group-derived security state

- **Sources:** `draft-ietf-ace-key-groupcomm-oscore-21`, *Key Management for Group OSCORE Using ACE*; `draft-ietf-ace-group-oscore-profile-07`, *The Group OSCORE Profile of ACE*
- **Primary links:** https://datatracker.ietf.org/doc/draft-ietf-ace-key-groupcomm-oscore/ ; https://datatracker.ietf.org/doc/html/draft-ietf-ace-group-oscore-profile-07
- **Source type / venue:** IETF ACE Working Group / RFC Editor queue and active Standards Track Internet-Draft
- **Publication/update dates:** March 2026 and July 6, 2026
- **Verified claim:** the Group OSCORE ACE work encodes requested roles as authorization scope bound to a named group, requires the authorization response to include expiration, and explicitly reports the actually authorized role set when it differs from the requested set. The key-management specification requires rekeying when members leave or are forcibly evicted because authorization expired or was revoked, thereby preventing former members from accessing later group communications. It can also rekey on join when backward security is required. The profile separately binds an access token to the client's public key used in the group.
- **Problem addressed:** ZK-ARCHE's role-membership proof establishes that a hidden role belongs to an allowed set, but that fact alone is not a complete authorization decision. R-008 already calls for audience/scope/policy/epoch/holder binding; the Group OSCORE work supplies a concrete constrained-system model for group/resource scope, requested-vs-granted role narrowing, expiration, proof of possession, and membership-triggered key invalidation.
- **Strongest distinct engineering idea:** make future authorization state an explicit tuple such as `(subject/holder commitment, audience or group, granted role-set/policy, issuer/provenance, policy epoch, validity, key/profile constraints)`. A role proof proves one component; it does not itself mint authorization. If granted roles shrink, expire, or are revoked, all security state whose confidentiality depends on the old authorization must be invalidated or rekeyed according to a dependency matrix.
- **Evidence maturity:** software
- **Limitations / uncertainty:** Group OSCORE is group communication with a Group Manager/KDC and signature-oriented group security. ZK-ARCHE must preserve its decentralized P2P option and cannot assume a permanent central manager. The useful result is the authorization and lifecycle discipline, not the exact ACE wire protocol.
- **ZK-ARCHE inference:** advance R-008 to `reproduce`. Build a deterministic authorization-context model where a peer requests role/scope, an authority or local trust policy may narrow the result, and the granted context has explicit expiry/epoch. Then test that role downgrade, membership removal, policy epoch change, and credential revocation invalidate dependent LINK/resumption/DATA state without requiring trust-store mutation during normal AUTH.
- **Wire / RAM / CPU / flash / dependency impact:** compact audience/group identifier, granted-role bitset or policy reference, validity/epoch, and holder binding. Exact bytes are profile-dependent and should be measured against `iot-core`. Rekey cost can be substantial in groups and should be event-driven/batched where safe.
- **Rust/C / vector compatibility impact:** no immediate wire change. Future vectors should separate `requested_roles`, `granted_roles`, and hidden proof witness and include downgrade/expiry/revocation transitions.
- **Recommended disposition:** reproduce

### 3. Dynamic rights updates need explicit series identity and recovery when authorization state is forgotten

- **Source:** `draft-ietf-ace-workflow-and-params-08`, *Short Distribution Chain (SDC) Workflow and New OAuth Parameters for the ACE Framework*
- **Primary link:** https://datatracker.ietf.org/doc/html/draft-ietf-ace-workflow-and-params-08
- **Source type / venue:** active IETF ACE Working Group Internet-Draft
- **Publication/update date:** July 6, 2026
- **Verified claim:** the draft defines a `token_series_id` and an `updated_rights` indication so an authorization server can replace a client's authorization information while preserving the same secure communication association. The series identifier is scoped with client and audience. A new token supersedes the old authorization state only when the resource server still has the matching old series state. If that old state has been forgotten, the draft requires an explicit recovery path rather than ambiguously interpreting the update as a fresh authorization; the old/new tokens are revoked and a new series can be established.
- **Problem addressed:** ZK-ARCHE R-012 covers invalidation and R-008 covers scoped authorization, but the framework does not yet distinguish `update current authorization` from `establish new authorization` with an explicit lineage identifier. Storage loss or rollback could otherwise turn a rights update into an unintended new grant or leave a session associated with stale privileges.
- **Strongest distinct engineering idea:** give mutable authorization state an explicit lineage identifier plus monotonic generation/epoch. A rights update must reference the authorization lineage it replaces and be accepted only if the peer still has the expected predecessor state. Missing predecessor, rollback, or lineage mismatch must fail closed into reauthorization/re-enrollment rather than silently creating a new grant on an existing session.
- **Evidence maturity:** software
- **Limitations / uncertainty:** this is still an Internet-Draft and uses ACE/OAuth token semantics. ZK-ARCHE does not need OAuth token series. The transferable design principle is explicit authorization lineage and fail-closed state replacement.
- **ZK-ARCHE inference:** R-012 should include authorization-lineage tests: valid in-place scope reduction, valid scope expansion only with authorized provenance, stale generation, wrong audience, wrong holder, missing predecessor after storage loss, replayed update, concurrent updates, and rollback. Resumption should carry or validate the authorization generation so a session cannot outlive a rights update unnoticed.
- **Wire / RAM / CPU / flash / dependency impact:** one bounded lineage identifier plus generation/epoch and predecessor state; persistent storage must be atomic/rollback-aware. No additional heavy cryptography is required.
- **Rust/C / vector compatibility impact:** compatible as a future extension. Deterministic state-machine vectors should model replace-vs-new semantics and storage-loss recovery.
- **Recommended disposition:** reproduce

### 4. Privacy claims must include correlation identifiers and capability fingerprints, not only hidden credentials and errors

- **Source:** RFC 9528, *Ephemeral Diffie-Hellman Over COSE (EDHOC)*, Sections 3.3 and 9.5
- **Primary link:** https://datatracker.ietf.org/doc/html/rfc9528
- **Source type / venue:** IETF Standards Track RFC
- **Publication date:** March 2024
- **Verified claim:** EDHOC states that clear connection identifiers can correlate packets across paths or time and recommends mechanisms to update them where privacy matters. It also warns that supported cipher-suite lists may fingerprint the application. The RFC notes that such identifier-rotation privacy mechanisms do not help when stable lower-layer identifiers such as IP or MAC addresses already dominate linkability.
- **Problem addressed:** R-015 currently focuses on observable failures, timing, response classes, lookup state, and retry behavior. ZK-ARCHE also negotiates capabilities/suites/profiles and uses session identifiers. Even perfect PID rerandomization cannot provide meaningful unlinkability if stable session/correlation identifiers or distinctive capability vectors persist across handshakes.
- **Strongest distinct engineering idea:** extend the privacy-observability contract to include a **correlation surface inventory**: connection/session IDs, transport addresses, capability/profile/suite lists and ordering, extension sets, retry tokens, packet-size patterns, and lower-layer identifiers. For each claimed privacy level, state which surfaces rotate, which are stable by design, and which lower-layer metadata makes stronger claims impossible.
- **Evidence maturity:** externally-reviewed
- **Limitations / uncertainty:** EDHOC connection identifiers are not ZK-ARCHE session IDs. Rotating identifiers can increase state-management complexity and does not solve network-layer tracking. Capability-list normalization may also conflict with constrained negotiation and feature discovery.
- **ZK-ARCHE inference:** keep R-015 at `reproduce` but broaden its test matrix. Repeated AUTH/P2P runs should test whether session identifiers, suite/profile/capability offers, extension ordering, retry behavior, and packet lengths permit linking the same node. Privacy documentation should state passive and active unlinkability bounds in the presence of stable IP/MAC/radio identifiers.
- **Wire / RAM / CPU / flash / dependency impact:** potentially randomized/rotated short identifiers and normalized capability presentation; small state cost but measurable interoperability/DoS implications.
- **Rust/C / vector compatibility impact:** no immediate change. Add repeated-session metadata fixtures and cross-language checks for any future canonical capability/identifier policy.

## Cross-source synthesis

The main conclusion is that ZK-ARCHE needs an explicit **authorization-state lifecycle** that is as rigorous as its authentication transcript.

A useful future model is:

```text
AUTH proves holder + protocol context
        ↓
resolve/obtain authorization context
(holder, audience/group, granted roles/policy, provenance, epoch, validity)
        ↓
associate authorization lineage/generation with LINK/resumption/DATA state
        ↓
rights update replaces a known predecessor only
        ↓
revocation/expiry/downgrade invalidates dependent state
        ↓
offline peers reconcile revocation view on reconnect
```

The revocation mechanism should not assume instantaneous connectivity. Instead, the specification should make the stale-authorization window explicit and measurable. Likewise, role membership should not be conflated with authorization: a role proof may establish eligibility while the granted scope can be narrower, time-limited, audience-bound, or revoked later.

For privacy, yesterday's error/timing work remains necessary but incomplete. RFC 9528 reinforces that correlation metadata outside the protected identity payload—session IDs, capability offers, and lower-layer identifiers—must be part of the claim boundary.

No finding justifies changing the current Ristretto/SHA-2/HKDF/HMAC baseline or adding a new mandatory dependency.
