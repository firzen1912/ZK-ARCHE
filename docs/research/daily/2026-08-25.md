## Findings

### 1. Resumption must revalidate authorization context and bound PSK/ticket reuse

- **Sources:** `draft-ietf-lake-edhoc-psk-07`, *EDHOC Authenticated with Pre-Shared Keys (PSK)*; RFC 9813, *Operational Considerations for Using TLS Pre-Shared Keys (TLS-PSKs) with RADIUS*; RFC 5077, *TLS Session Resumption without Server-Side State*
- **Primary links:** https://datatracker.ietf.org/doc/html/draft-ietf-lake-edhoc-psk-07 ; https://datatracker.ietf.org/doc/html/rfc9813 ; https://datatracker.ietf.org/doc/html/rfc5077
- **Source type / venue:** IETF LAKE Working Group Standards-Track Internet-Draft plus IETF RFC operational/security guidance
- **Publication/update dates:** EDHOC-PSK-07 published 2026-03-01; RFC 9813 current RFC; RFC 5077 historical standards-track privacy guidance
- **Verified claim:** EDHOC-PSK defines resumption PSKs derived from a previous EDHOC session and states that they must be protected like session keys; parties should prevent excessive reuse of the same resumption PSK. RFC 9813 requires systems using PSK resumption to cache enough original authentication/authorization state to make a safe decision during resumption, to reevaluate authorization/policy when relevant connection information changed, and to fall back to a full handshake when a safe decision cannot be made. RFC 5077 additionally warns that repeated presentation of the same ticket can let an on-path observer link sessions even when ticket contents are confidential.
- **Problem addressed:** ZK-ARCHE zk221/R-012 already requires replay-safe, privilege-preserving resumption and invalidation when registry/role/policy state changes, but the evidence contract does not yet state a concrete resumption-credential reuse policy, secure-cached-context requirement, full-handshake fallback rule, or privacy test for repeated ticket/PSK identifiers.
- **Strongest distinct engineering idea:** define a future resumption record as an authenticated cache of both cryptographic and authorization context, not merely a secret. At minimum bind a resumption credential to holder/peer, suite/profile, deployment/domain, authorization lineage/generation, policy/registry epoch, issue/expiry time, usage/reuse counter, and the original security context. On resumption, compare current observable/contextual inputs with the cached decision inputs; if any changed field can alter authorization and cannot be safely reevaluated, reject resumption and perform full AUTH. Prefer one-time or tightly bounded resumption identifiers where privacy requires unlinkability.
- **Evidence maturity:** externally-reviewed
- **Limitations / uncertainty:** RFC 9813 is RADIUS/TLS-PSK operational guidance and RFC 5077 predates TLS 1.3; neither is a ZK-ARCHE specification. EDHOC-PSK remains an Internet-Draft. The transferable result is the lifecycle discipline, not the exact wire format or ticket mechanism.
- **ZK-ARCHE inference:** R-012 should add deterministic resumption tests for changed role/policy epoch, changed audience/deployment, revoked credential, missing cached authorization state, stale lineage, and unsafe contextual drift. R-015 should add repeated-resumption-identifier linkability tests and a per-profile reuse/rotation policy. R-009 should include resumption-secret lifetime/reuse counters and secure erasure/expiry behavior.
- **Wire / RAM / CPU / flash / dependency impact:** bounded persistent resumption metadata and counters; potentially more frequent full AUTH when context cannot be safely reused. One-time/bounded-use tickets may increase issuance/storage churn. No new mandatory primitive is implied.
- **Rust/C / vector compatibility impact:** no immediate wire change. Future deterministic vectors should model resumption acceptance/rejection as a function of cached authorization/policy context and verify Rust/C agreement on stale/missing/changed-context cases.
- **Recommended disposition:** reproduce

### 2. Constrained-target assurance must record crypto-module boundaries, seed-derived keys, accelerators, and entropy/self-test posture

- **Source:** NIST Cryptographic Module Validation Program, FIPS 140-3 Implementation Guidance update dated 2026-08-19
- **Primary link:** https://csrc.nist.gov/Projects/cryptographic-module-validation-program/fips-140-3-ig-announcements
- **Source type / venue:** official NIST CMVP implementation guidance
- **Publication/update date:** 2026-08-19
- **Verified claim:** the August 19 update adds guidance clarifying hybrid cryptographic modules; updates processor algorithm accelerator/implementation requirements; adds key-pair self-test guidance for keys generated from stored seeds; updates combined cryptographic self-test treatment; and continues current guidance around entropy/DRBG, key/IV uniqueness, hybrid KEMs, and cryptographic module boundaries. The same announcement records recent guidance that physical noise sources should be evaluated across operating conditions and that hybrid KEMs and hardware accelerators require explicit validation context.
- **Problem addressed:** R-005 already asks for entropy state, DRBG/reseed behavior, root-seed versus private-key storage, secure boot/debug state, and acceleration configuration. R-003 asks for PQ/hybrid storage and packet/CPU/RAM evidence. Neither yet requires a structured statement of *where the cryptographic boundary is*, whether an accelerator belongs inside/outside that boundary, how seed-derived key pairs are self-tested, or what exact hardware family/microarchitecture is relied upon.
- **Strongest distinct engineering idea:** add a `crypto_execution_context` record to each future target benchmark/evidence package. Record implementation/library version, hardware/firmware crypto boundary, accelerator family/microarchitecture, whether keys are imported/generated/derived from a stored root seed, entropy source and health-test posture, DRBG mode/reseed rules, self-test strategy, secure-storage location, zeroization/rollback assumptions, and which operations fall back to software. Measurements are only comparable when this context is pinned.
- **Evidence maturity:** externally-reviewed
- **Limitations / uncertainty:** FIPS 140-3 validation is not currently a ZK-ARCHE requirement, and the project must not imply CMVP certification. Some NIST guidance is validation-program-specific. The value here is as an assurance/evidence taxonomy for heterogeneous embedded targets, not a mandate to pursue FIPS certification.
- **ZK-ARCHE inference:** R-005 should require crypto-boundary and accelerator metadata in every STM32/ESP32-S3 benchmark. R-003 should require the same context for any ML-KEM/hybrid measurement, especially where keys are represented as seeds or hardware/firmware modules share responsibility. Results collected without this context should be treated as implementation-specific observations, not portable profile evidence.
- **Wire / RAM / CPU / flash / dependency impact:** no protocol wire impact. Evidence collection cost increases slightly; self-test/health-test and secure-storage implementation choices may affect boot latency, flash, and RAM and therefore should be measured separately.
- **Rust/C / vector compatibility impact:** no vector semantics change. Benchmark manifests should identify which Rust/C implementation paths, library versions, accelerator paths, and seed/key-generation modes produced each measurement.
- **Recommended disposition:** benchmark

### 3. Field-readiness evidence must map protocol/profile claims to the surrounding IoT product and system risk context

- **Sources:** NIST SP 800-213 Rev. 1 (Initial Public Draft), *IoT Product Cybersecurity Guidelines for the Federal Government: Establishing IoT Product Cybersecurity Requirements*; NIST SP 800-213A, *IoT Device Cybersecurity Requirement Catalog*
- **Primary links:** https://csrc.nist.gov/pubs/sp/800/213/r1/ipd ; https://csrc.nist.gov/pubs/sp/800/213/a/final
- **Source type / venue:** official NIST IoT cybersecurity guidance
- **Publication/update dates:** SP 800-213 Rev. 1 draft published 2026-06-24; public comment closed 2026-08-24; SP 800-213A final published 2021-11-29
- **Verified claim:** SP 800-213 Rev. 1 explicitly treats an IoT product as a system element whose acquisition/integration can alter the system risk assessment and therefore the controls that must be selected and implemented. SP 800-213A provides a catalog of device cybersecurity and supporting capabilities that organizations can map to security controls.
- **Problem addressed:** ZK-ARCHE's current `iot-core`/`iot-edge` profile skeleton and assurance roadmap correctly require wire/RAM/CPU evidence, but a protocol-level pass can still coexist with an insecure product integration—for example weak debug policy, unprotected firmware, poor lifecycle support, missing update/asset controls, or an authorization deployment that violates system assumptions.
- **Strongest distinct engineering idea:** keep protocol conformance evidence separate from a future deployment-context evidence layer. A field-readiness claim should identify which ZK-ARCHE profile was tested, the surrounding device/product security capabilities and trust assumptions, deployment risk context, lifecycle/update posture, credential provisioning/revocation authority, and any controls supplied outside ZK-ARCHE. This prevents cryptographic success from being misreported as whole-product assurance.
- **Evidence maturity:** externally-reviewed
- **Limitations / uncertainty:** SP 800-213 Rev. 1 remains a draft and its comment period only just closed; final text may change. It is federal IoT acquisition/risk guidance rather than a protocol specification. This should not create a new mandatory runtime dependency or conformance layer inside `iot-core`.
- **ZK-ARCHE inference:** no new backlog item is necessary. R-005/TD-002 evidence packages should eventually include deployment-context metadata, and TD-004/spec work should clearly label which requirements are protocol-native versus supplied by the platform/product/operator. `iot-core` conformance should never by itself imply product or field readiness.
- **Wire / RAM / CPU / flash / dependency impact:** none at protocol runtime. Documentation/evidence cost only.
- **Rust/C / vector compatibility impact:** none. The effect is on qualification manifests and claim boundaries rather than deterministic vectors.
- **Recommended disposition:** investigate

## Cross-source synthesis

The three sources converge on a useful boundary: **a secure session is not a sufficient security claim**.

For resumption, the protocol must carry forward only authorization state that is still valid and safely reevaluable; possession of a cached secret is not enough. For constrained hardware, benchmark numbers are meaningful only when the cryptographic execution boundary, entropy/key-generation mode, secure storage, and accelerators are pinned. For deployment, a passing protocol/profile test must still be interpreted inside the surrounding IoT product and system risk context.

A useful future evidence chain is:

```text
protocol/vector conformance
        ↓
cryptographic execution-context evidence
(target, entropy, keys/seeds, accelerator, storage, self-tests)
        ↓
resumption / authorization lifecycle evidence
(context revalidation, invalidation, privacy, fallback)
        ↓
deployment-context evidence
(product capabilities, lifecycle, provisioning authority, external controls)
        ↓
truthful readiness claim bounded to that exact context
```

This strengthens the existing evidence-gated roadmap without changing the cryptographic baseline.
