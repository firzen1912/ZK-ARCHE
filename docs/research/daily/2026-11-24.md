## 2. Executive synthesis

- A valid zero scalar or identity-valued intermediate is not automatically an invalid group encoding. The RFC 9496 algebra and libsodium's multiplication return contract differ at precisely this boundary.
- Exact-head C proof routines propagate multiplication errors as invalid-point/proof failure; Rust uses dalek group arithmetic directly. The discrepancy is distinct from November 19's missing-role panic and November 6's witness-dependent branch/RNG schedule.
- A host libsodium 1.0.18 probe confirmed three identity-result multiplication failures, two successful multiplication controls, and a successful identity-addition control. This is measured primitive behavior, not an executed end-to-end ZK-ARCHE Rust/C mismatch.
- A field-specific policy and paired positive/negative corpus are needed before changing arithmetic or sampling. Never weaken public-key/DH identity rejection to make proof arithmetic total.
- No new externally published vulnerability is claimed: the newly obtained evidence is the exact-head mapping and host reproduction, using historical RFC/API documentation and the current November 2 CFRG draft. A bounded recent IETF discovery pass did not supply a stronger decision-changing source for this question.

## 5. Detailed finding

### D20261124-F01 — Separate total proof-group arithmetic from nonidentity public-key policy

- **Novelty / owner:** refines R-007 (P0 reproduce), TD-001; zk207/208/209. New source-to-backend mapping and local primitive evidence; not a new RFC or vulnerability disclosure.
- **Primary sources/date/type:** [RFC 9496](https://www.rfc-editor.org/rfc/rfc9496.html), December 2023, IRTF Informational, sections 3, 4.4 and Appendix A.1; [libsodium official Ristretto documentation](https://doc.libsodium.org/advanced/point-arithmetic/ristretto), living implementation documentation (accessed 2026-11-24, publication date not asserted); [dalek 4.1.3 tagged Ristretto source](https://github.com/dalek-cryptography/curve25519-dalek/blob/curve25519-4.1.3/curve25519-dalek/src/ristretto.rs), exact version used in Rust lock, inspected 2026-11-24; [CFRG Sigma Proofs for Linear Relations -04](https://datatracker.ietf.org/doc/html/draft-irtf-cfrg-sigma-protocols-04), November 2 2026, work in progress, sections 3.2/3.5 and appendix A.2/A.3 identity cases. The CFRG draft covers linear relations, not the custom CDS OR proof.
- **Verified external claim:** RFC 9496 includes zero among canonical scalars and defines group identity and scalar multiplication algebraically. The libsodium multiplication functions report failure for identity results, whereas valid element addition can return identity or accept identity operands. Dalek tagged Ristretto multiplication returns a RistrettoPoint rather than an error result. The CFRG comparator permits zero coefficients and identity images in particular validated linear relations; whether a specific application permits them is a separate policy.
- **Exact repository facts:** C auth_scalarmult_base and auth_scalarmult in c/src/crypto/crypto.c map nonzero libsodium status to AUTH_ERR_INVALID_POINT. In c/src/crypto/proofs.c, the CDS prover and verifier calculate Y_i = C' - G*r_i using auth_scalarmult_base, and the verifier computes h*s_i and Y_i*c_i via auth_scalarmult, returning failure on an error. Rust crypto.rs computes the same expressions with group multiplication; random_scalar_with_rng reduces 64 bytes modulo group order without rejecting zero. The Rust verifier checks challenge sum and group equations, not a nonzero test on each branch scalar. Rust's separate reject_identity helper is explicitly for points received from wire or storage; protocol ingress can impose additional constraints. The deterministic role_set_membership.json vector documents per-branch draw order; it does not by itself qualify these exceptional arithmetic cases.
- **Bottleneck:** Backend-specific key-exchange-style error behavior can be accidentally imported into proof algebra, resulting in different valid-input domains or retry behavior even with matching ordinary vectors.
- **Host reproduction, 2026-11-24:** Python ctypes called the installed x86-64 libsodium.so.23, sodium_version_string = 1.0.18, after sodium_init. Inputs are public synthetic scalars 0 and 1, RFC 9496 generator G (e2f2ae0a6abc4e71a884a961c500515f58e30b6aa582dd8db6a65945e08d2d76), identity I (32 zero bytes). Output buffers initialized to zero. Raw return observations:

| Primitive | Return | Output |
|---|---:|---|
| crypto_scalarmult_ristretto255_base(0) | -1 | I |
| crypto_scalarmult_ristretto255(0,G) | -1 | I |
| crypto_scalarmult_ristretto255(1,I) | -1 | I |
| crypto_scalarmult_ristretto255_base(1) | 0 | G |
| crypto_scalarmult_ristretto255(1,G) | 0 | G |
| crypto_core_ristretto255_add(I,G) | 0 | G |
| crypto_core_ristretto255_is_valid_point(I) | 1 | n/a |

  Output bytes on error are observations only, not an API success guarantee. A future implementation must not reinterpret every failure as a valid identity result. Reproduction recipe: load library using ctypes.util.find_library("sodium"), initialize, use a 32-byte output buffer, call the named symbols with little-endian scalars and canonical point encodings above; retain return and buffer hex. No secret material used.
- **Distinct engineering idea:** Define a field/operation domain matrix: canonical scalar parsing; externally provided point nonidentity checks; internal group arithmetic; nonzero secret/ephemeral sampling; proof commitment, simulated challenge, response and derived Y policy; DH shared-point rejection. Explicitly distinguish encoding validity, mathematical equation validity and authorized protocol admissibility. Build paired low-level positive controls and negative tests with zero scalar, identity intermediate, invalid point encoding, noncanonical scalar, role code zero (only if admitted by policy), and an ordinary valid branch. Then construct complete transcript-consistent edge vectors under a reviewed statement; changing one challenge without re-establishing challenge sum is not a valid positive vector. Test each policy boundary and no partial AUTH/trust effect.
- **Evidence maturity:** software for host primitive probe and repository/source inspection; concept for a proposed protocol-level contract. Rust backend source read but not executed; no cargo available in host probe environment. No full ZK-ARCHE binary, independent proof, or hardware result.
- **Limitations:** This does not prove role code zero is an allowed protocol role, that zero challenges/responses are admitted by every profile, that a full proof with such values is accepted by current Rust ingress, or a remotely reachable vulnerability. Naturally sampled zero is extremely rare under correct uniform randomness; forced tests are conformance/fault evidence, not a production failure-rate estimate. RFC 9496 does not mandate a specific application policy. The host library is not a pinned production C build. The November 2 draft is not a reviewed CDS-OR composition.
- **ZK-ARCHE inference:** A human-reviewed distinction between total internal proof arithmetic and restricted public-key/DH operations is required. A change to zero rejection or resampling can alter distribution, deterministic draw order, side-channel behavior, and interoperability; do not adopt one casually. In particular do not remove nonidentity checks or silently treat arbitrary invalid encodings as identity.
- **Likely impacts:** Wire none for qualification alone; potential compatibility change if acceptance policy changes, requiring explicit version/profile review. CPU/RAM/flash: small additional tests, possible validation/conditional-selection cost to measure, no measured target overhead. Dependency: retain current dalek/libsodium until qualified alternatives justified. Trust: no new roots; privacy: avoid adding role-dependent error/retry/timing behavior; no privacy theorem inferred.
- **Rust/C/vector/profile compatibility:** Keep native 0x0001 and current valid vectors unchanged. Add proposed separately labeled arithmetic positives and protocol policy negatives, forced deterministic edge draws, and retain actual backend/compiler/target provenance; a new sampling algorithm would require explicit vector review. Do not make iot-core selectable from this evidence.
- **Required next evidence:** local exact-head Rust/C build; pin C libsodium source and Rust backend/feature/compiler identity; replay primitive matrix and transcript-consistent cases at API and framed boundaries; establish field-specific zero/identity policy with independent proof review; verify errors, side-channel and RNG-call behavior under forced edges on actual target. No hosted Actions required.
