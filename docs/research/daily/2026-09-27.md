## 2. Executive synthesis

1. The new LAKE PQ-suite draft makes **method × suite compatibility** explicit because KEM key exchange is not interchangeable with every DH/NIKE-based method. ZK-ARCHE should make future key-establishment API, authentication-method, suite, and profile compatibility machine-testable.
2. The draft explicitly says standardized PQ primitives inside a suite are **not sufficient to claim overall protocol post-quantum security** in its Q1 model. For ZK-ARCHE, ML-KEM key establishment would not make the current Ristretto/Schnorr/CDS role-proof path quantum-resistant.
3. Standardized object sizes create immediate constrained-wire pressure. FIPS 203 gives ML-KEM encapsulation-key/ciphertext sizes of 800/768, 1184/1088, and 1568/1568 bytes. FIPS 204 gives an ML-DSA-44 signature size of 2420 bytes. Current C bounds a datagram at 2048 bytes, so that signature alone is 372 bytes over the current bound before framing/context.
4. X-Wing -11 is useful as a research comparator, not a selection: it is an individual Internet-Draft with no formal IETF standards standing, uses X25519 + ML-KEM-768, has a 1216-byte public key and 1120-byte ciphertext, and is explicitly not an authenticated KEM.
5. R-003 remains `benchmark`. No suite/profile/wire allocation or implementation change is justified.

## 5. Findings

### D20260927-F01 — PQ transition needs explicit method × suite × profile compatibility

- **Source/date/type:** `draft-ietf-lake-pqsuites-01`, 2026-09-19, IETF LAKE WG active Standards-Track Internet-Draft.
- **Primary link:** https://datatracker.ietf.org/doc/html/draft-ietf-lake-pqsuites-01
- **Verified claim:** the draft adds registry metadata for whether a method requires DH/NIKE and whether a suite supports DH/NIKE. Method 0 and the proposed PSK method do not require it, methods 1–3 do, and the proposed ML-KEM suites do not support DH/NIKE. It also points to a separate KEM-authentication method.
- **Bottleneck addressed:** “suite supported” does not establish that the selected authentication method, key-establishment API, proof path, and profile can use that suite.
- **Distinct engineering idea:** future suite registration should classify its key-establishment interface (`DH/NIKE`, `KEM`, or reviewed `PQ/T KEM`), authentication/proof compatibility, and profile compatibility. Negotiation rejects known-but-incompatible cross-products.
- **Evidence maturity:** standards work / concept.
- **Limitations:** the LAKE document is still a draft; its method numbering and COSE design are comparator evidence, not ZK-ARCHE dependencies.
- **ZK-ARCHE inference:** add a deterministic method × suite × profile corpus covering known-but-incompatible combinations, downgrade/fallback, and cross-profile substitution.
- **Impact:** tiny metadata cost; no new online dependency. Rust/C must reach the same selection/rejection result and bind the final tuple into authenticated context.
- **Disposition:** reproduce; R-003/R-011.
- **Roadmap impact:** zk224/zk225/zk226/zk241 candidate only; explicit human review.

### D20260927-F02 — Primitive PQ security is not a protocol-level PQ-security claim

- **Sources/date/type:** `draft-ietf-lake-pqsuites-01` (2026-09-19, IETF WG draft); NIST FIPS 203 and FIPS 204 (2024-08-13, final standards).
- **Primary links:** https://datatracker.ietf.org/doc/html/draft-ietf-lake-pqsuites-01 ; https://csrc.nist.gov/pubs/fips/203/final ; https://csrc.nist.gov/pubs/fips/204/final
- **Verified claim:** the LAKE draft says ML-KEM/ML-DSA primitive QROM analysis is not enough to claim overall LAKE post-quantum security; establishing the Q1 protocol properties is left for future work. It separately identifies ephemeral ML-KEM key exchange as SNDL protection.
- **Bottleneck addressed:** a future ML-KEM or hybrid key-exchange component could otherwise be mislabeled as making all ZK-ARCHE authentication/authorization properties post-quantum secure.
- **Distinct engineering idea:** define a property-level PQ claim matrix covering at least SNDL/key-establishment confidentiality, mutual authentication, role-proof soundness/privacy, authorization binding, resumption/retained secrets, replay/lifecycle, and long-term credential exposure.
- **Evidence maturity:** final primitive standards plus active protocol standards work; ZK-ARCHE protocol-level PQ evidence absent.
- **Limitations:** the LAKE Q1 statement is about LAKE. It supplies claim discipline, not a proof for ZK-ARCHE.
- **ZK-ARCHE inference:** an ML-KEM-only experiment should be described narrowly as PQ-resistant key-establishment/SNDL research unless authentication and the role proof are separately upgraded and analyzed. Current Ristretto/Schnorr/CDS role-proof assurance remains governed by TD-001/R-007 and TD-003/R-004.
- **Impact:** no immediate wire change; substantially higher composition/review evidence burden.
- **Rust/C/vector impact:** future evidence should identify the security property under test rather than emit one undifferentiated “PQ pass.”
- **Disposition:** reproduce.
- **Roadmap impact:** zk204/zk224/zk241; no promotion without explicit human review and cryptographic/formal evidence.

### D20260927-F03 — Standardized PQ object sizes already cross current constrained-message boundaries

- **Sources/date/type:** NIST FIPS 203/204 final standards; X-Wing -11 individual Internet-Draft published 2026-09-23; RFC 9794 IETF Informational consensus terminology.
- **Primary links:** https://csrc.nist.gov/pubs/fips/203/final ; https://csrc.nist.gov/pubs/fips/204/final ; https://datatracker.ietf.org/doc/html/draft-connolly-cfrg-xwing-kem-11 ; https://www.rfc-editor.org/rfc/rfc9794.html
- **Verified claim:** FIPS 203 fixes ML-KEM key/ciphertext sizes at 800/768 (512), 1184/1088 (768), and 1568/1568 (1024) bytes. FIPS 204 fixes ML-DSA-44/65/87 signatures at 2420/3309/4627 bytes. X-Wing -11 specifies a 1216-byte encapsulation key, 1120-byte ciphertext, and 32-byte private seed; it is explicitly not an authenticated KEM and is not an IETF-endorsed standard.
- **Bottleneck addressed:** primitive availability says little about packet, memory, loss, fragmentation, and pre-auth resource feasibility.
- **Distinct engineering idea:** build an exact packet/resource budget before integrating a PQ primitive.

| object | bytes | residual vs current 2048-byte C datagram ceiling |
|---|---:|---:|
| ML-KEM-512 encapsulation key | 800 | 1248 |
| ML-KEM-512 ciphertext | 768 | 1280 |
| ML-KEM-768 encapsulation key | 1184 | 864 |
| ML-KEM-768 ciphertext | 1088 | 960 |
| ML-KEM-1024 encapsulation key | 1568 | 480 |
| ML-KEM-1024 ciphertext | 1568 | 480 |
| ML-DSA-44 signature | 2420 | -372 |
| X-Wing -11 encapsulation key | 1216 | 832 |
| X-Wing -11 ciphertext | 1120 | 928 |

- **Evidence maturity:** final standardized primitive sizes; X-Wing only a research comparator.
- **Limitations:** these are component sizes, not complete ZK-ARCHE messages. A future profile may use another transport, fragmentation, or another authentication method.
- **ZK-ARCHE inference:** ML-DSA-44 cannot fit as a single field under the present 2048-byte C datagram ceiling. ML-KEM/X-Wing components may individually fit but sharply reduce headroom for framing, credentials, transcript/context, proof, and anti-DoS metadata.
- **Impact:** high wire pressure; likely higher reassembly RAM, flash/dependency footprint, CPU/energy, and RNG demand. The LAKE draft also requires a fresh ephemeral ML-KEM key pair per session, cross-linking R-005 RNG/lifecycle evidence.
- **Rust/C/vector impact:** exact packet-length, ceiling-boundary, fragmentation/loss/replay (if introduced), fixed-buffer, and oversize reject-class parity are required.
- **Disposition:** benchmark; next step is a byte-accurate complete-message budget then measured Rust/C prototypes.
- **Roadmap impact:** zk216/zk224/zk225/zk236; explicit human review only.

## 6. Cross-source synthesis

The actionable lesson is not “add ML-KEM” or “adopt X-Wing.” A safe PQ transition has three independent gates:

```text
method / key-establishment API / profile compatibility
                     ↓
property-specific PQ claim boundary
                     ↓
whole-message + target resource evidence
```

A future optional PQ profile must pass all three. The mandatory Common Contract remains unchanged until a reviewed portable floor with constrained-target evidence exists.
