## 2. Executive synthesis

1. **Authenticating the final selected tuple is necessary but not always sufficient to prove downgrade-resistant negotiation.** RFC 9528 protects EDHOC cipher-suite preference by carrying every initiator-preferred suite above the selected suite and requiring the responder to reject a selection if it supports a more-preferred offered suite; manipulation is detected through the authenticated transcript. ZK-ARCHE's new immutable selected tuple is strong, but future negotiation evidence should also prove that an attacker cannot remove or reorder stronger offered choices before the tuple is formed.
2. **Unauthenticated retry/error hints must never rewrite local preference policy.** EDHOC explicitly warns that suite-error messages can be forged and forbids changing the initiator's preference order or omitting more-preferred suites because of them. This is directly relevant to any future ZK-ARCHE retry/fallback mechanism.
3. **A future fallback/version-transition mechanism should prove same-conversation agreement, not rely on reconnect heuristics.** The June 17, 2026 IKEv2 downgrade-prevention draft strengthens downgrade resistance by authenticating more of the initial conversation; TLS 1.3 similarly warns that multiple backward-compatible connection attempts are downgrade-prone. This supports a future ZK-ARCHE formal property over advertisement → selection → AUTH handoff.
4. **No backlog status transition is justified.** The repository still lacks a canonical negotiation advertisement/preference encoding, deterministic downgrade corpus covering stripping/reordering/forged retry, and a formal conversation-agreement theorem tied to Rust/C behavior.
5. No wire, suite, profile, roadmap, ADR, debt, assurance, release, or CI policy is changed by this report.

### D20260915-F01 — Final selected-tuple authentication should be complemented by preference/offer integrity

- **Novelty:** new/refines
- **Backlog owner:** R-001 / R-011 / R-004
- **Sources:** RFC 9528, *Ephemeral Diffie-Hellman Over COSE (EDHOC)*; RFC 9846, *The Transport Layer Security (TLS) Protocol Version 1.3*; RFC 7696, *Guidelines for Cryptographic Algorithm Agility and Selecting Mandatory-to-Implement Algorithms*
- **Primary links:** https://www.rfc-editor.org/rfc/rfc9528.html ; https://www.rfc-editor.org/rfc/rfc9846.html ; https://www.rfc-editor.org/rfc/rfc7696.html
- **Source type / venue:** IETF Standards Track / Best Current Practice
- **Publication dates:** March 2024; July 2026; November 2015
- **Verified claim:** EDHOC requires the initiator to include every suite it prefers over the selected suite and requires the responder to reject when it supports a more-preferred offered suite; manipulation of that offer is later detected through transcript authentication. TLS 1.3 authenticates negotiation through the handshake transcript and states that extension design should prevent attackers from forcing feature use/non-use. RFC 7696 states that cryptographic algorithm selection/negotiation should be integrity protected because otherwise transition creates downgrade opportunities.
- **Existing engineering owner:** R-001 / R-011 / R-004 / TD-003 / TD-004 / `spec/negotiation-selection-state-machine.md`
- **Repository fact:** ZK-ARCHE now authenticates the final selected semantic tuple in AUTH-v3, but the normative state machine does not yet define a canonical authenticated representation of the original version/suite/profile/capability preference advertisements or a proof that no stronger acceptable option was stripped before selection.
- **Problem addressed:** an implementation can agree on and authenticate a weaker final tuple while still lacking evidence that an active attacker did not suppress a stronger mutually acceptable choice during unauthenticated negotiation.
- **Strongest distinct engineering idea:** define a negotiation-agreement property separate from tuple equality: the authenticated result must be consistent with each peer's immutable local policy and the security-relevant offer/preference conversation. This can be implemented by transcript-committing the relevant offer data or by another construction that proves the selected result is the correct policy function of the offers.
- **Evidence maturity:** externally-reviewed standards; ZK-ARCHE mapping is concept/formal-target research
- **Limitations / uncertainty:** ZK-ARCHE need not copy EDHOC's exact `SUITES_I` encoding or TLS ClientHello. Authenticating every capability advertisement may increase wire/transcript complexity and fingerprinting surface; only security-relevant preference information should be committed.
- **ZK-ARCHE inference:** the existing selected tuple should remain immutable, but future conformance should distinguish `selected_tuple_authenticated` from `selection_downgrade_resistant`.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** likely small transcript/wire increase if offer commitments are explicit; hashing cost is negligible relative to AUTH proofs. No new online dependency or trust authority is implied. Privacy impact depends on whether full capability/preference lists become visible; minimization remains necessary.
- **Rust/C / vector compatibility impact:** add deterministic stripping, reordering, stronger-suite omission, unsupported-selected-suite, and same-final-tuple/different-offer-history negatives; Rust/C must agree on both selection and authenticated conversation commitment.
- **Required next evidence:** canonical security-relevant advertisement/preference representation; exact selection function; Rust/C downgrade corpus; formal theorem/counterexample for attacker-controlled offer mutation.
- **Recommended disposition:** reproduce

### D20260915-F02 — Forged retry/error hints must not mutate local negotiation preference policy

- **Novelty:** refines
- **Backlog owner:** R-011 / R-014
- **Source:** RFC 9528
- **Primary link:** https://www.rfc-editor.org/rfc/rfc9528.html
- **Source type / venue:** IETF Standards Track RFC
- **Publication date:** March 2024
- **Verified claim:** EDHOC permits an unsupported-suite error to inform a subsequent attempt but explicitly notes that such errors may be forged; the initiator must not change its preference order or omit a more-preferred suite because of previous errors.
- **Existing engineering owner:** R-011 / R-014 / TD-004 / future retry/negotiation behavior
- **Repository fact:** ZK-ARCHE's new negotiation state machine says future fallback must be transcript-bound and downgrade resistant, while current retry/source-validation research is intentionally separate from identity and authorization authority.
- **Problem addressed:** a forged pre-authentication retry/error can become a downgrade oracle if it mutates persistent local security preference rather than merely supplying untrusted routing/selection input for a fresh attempt.
- **Strongest distinct engineering idea:** model retry/error hints as untrusted observations. They may reduce wasted attempts only if the fresh selection is recomputed under unchanged local policy and the final authenticated conversation proves the chosen security context.
- **Evidence maturity:** externally-reviewed standard; ZK-ARCHE mapping is concept/reproduction target
- **Limitations / uncertainty:** ZK-ARCHE does not yet define the corresponding suite/profile retry wire behavior. Some authenticated post-association policy updates can legitimately change local policy; those are different from unauthenticated retry hints.
- **ZK-ARCHE inference:** future retry caches should separate `peer_hint_cache` from `local_security_policy`; cache loss may cost latency, but forged cache input must not lower the permitted security floor.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** bounded volatile hint state can reduce repeated failed attempts; no persistent trust mutation is needed. Privacy/fingerprinting effects of error detail remain under R-015.
- **Rust/C / vector compatibility impact:** forged unsupported-suite/profile hint, reordered hint, stale cached hint, policy-update-after-cache, and fresh-attempt recomputation vectors should produce identical decisions.
- **Required next evidence:** specify retry-hint cache semantics and lifetime; build deterministic forged/stale-hint corpus; measure whether normalized errors create unacceptable extra CPU/round trips.

### D20260915-F03 — Future fallback/version transitions need authenticated same-conversation evidence

- **Novelty:** refines
- **Backlog owner:** R-001 / R-004
- **Sources:** `draft-ietf-ipsecme-ikev2-downgrade-prevention-06`; RFC 9846
- **Primary links:** https://datatracker.ietf.org/doc/draft-ietf-ipsecme-ikev2-downgrade-prevention/06/ ; https://www.rfc-editor.org/rfc/rfc9846.html
- **Source type / venue:** IETF Standards Track Internet-Draft (work in progress); IETF Standards Track RFC
- **Publication dates:** June 17, 2026; July 2026
- **Verified claim:** the current IKEv2 downgrade-prevention draft protects downgrade-sensitive initial negotiation by having peers authenticate/confirm more of the same initial conversation. TLS 1.3 provides transcript-based downgrade protection and explicitly warns that multiple connection attempts used for backward compatibility are downgrade-vulnerable and not recommended.
- **Existing engineering owner:** R-001 / R-004 / TD-003 / TD-004
- **Repository fact:** ZK-ARCHE currently forbids silent fallback after committing to a higher version and says any future fallback must be transcript-bound, but no fallback mechanism or same-conversation formal property exists yet.
- **Problem addressed:** reconnect-and-try-lower logic can erase evidence of the attacker's influence on the failed stronger attempt, even if the eventual lower-version AUTH is internally valid.
- **Strongest distinct engineering idea:** if fallback is ever introduced, require cryptographic evidence connecting the final authenticated attempt to the downgrade-sensitive conversation/policy that authorized fallback; otherwise fail closed and require an explicit new local-policy decision rather than automatic downgrade.
- **Evidence maturity:** current IETF work-in-progress plus mature TLS precedent; ZK-ARCHE mapping is concept/formal research
- **Limitations / uncertainty:** the IKEv2 draft is not final and ZK-ARCHE currently has no need to support automatic cross-version fallback. The safest design may remain to reject automatic fallback entirely.
- **ZK-ARCHE inference:** formal assurance should state a conversation-agreement/downgrade property before any future fallback feature is promoted. The current no-silent-fallback rule is conservative and should not be weakened merely for compatibility.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** none if automatic fallback remains forbidden; a future authenticated fallback proof would add transcript/state and possibly bytes. No infrastructure dependency is implied.
- **Rust/C / vector compatibility impact:** future corpus should include stripped higher version, altered preference order, cross-attempt replay, forged retry, and lower-version success that must still be rejected when fallback authorization is absent.
- **Required next evidence:** formalize negotiation conversation agreement; decide whether automatic fallback is needed at all; if yes, define cryptographic linkage and deterministic Rust/C negatives before implementation promotion.

## 6. Cross-source synthesis

The sources converge on one boundary: **negotiation security is a property of the authenticated selection conversation, not merely a valid final algorithm identifier.** RFC 7696 establishes the general need for integrity-protected algorithm transition; EDHOC gives a constrained protocol example where preference ordering is retained and transcript-protected; TLS 1.3 authenticates negotiation and warns against reconnect-based compatibility downgrade; current IKEv2 work shows why older protocols are adding fuller conversation confirmation.

For ZK-ARCHE, the new selected tuple is a strong handoff boundary, but the next assurance step should prove that the tuple is the correct result of immutable local policy applied to the security-relevant peer offers, under attacker-controlled transport. This should remain separate from privacy: exposing every local capability merely to prove downgrade resistance could worsen fingerprinting, so the committed negotiation representation should be minimal and profile-defined.
