## 2. Executive synthesis

1. **A composition ambiguity remains in the draft**: `spec/tls-exporter-channel-binding.md` requires `auth_transcript_hash`, whereas the candidate `KC-TRANSCRIPT-v3` contains `channel_binding_hash`. Using the *final* transcript as the exporter's input would be circular. An explicit pre-binding checkpoint is needed before any spec promotion.
2. RFC 9846 specifies a regular TLS exporter over `Hash(context_value)`; local Rust/C helpers currently return only a SHA-256 **context digest**, not actual TLS exported keying material. Digest-separation fixtures cannot qualify either an adapter's exporter invocation or AUTH-v3 binding.
3. RFC 9266's registered `tls-exporter` channel binding is connection-unique, **not** AUTH-instance-unique. ZK-ARCHE's different label and nonempty context may enable instance separation but need their own adversarial and cross-language evidence.
4. The July 2026 Extended Key Update **draft** explicitly separates the regular static exporter from an optional epoch-aware exporter. Neither ordinary TLS KeyUpdate nor a future draft mechanism should silently refresh ZK-ARCHE identity, authorization, or replay authority.
5. **No new cryptographic security result was proved**. R-010 remains P0/`reproduce`; the output is a narrower evidence contract for human review, not a wire/profile decision.

### D20261019-F01 — Specify an acyclic pre-binding transcript checkpoint

- **Novelty / selected owner:** refines / R-010; related R-004 model-to-code traceability.
- **Primary source / type / date:** RFC 9846 §7.5, IETF Standards Track, **July 2026**, https://www.rfc-editor.org/rfc/rfc9846.html ; RFC 9266 §4.1, IETF Standards Track, **July 2022**, https://www.rfc-editor.org/rfc/rfc9266.html .
- **Verified source fact:** TLS exporter computations bind a label, context value, and length under a TLS exporter secret; RFC 9266 specifically distinguishes connection uniqueness from upper-layer authentication-instance uniqueness.
- **Existing owner / repository fact:** `zk217/zk228`, `spec/tls-exporter-channel-binding.md` §3, `spec/auth-v3-kc-transcript-encoding.md` §§5,10, TD-004. The first demands `auth_transcript_hash`; the second hashes a transcript containing `channel_binding_hash`. The exporter spec delegates checkpoint selection to a future profile.
- **Bottleneck / distinct idea:** forbid using `TH_v3` as its own exporter-context dependency. Candidate **staging for explicit human review**, not a normative change:

  `unbound validated AUTH fields → canonical pre-binding bytes/hash → exporter context digest → regular TLS exporter value → canonical channel-binding context/hash → final KC-TRANSCRIPT-v3/TH_v3 → directional Finished verification`.

  Select byte-exact ownership/order of each input and whether the pre-binding checkpoint includes both party contributions before any binding operation. Model the graph as acyclic and reject a wrong-stage digest.
- **Evidence maturity / limitations:** **concept** (standards + repository-composition analysis). No new symbolic proof, trace execution, or demonstrated exploit. The right checkpoint and live TLS sequencing remain to be selected/reproduced.
- **ZK-ARCHE inference / impact:** no mandatory wire or suite change justified; potentially extra SHA-256 state and per-AUTH intermediate 32-byte digest, bounded CPU/RAM, negligible expected flash unless vectors/state are retained. Correct binding improves trust-context separation; no claim about TLS metadata privacy.
- **Rust/C/vector/profile compatibility:** require staged vectors with explicit pre-binding byte string/digest, exporter input, binding-context encoding, final transcript digest, and client/server Finished values; reject circular/final-transcript substitution, absent/duplicate fields, wrong checkpoint, and inconsistent stage ordering in both languages. AUTH-v3/BIND remain draft.
- **Required next evidence / disposition / weekly:** independent graph review and byte-exact Rust/C + local exact-head execution; **reproduce / yes**.

### D20261019-F02 — Qualify the TLS API boundary, not only the context hash

- **Novelty / owner:** refines / R-010.
- **Primary sources / type / dates:** RFC 9846 §7.5 (IETF Standards Track, July 2026), https://www.rfc-editor.org/rfc/rfc9846.html ; RFC 9266 §§2,4.1 (IETF Standards Track, July 2022), https://www.rfc-editor.org/rfc/rfc9266.html .
- **Verified source fact:** RFC 9846's TLS-Exporter internally hashes the **supplied context**, and distinguishes regular exporters from early exporters. RFC 9266 standardizes a different fixed-label, zero-length-context, 32-byte connection binding and disallows using that registered binding for multiple upper-layer authentication instances on one TLS connection.
- **Repository fact / bottleneck:** `tls_exporter_context_digest()` and `auth_tls_exporter_context_v1_digest()` calculate a SHA-256 digest of length-framed ZK-ARCHE context; they do not call a TLS library. Shared TB-N01..N10 demonstrate separation of selected context digests, not shared exporter output or verified AUTH. The ZK-ARCHE draft explicitly proposes a **different** label, `EXPORTER-ZK-ARCHE-v1`, nonempty digest context, and distinct AUTH-instance IDs. The RFC's registered binding security argument cannot simply be inherited.
- **Distinct engineering idea:** define adapter contract `TLS-Exporter(label, 32-byte context_digest, 32)` using the current completed TLS handshake, then feed the resulting **output**, not the context digest, into the canonical ZK-ARCHE channel-binding representation. Test against a TLS implementation on both ends, including deliberate misuse of raw context vs prehashed context, empty-context API paths, second interleaved AUTH instance, identity/ALPN mismatch, proxy termination, and new resumed TLS connection.
- **Evidence maturity / limits:** **software** for existing *digest-only* Rust/C fixtures; **concept** for end-to-end binding. No live TLS interop has been run in this research pass. Context hashes that differ do not by themselves prove unknown-key-share or cross-instance resistance. Regular TLS exporters do not by themselves establish ZK-ARCHE enrollment/trust authority or client-certificate identity.
- **Wire/resource/dependency/trust/privacy:** 32-byte exporter output and digest, per-instance context state and a supported TLS adapter when selected; software CPU/RAM overhead must be benchmarked, especially on constrained targets. TLS remains optional, with potential metadata exposure and hop-local termination semantics. No Common Contract PKI dependency inferred.
- **Rust/C/vector/profile:** add golden inputs and **actual output** vectors keyed by TLS library/version/cipher suite/handshake; force reject for wrong instance, wrong stage, wrong ALPN/application, stale TLS connection, unrecognized mandatory binding and required-binding downgrade. The existing TB corpus is a baseline, not completion evidence.
- **Next evidence / disposition / weekly:** exact-head two-peer TLS adapter and cross-instance trace with shared expected accept/reject decisions; **reproduce / yes**.

### D20261019-F03 — Keep exporter phases and generations disjoint

- **Novelty / owner:** corroborates / R-010; R-009 maintains separate replay/rekey/resumption ownership.
- **Primary source / type / date:** RFC 9846 §§7.5,8 (IETF Standards Track, July 2026), https://www.rfc-editor.org/rfc/rfc9846.html ; `draft-ietf-tls-extended-key-update-13` §§10.1–10.2 (IETF TLS WG **work in progress**, **2026-07-04**), https://datatracker.ietf.org/doc/html/draft-ietf-tls-extended-key-update-13 .
- **Verified source fact:** ordinary TLS exporters use the regular `exporter_secret`, while 0-RTT has a distinct early exporter with weaker replay setting. The Extended Key Update draft says ordinary `exporter_secret` remains static under standard KeyUpdate; its proposed separate exporter evolves with a completed extended key exchange and requires epoch-aware notification.
- **Repository fact / bottleneck:** the draft ZK-ARCHE binding requires the current TLS security context, but no deployed epoch-aware adapter is established; replacing a resumption or authorization check with a mere traffic-key update would cross authority boundaries.
- **Distinct idea / inference:** record exporter **interface/phase**, TLS-connection identity and AUTH-instance identity as distinct local test dimensions. For an optional future extended-update profile, treat epoch labels as potentially local and require an explicit cryptographic association to the selected generation; never equate traffic-key rotation with new authorization, revocation view, replay epoch or resumption-origin legitimacy.
- **Evidence / limits:** **concept**, standards/draft comparison only; draft is not final, no PCS or epoch support demonstrated for ZK-ARCHE. No hardware evidence.
- **Wire/CPU/RAM/flash/dependency/trust/privacy:** zero baseline wire change; optional epoch-aware profile could require extra state, handshake/CPU/wire overhead and retiring predecessor material; must quantify separately. No automatic privacy or PCS promotion.
- **Rust/C/vectors / next evidence / disposition / weekly:** wrong early/regular output, stale resumed output, ordinary KeyUpdate continuity, optional EKU generation mismatch and predecessor retirement negative tests; **research-only optional EKU**, **reproduce regular/resumed correctness**, **no**.

## 6. Cross-source synthesis

The open R-010 gap is not the SHA-256 context encoder in isolation; it is the **binding composition** between verified ZK-ARCHE transcript state and the particular finished TLS handshake/exporter interface. RFC 9266 supplies a useful counterexample to assuming connection uniqueness implies instance uniqueness. RFC 9846 fixes exporter-interface semantics. The draft future exporter mechanism does not change the baseline. The engineering decision should remain gated on byte-level staged vectors, two-language implementation agreement, and live TLS negative traces.
