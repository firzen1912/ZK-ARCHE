# ZK-ARCHE Research — 2026-08-18

## Executive synthesis

The current `dev` branch remains at the 2026-08-17 research commit with no intervening implementation, roadmap, spec, vector, or assurance changes. Today’s highest-value work therefore targeted unresolved semantics rather than new primitives.

Three findings materially sharpen the research plan:

1. **ACE’s July 2026 EDHOC/OSCORE profile provides a concrete separation between authentication and authorization that maps directly to ZK-ARCHE’s role model.** Authentication credentials are bound to authorization tokens, while the resulting secure context is associated with the authorization information used for resource decisions. ZK-ARCHE should explicitly model whether a role proof proves only credential possession/membership or also conveys authorization scope, validity, audience, policy epoch, and revocation state.
2. **Tamarin 1.12 is now a stable, current baseline for R-004 reproducibility.** ZK-ARCHE’s formal models are still ProVerif skeletons. Pinning Tamarin 1.12 and its dependency environment provides a concrete, reproducible tool target for stateful AUTH/replay/rekey properties and avoids an indefinite “Tamarin later” placeholder.
3. **OSCORE key-usage-limit work makes key exhaustion a protocol lifecycle condition, not only an implementation counter.** Its model tracks encryption/decryption usage against AEAD limits and requires peers to stop using a security context before limits are exceeded. ZK-ARCHE’s future `LINK`/`DATA` profiles should define per-suite usage accounting, warning/rekey thresholds, counter persistence, crash/rollback behavior, and fail-closed exhaustion semantics.

No evidence reviewed today justifies changing the mandatory suite, wire format, profile definitions, or maturity claims.

## Findings

### 1. ACE EDHOC/OSCORE separates authenticated credential identity from authorization state

- **Source:** `draft-ietf-ace-edhoc-oscore-profile-11`, *Ephemeral Diffie-Hellman Over COSE (EDHOC) and Object Security for Constrained Environments (OSCORE) Profile for Authentication and Authorization for Constrained Environments (ACE)*
- **Primary link:** https://datatracker.ietf.org/doc/html/draft-ietf-ace-edhoc-oscore-profile-11
- **Source type / venue:** IETF ACE Working Group Internet-Draft
- **Publication date:** 2026-07-06
- **Verified claim:** the profile uses EDHOC for mutual authentication, binds the client authentication credential to an ACE access token, and associates the resulting OSCORE Security Context with authorization information. The resource server enforces access using the authorization information associated with that context; updated access rights can be represented by later tokens in the same token series.
- **Problem addressed:** ZK-ARCHE currently treats role-membership proof as part of authentication and later roadmap work envisions policy-bound release, delegation, and revocation. Without an explicit boundary, a valid proof of membership can be accidentally treated as indefinite or context-free authorization.
- **Strongest distinct engineering idea:** define an authorization-context object separate from the authentication credential/proof. Bind at least audience/resource scope, authorized role/policy, validity interval, policy/registry epoch, revocation state, and session/channel context. Authentication proves who/what credential is present; authorization decides what that authenticated peer may do now.
- **Evidence maturity:** concept
- **Limitations / uncertainty:** ACE uses OAuth/CWT/EDHOC/OSCORE and is not a direct ZK-ARCHE design. Copying its token architecture would add dependencies and may conflict with ZK-ARCHE privacy goals.
- **ZK-ARCHE inference:** use ACE as a semantic comparator, not a dependency. A future ZK-ARCHE authorization ticket or policy-bound release token should be explicitly scoped and revocable rather than overloading the role proof itself. This is particularly relevant to zk230, zk234, zk239 and TD-004 specification work.
- **Wire / RAM / CPU / dependency impact:** no current change. A future compact authorization-context/ticket introduces bytes and policy state; exact cost must be measured for `iot-core`. Avoid mandatory OAuth/CWT machinery unless separately justified.
- **Rust/C / vector compatibility impact:** none at research stage. Any normative authorization object would require new versioned vectors and negative tests for wrong audience, expired policy, stale epoch, revoked authority and cross-session replay.
- **Recommended disposition:** investigate

### 2. Tamarin 1.12 gives R-004 a concrete reproducible baseline

- **Sources:** Tamarin Prover official documentation and release news
- **Primary links:** https://tamarin-prover.com/documentation.html and https://tamarin-prover.com/news.html
- **Source type / venue:** official formal-methods project documentation
- **Release date:** Tamarin 1.12 released 2026-03-08
- **Verified claim:** the official documentation identifies Tamarin 1.12 as the latest stable technical-reference baseline. Tamarin models protocols as multiset-rewriting transition systems and supports analysis with arbitrarily many interleaved protocol-role instances under an adversary model.
- **Problem addressed:** R-004 asks for a pinned formal-verification environment and reproducible outputs, while the repository currently only has ProVerif skeleton models and no pinned Tamarin result set.
- **Strongest distinct engineering idea:** pin a formal-analysis toolchain before expanding the model: Tamarin 1.12 plus recorded Maude/version dependencies, exact invocation, model hash, timeout/resource settings, lemma list, and machine-readable proof/failure outputs. Start with AUTH authentication/secrecy/replay/session-mixup lemmas, then add rekey state and policy epochs.
- **Evidence maturity:** software
- **Limitations / uncertainty:** a stable tool version does not validate a model. Symbolic proofs still depend on abstraction quality and model-to-code traceability.
- **ZK-ARCHE inference:** R-004 can move from generic reproduction intent to a concrete reproducibility target without changing its maturity status. The first useful deliverable is not “formally verified”; it is a pinned environment with a minimal executable AUTH model and explicit assumptions.
- **Wire / RAM / CPU / dependency impact:** no runtime protocol impact; analysis requires workstation/CI compute and Tamarin/Maude dependencies.
- **Rust/C / vector compatibility impact:** no wire change. Model events and terms should be traceable to existing Rust/C message fields, transcript values, state transitions and deterministic vectors.
- **Recommended disposition:** reproduce

### 3. AEAD key-usage limits should become an explicit LINK/DATA lifecycle invariant

- **Source:** `draft-ietf-core-oscore-key-limits-06`, *Key Usage Limits for OSCORE*
- **Primary link:** https://datatracker.ietf.org/doc/html/draft-ietf-core-oscore-key-limits-06
- **Source type / venue:** IETF CoRE Working Group Internet-Draft
- **Publication date:** 2026-01-07
- **Verified claim:** the draft requires tracking AEAD key usage because confidentiality/integrity guarantees degrade when algorithm-specific encryption/verification limits are exceeded. It defines context-associated accounting and requires peers to stop using an OSCORE Security Context as limits approach, with key update required before secure communications continue.
- **Problem addressed:** ZK-ARCHE’s roadmap includes rekey/resumption and a future DATA suite, but current research backlog does not explicitly track cryptographic key-use exhaustion, persistent counters, rollback, or what happens when a peer cannot safely continue under the same key.
- **Strongest distinct engineering idea:** make per-suite key-use budget a protocol-visible lifecycle invariant: count sender encryptions and relevant failed/successful verification attempts as required by the chosen AEAD analysis; define conservative warning and hard-stop thresholds; bind rekey to epoch change; persist or safely reconstruct counters; fail closed after rollback/uncertain state rather than silently reusing a potentially exhausted key.
- **Evidence maturity:** concept
- **Limitations / uncertainty:** the cited draft is OSCORE-specific and was expired at the time checked; exact limits differ by AEAD and usage model. ZK-ARCHE must derive thresholds from the actual mandatory/optional AEAD suites it adopts.
- **ZK-ARCHE inference:** zk213/zk221/zk230/zk233 should eventually include a key-lifecycle contract covering usage counters, rekey trigger, crash recovery, rollback detection, resumption interaction and exhausted-context behavior. This should be specified before long-lived field sessions are claimed safe.
- **Wire / RAM / CPU / dependency impact:** counters add small state; crash-safe persistence may create flash-wear and atomicity costs on MCUs. Rekey frequency affects latency/energy. No immediate packet-format change is required at research stage.
- **Rust/C / vector compatibility impact:** no current impact. Future tests should cover threshold-1, threshold, post-threshold rejection, counter rollback, resumption near exhaustion, simultaneous rekey and stale-context replay.
- **Recommended disposition:** investigate

## Cross-source synthesis

The common theme is **security context needs explicit lifecycle semantics beyond successful authentication**. ACE shows that authentication and authorization state should be separately represented and bound. Tamarin provides a practical way to model those state transitions and adversarial interleavings. AEAD usage-limit work shows that even a cryptographically valid session must eventually become unusable when key-lifecycle conditions are reached.

For ZK-ARCHE, the immediate research priority should therefore be a compact security-context contract that identifies: authenticated peer/credential, authorization scope/policy epoch, key epoch, replay state, usage counters, resumption eligibility, and invalidation conditions. This is a specification/research target only; no automatic protocol change is justified.
