## 1. Executive synthesis

1. **The TLS/DTLS 1.3 IoT profile became a materially stronger comparator on September 3, 2026.** The IESG approved `draft-ietf-uta-tls13-iot-profile-25` for publication as a Proposed Standard. ZK-ARCHE should therefore treat its constrained-device profile discipline as a near-final standards reference rather than merely an exploratory draft, while still avoiding automatic protocol adoption.
2. **Constrained-profile memory limits need a protocol-visible evidence contract, not only a target benchmark.** The approved IoT profile requires TLS/DTLS implementations to implement Record Size Limit and to use it to communicate RAM/record-size limits unless approximately 18 KB of default TLS 1.3 record-processing memory is acceptable. ZK-ARCHE already fixes `iot-core` to a 2048-byte maximum datagram and requires stack/heap/static-RAM measurements, but the current profile does not yet state a separately measured maximum parser/crypto working set or an explicit peer-facing receive ceiling. TD-002 evidence should therefore distinguish wire/message ceiling, transport fragmentation ceiling, parser allocation ceiling, and peak cryptographic working set.
3. **Resumption optimization does not justify generic early execution.** The approved profile treats ticket count, lifetime, and reuse as deployment policy balancing bandwidth/availability against anti-replay and privacy, and it forbids 0-RTT unless an application-specific profile defines replay-safe interactions. ZK-ARCHE's current resumption contract is already aligned by making the secret non-authoritative and keeping general state-changing 0-RTT out of the constrained baseline. Future resumption evidence should preserve this separation rather than adding a generic early-data fast path.
4. **Application/service context is an authentication binding, not just routing metadata, when one key can serve multiple protocols or contexts.** The approved IoT profile requires ALPN support and recommends its use when multiple application protocols, versions, or contexts share the same endpoint/credential; it also requires raw public keys to be bound to the expected peer identity. ZK-ARCHE's BIND classifier already checks AUTH-instance, peer, and profile context, while R-010 already anticipates application/ALPN binding. The next evidence should make the application/service-context match explicit in the concrete TLS/DTLS binding adapter and cross-protocol negative corpus.
5. **Target qualification should remain lifecycle/provenance aware.** NIST IR 8615, published September 1, frames next-generation hardware assurance as an evidence-based lifecycle problem spanning silicon, manufacturing, deployment, operation, and end-of-life, with provenance, attestation, formal methods, fuzzing, and standardized testing as complementary evidence. This supports ZK-ARCHE's existing separation between protocol conformance and TD-002 physical-target/deployment evidence; it does not create a new mandatory hardware mechanism.
6. **No wire, suite, roadmap, ADR, debt status, profile selectability, or maturity claim changes today.** The backlog already owns the affected questions, so no backlog row is modified.

### D20260904-F02 — Resource ceilings need separate wire and working-set evidence

- **Novelty:** refines
- **Source:** `draft-ietf-uta-tls13-iot-profile-25`, Section 12; RFC 8449 Record Size Limit
- **Primary links:** https://www.ietf.org/ietf-ftp/internet-drafts/draft-ietf-uta-tls13-iot-profile-25.html ; https://www.rfc-editor.org/rfc/rfc8449.html
- **Source type / venue:** IESG-approved IETF document plus Standards Track RFC
- **Publication / approval date:** September 3, 2026 for the IoT profile
- **Verified claim:** compliant implementations must implement Record Size Limit and must use it to indicate RAM or record-size limitations unless default TLS 1.3 record processing—approximately 18 KB for ciphertext plus associated buffers—is acceptable. RFC 8449 distinguishes the receive record limit from path MTU and makes the limit apply to records sent toward the endpoint that advertised it.
- **Existing owner:** R-005 / TD-002 / `spec/iot-profiles.md`
- **Repository fact:** draft ZK-ARCHE `iot-core` fixes a 2048-byte maximum datagram and requires target RAM/flash/CPU evidence, while `spec/implementation-requirements.md` requires bounded parsing and physical stack/heap/static-RAM measurements. The 2048-byte datagram ceiling is not itself a measured peak parser/crypto working-set bound.
- **Problem addressed:** a wire-size limit can coexist with a substantially larger transient working set, fragmentation/reassembly buffer, proof-verification scratch space, registry-search state, or transport buffer. Treating “max datagram = 2048” as a RAM guarantee would be an evidence-category error.
- **Strongest distinct engineering idea:** every constrained-profile evidence manifest should report at least four distinct ceilings: (1) maximum protocol message/datagram accepted; (2) transport fragmentation/reassembly ceiling; (3) maximum parser/materialization allocation for hostile and valid inputs; and (4) measured peak cryptographic/protocol working set on the target. If a transport/profile supports a peer-advertised receive limit, its semantics should be separate from path MTU.
- **Evidence maturity:** externally-reviewed comparator; ZK-ARCHE target evidence remains unmeasured
- **Limitations / uncertainty:** TLS record processing differs from ZK-ARCHE message/proof processing, so the 18 KB figure is not a ZK-ARCHE RAM estimate.
- **ZK-ARCHE inference:** the useful lesson is evidence separation and explicit resource-limit signaling/semantics, not adoption of TLS RSL.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** may add profile/adapter metadata if peer-visible receive limits are eventually supported; otherwise primarily changes benchmark/evidence structure. No mandatory dependency.
- **Rust/C / vector compatibility impact:** add shared boundary fixtures for exact maximum accepted size, one-byte-over limit, fragmented/reassembled equivalents where applicable, and instrumentation reports for peak working set. Rust/C accept/reject decisions must remain equal even if allocators differ.
- **Required next evidence:** STM32/ESP32-S3 measurements separating wire ceiling, transport buffers, parser allocations, proof scratch/stack, replay state, registry state, and end-to-end peak RAM for valid/hostile cases.
- **Recommended disposition:** benchmark
- **Weekly finding candidate:** yes

### D20260904-F03 — Resumption does not imply generic early-data safety

- **Novelty:** corroborates/refines
- **Source:** `draft-ietf-uta-tls13-iot-profile-25`, Sections 5 and 15
- **Primary link:** https://www.ietf.org/ietf-ftp/internet-drafts/draft-ietf-uta-tls13-iot-profile-25.html
- **Source type / venue:** IESG-approved IETF document
- **Publication / approval date:** September 3, 2026
- **Verified claim:** resumption can reduce bandwidth, latency, and cryptographic cost, but ticket count/lifetime/reuse policy must balance availability and bandwidth against server state, anti-replay, and privacy. 0-RTT must not be used unless an application-specific profile defines which interactions are safe and how fallback is handled; the IoT profile does not enable 0-RTT for common IoT protocols lacking such a profile.
- **Existing owner:** R-009 / R-012 / R-015 / `spec/resumption-authorization-decision.md`
- **Repository fact:** ZK-ARCHE already makes a resumption secret non-authoritative, requires bounded reuse and lifecycle freshness, and explicitly keeps general-purpose state-changing 0-RTT outside the constrained baseline. It does not yet define a resumption ticket/PSK wire protocol.
- **Problem addressed:** performance pressure can otherwise collapse three distinct claims—credential reuse, resumption authorization, and replay-safe early operation—into one “fast path.”
- **Strongest distinct engineering idea:** preserve three gates: (1) resumption credential validity/lifecycle; (2) authorization revalidation for the resumed association; (3) a separate operation-specific early-execution profile, if ever introduced, whose accepted operations are demonstrably replay-safe/idempotent and whose rejection/fallback semantics are explicit.
- **Evidence maturity:** externally-reviewed comparator; current ZK-ARCHE decision contract is software/spec-draft evidence
- **Limitations / uncertainty:** TLS ticket mechanics do not define a ZK-ARCHE ticket format or replay model.
- **ZK-ARCHE inference:** no generic `early_data_allowed` capability should be inferred from successful resumption. Any future early execution should be versioned/profile-specific and independently reviewed.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** no current wire change; future ticket storage/reuse state has persistent-state and privacy cost.
- **Rust/C / vector compatibility impact:** future corpus should distinguish `RESUME` from any early-operation authorization and reject state-changing early execution in the baseline; ticket reuse/lifetime/privacy metadata should be deterministic where protocol-visible.
- **Required next evidence:** future ticket/PSK issuance/protection design, persistent reuse/expiry tests, resumption privacy/linkability measurements, and explicit proof that baseline operations cannot execute before current authorization is established.

### D20260904-F04 — Application/service context should be explicit in secure-channel binding

- **Novelty:** refines
- **Source:** `draft-ietf-uta-tls13-iot-profile-25`, credential/SNI/ALPN guidance
- **Primary link:** https://www.ietf.org/ietf-ftp/internet-drafts/draft-ietf-uta-tls13-iot-profile-25.html
- **Source type / venue:** IESG-approved IETF document
- **Publication / approval date:** September 3, 2026
- **Verified claim:** raw public keys need a binding to the expected peer identity; ALPN must be supported and should be used when multiple application protocols, versions, or application contexts share the same TLS endpoint/credential. The profile states that ALPN helps prevent cross-protocol confusion.
- **Existing owner:** R-010 / R-013 / R-015 / `spec/transport-binding-and-adapter-authority.md`
- **Repository fact:** ZK-ARCHE BIND currently normalizes `auth_instance_match`, `peer_context_match`, and `profile_context_match`; the current classifier input list does not separately expose an application/service-context match. R-010 already names application/ALPN and deployment/domain binding as required evidence.
- **Problem addressed:** one authenticated key/channel could otherwise be valid for multiple services or protocol instances while the upper layer accidentally authorizes the wrong application context.
- **Strongest distinct engineering idea:** keep the Common Contract transport-neutral, but require each concrete secure-channel adapter to state whether an authenticated application/service context exists and, where a selected profile needs it, bind that context into the normalized BIND construction. For TLS this can derive from ALPN plus deployment/application identifiers; other transports need equivalent explicit semantics rather than copying ALPN.
- **Evidence maturity:** externally-reviewed comparator; ZK-ARCHE adapter construction remains reproduce-stage
- **Limitations / uncertainty:** ALPN is TLS-specific and not itself authorization. Some single-purpose deployments can omit it because application context is fixed by configuration.
- **ZK-ARCHE inference:** application context should not become mandatory for every native P2P profile, but profiles allowing credential/channel reuse across services need an authenticated equivalent and negative cross-context tests.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** no mandatory core dependency; concrete TLS/DTLS binding context gains a small authenticated context input.
- **Rust/C / vector compatibility impact:** add same peer/key/profile but wrong application/service-context fixtures; same service under wrong protocol version; and single-purpose configured-context success. Rust/C must derive identical normalized context hashes where the adapter is shared.
- **Required next evidence:** normative `EXPORTER-ZK-ARCHE-v1` application/deployment context encoding plus cross-protocol/cross-service negative fixtures and proxy/termination assumptions.

## 5. Cross-source synthesis

The September 3 IESG action makes the TLS/DTLS IoT profile a stronger standards comparator precisely where ZK-ARCHE is still evidence-gated: constrained resource contracts, application/context identity, resumption/replay policy, and explicit profile behavior. The main transferable lesson is not “use TLS.” It is that **a constrained security profile is a complete semantic and resource contract**: peers and implementers need to know not only algorithms and maximum packet size, but also what application/identity context is authenticated, how much state/working memory the profile requires, and which lifecycle optimizations remain replay-safe.

NIST IR 8615 adds an orthogonal boundary: even a rigorously specified constrained protocol profile does not establish hardware/platform assurance. ZK-ARCHE should continue to keep protocol conformance, constrained-target measurement, hardware lifecycle/provenance, and deployment qualification as separate evidence classes.
