The controlling debts therefore remain TD-001 independent review of the custom role-membership proof, TD-002 constrained-target measurements, TD-003 reproducible formal evidence, and TD-004 completion of the normative specification.

Today's strongest new evidence is methodological. The ASIA CCS 2026 paper *Formal Verification of EDHOC-PSK: A Symbolic Approach with SAPIC+* demonstrates a reproducible workflow in which one protocol model is compiled to both ProVerif and Tamarin, with the two backends used for complementary property classes. The work also makes a distinction that ZK-ARCHE's current assurance language does not yet make sharply enough: **anonymity and unlinkability are different privacy properties, and observable failure behavior can break unlinkability or stronger identity protection even when identity-bearing data is cryptographically protected.**

This matters directly to ZK-ARCHE because the current ProVerif file is intentionally only a small authentication skeleton, while `spec/privacy-considerations.md` lists PID unlinkability and timing/error leakage only as future topics. The current model does not represent registry lookup, credential/reference resolution, retry behavior, malformed-message error classes, response timing, repeated AUTH sessions, or privacy equivalence. A future formal effort should therefore not merely add more secrecy/authentication lemmas to the existing skeleton; it should define explicit privacy games/equivalences and model observable abort behavior.

A secondary result concerns constrained symmetric-suite evolution. The July 2026 individual COSE Ascon draft now provides a concrete CBOR/COSE mapping for NIST-standardized Ascon-AEAD128 and Ascon-Hash256. This strengthens the case for keeping Ascon in the optional benchmark set for future LINK/DATA/COSE-oriented profiles, but it does **not** justify changing ZK-ARCHE's current Ristretto/HKDF/HMAC authentication baseline or making Ascon mandatory for `iot-core` without target measurements and standards maturity.

The actionable outcome is to sharpen R-004 and add a distinct R-015 privacy-observability research item. No roadmap, spec, source code, CI, ADR, assurance, release, or `main` content is changed.

## Findings

### 1. Use a single-source multi-backend formal model and separate anonymity from unlinkability

- **Source:** Elsa López Pérez, Thomas Watteyne, Cristina Onete, Dhekra Mahmoud, Pascal Lafourcade, Vaishnavi Sundararajan, and Mališa Vučinić, *Formal Verification of EDHOC-PSK: A Symbolic Approach with SAPIC+*
- **Primary link:** https://sancy.iut.uca.fr/~lafourcade/PAPERS/PDF/Formal_Verification_of_EDHOC_PSK__A_Symbolic_Approach_with_SAPIC.pdf
- **DOI:** https://doi.org/10.1145/3779208.3805979
- **Source type / venue:** peer-reviewed ACM ASIA CCS 2026 paper
- **Publication date:** 2026-06
- **Verified claim:** the authors model EDHOC-PSK once in SAPIC+ and generate inputs for both ProVerif and Tamarin. They use ProVerif particularly for equivalence-based identity-protection properties and Tamarin for detailed authentication, confidentiality, and key-agreement reasoning and attack-trace inspection. The model extends a normal Dolev-Yao attacker with explicit compromise capabilities, including ephemeral-secret leakage, long-term PSK leakage, session-key leakage, and a delayed discrete-log oracle representing a Store-Now-Decrypt-Later adversary. The paper provides a public reproducibility environment. It distinguishes anonymity from unlinkability rather than treating them as synonyms: in the analyzed protocol, anonymity holds more broadly than unlinkability, and some unlinkability properties fail under stronger attacker models.
- **Problem addressed:** ZK-ARCHE TD-003 currently has duplicated ProVerif skeletons and a backlog goal to add Tamarin, but the existing model is too abstract to establish privacy, lifecycle, registry, or implementation-traceability claims. Merely adding a second independently maintained model risks semantic drift between verification backends.
- **Strongest distinct engineering idea:** evaluate SAPIC+ or an equivalent single-source modeling discipline as the *authoritative symbolic model source*, then compile/export to ProVerif and Tamarin so both tools analyze the same state machine and term structure. Define a property matrix before modeling: secrecy, non-injective/injective agreement, key confirmation, replay/lifecycle invariants, anonymity, unlinkability, credential/reference misbinding, compromise cases, and delayed cryptanalytic/SNDL cases. Use backend-specific strengths intentionally rather than expecting one tool to prove every class of property.
- **Evidence maturity:** externally-reviewed
- **Limitations / uncertainty:** the paper analyzes EDHOC-PSK draft 06, not ZK-ARCHE. Symbolic verification still relies on perfect-cryptography abstractions and cannot by itself validate the custom CDS OR-composed role-membership proof, constant-time behavior, RNG quality, subgroup/implementation defects, memory safety, or real packet-size/timing leakage. Adopting SAPIC+ would add tooling/dependency cost and requires proving that the generated models preserve the intended ZK-ARCHE semantics. A unified source is valuable only if model-to-code traceability is maintained.
- **ZK-ARCHE inference:** R-004 should require one canonical formal state-machine model or a mechanically synchronized modeling source rather than two hand-maintained ProVerif/Tamarin models. The model should include the stateful trust/registry semantics already identified by R-013, invalidation/replay continuity from R-009/R-012, and the exact AUTH transcript/sequence conditions. Privacy claims should be named precisely: "PID changes" is not evidence of unlinkability, and anonymity under one attacker model must not be reported as unlinkability under another.
- **Wire / RAM / CPU / flash / dependency impact:** no protocol wire or target-runtime cost unless a future verified design change is promoted. Research/tooling impact includes SAPIC+ plus supported ProVerif/Tamarin versions, containerized reproducibility, model generation, and retained proof outputs/counterexamples.
- **Rust/C / vector compatibility impact:** none directly. The required traceability artifact should map formal message/state transitions and security events to concrete Rust/C functions, fields, transcript components, negative vectors, and persistent-state transitions. Formal counterexamples should become deterministic regression tests where representable.
- **Recommended disposition:** reproduce

### 2. Treat abort/error/timing observability as part of the privacy protocol, not only implementation hygiene

- **Source:** same ASIA CCS 2026 EDHOC-PSK formal-analysis paper, identity-protection analysis
- **Primary link:** https://sancy.iut.uca.fr/~lafourcade/PAPERS/PDF/Formal_Verification_of_EDHOC_PSK__A_Symbolic_Approach_with_SAPIC.pdf
- **Source type / venue:** peer-reviewed formal protocol analysis
- **Publication date:** 2026-06
- **Verified claim:** the paper's privacy analysis shows that an active adversary can exploit whether a manipulated encrypted identity causes acceptance, decryption failure, or another observable abort behavior. It explicitly notes that differences such as "unknown credential" versus "authentication failure" or timing differences can reveal whether a candidate identity/credential was valid. The authors prove different results for anonymity and unlinkability and show that active manipulation can defeat stronger identity-protection notions even though the credential itself is encrypted.
- **Problem addressed:** ZK-ARCHE aims for pseudonymous/unlinkable role authentication, while current work also introduces retry behavior, encrypted lookup hints, registry prefilters, explicit alerts, and future credential/reference resolution. These features create new externally observable branches. If different failure reasons, response lengths, retry policies, proof-verification order, or processing times correlate with whether a lookup/credential/role exists, a passive-identity-hiding mechanism can still become an active membership oracle.
- **Strongest distinct engineering idea:** define a **privacy-observability contract** for unauthenticated and privacy-sensitive states. For each AUTH/ENROLL/P2P failure class, specify what a network observer may distinguish: response/no-response, packet type, packet length bucket, retry-cookie behavior, error code, connection close behavior, and timing class. Then create paired privacy regression tests that vary only the hidden fact (known vs unknown lookup key, allowed vs disallowed role, real vs decoy credential/reference, valid vs stale epoch) and verify that pre-authentication observable behavior does not reveal more than the stated privacy policy.
- **Evidence maturity:** externally-reviewed
- **Limitations / uncertainty:** constant-time equality at the primitive level cannot make a whole network protocol constant-time. Real networks introduce noise, scheduler variance, caches, allocator effects, storage lookup differences, and retransmission timing. Some failure distinctions may be operationally necessary after authentication. The goal is therefore an explicit leakage budget and indistinguishability policy by state, not a blanket requirement that every failure take identical wall-clock time.
- **ZK-ARCHE inference:** the future spec should distinguish at least passive unlinkability, active unlinkability, and anonymity, with attacker capabilities stated for each claim. Before authenticated context exists, lookup-hint decryption failure, unknown registry key, unknown credential/reference, PID mismatch, role-policy failure, malformed proof, stale epoch, and unsupported private extension should be reviewed for oracle behavior. `AUTH_RETRY` should not itself become a stable device discriminator. After authentication, richer diagnostics may be allowed locally or inside a protected channel while the wire still uses a coarse alert taxonomy.
- **Wire / RAM / CPU / flash / dependency impact:** potentially small fixed padding or response normalization cost; possible added bounded dummy/constant-work operations for selected failure classes; additional test/benchmark tooling. Exact costs require measurement because deliberately equalizing expensive proof paths can create a DoS amplification risk. Privacy normalization must therefore be designed together with `AUTH_RETRY` and cheap pre-validation.
- **Rust/C / vector compatibility impact:** compatible if implemented as alert/state-machine discipline without changing successful AUTH semantics. Add deterministic negative vectors for error classification plus network-level fixtures measuring response type/length and bounded timing distributions. Rust/C must agree on which failures are externally distinguishable even if their internal diagnostic enums differ.
- **Recommended disposition:** reproduce

### 3. Keep Ascon as an optional measured constrained-suite candidate; COSE mapping maturity is improving but not yet a baseline mandate

- **Source:** `draft-ochkas-cose-ascon-04`, *Ascon-AEAD128 and Ascon-Hash256 for COSE*
- **Primary link:** https://datatracker.ietf.org/doc/draft-ochkas-cose-ascon/
- **Source type / venue:** active individual Internet-Draft discussed in the COSE context; not an IETF standard
- **Publication/update date:** 2026-07-06
- **Verified claim:** the draft defines COSE serialization/algorithm identifiers and test material for Ascon-AEAD128 and Ascon-Hash256, explicitly building on NIST SP 800-232. The document is an individual Internet-Draft and therefore has no formal IETF standards standing. IETF 126's COSE agenda included discussion of this Ascon work, showing active ecosystem interest rather than completion of standardization.
- **Problem addressed:** ZK-ARCHE's future LINK/DATA and optional COSE-oriented profiles need a constrained symmetric/hash suite strategy that can be benchmarked on MCU targets without making hardware-specific acceleration part of protocol correctness.
- **Strongest distinct engineering idea:** retain the current conservative authentication baseline while adding Ascon-AEAD128/Ascon-Hash256 to the *benchmark matrix* for future encrypted LINK/DATA or COSE-bound profiles. Compare against ChaCha20-Poly1305 and target hardware AES-based AEAD where applicable using the same STM32/ESP32-S3 methodology: wire overhead, cycles/latency, stack/heap, flash, energy where measurable, hardware acceleration availability, side-channel implementation maturity, and Rust/C library quality.
- **Evidence maturity:** software
- **Limitations / uncertainty:** the COSE mapping is still an individual draft and may change. ZK-ARCHE AUTH currently relies on Ristretto/SHA-2/HKDF/HMAC rather than a general AEAD session layer in the core protocol crate, so this is primarily future LINK/DATA/profile work. NIST standardization of Ascon does not imply that every ZK-ARCHE target will outperform existing primitives with it.
- **ZK-ARCHE inference:** Ascon should remain optional and negotiated until exact target measurements and implementation maturity justify a profile decision. A high-end node must still interoperate downward with the constrained mandatory floor. Do not introduce Ascon solely for novelty or because a COSE draft exists.
- **Wire / RAM / CPU / flash / dependency impact:** AEAD tag/nonce framing and library footprint depend on the final profile encoding and implementation. Exact target costs are unknown and are the purpose of the benchmark. Adding another mandatory suite would increase code size and review surface, so any adoption should be optional unless measurements show a clear whole-profile benefit.
- **Rust/C / vector compatibility impact:** no current compatibility impact. A future experiment should use NIST and COSE draft vectors as external conformance anchors and add identical Rust/C profile fixtures before any suite identifier is considered stable.
- **Recommended disposition:** benchmark

## Cross-source synthesis

The main conclusion is not that ZK-ARCHE needs more cryptography. It needs **more precise evidence semantics**.

The ASIA CCS work shows that a protocol can satisfy authentication and secrecy properties while its privacy claims vary sharply by attacker model and by what failure behavior an attacker can observe. That maps directly onto current ZK-ARCHE work: encrypted lookup hints, pseudonymous PIDs, retry cookies, role proofs, and hidden credential/reference state all need an explicit observable-failure policy. A cryptographically hidden value is not automatically unlinkable if the protocol becomes an oracle for whether that hidden value was valid.

For formal verification, a single canonical model feeding complementary backends is a stronger direction than independently extending the current duplicated ProVerif skeletons. ProVerif-equivalence style privacy properties and Tamarin stateful/trace properties can then be tied to one modeled state machine and one explicit attacker/property matrix. This does not replace TD-001's independent cryptographic review or target/runtime assurance.

The Ascon/COSE development is useful but secondary. It gives a more concrete interoperability benchmark for future constrained encrypted-data profiles, not a reason to perturb the current authentication baseline.
