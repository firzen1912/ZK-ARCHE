## 1. Executive synthesis

1. **The new persistent formal replay table is stronger than the concrete runtime replay memory unless its lifetime assumption is made explicit.** C uses a volatile fixed-capacity 64-entry FIFO-style cache; Rust uses a volatile profile-dependent `HashSet` cache with arbitrary eviction (32 entries for Minimal, 4096 for Standard, 32768 for Gateway). RFC 8613 treats loss of replay state across reboot as security-relevant state loss that must not silently permit old messages under the same security context. This materially refines R-009 and R-004.
2. **Rust/C replay decisions can diverge after cache pressure even though the roadmap requires decision compatibility.** The differing capacities and eviction rules make an eviction/replay parity test necessary before replay semantics can be treated as a common-contract property.
3. **The current C atomic replay transaction is correctly check-after-decode / record-after-full-verification, but its lock boundary covers expensive unauthenticated proof work and registry candidate scanning.** RFC 9147 and RFC 9528 both identify state allocation and expensive cryptography on unauthenticated datagram handshakes as DoS surfaces and recommend reachability/source-validation mechanisms. This refines the existing `AUTH_RETRY` / R-014 direction rather than creating a new mechanism.
4. **No replay vulnerability is claimed today.** A specific reproduction hypothesis is now justified: capture a valid accepted `AUTH_1`, force replay-key eviction or restart, then resend the same payload under a fresh header/session. The current AUTH_1 proof inputs bind PID, client nonce, and client ephemeral key, not the outer session ID/sequence; executable Rust/C testing is required before concluding whether this produces an accepted second run in the complete state machine.
5. No mandatory suite, wire format, roadmap phase, debt status, maturity claim, or release posture changes. The research outcome is a tighter evidence contract for R-004, R-009, and R-014.

## 4. Findings

### D20260826-F01 — Replay protection needs a normative lifetime/persistence/eviction contract aligned with the formal model

- **Novelty:** refines
- **Sources:** RFC 8613, *Object Security for Constrained RESTful Environments (OSCORE)*; RFC 9147, *The Datagram Transport Layer Security (DTLS) Protocol Version 1.3*
- **Primary links:** https://www.rfc-editor.org/rfc/rfc8613.html ; https://www.rfc-editor.org/rfc/rfc9147.html
- **Source type / venue:** IETF Standards Track RFCs
- **Publication or release date:** RFC 8613 — July 2019; RFC 9147 — April 2022
- **Verified claim:** RFC 8613 treats the replay window as mutable security-context state and explicitly addresses loss of replay state after reboot: an endpoint must prevent accepting previously received traffic when the same security context remains in use, with persistence, state-recovery procedures, or establishment of a fresh context among the available approaches. RFC 9147 specifies functional anti-replay behavior independent of implementation details and requires the replay window to advance only after successful record deprotection.
- **Existing owner:** R-004 / R-009 / TD-003 / zk203 / zk218 / zk229
- **Repository fact:** the latest ProVerif model now uses a persistent `replay_seen` table, but both concrete servers keep replay keys only in RAM. C defaults to 64 replay keys and replaces entries after capacity. Rust has profile-dependent capacities of 32/4096/32768 and evicts an arbitrary set entry. The two lanes therefore do not currently share one replay-retention decision boundary under pressure, and both forget replay state on process restart.
- **Problem addressed:** a formal proof or correspondence result about an unbounded/persistent replay table can overstate what the current bounded volatile implementations actually retain. The common-contract requirement also needs Rust/C agreement on when an old accepted AUTH_1 becomes eligible for processing again.
- **Strongest distinct engineering idea:** define replay protection relative to an explicit **replay epoch/lifetime contract**. For each profile, specify what causes a fresh replay epoch (e.g. credential/key/policy epoch transition or authenticated state recovery), what replay state must survive restart, the minimum retention/eviction semantics, and the fail-closed behavior when durable state is missing or rolled back. Formal results should state whether replay state is persistent/unbounded, bounded, or reset only with a modeled epoch transition; executable tests should cover the concrete bounded behavior.
- **Evidence maturity:** software
- **Limitations / uncertainty:** OSCORE and DTLS use sequence/replay-window constructions different from ZK-ARCHE's hash-key cache. Their exact mechanisms are comparators, not protocol requirements. The repository inspection has not executed a post-eviction or post-restart replay attack; acceptance after state loss remains a reproduction hypothesis.
- **ZK-ARCHE inference:** before FM-04/replay claims advance, reproduce at least: (a) fill the C cache past 64 and replay the evicted first accepted AUTH_1; (b) perform the equivalent test at each Rust profile capacity; (c) restart each server and replay a previously accepted AUTH_1; (d) roll back any future persistent replay state; and (e) replay under a fresh outer session ID/sequence. If the same profile is claimed in both languages, acceptance/rejection must match. If bounded retention is intentionally profile-specific, that difference must be normative and security-justified.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** durable replay continuity may require bounded NVM metadata, authenticated epochs, or explicit fresh-context transitions; constrained devices need flash-wear/crash-atomicity measurements. Aligning capacities may increase RAM on C or reduce Rust retention. No new primitive is implied.
- **Rust/C / vector compatibility impact:** no immediate byte-vector change, but stateful cross-language conformance scenarios are required. A deterministic replay corpus should include cache-fill order, eviction boundary, restart, rollback, and epoch-transition cases.
- **Required next evidence:** Rust/C eviction and restart replay tests; explicit replay epoch/lifetime semantics; persistence/rollback design or authenticated fresh-context rule; profile retention parity; formal assumption manifest tying `replay_seen` semantics to runtime behavior.
- **Recommended disposition:** reproduce

### D20260826-F02 — Source validation should precede expensive AUTH_1 state/crypto work; replay atomicity should not become a global DoS bottleneck

- **Novelty:** refines
- **Sources:** RFC 9147, Section 5.1 denial-of-service countermeasures; RFC 9528, Section 9.7 denial of service and Section 7 message deduplication; `draft-ietf-lake-edhoc-impl-cons-07` as current LAKE implementation-guidance context
- **Primary links:** https://www.rfc-editor.org/rfc/rfc9147.html ; https://www.rfc-editor.org/rfc/rfc9528.html ; https://datatracker.ietf.org/doc/draft-ietf-lake-edhoc-impl-cons/
- **Source type / venue:** IETF Standards Track RFCs plus active LAKE WG Internet-Draft
- **Publication or release date:** RFC 9147 — April 2022; RFC 9528 — March 2024; EDHOC implementation considerations revision 07 — July 6, 2026
- **Verified claim:** RFC 9147 identifies unauthenticated datagram handshakes as a DoS vector because attackers can force state allocation and expensive cryptographic work; it uses a stateless cookie reachability check and recommends keeping cookie generation/verification cheap. RFC 9528 likewise notes that new or replayed EDHOC `message_1` can force state allocation, cryptographic operations, and amplification, recommending lower-layer reachability mechanisms. EDHOC deduplication also requires that a duplicate message not be processed into another next-message instance within the same session.
- **Existing owner:** R-014 / zk219 / zk229; secondary relevance R-009
- **Repository fact:** C reserves a session-table slot before registry candidate scanning. For each candidate it acquires the dedicated replay mutex and holds it across `auth_server_handle_auth1_guarded`, which performs replay lookup, full Schnorr/PID/rerandomization/role proof processing, and replay insertion. This preserves atomicity for concurrent UDP/TCP duplicate claims, but it serializes expensive unauthenticated AUTH_1 verification across workers. Rust currently serializes the full shared state under one mutex in its reference server and explicitly notes that production deployment would split concerns.
- **Problem addressed:** a correct replay transaction can still become an availability bottleneck if adversarial, unauthenticated traffic reaches state reservation, O(n) candidate scanning, or expensive proof verification before source validation. Large registries increase this cost.
- **Strongest distinct engineering idea:** retain check→verify→record atomic semantics, but put a cheap **stateless/bounded `AUTH_RETRY` source-validation gate before session reservation, registry scan, and proof verification** in exposed datagram profiles. Then narrow replay synchronization to the minimum race-sensitive transition (for example reservation/commit semantics) rather than holding a global replay mutex across all expensive cryptographic work. Measure instead of assuming that the narrower design is safe.
- **Evidence maturity:** software
- **Limitations / uncertainty:** a cookie proves return-routability, not authorization, and does not stop DoS from valid source addresses. TCP and protected/local deployments may need different policy. Lock splitting can introduce races if implemented incorrectly; atomic replay acceptance remains the security invariant.
- **ZK-ARCHE inference:** extend R-014's prototype/benchmark contract with adversarial concurrency measurements: invalid AUTH_1 rate, registry sizes 10/100/1k/10k, UDP/TCP mixed load, session-slot occupancy, replay-lock wait time, proof CPU, and amplification bytes before/after source validation. Add a race test where two workers present the same valid AUTH_1 and exactly one transition may create new accepted state while any allowed retransmission returns only the cached prior response.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** optional retry adds a round trip and small cookie bytes but can sharply reduce unauthenticated CPU/state cost. Cookie keys require rotation/lifetime policy but no new trust authority. Narrower locking can improve multicore throughput without changing authentication semantics.
- **Rust/C / vector compatibility impact:** a future retry extension would require compatible wire/state-machine vectors; the concurrency benchmark itself does not change existing vectors. Both lanes need the same accept/retry/error semantics for the common profile.
- **Required next evidence:** retry-before-allocation design; cookie cost/size and amplification budget; mixed-load concurrency benchmark; duplicate-race test; Rust/C state-machine parity; proof that lock narrowing does not permit double acceptance.
- **Recommended disposition:** benchmark
- **Weekly finding candidate:** yes

## 5. Cross-source synthesis

The new repository work makes replay a state-lifecycle problem rather than only a duplicate-key lookup. The standards evidence converges on three separable responsibilities:

```text
same-session duplicate handling
        → do not process twice; cached response may be retransmitted

cross-session / accepted-message replay memory
        → define retention + epoch + persistence / state-loss behavior

unauthenticated datagram admission
        → validate source cheaply before expensive state/crypto when deployment requires it
```

ZK-ARCHE now implements useful pieces of the first two, but the exact lifetime contract is not yet aligned across Rust, C, and the formal model. `AUTH_RETRY` is already the natural owner for the third. The correct next move is therefore reproduction and benchmark evidence, not another cryptographic primitive or an ad hoc larger cache.
