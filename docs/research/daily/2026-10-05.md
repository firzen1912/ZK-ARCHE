## 2. Executive synthesis

- The August R-011 pass correctly separated deterministic reserved unknown-value fixtures from any future live GREASE. The newer IAB protocol-greasing draft adds a sharper implementation requirement: GREASE only has value when the extension point already treats arbitrary unknown values as ignorable, and the implementation must not recognize GREASE values as a special case.
- ZK-ARCHE therefore needs a per-extension-point unknown-handling / GREASE-eligibility matrix, not just per-registry reserved ranges. An extension point is grease-eligible only where its normal catch-all behavior for unknown values is ignore/continue. Security-critical selections whose normal unknown behavior is reject are not live-GREASE candidates.
- The conformance corpus should distinguish four decision classes: known-valid, known-but-invalid/incompatible, ordinary unknown, and reserved-GREASE unknown. For an ignorable extension point, ordinary-unknown and GREASE-reserved values must have the same decision. Known-invalid values must still fail even if their numeric pattern resembles a greasing reservation.
- GREASE by itself is incomplete anti-ossification evidence because it exercises only reserved GREASE values. R-011 should retain generic non-GREASE unknown-value vectors and legal positive-variability tests where semantics permit them.
- The draft iot-core profile currently selects no critical extensions and an exact security-capability set. No live GREASE mechanism is justified for that baseline today. Test-only anti-ossification evidence has zero production wire cost and should come first.
- R-011 remains reproduce. No registry allocation, wire behavior, live GREASE requirement, profile change, implementation change, or roadmap modification is authorized by this research run.

## 5. Findings

### D20261005-F01 — GREASE eligibility belongs to the extension point's ordinary unknown-value semantics, not to a magic reserved range

- **Novelty:** new / refines the 2026-08-27 R-011 result.
- **Backlog owner:** R-011 / TD-004.
- **Source:** draft-iab-protocol-greasing-01, Considerations For Maintaining Protocols Using Grease and Variability.
- **Primary link:** https://datatracker.ietf.org/doc/html/draft-iab-protocol-greasing-01
- **Source date / type:** published 2026-07-06; active IAB Internet-Draft; intended Informational; work in progress rather than an Internet Standard.
- **Verified claim:** the draft says GREASE values must not be special-cased. Ignoring them must be the same general unknown/unhandled-value behavior used for ordinary unknowns. Consequently, GREASE is meaningful only at extension points where arbitrary unknown values are ignored by default; mandatory or critical values must not be marked as GREASE.
- **Bottleneck addressed:** the repository has reserved anti-ossification numeric ranges, but a range reservation by itself does not establish whether each syntactic use of that registry is safe to ignore, must reject, or can become an authenticated selection.
- **Strongest distinct engineering idea:** add a language-neutral extension-point matrix with at least: registry/field, syntactic position, unknown-value action, known-invalid action, selected/authoritative status, criticality rule, and live-GREASE eligibility. A live GREASE candidate is eligible only if the extension point's ordinary unknown-value action is ignore/continue.
- **Evidence maturity:** external primary guidance, but still an Internet-Draft.
- **Limitations:** the draft is general protocol-maintenance guidance, not ZK-ARCHE-specific and not standards-track. It does not prove that live GREASE is worthwhile for a small constrained deployment.
- **ZK-ARCHE relevance:** high for TD-004 negotiation/registry conformance. Current deterministic test ranges remain useful, but they must not become magic values whose special recognition masks a broken generic unknown-value path.
- **Likely impact:** test-only implementation has zero production wire cost and negligible CPU/RAM/flash impact. A future live GREASE scheme would add advertisement variability and parser/test complexity, but no new trust authority or cryptographic dependency.
- **Rust/C/vector/profile compatibility:** shared decision vectors should feed both lanes. At an ignorable extension point, a reserved GREASE value and an ordinary unassigned non-GREASE value must produce the same accept/ignore decision. At reject-class extension points, both must fail according to the normal field rule.
- **Disposition:** retain R-011 at reproduce; refine evidence contract.
- **Roadmap-impact record:** human review candidate for future registries/conformance work under zk225/zk226/zk229 and TD-004. No roadmap/spec/code edit authorized today.

### D20261005-F02 — Known-invalid and unknown-ignorable values require separate decision branches

- **Novelty:** new / refines.
- **Backlog owner:** R-011.
- **Source:** draft-iab-protocol-greasing-01; corroborated by RFC 9170.
- **Primary links:** https://datatracker.ietf.org/doc/html/draft-iab-protocol-greasing-01 and https://www.rfc-editor.org/rfc/rfc9170.html
- **Source date / type:** IAB Internet-Draft published 2026-07-06; RFC 9170 is an IAB Informational RFC published 2021-12.
- **Verified claim:** the IAB draft gives the safe processing shape as known-and-valid => handle, known-but-invalid => explicit error, otherwise => generic unknown handling. It warns that testing for GREASE first and ignoring those values can incorrectly bypass a recognized-invalid condition. RFC 9170 independently explains that greasing works by routinely exposing implementations to unknown values and that extension mechanisms remain viable through active use, not through registry design alone.
- **Bottleneck addressed:** ZK-ARCHE already says known does not imply compatible, but R-011 does not yet require a single cross-language branch corpus that proves incompatibility checks cannot be bypassed by numeric reservation patterns.
- **Strongest distinct engineering idea:** define one shared decision table covering: known-valid/compatible; known-but-incompatible; reserved/draft-not-promoted; unknown critical; ordinary unknown ignorable; reserved-GREASE unknown ignorable; and unsupported selected value. The expected result must be derived from field semantics before any optional GREASE label is considered.
- **Evidence maturity:** RFC-backed general principle plus newer IAB draft refinement.
- **Limitations:** exact error-code normalization remains a ZK-ARCHE design matter; externally visible diagnostic specificity must still obey the repository privacy/error-oracle rules.
- **ZK-ARCHE inference:** for selected version/suite/profile/security capabilities, unknown or incompatible values remain fail-closed and should not be made live-GREASE positions merely to exercise extensibility. For v2 ignorable HELLO TLVs, future GREASE experimentation would have to use the same generic skip path as any other unknown TLV. For v3 critical extensions, the critical bit determines reject semantics; a GREASE reservation must never override it.
- **Likely impact:** no production wire/CPU/RAM/flash/dependency impact for deterministic vectors. Trust impact is positive: it prevents a greasing recognizer from becoming an accidental downgrade or compatibility bypass.
- **Rust/C/vector/profile compatibility:** require exact decision parity and normalized externally observable failure class where privacy requires it; include same numeric value in different semantic positions where legal to prove position/criticality, not the number alone, controls the result.
- **Disposition:** reproduce.
- **Roadmap-impact record:** recommend an explicit compatibility/unknown decision corpus for human promotion into conformance evidence; no direct spec or implementation modification in this run.

### D20261005-F03 — Reserved GREASE coverage is incomplete without generic unknowns and bounded legal variability

- **Novelty:** refines.
- **Backlog owner:** R-011 / R-015 / R-005.
- **Sources:** draft-iab-protocol-greasing-01; RFC 9170; draft-ietf-moq-transport-22 as a current deployment example.
- **Primary links:** https://datatracker.ietf.org/doc/html/draft-iab-protocol-greasing-01 ; https://www.rfc-editor.org/rfc/rfc9170.html ; https://datatracker.ietf.org/doc/html/draft-ietf-moq-transport-22
- **Source date / type:** IAB greasing draft 2026-07-06; RFC 9170 Informational; MOQT -22 published 2026-10-01 as an IETF MOQ WG Standards Track Internet-Draft.
- **Verified claim:** the IAB draft explicitly notes that GREASE tests the reserved GREASE values rather than every possible future/unknown value and recommends considering positive variability where legal. It also records implementation, CPU/RAM/network-efficiency, wire-image, and fingerprinting tradeoffs. MOQT -22 is a fresh example of a protocol reserving patterned GREASE values in registries whose unknown values are required to be handled gracefully.
- **Bottleneck addressed:** a test suite can pass all named GREASE fixtures while still having a brittle generic unknown path or ossified legal ordering/size assumptions.
- **Strongest distinct engineering idea:** keep three independent evidence lanes: (1) deterministic reserved GREASE fixtures; (2) deterministic ordinary unassigned non-GREASE values spanning each unknown-handling class; and (3) bounded legal positive variability such as permitted order changes or harmless optional advertisement variation. Treat them as complementary rather than interchangeable.
- **Evidence maturity:** RFC/IAB guidance plus a current WG draft deployment example.
- **Limitations:** positive variability can increase complexity and resource use. Wire-image variation involving packet sizes, counts, timing, padding, or fragmentation can create privacy/fingerprinting and constrained-network costs and is not automatically beneficial.
- **ZK-ARCHE inference:** do not add live GREASE to draft iot-core merely to satisfy R-011. First prove generic unknown handling locally. If later live variability is proposed, restrict it to semantically ignorable advertisement surfaces and require R-015 privacy/fingerprinting analysis plus R-005 wire/RAM/CPU/energy measurements before profile promotion.
- **Likely impact:** deterministic local corpus: zero wire impact and small test footprint. Live variability: potentially increased wire bytes, packetization variability, parser paths, CPU/RAM, and fingerprinting surface; no inherent cryptographic benefit.
- **Rust/C/vector/profile compatibility:** both implementations should consume the same deterministic generic-unknown corpus. Legal order variation must preserve the same canonical authenticated result when semantics are set-like; any variation that changes selected authenticated context is not “harmless variability” and requires explicit protocol semantics.
- **Disposition:** R-011 remains reproduce; live deployment behavior remains unpromoted.
- **Roadmap-impact record:** cross-link any future live variability proposal to R-015 and R-005; explicit human review required before wire/profile changes.

## 6. Cross-source synthesis

RFC 9170 establishes the long-term principle: an extension mechanism stays usable through repeated real handling of new/unknown values, not by specification text alone. The 2026 IAB greasing draft tightens that into an implementation rule: GREASE must exercise the same ordinary unknown path and is only suitable where arbitrary unknown values are semantically ignorable. The October 2026 MOQT draft demonstrates that current protocol work still applies this pattern to registries designed for graceful unknown handling.

For ZK-ARCHE, this means reserved anti-ossification ranges are test inputs, not policy authority. The authoritative object is the extension point's semantics. A concise conformance model is:

| Input class | Ignorable advertisement point | Security-critical / selected point |
|---|---|---|
| known + valid | handle | handle if profile-compatible |
| known + invalid/incompatible | reject | reject |
| ordinary unknown | ignore only if the point defines that behavior | reject/fail closed |
| reserved GREASE unknown | same as ordinary unknown; never special-case | reject/fail closed; do not select |

This preserves the security boundary already present in ZK-ARCHE while making the anti-ossification evidence harder to game accidentally.
