# ZK-ARCHE Research — 2026-08-15

## Executive synthesis

Today's repo-first review indicates that ZK-ARCHE's highest-value research work is not a wholesale primitive replacement. The immediate leverage is to make the current custom protocol easier to specify, benchmark, and review against mature constrained-security practice.

Five findings matter now:

1. **EDHOC provides a concrete constrained authenticated-key-exchange benchmark**: RFC 9528 publishes 101-byte total three-message examples for static-DH authentication with compact key identifiers, requires transcript-bound negotiation and an exporter, and documents security properties informed by multiple formal analyses. ZK-ARCHE should benchmark AUTH against this baseline rather than merely citing EDHOC stylistically.
2. **CFRG's 2026 Fiat–Shamir draft gives a timely audit reference for ZK-ARCHE's custom transcript machinery**. The current Rust implementation uses an append-only custom encoding plus SHA-512 wide reduction for Schnorr challenges; the CFRG draft explicitly specifies codecs, serialization, and stateful transcript absorption. This is a strong reason to perform a transcript/domain-separation review before AUTH transcript v3, not an instruction to change the wire format automatically.
3. **NIST SP 800-232 makes Ascon a standards-backed lightweight symmetric benchmark candidate** for constrained profiles. It should be measured against the current SHA-256/HMAC/ChaCha-oriented direction on actual MCU targets; no default-suite change is justified without Rust/C vectors and target measurements.
4. **BBS remains a credible selective-disclosure/unlinkable credential research candidate, but not an MCU baseline**. The active CFRG draft provides selective disclosure, unlinkable proofs, domain separation, and test vectors, but ZK-ARCHE still needs exact proof-size, pairing cost, RAM/flash, implementation, and review evidence before considering any role-credential migration.
5. **Current hybrid-PQ guidance reinforces the existing optional/edge-only posture**. CFRG's May 2026 hybrid-KEM draft defines combiners intended to retain security when either the PQ or traditional component remains secure; paired with ML-KEM standardization, it provides a better research basis, but ZK-ARCHE still lacks MTU, CPU, RAM, and transcript/downgrade measurements.

The strongest next step is therefore a bounded **benchmark + specification-assurance program** spanning R-001, R-002, R-003, and R-005. R-004 remains queued because the repo still has only symbolic skeletons and today's sources do not by themselves close model-to-code traceability.

## Findings

### 1. EDHOC is now a concrete AUTH benchmark, not merely a design analogy

- **Source:** RFC 9528, *Ephemeral Diffie-Hellman Over COSE (EDHOC)*
- **Primary link:** https://www.rfc-editor.org/rfc/rfc9528.html
- **Source type / venue:** IETF Standards Track RFC
- **Publication date:** March 2024
- **Verified claim:** RFC 9528 specifies a compact three-message authenticated ephemeral-DH exchange for constrained environments, requires an `EDHOC_Exporter`, binds negotiated/security-relevant material through transcript hashes, and publishes example total message sizes as low as 101 bytes for static-DH authentication with compact key identifiers. The RFC also states that prior EDHOC versions were formally analyzed and the specification was updated based on that work.
- **Problem addressed:** ZK-ARCHE currently references EDHOC as a maturity/compactness model but has no checked-in side-by-side wire, transcript, state-machine, or exporter benchmark.
- **Strongest distinct engineering idea:** define an apples-to-apples ZK-ARCHE AUTH benchmark against one or more EDHOC profiles, including total handshake bytes, number of flights, credential handling, exporter semantics, retransmission behavior, privacy properties, and exact target cost.
- **Evidence maturity:** externally-reviewed
- **Limitations / uncertainty:** EDHOC and ZK-ARCHE have different authorization/privacy goals. EDHOC does not provide ZK-ARCHE's custom role-membership proof, so message-size comparison must separate base authenticated key exchange from authorization-proof overhead. Published EDHOC examples are configuration-specific rather than universal maxima.
- **ZK-ARCHE inference:** R-001 should move from generic investigation to a benchmark task. A meaningful target is not "be smaller than EDHOC" but explain exactly what extra ZK-ARCHE bytes/cycles buy in privacy/role authorization and keep the constrained floor defensible.
- **Wire / RAM / CPU / dependency impact:** no immediate protocol change. Benchmarking requires exact serialized AUTH sizes, per-stage CPU, stack/heap, and code-size/dependency measurements. Optional CBOR/COSE work remains separate and should not be imported merely to imitate EDHOC.
- **Rust/C / vector compatibility impact:** compatible research only. Existing vectors remain untouched. A future exporter/channel-binding change would require versioned vectors and checkpoint review.
- **Recommended disposition:** benchmark

### 2. CFRG Fiat–Shamir work is a direct review reference for ZK-ARCHE transcript v3

- **Source:** `draft-irtf-cfrg-fiat-shamir-02`, *Fiat-Shamir Transformation*
- **Primary link:** https://datatracker.ietf.org/doc/draft-irtf-cfrg-fiat-shamir/
- **Source type / venue:** active CFRG Internet-Draft
- **Publication date:** 2026-03-02
- **Verified claim:** the draft defines a generic Fiat–Shamir construction using an explicit stateful duplex-sponge interface and defines codecs for mapping prover messages into the transcript domain, deriving verifier messages, and serializing the non-interactive argument string.
- **Problem addressed:** ZK-ARCHE currently has a custom append-only transcript encoding and multiple wire-stable domain separators whose security and serialization discipline are implementation-defined rather than specification-defined.
- **Strongest distinct engineering idea:** perform a field-by-field transcript audit using the CFRG draft as a checklist: typed encoding, unambiguous length framing, context/domain separation, prover/verifier message ordering, suite/profile/deployment binding, and explicit serialization semantics.
- **Evidence maturity:** concept
- **Limitations / uncertainty:** this is an Internet-Draft, not an RFC, and its duplex-sponge construction is not automatically a drop-in replacement for ZK-ARCHE's SHA-512-based challenge derivation. Changing transcript construction would be wire-breaking and could invalidate existing proofs/vectors.
- **ZK-ARCHE inference:** do **not** replace the current transcript because the draft exists. Instead, use it to review the current `Transcript` abstraction and AUTH transcript-v3 roadmap before deciding whether to preserve the current hash-based encoding, refine it, or introduce a versioned construction.
- **Wire / RAM / CPU / dependency impact:** audit-only has no runtime impact. Adopting a new transcript primitive could affect code size, state RAM, dependencies, and vectors and therefore requires constrained-target measurements.
- **Rust/C / vector compatibility impact:** current research is compatible. Any adopted transcript change would be a versioned breaking change across Rust, C, test vectors, proofs, KDF/key-confirmation, and formal models.
- **Recommended disposition:** reproduce

  required_next_evidence: "Transcript-v3 coverage matrix comparing every current Rust/C challenge/KDF/KC field and domain separator against an explicit specification and mutation tests"

### 3. NIST Ascon should become a measured constrained symmetric-profile candidate

- **Source:** NIST SP 800-232, *Ascon-Based Lightweight Cryptography Standards for Constrained Devices: Authenticated Encryption, Hash, and Extendable Output Functions*
- **Primary link:** https://csrc.nist.gov/pubs/sp/800/232/final
- **Source type / venue:** final NIST Special Publication
- **Publication date:** 2025-08-13
- **Verified claim:** NIST standardized Ascon-AEAD128, Ascon-Hash256, Ascon-XOF128, and Ascon-CXOF128 specifically as lightweight cryptographic primitives for constrained devices and embedded/IoT environments.
- **Problem addressed:** ZK-ARCHE's roadmap correctly requires hardware/profile-specific evidence, but its conservative symmetric direction is not yet compared against the finalized NIST lightweight standard on target MCUs.
- **Strongest distinct engineering idea:** benchmark an **optional** Ascon-based symmetric/link profile against the current baseline, especially where AES hardware acceleration is absent or where code/RAM/energy characteristics favor lightweight permutation-based crypto.
- **Evidence maturity:** externally-reviewed
- **Limitations / uncertainty:** NIST standardization does not imply Ascon wins on every target. ESP32-S3, for example, exposes hardware AES/SHA/HMAC/RSA capabilities, so software Ascon can lose against accelerated platform primitives. ZK-ARCHE's Ristretto/Schnorr authorization layer is unaffected by Ascon standardization.
- **ZK-ARCHE inference:** add Ascon to the benchmark matrix, not the mandatory suite. Compare with the current ChaCha20-Poly1305/HMAC/SHA-oriented floor and any hardware-aligned AES profile by wire compatibility, cycles, stack/RAM, flash, energy if measurable, and implementation availability in Rust/C.
- **Wire / RAM / CPU / dependency impact:** potentially favorable on some constrained targets, but target-dependent. A suite addition would add implementation/dependency and negotiation costs.
- **Rust/C / vector compatibility impact:** benchmark-only is compatible. Adoption requires a new negotiated suite ID and deterministic cross-language vectors; it must not silently change existing suite `0x0001` semantics.
- **Recommended disposition:** benchmark

### 4. BBS is a stronger research comparator for private role credentials, but remains edge/research-only

- **Source:** `draft-irtf-cfrg-bbs-signatures-10`, *The BBS Signature Scheme*
- **Primary link:** https://datatracker.ietf.org/doc/draft-irtf-cfrg-bbs-signatures/
- **Source type / venue:** active CFRG research-group Internet-Draft
- **Publication date:** 2026-01-08
- **Verified claim:** the draft specifies multi-message BBS signatures supporting proof of knowledge, selective disclosure, and unlinkable zero-knowledge proofs; it also defines explicit API/domain-separation structure and includes test vectors. Datatracker continues to list revision `-10` as the active RG document, although that revision's nominal I-D expiry date was 2026-07-12.
- **Problem addressed:** ZK-ARCHE's custom role-set-membership proof needs independent review and currently provides a narrow membership property rather than a general reviewed selective-disclosure credential framework.
- **Strongest distinct engineering idea:** use BBS as an **external privacy and credential-functionality comparator** for R-002: quantify which privacy/authorization properties ZK-ARCHE gains or lacks versus BBS, then measure proof size, verification/proving CPU, RAM, flash, dependencies, and provisioning complexity.
- **Evidence maturity:** concept
- **Limitations / uncertainty:** BBS uses pairing-based cryptography and BLS12-381 ciphersuites, creating substantially different implementation and constrained-device costs than the current Ristretto-based proof stack. Active-draft status is not equivalent to a final RFC or production endorsement.
- **ZK-ARCHE inference:** BBS should not replace the MCU `iot-core` role proof. It is worth evaluating for gateway/edge or future optional privacy-credential suites, and it provides useful external semantics for selective disclosure and unlinkable presentations when reviewing the custom role proof.
- **Wire / RAM / CPU / dependency impact:** expected to be materially larger/more expensive than the current small Ristretto proof path, but exact ZK-ARCHE-relevant numbers still need measurement; pairing libraries also raise dependency and review surface.
- **Rust/C / vector compatibility impact:** no effect while research-only. Any future suite requires independent vectors and negotiated isolation from the constrained baseline.
- **Recommended disposition:** research-only

### 5. Hybrid PQ/T KEM work supports ZK-ARCHE's optional edge-only PQ posture

- **Sources:** `draft-irtf-cfrg-hybrid-kems-11`, *Hybrid PQ/T Key Encapsulation Mechanisms*; NIST FIPS 203, *Module-Lattice-Based Key-Encapsulation Mechanism Standard*
- **Primary links:** https://datatracker.ietf.org/doc/html/draft-irtf-cfrg-hybrid-kems-11 ; https://csrc.nist.gov/pubs/fips/203/final
- **Source type / venue:** active CFRG Internet-Draft plus final NIST FIPS
- **Publication dates:** 2026-05-07; 2024-08-13
- **Verified claim:** CFRG's current hybrid-KEM draft defines generic PQ/traditional hybrid KEM constructions intended to remain secure as long as either underlying algorithm remains secure. FIPS 203 standardizes ML-KEM as NIST's module-lattice KEM.
- **Problem addressed:** ZK-ARCHE has an optional PQ roadmap track but needs a current combiner model and concrete standardized KEM basis rather than ad hoc concatenation or an unspecified "hybrid" label.
- **Strongest distinct engineering idea:** if ZK-ARCHE prototypes PQ, base the research harness on a current hybrid construction and make downgrade/transcript binding, ciphertext/public-key bytes, fragmentation/MTU behavior, CPU/RAM, and resumption implications explicit.
- **Evidence maturity:** externally-reviewed
- **Limitations / uncertainty:** the hybrid construction is still an Internet-Draft, and ZK-ARCHE currently has no evidence that PQ handshake sizes fit constrained UDP/MCU goals. NIST's ML-KEM publication page also carries an errata planning note, reinforcing the need to pin exact versions/spec text in any experiment.
- **ZK-ARCHE inference:** R-003 should move to benchmark status for an edge/gateway-only harness. No MCU baseline or mandatory-suite promotion is justified.
- **Wire / RAM / CPU / dependency impact:** likely substantial due to ML-KEM key/ciphertext material plus the traditional component; exact numbers must be measured against ZK-ARCHE datagram caps and target profiles.
- **Rust/C / vector compatibility impact:** research-only until a new isolated suite is defined. Any adopted hybrid profile requires downgrade-safe negotiation, explicit transcript binding, versioned deterministic vectors, and both Rust/C implementations before interoperability claims.

### 6. ESP32-S3 hardware capabilities make target-specific benchmarking mandatory

- **Sources:** Espressif ESP-IDF / Product Security documentation for ESP32-S3 HMAC, digital signature, and crypto features
- **Primary links:** https://docs.espressif.com/projects/esp-idf/en/latest/esp32s3/api-reference/peripherals/hmac.html ; https://docs.espressif.com/projects/esp-product-security/en/latest/security-features.html ; https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-reference/peripherals/ds.html
- **Source type / venue:** official vendor documentation
- **Source checked:** 2026-08-15
- **Verified claim:** ESP32-S3 provides hardware support including AES/SHA/RSA-class acceleration and an HMAC accelerator backed by eFuse-resident keys; its RSA Digital Signature peripheral can perform signing without exposing the protected private-key material to software.
- **Problem addressed:** generic "constrained" benchmarks can produce wrong design conclusions when hardware acceleration, key storage, and secure-boot/eFuse capabilities differ significantly by target.
- **Strongest distinct engineering idea:** define R-005 benchmark profiles that explicitly separate pure-software portable crypto from hardware-assisted platform profiles and record which security assumptions move into eFuse/accelerator/secure-boot boundaries.
- **Evidence maturity:** deployed
- **Limitations / uncertainty:** these accelerators do not directly accelerate ZK-ARCHE's Ristretto255 proof path. Hardware-backed RSA identity is a different primitive/profile and should not become a hidden dependency. Vendor capability documentation is not ZK-ARCHE benchmark evidence.
- **ZK-ARCHE inference:** the MCU benchmark harness should record hardware acceleration enabled/disabled, compiler and ESP-IDF version, RNG source, eFuse/HMAC usage, secure-boot/flash-encryption state, and whether long-term secrets are software-readable. This is necessary for reproducible security/performance claims.

- **Rust/C / vector compatibility impact:** no wire impact for benchmarking. Hardware-backed storage/acceleration adapters must preserve canonical vectors and protocol semantics.

## Cross-source synthesis

### Corroborated conclusions

- **Specification discipline is now the most leverageable assurance improvement.** EDHOC's mature transcript/exporter/state-machine treatment and CFRG's explicit Fiat–Shamir serialization work both reinforce ZK-ARCHE's existing zk217/zk226 direction. The current implementation already has transcript structure, but the normative spec is behind the code.
- **Constrained efficiency must be measured per target, not inferred from algorithm labels.** NIST standardized Ascon specifically for constrained environments, while ESP32-S3 exposes strong AES/SHA/HMAC hardware. The correct outcome can differ by MCU and build profile.
- **Advanced credentials and PQ belong behind suite/profile isolation.** BBS and hybrid PQ/T KEM work are technically relevant and more mature as external references than generic research ideas, but neither currently justifies changing `iot-core` or `p2p-iot-core`.
- **ZK-ARCHE should explain its incremental privacy/authorization cost relative to mature AKE baselines.** EDHOC's published compact examples make this measurable.

### Unresolved assumptions

- No checked-in ZK-ARCHE report currently establishes exact AUTH_1/AUTH_2/AUTH_3 total bytes, peak stack/heap, MCU latency, or energy on STM32/ESP32-S3.
- The custom role-membership proof still requires independent cryptographic review; BBS provides a comparator, not validation of the custom proof.
- The custom transcript's security is not invalidated by CFRG's Fiat–Shamir draft, but its specification/domain-separation discipline needs explicit review and mutation coverage.
- No evidence yet shows Ascon outperforming the existing baseline on ZK-ARCHE's declared targets.
- No evidence yet shows a hybrid PQ/T profile fitting the datagram and low-SWaP constraints required by the constrained floor.
