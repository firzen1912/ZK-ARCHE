## 1. Executive synthesis

1. **The new resumption contract appears to conflate retained binding identity with fresh channel-binding evidence.** It currently requires exact equality of `channel_binding_context` between the retained record and current authority. TLS 1.3 resumption, however, establishes a new connection with a new handshake and unique per-connection keys; RFC 9266 defines TLS channel binding as identifying a specific TLS connection. A safe ZK-ARCHE resumption design should therefore retain the *binding policy/peer/application requirements* from the predecessor association but require fresh binding evidence for the resumed association. Reusing the predecessor binding bytes should not be the normal success condition.
2. **`key_epoch` needs a similar two-axis treatment.** A resumption credential may be derived from predecessor key lineage, but successful resumption should create fresh traffic/session keys. The retained record needs to identify the credential's derivation/lineage generation while the new association independently establishes a new current traffic-key epoch. Exact equality between predecessor issuance key epoch and post-resumption traffic-key state would either reject legitimate fresh-key resumption or encourage stale key-state reuse.
3. **Per-ticket expiry and `max_uses` are not sufficient to bound a resumption chain.** RFC 9846 explicitly warns that repeatedly issuing new tickets can indefinitely extend keying material originally tied to an older full authentication and recommends a total-lifetime limit. ZK-ARCHE should eventually retain an origin/full-AUTH lineage anchor and a non-resettable cumulative lifetime/re-authentication bound across replacement resumption credentials.
4. These findings refine R-009/R-010 and TD-003/TD-004. They do not change the wire format, specification, roadmap, implementation, formal proof status, or maturity claims. Promotion requires explicit human review.

### D20260911-F01 — Rebind resumption to fresh current channel evidence, not predecessor binding bytes

- **Novelty:** refines
- **Sources:** RFC 9846, *The Transport Layer Security (TLS) Protocol Version 1.3*; RFC 9266, *Channel Bindings for TLS 1.3*; RFC 9813, *Operational Considerations for Using TLS Pre-Shared Keys with RADIUS*
- **Primary links:** https://www.rfc-editor.org/rfc/rfc9846.html ; https://www.rfc-editor.org/rfc/rfc9266.html ; https://www.rfc-editor.org/rfc/rfc9813.html
- **Source type / venue:** IETF Standards Track / operational RFCs
- **Publication / release date:** RFC 9846 — June 2026; RFC 9266 — July 2022; RFC 9813 — May 2026
- **Verified claim:** TLS 1.3 resumption uses a PSK established by a previous connection to establish a **new connection**. RFC 9846 requires binder validation in the new handshake and states that distinct handshakes produce distinct, unrelated session keys. RFC 9266 defines channel-binding uniqueness in terms of a specific TLS connection. RFC 9813 requires authorization/policy decisions affected by changed information to be reevaluated on resumption and requires full authentication if a safe decision cannot be made.
- **Existing owner:** R-010 / R-009 / TD-004
- **Repository fact:** `spec/resumption-lifecycle.md` currently includes `channel_binding_context` in the retained record and requires exact equality with current authority, while also saying a changed required channel binding rejects resumption.
- **Problem addressed:** exact predecessor/current channel-binding equality can be the wrong invariant when resumption intentionally creates a fresh channel. It risks either making correct fresh-channel resumption impossible or encouraging reuse of stale predecessor binding evidence.
- **Strongest distinct engineering idea:** split retained binding state into (a) stable binding **requirements/identity**—peer, holder, application/service/deployment/profile and required binding mode—and (b) fresh **binding evidence** for the resumed association. The new association must satisfy the retained requirements using its own current channel evidence; predecessor binding bytes must not be treated as current proof merely because the resumption credential is valid.
- **Evidence maturity:** externally-reviewed standards; ZK-ARCHE implication is concept/spec research
- **Limitations / uncertainty:** ZK-ARCHE resumption is not required to copy TLS PSK resumption. A future native resumption mode may define different binding inputs. The invariant is transport-neutral: fresh resumed association evidence should be current for that association, while predecessor policy identity remains continuity context.
- **ZK-ARCHE relevance:** directly affects the new resumption logical contract and its interaction with the TLS-exporter binding work from September 10.
- **Wire / CPU / RAM / flash / dependency / trust/privacy impact:** potentially wire-neutral if binding evidence is adapter-local. Small bounded state increase if predecessor binding-policy identity and current binding evidence are represented separately. No new infrastructure dependency. Privacy improves if connection-specific binding material is not promoted to a stable cross-connection identifier.
- **Rust/C / vector/profile compatibility impact:** future shared corpus should include predecessor binding valid + fresh resumed binding valid (accept), stale predecessor binding reused as current evidence (reject), current binding missing/stale (reject), and application/deployment/profile mismatch despite cryptographically fresh channel evidence (reject).
- **Required next evidence:** transport-neutral resumption binding-state schema; TLS adapter fixture using a predecessor resumption credential plus new connection exporter/binding evidence; Rust/C decision parity; full-AUTH fallback case.
- **Recommended disposition:** reproduce

### D20260911-F02 — Separate resumption credential lineage from new traffic-key epoch

- **Novelty:** refines
- **Source:** RFC 9846, *The Transport Layer Security (TLS) Protocol Version 1.3*
- **Primary link:** https://www.rfc-editor.org/rfc/rfc9846.html
- **Source type / venue:** IETF Standards Track RFC
- **Publication / release date:** June 2026
- **Verified claim:** TLS 1.3 resumption PSKs bootstrap a unique per-connection set of short-term session keys. The resumption secret needed for connection N+1 is separate from connection N traffic keys, and PSK with asymmetric key establishment can provide forward secrecy for the new session keys. The PSK binder ties the prior PSK lineage to the current handshake.
- **Existing owner:** R-009 / TD-003 / TD-004
- **Repository fact:** the retained ZK-ARCHE resumption record contains one `key_epoch`, current authority supplies one `key_epoch`, exact equality is required, and a key-epoch/rekey replacement invalidates predecessor records unless a later reviewed transition is defined.
- **Problem addressed:** one integer can accidentally conflate the generation from which a resumption credential was derived with the traffic-key generation that should result from successful resumption.
- **Strongest distinct engineering idea:** model at least two lifecycle facts: `resumption_derivation_generation` (which predecessor key/authentication lineage authorized issuance of the credential) and `association_key_generation_current` (the fresh traffic-key generation established by the new association). Resumption eligibility validates the former; successful resumption establishes/advances the latter. A credential from stale/revoked derivation lineage still fails closed.
- **Evidence maturity:** externally-reviewed standard plus concept-level ZK-ARCHE mapping
- **Limitations / uncertainty:** exact fields/names depend on the eventual native wire/KDF design. This report does not prescribe TLS's key schedule or require PSK-DHE.
- **ZK-ARCHE relevance:** prevents a future resumption implementation from either reusing predecessor traffic keys or rejecting every mechanism that correctly derives fresh traffic keys.
- **Wire / CPU / RAM / flash / dependency / trust/privacy impact:** one additional bounded lineage/currentness distinction; no mandatory external dependency. Fresh traffic keys improve compartmentalization; optional asymmetric re-establishment has CPU/wire cost that must be profile-measured.
- **Rust/C / vector/profile compatibility impact:** add vectors for current derivation lineage + fresh new key generation (accept), stale derivation lineage (reject), predecessor traffic key reused without reviewed semantics (reject), and full-AUTH/rekey invalidation.
- **Required next evidence:** normative key-lineage state machine before wire allocation; shared Rust/C lifecycle corpus; formal event mapping for credential issuance, resume acceptance, and new association key establishment.
- **Recommended disposition:** reproduce

### D20260911-F03 — Bound cumulative resumption lineage lifetime across credential replacement

- **Novelty:** refines
- **Sources:** RFC 9846, *TLS 1.3*; RFC 9190, *EAP-TLS 1.3*
- **Primary links:** https://www.rfc-editor.org/rfc/rfc9846.html ; https://www.rfc-editor.org/rfc/rfc9190.html
- **Source type / venue:** IETF Standards Track RFCs
- **Publication / release date:** June 2026 / February 2022
- **Verified claim:** RFC 9846 notes that repeatedly issuing new tickets can indefinitely extend keying material originally derived from an earlier non-PSK authentication and recommends limiting the **total lifetime** of that lineage, considering credential lifetime, revocation likelihood, and time since online authentication. EAP-TLS also requires enough cached original-handshake information to make authorization decisions during resumption and forbids resumption if that state cannot be retrieved securely.
- **Existing owner:** R-009 / R-012 / TD-004
- **Repository fact:** the new ZK-ARCHE resumption contract correctly requires per-record `issued_at`, `expires_at`, `use_count`, finite `max_uses`, generation/rollback checks, and invalidation on upstream authority changes. It does not yet define a non-resettable origin/full-AUTH lineage age or cumulative replacement lifetime across newly issued successor resumption credentials.
- **Problem addressed:** an implementation could satisfy every per-ticket lifetime/use bound yet continuously mint successor credentials and preserve authority indefinitely without a fresh full authentication/possession proof.
- **Strongest distinct engineering idea:** retain an immutable or monotonically constrained `origin_auth_generation` / `origin_authenticated_at` / `lineage_not_after` equivalent that successor resumption credentials cannot reset. Require full AUTH (or another explicitly reviewed strong reauthentication event) when the cumulative lineage bound is reached.
- **Evidence maturity:** externally-reviewed standards; ZK-ARCHE mapping remains concept/spec research
- **Limitations / uncertainty:** constrained devices without trusted wall clocks may need a monotonic generation/lease model instead of absolute time. Exact duration is deployment/profile policy and should not be invented by this report.
- **ZK-ARCHE relevance:** strengthens the existing bounded-reuse design without making online infrastructure mandatory and composes naturally with revocation/policy generations.
- **Wire / CPU / RAM / flash / dependency / trust/privacy impact:** small persistent metadata cost; may increase full-AUTH frequency. No online dependency is required if the peer has a rollback-safe monotonic lifetime/generation source. Avoid exposing the origin identifier on wire to reduce linkability.
- **Rust/C / vector/profile compatibility impact:** future corpus should prove successor issuance does not reset lineage age/budget; boundary case forces full AUTH; restart/rollback cannot extend lineage; revocation/policy updates still invalidate earlier.
- **Required next evidence:** storage-neutral cumulative-lineage lifetime semantics for clocked and clockless targets; Rust/C replacement corpus; rollback test; constrained flash-write and full-AUTH frequency benchmark.

## 5. Cross-source synthesis

The resumption contract should eventually distinguish predecessor continuity from new-association freshness:

```text
prior authenticated association
        ↓
resumption credential
├─ peer / holder / audience / scope / policy lineage
├─ derivation generation
├─ replay + rollback continuity
├─ finite per-credential reuse/lifetime
└─ non-resettable origin/full-AUTH lineage bound
        ↓
new resumption attempt
├─ re-evaluate current authority
├─ validate credential lineage
├─ establish fresh current channel binding evidence
└─ establish fresh current traffic/session key state
        ↓
resumed authenticated association
```

This avoids two dangerous substitutions: predecessor channel evidence is not current channel evidence, and predecessor traffic-key state is not the new association's traffic-key state. At the same time, fresh keys/channel evidence do not erase predecessor authorization/revocation/replay lineage; both dimensions must succeed.
