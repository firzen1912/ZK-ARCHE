# ZK-ARCHE Research — 2026-08-16

## Executive synthesis

Today’s repo-first review points to a narrower and more actionable priority than adding new cryptographic primitives: **make ZK-ARCHE’s profile negotiation, enrollment/rekey lifecycle, and assurance evidence as explicit and testable as the protocol’s current proof machinery**.

Four findings matter most:

1. **EDHOC Application Profiles revision -05 (6 July 2026) gives ZK-ARCHE a concrete model for profile semantics.** It defines canonical profile representations, integer profile IDs, in-session profile advertisement, prescriptive versus non-prescriptive parameters, and fail-closed behavior when a peer violates a prescriptive profile. ZK-ARCHE already has capability bits and local `ProfileKind` values, but its Rust `Negotiated` result returns only version, suite, and intersected capability bits; it does not explicitly select and bind a profile. This deserves a profile-negotiation/transcript audit before the RFC-style spec hardens.
2. **KUDOS provides a detailed constrained rekey state-machine comparator.** The March 2026 OSCORE key-update draft covers peer-initiated rekey, forward-secret and no-forward-secret modes, temporary/new/old contexts, reboot recovery, non-volatile storage limitations, lost-message behavior, and replay-window/sequence reset. ZK-ARCHE’s zk213 rekey direction should be reviewed against these lifecycle failure modes rather than only specifying “authenticate old and new keys.”
3. **Remote Attestation over EDHOC revision -06 (6 July 2026) shows how integrity evidence can be layered into a constrained authenticated session without redefining the base authentication protocol.** It carries EAT-based evidence/results through extension fields, binds evidence to the handshake/exporter, supports both initiator and responder attestation, and separates Attester/Verifier/Relying-Party roles. This is relevant to ZK-ARCHE’s future device-trust posture, but should remain optional/research-only until trust-root, privacy, packet-size, verifier, and MCU costs are measured.
4. **R-004 can move from `queued` to `reproduce`.** Tamarin 1.12 was released on 8 March 2026, while ZK-ARCHE still has only a highly abstract ProVerif skeleton. The immediate next step is not a claim of formal verification; it is a reproducible property/model matrix that matches the actual AUTH state machine, replay/retransmission semantics, negotiation, and transcript boundaries.

The main research action is therefore to tighten R-001 and R-004 and add one bounded research-only question for attestation. No evidence found today justifies changing the mandatory cryptographic suite, making remote attestation mandatory, or promoting a new release/maturity claim.

## Findings

### 1. EDHOC Application Profiles -05 is a direct model for ZK-ARCHE profile negotiation and downgrade discipline

- **Source:** `draft-ietf-lake-app-profiles-05`, *Coordinating the Use of Application Profiles for Ephemeral Diffie-Hellman Over COSE (EDHOC)*
- **Primary link:** https://datatracker.ietf.org/doc/html/draft-ietf-lake-app-profiles-05
- **Source type / venue:** IETF LAKE Working Group Internet-Draft, intended Standards Track
- **Publication date:** 2026-07-06
- **Verified claim:** revision -05 defines a canonical CBOR representation for EDHOC application profiles, integer Profile IDs, profile discovery/advertisement mechanisms, and explicit semantics for prescriptive versus non-prescriptive parameters. During an EDHOC session, supported profiles can be advertised in early messages; a peer must abort when a prescriptive parameter is violated. The revision also includes coordination for session resumption with EDHOC-PSK and exporter output lengths.
- **Problem addressed:** ZK-ARCHE currently has three overlapping concepts that are not yet normatively unified: capability bits in `caps.rs`, runtime `ProfileKind` resource limits in `profile.rs`, and protocol-profile names in `spec/iot-profiles.md`. The current `Negotiated` object does not return an explicit selected profile.
- **Strongest distinct engineering idea:** separate **capability negotiation** from **profile selection**, give stable protocol profiles explicit identifiers, define which profile parameters are prescriptive, and transcript-bind the selected profile plus every prescriptive security parameter. Unknown/unsupported or violated prescriptive parameters should fail deterministically rather than silently collapsing to capability intersection.
- **Evidence maturity:** concept
- **Limitations / uncertainty:** the source is still an Internet-Draft and uses CBOR/EDHOC-specific structures. ZK-ARCHE does not need to adopt CBOR or copy EDHOC’s registry. The value is the negotiation discipline, not the encoding.
- **ZK-ARCHE inference:** before AUTH transcript v3 and RFC-style profile specification are finalized, create a matrix that distinguishes (a) build/runtime resource profile, (b) negotiated security profile, and (c) optional capability bits. Decide whether `iot-core`, `p2p-iot-core`, `iot-edge`, and future profiles require stable wire IDs and an explicit `selected_profile` in negotiation state. A high-end peer should not be able to advertise broad capabilities and then accidentally execute semantics inconsistent with the constrained profile selected for the session.
- **Wire / RAM / CPU / dependency impact:** explicit profile IDs can be very small on wire; the main cost is state/spec/test complexity, not cryptographic CPU. No new dependency is required if native TLV encoding is retained.
- **Rust/C / vector compatibility impact:** research-only now. A future explicit profile field or transcript binding may be wire-compatible if introduced through an existing extension point, or versioned-breaking if inserted into existing canonical transcript bytes. Both Rust and C plus deterministic vectors would need synchronized changes.
- **Recommended disposition:** reproduce

### 2. KUDOS supplies the missing lifecycle failure model for authenticated rekey

- **Source:** `draft-ietf-core-oscore-key-update-13`, *Key Update for OSCORE (KUDOS)*
- **Primary link:** https://datatracker.ietf.org/doc/html/draft-ietf-core-oscore-key-update-13
- **Source type / venue:** IETF CoRE Working Group Internet-Draft, intended Standards Track
- **Publication date:** 2026-03-02
- **Verified claim:** KUDOS defines a lightweight key-update procedure with explicit old, temporary, and new security contexts; either peer can initiate; the stateful mode provides forward secrecy; the draft defines a state machine, lost/divergent-message handling, reboot behavior, context retention, replay-window and sequence-number reinitialization, and a no-forward-secrecy mode for devices that cannot safely persist state to non-volatile memory.
- **Problem addressed:** ZK-ARCHE zk213 already requires authenticated rekey/re-registration and atomic revocation/tombstoning, but the roadmap does not yet spell out all interrupted-transition states, in-flight message handling, reboot recovery, or constrained non-volatile-storage tradeoffs.
- **Strongest distinct engineering idea:** model rekey as a **transactional state machine**, not just a cryptographic exchange. Define OLD/PENDING(or TEMP)/NEW ownership, commit point, rollback/abort behavior, late packet handling, replay-window reset, crash/reboot recovery, simultaneous initiation policy, and explicit rules for when application traffic is blocked or accepted during transition.
- **Evidence maturity:** concept
- **Limitations / uncertainty:** KUDOS updates OSCORE contexts, not ZK-ARCHE registry credentials. Its exact fields and state names are not directly reusable. The no-FS fallback may be unacceptable for some ZK-ARCHE profiles.
- **ZK-ARCHE inference:** zk213/zk214 should eventually have negative tests for crash-before-commit, crash-after-commit, duplicate rekey messages, simultaneous rekey, old-session packet arrival, stale epoch restoration, partial persistent writes, and rollback to a tombstoned credential. For `iot-core`, the design must explicitly state what persistent writes are required and what happens on boards without safe dynamic NVM updates.
- **Wire / RAM / CPU / dependency impact:** the cryptographic overhead depends on the chosen rekey protocol, but the key engineering costs are bounded additional state, persistent metadata/epochs, and response-cache/late-packet handling. No dependency change is implied by this research.
- **Rust/C / vector compatibility impact:** no immediate impact. Any future rekey messages/state require new message/vector coverage in both lanes and should not mutate existing AUTH vectors silently.
- **Recommended disposition:** reproduce

### 3. Remote Attestation over EDHOC -06 provides a bounded pattern for adding device-integrity evidence without replacing authentication

- **Source:** `draft-ietf-lake-ra-06`, *Remote attestation over EDHOC*
- **Primary link:** https://datatracker.ietf.org/doc/html/draft-ietf-lake-ra-06
- **Source type / venue:** IETF LAKE Working Group Internet-Draft, intended Standards Track
- **Publication date:** 2026-07-06
- **Verified claim:** revision -06 integrates RATS-style remote attestation with EDHOC while keeping the EDHOC authentication flow intact. It supports initiator or responder attestation, background-check and passport models, EAT-based evidence/results, freshness nonces, and handshake/exporter binders. It explicitly separates Attester, Verifier, and Relying Party roles and includes re-attestation considerations.
- **Problem addressed:** ZK-ARCHE authenticates possession of enrolled cryptographic material and role membership, but that does not establish that the running firmware/device state is trustworthy. A compromised device can legitimately possess its key.
- **Strongest distinct engineering idea:** treat attestation as **optional evidence bound to an authenticated session**, not as a replacement credential or a new trust root hidden inside AUTH. Keep the verifier role logically separate, bind attestation evidence/result to the session transcript or exported key context, and let policy decide whether a given profile requires it.
- **Evidence maturity:** concept
- **Limitations / uncertainty:** remote attestation introduces hardware/root-of-trust assumptions, verifier/reference-value infrastructure, evidence-format dependencies, freshness/time assumptions, privacy risks, and potentially large packets. The draft is not a final RFC. Many STM32/ESP32 deployments will not have a strong attestation root or standardized evidence service.
- **ZK-ARCHE inference:** remote attestation is worth tracking for `iot-edge`, gateway, or explicitly attestation-capable MCU deployments, particularly where device compromise is in the threat model. It should **not** become mandatory for `iot-core` or be treated as proof that software is uncompromised without a defined root of trust and appraisal policy.
- **Wire / RAM / CPU / dependency impact:** potentially substantial and evidence-format dependent; EAT/CBOR parsing, signatures, evidence payloads, verifier communication, and reference-value handling add code/RAM/wire cost. A compact result/passport can be cheaper than transporting raw evidence but adds trust in the verifier.
- **Rust/C / vector compatibility impact:** none while research-only. A future extension should be profile-negotiated, isolated from baseline AUTH vectors, and transcript/channel bound with independent negative vectors for stale/wrong-session/wrong-verifier evidence.
- **Recommended disposition:** research-only

## Cross-source synthesis

The sources converge on one architectural lesson: mature constrained-security protocols increasingly treat **profile, lifecycle, authorization, and evidence semantics as first-class protocol state**, not as implementation-side configuration.

For ZK-ARCHE, this does not argue for copying EDHOC/OSCORE. It does argue for making currently implicit boundaries explicit:

- capability support is not the same as selecting a security profile;
- selecting a profile should determine prescriptive behavior that is transcript-bound and fail-closed;
- rekey is not complete until crash/reboot/concurrency/late-packet state is specified;
- authentication of a key does not prove platform integrity, so optional attestation must remain a separate evidence layer;
- formal models need a claim-to-code mapping or they risk validating an abstraction that omits the actual dangerous state transitions.

There is also a useful compatibility discipline across all four findings: none requires changing suite `0x0001` now. Each can first be evaluated through state tables, mutation/negative tests, model traces, and benchmark harnesses without destabilizing canonical Rust/C vectors.
