## 2. Executive synthesis

- **Current sender/channel proof is not current authorization.** NIST IR 8587 treats proof-of-possession/sender constraining, revocation, advanced authorization, validity length, audience restriction, and session analysis as complementary controls. RFC 9449 likewise defines DPoP as sender-constraining a token to a proof key. ZK-ARCHE should preserve its existing architecture in which channel binding cannot refresh authorization generation, revocation state, lineage, or policy.
- **Revocation convergence is a temporal security property, not only a Boolean state.** RFC 9770 explicitly identifies the vulnerable period between authorization revocation and a constrained resource server learning that revocation, and requires implementers to trade polling frequency against the maximum vulnerable window. NIST IR 8587 additionally says connected relying parties that receive revocation status must reject revoked tokens and terminate associated active sessions. ZK-ARCHE therefore needs measured connected propagation/application latency and an explicit disconnected stale-authority bound per profile.
- **Short authority lifetime caps residual risk but does not replace revocation.** NIST recommends defined short token lifetimes and uses refresh/reauthentication, revocation, proof of possession, and session analysis together. For ZK-ARCHE, a profile-level lifetime/generation budget can cap stale authority when revocation updates cannot arrive, but expiration must not be represented as equivalent to timely revocation and must not silently reset replay, lineage, or authorization generations.
- **The repository is already directionally correct.** Current association admission and DATA release independently gate binding, authorization-generation currentness, revocation, lineage, replay/restart/rollback continuity, and lifecycle state. Current resumption distinguishes recoverable full-auth fallback from terminal retained-authority failures. Research therefore refines qualification evidence rather than authorizing protocol rewrites.
- **No status promotion is justified.** R-012 and R-010 remain `reproduce`. No roadmap, spec, ADR, code, test, formal model, CI, issue, PR, or release change is authorized by this report.

### D20260922-F01 — Sender/channel binding currentness is independent from authorization/revocation currentness

- **Novelty:** refines
- **Backlog owner:** R-010 / R-012
- **Source:** NIST IR 8587, *Protecting Tokens and Assertions from Forgery, Theft, and Misuse*; RFC 9449, *OAuth 2.0 Demonstrating Proof of Possession (DPoP)*; RFC 8705, *OAuth 2.0 Mutual-TLS Client Authentication and Certificate-Bound Access Tokens*
- **Primary link:** <https://csrc.nist.gov/pubs/ir/8587/final>; <https://www.rfc-editor.org/rfc/rfc9449.html>; <https://www.rfc-editor.org/rfc/rfc8705.html>
- **Source type / venue:** final NIST Interagency Report; IETF Standards Track RFCs
- **Publication or release date:** NIST IR 8587 final 15 September 2026; RFC 9449 September 2023; RFC 8705 February 2020
- **Verified claim:** NIST IR 8587 lists proof-of-possession/sender constraining alongside, rather than in place of, revocation, advanced authorization, compromise/session analysis, audience restriction, and token lifetime controls. Its token-management guidance recommends combinations of revocation and proof-of-possession where possible. RFC 9449 defines DPoP as binding token use to possession of a key so that leaked/stolen tokens are harder to replay by another presenter; RFC 8705 provides the corresponding certificate-bound/mTLS sender-constraining model.
- **Existing engineering owner:** R-010 for current channel-binding evidence; R-012 for authorization/revocation freshness
- **Repository fact:** current ZK-ARCHE association and DATA-release decisions already model channel-binding validity separately from authorization-generation currentness, revocation, lineage, replay/restart/rollback continuity, and lifecycle state.
- **Problem addressed:** a system can have a perfectly current channel or holder proof for an actor whose authorization was revoked, whose policy generation is stale, or whose retained lineage is no longer authoritative. Treating binding refresh as authority refresh would collapse separate trust domains.
- **Strongest distinct engineering idea:** retain a conjunctive authority gate rather than a composite `authenticated == authorized` flag: `binding_current && authz_generation_current && revocation_current && lineage_current && policy/audience_current && replay/lifecycle_current` before protected use.
- **Evidence maturity:** authoritative guidance + standards comparator; repository implementation/state evidence exists but deployment-level qualification is incomplete
- **Limitations / uncertainty:** NIST IR 8587 primarily targets token/assertion systems and federal/cloud use cases, while ZK-ARCHE does not require OAuth tokens. DPoP and mTLS are comparators for sender-constraining semantics, not required ZK-ARCHE mechanisms.
- **ZK-ARCHE inference:** `BIND`/TLS-exporter proof or any future sender-constrained credential can establish that the current presenter owns the expected channel/key context, but must not advance authorization generation, clear revocation, repair lineage, reset replay continuity, or make a stale policy current.
- **Wire / RAM / CPU / flash / dependency / trust-model/privacy impact:** no new wire bytes are inherently required because the separation can remain local state. CPU is a small constant-time set of currentness checks relative to cryptographic verification. RAM is a bounded set of generation/status fields; flash cost exists only where currentness must survive restart. No new mandatory online dependency follows. Trust semantics materially improve by preventing possession/binding from becoming a universal authority oracle. Privacy impact is neutral if no new stable identifier is introduced.
- **Rust/C / vector / profile compatibility impact:** shared vectors should continue to prove both directions: current binding + revoked/stale authorization => deny; current authorization + stale/invalid binding => deny. Add explicit cross-product cases where full AUTH or channel rebinding succeeds after a revocation update and DATA remains denied until a new authorized generation is explicitly established.
- **Required next evidence:** exact-head Rust/C cross-product corpus covering binding refresh versus revocation/authz-generation transitions; model-to-runtime trace; target profile measurements showing the checks are retained under constrained builds.
- **Recommended disposition:** reproduce

### D20260922-F02 — Revocation convergence needs an explicit measured propagation and stale-authority budget

- **Novelty:** refines
- **Backlog owner:** R-012
- **Source:** RFC 9770, *Notification of Revoked Access Tokens in the Authentication and Authorization for Constrained Environments (ACE) Framework*; NIST IR 8587
- **Primary link:** <https://www.rfc-editor.org/rfc/rfc9770.html>; <https://csrc.nist.gov/pubs/ir/8587/final>
- **Source type / venue:** IETF Standards Track RFC / ACE; final NIST Interagency Report
- **Publication or release date:** RFC 9770 June 2025; NIST IR 8587 final 15 September 2026
- **Verified claim:** RFC 9770 explicitly identifies a vulnerable time window in which a constrained resource server can continue accepting a token after revocation but before learning the update. If polling is used, it recommends an adequate trade-off between polling frequency and the maximum vulnerable window. It also supports CoAP observation for revocation updates. NIST IR 8587 says token services should propagate revocation status to relying parties and, where that capability exists, connected relying parties must reject revoked tokens and terminate active sessions associated with them.
- **Existing engineering owner:** R-012; R-005 when hardware/storage cost becomes profile-specific; R-004 if a bounded temporal/state abstraction is promoted into formal evidence
- **Repository fact:** R-012 already asks for full/diff revocation-view reconciliation, missed-update/offline reconnect behavior, and a maximum stale-authorization window per profile. Current Rust/C state vectors and temporal tests prove deterministic state behavior after a revocation/currentness input changes, but they do not measure how quickly a real constrained node receives, persists, and applies that change.
- **Problem addressed:** a Boolean `revocation_current` predicate hides the security-critical interval before it becomes false. A system can be logically fail-closed once an update is known yet still have an unbounded stale-authority window if propagation/application timing is never measured.
- **Strongest distinct engineering idea:** qualify revocation as an end-to-end freshness budget. Measure at least `T_detect` (authoritative change known), `T_publish` (available for distribution), `T_receive` (target receives), `T_apply` (local state becomes authoritative), and `T_enforce` (existing association/DATA authority can no longer succeed). Define `T_stale_connected = T_receive + T_apply + T_enforce` under a declared starting point, and separately define the maximum disconnected stale-authority budget rather than merging the two.
- **Evidence maturity:** standards-based concept; not yet measured for ZK-ARCHE targets
- **Limitations / uncertainty:** RFC 9770 is an ACE/CoAP revocation protocol, not a mandated ZK-ARCHE distribution mechanism. NIST's connected-RP guidance assumes a signaling/status capability exists. Actual bounds depend on topology, loss, sleep cycles, storage semantics, and profile policy.
- **ZK-ARCHE inference:** a profile should not claim bounded revocation merely because generation fields exist. It should state how currentness arrives, how missed updates reconcile, how active retained associations are invalidated, what happens while disconnected, and the measured or conservatively configured maximum stale-authority period.
- **Wire / RAM / CPU / flash / dependency / trust-model/privacy impact:** push/observe-style updates add background wire traffic; polling adds predictable request traffic and can amplify cost at short intervals. CPU is low for small generation/status updates but authentication/integrity verification remains mandatory. RAM can be `O(1)` for monotonic current-generation state or larger for explicit revoked-object sets; flash writes/endurance matter if revocation currentness must survive power loss/rollback. An external status authority creates availability/trust dependencies unless replicated or fail-closed. Update cadence and identifier-bearing queries can expose activity patterns, so privacy needs profile review.
- **Rust/C / vector / profile compatibility impact:** deterministic vectors should represent current generation/status and missed/out-of-order update behavior independent of transport. Integration benchmarks should inject a revocation/policy-generation transition while an authenticated retained association is actively releasing DATA, then measure time and packet count until all subsequent releases fail. Rust/C must produce the same terminal semantics after update application.
- **Required next evidence:** local/exact-head network harness with deterministic fault injection; connected propagation/application latency percentiles; disconnected/reconnect reconciliation; restart/rollback during stale/current transition; ESP32-S3/STM32 flash-write and memory measurements for the chosen metadata representation.
- **Recommended disposition:** reproduce / benchmark

### D20260922-F03 — Bounded authority lifetime caps disconnected residual risk but cannot substitute for revocation

- **Novelty:** refines
- **Backlog owner:** R-012 / R-009
- **Source:** NIST IR 8587; RFC 9770
- **Primary link:** <https://csrc.nist.gov/pubs/ir/8587/final>; <https://www.rfc-editor.org/rfc/rfc9770.html>
- **Source type / venue:** final NIST Interagency Report; IETF Standards Track RFC
- **Publication or release date:** NIST IR 8587 final 15 September 2026; RFC 9770 June 2025
- **Verified claim:** NIST IR 8587 recommends time-bounded tokens with short validity periods, tailored to risk, and treats refresh/reauthentication, revocation, sender constraining, proof of possession, and session analysis as complementary mechanisms. It notes that immediate global revocation is not always possible for stateless token systems and that short-lived authority can limit the time a compromised token remains useful. RFC 9770 independently shows why pre-expiry revocation still matters: an otherwise unexpired credential can become unauthorized before its nominal expiration.
- **Existing engineering owner:** R-012 for stale authorization/revocation bounds; R-009 for persistent lifecycle/generation continuity and restart/rollback behavior
- **Repository fact:** ZK-ARCHE already uses explicit authorization/revocation generations and fail-closed lifecycle predicates, and R-012 already asks for a maximum stale-authorization window. Clock quality, durable time, and rollback behavior remain target/profile evidence questions rather than universally qualified assumptions.
- **Problem addressed:** disconnected constrained devices cannot always receive a revocation update immediately. Without a bounded authority lifetime or mandatory re-synchronization point, stale but locally valid authority can persist indefinitely. Conversely, treating expiry alone as revocation would leave a large pre-expiry compromise window and obscure state propagation failures.
- **Strongest distinct engineering idea:** define a profile-specific residual-authority cap that is independent from revocation propagation. Where trustworthy time exists, this can be a short validity lease. On clock-poor devices, an authenticated monotonic generation/operation budget or mandatory synchronization/full-AUTH boundary may be safer than pretending wall-clock expiry is reliable. Expiration/budget exhaustion only terminates authority; it does not reset replay state, lineage, key-use accounting, or revocation history.
- **Evidence maturity:** authoritative guidance + standards comparator; ZK-ARCHE mechanism remains unselected
- **Limitations / uncertainty:** NIST's one-hour recommendation is for its token/assertion scope and must not be copied as a ZK-ARCHE constant. A generation budget is a ZK-ARCHE inference and requires independent protocol/security review. Devices without trustworthy time or rollback-resistant monotonic state may be unable to make a strong bounded-lifetime claim offline.
- **ZK-ARCHE inference:** each deployable constrained profile should declare either a qualified authority-lifetime mechanism or an explicit fail-closed resynchronization requirement. The reported stale-authority bound should be the stricter result of revocation-convergence behavior and local lifetime/budget policy, with assumptions stated.
- **Wire / RAM / CPU / flash / dependency / trust-model/privacy impact:** no wire cost for a purely local budget until refresh/synchronization is needed; shorter lifetime increases refresh/authentication traffic and cryptographic work. RAM is small; rollback-resistant counters or validity state can impose flash/NVM wear. An online refresh dependency reduces disconnected availability. Frequent refresh can increase observable traffic and correlation opportunities; profiles should measure that privacy/availability tradeoff.
- **Rust/C / vector / profile compatibility impact:** add boundary vectors for expiry/budget exhaustion before/after revocation arrival, restart near the boundary, rollback to earlier lifetime/generation state, fresh AUTH after exhaustion, and successful binding refresh that still does not revive expired/revoked authority. Profile fixtures must declare whether they depend on wall clock, monotonic generation, or mandatory resynchronization.
- **Required next evidence:** select candidate clock/generation semantics per profile; Rust/C differential boundary corpus; power-loss/rollback tests; constrained refresh/re-auth wire/CPU/energy measurements; privacy/availability analysis.
- **Recommended disposition:** reproduce / benchmark

## 6. Cross-finding engineering interpretation

Today's sources support a four-part separation that should remain visible in ZK-ARCHE assurance:

```text
holder/channel currentness
        ∧
authorization/policy generation currentness
        ∧
revocation view currentness
        ∧
local lifetime / synchronization budget currentness
        ↓
protected association / DATA authority
```

No one predicate repairs another. A fresh TLS exporter proof does not clear revocation. A current authorization generation does not repair a stale channel binding. A short local lifetime bounds residual risk but does not prove revocation propagation. Receiving a revocation update is not complete enforcement until retained association/DATA authority is actually invalidated.

For qualification, the useful new metric is not simply “revocation test passed” but a declared profile contract such as:

```text
connected stale-authority bound:
    authoritative change -> received -> applied -> enforced

disconnected stale-authority bound:
    min(local lifetime/budget, mandatory resynchronization boundary)

restart/rollback condition:
    stale state must not extend either bound
```

The exact mechanism remains an explicit human-reviewed engineering decision.

## 8. Human-review recommendations

If promoted later through the normal findings/requests process, reviewers should consider:

1. defining a **profile-specific revocation freshness budget** with connected and disconnected semantics;
2. requiring an active retained association to lose DATA authority within the connected enforcement budget after a revocation/authorization-generation update is applied;
3. keeping sender/channel binding, authorization generation, revocation, lineage, replay continuity, and local authority lifetime as independent predicates;
4. selecting either trustworthy-time expiry, monotonic generation/operation budgets, or mandatory re-synchronization for constrained offline profiles based on qualified target capabilities;
5. measuring flash/NVM endurance, power-loss behavior, network cost, and privacy leakage before making field-readiness claims.
