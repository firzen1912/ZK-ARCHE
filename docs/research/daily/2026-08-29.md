### D20260829-F01 — FM-06 should test peer-identity/credential misbinding while preserving valid possession/agreement

- **Novelty:** refines
- **Sources:** RFC 9528, *Ephemeral Diffie-Hellman Over COSE (EDHOC)*; `draft-ietf-lake-edhoc-psk-08`; `draft-ietf-lake-edhoc-impl-cons-07`
- **Primary links:** https://www.rfc-editor.org/rfc/rfc9528.html ; https://datatracker.ietf.org/doc/draft-ietf-lake-edhoc-psk/ ; https://datatracker.ietf.org/doc/draft-ietf-lake-edhoc-impl-cons/
- **Source type / venue:** IETF Standards Track RFC plus active LAKE WG Internet-Drafts
- **Publication or release dates:** RFC 9528 — March 2024; EDHOC-PSK -08 — June 16, 2026 (Datatracker latest revision); EDHOC implementation considerations -07 — July 6, 2026
- **Verified claim:** RFC 9528 treats endpoint subject/identity information in an authentication credential as specifically relevant to preventing misbinding attacks. EDHOC-PSK -08 requires Initiator and Responder credentials to be distinct and requires identity information in both credentials to prevent reflection/misbinding. The current EDHOC implementation-considerations draft separately requires the selected credential to be acceptable for the specific other-peer identity and session context. EDHOC implementation guidance also defines consistency checks when a credential can be supplied/referenced through more than one mechanism, with failure requiring abort.
- **Existing owner:** R-013 / R-004 / TD-003 / TD-004 / FM-06
- **Repository fact:** current AUTH-v3 retained evidence already covers injective client/server agreement and carries peer public keys in completion events, but `docs/assurance/td-003-closure-audit-2026-08-29.md` correctly says FM-06 should advance only if a scenario is found that is not merely a renamed version of existing agreement. The protocol specification is still incomplete around full credential/reference and trust-role semantics, while `spec/implementation-requirements.md` requires local authentication decisions and NO-LEARNING behavior.
- **Problem addressed:** an authenticated key or valid proof can be cryptographically correct while the application/verifier attributes it to the wrong peer, role/policy record, credential reference, or authority-domain object. A theorem that only repeats “both sides agree on the same public key/context” may miss a resolver-layer attribution error or be redundant with existing agreement evidence.
- **Strongest distinct engineering idea:** define one explicit **identity-attribution resolver invariant** before adding FM-06. Conceptually:

  ```text
  credential/reference/hint
          -> exact credential/security object
          -> exact authentication key or commitment
          -> exact peer identity
          -> exact role/policy/audience/domain binding
  ```

  Then build a shared negative scenario in which possession/proof verification remains valid but the local resolver is maliciously or incorrectly switched from `peer A` to `peer B`, or two accepted reference paths resolve to inconsistent credentials/security objects. The expected result is fail-closed attribution, not merely failed cryptography. A formal event/query should then express the resolver binding explicitly so it adds a property beyond FM-02/FM-03.
- **Evidence maturity:** externally-reviewed standards guidance + software/formal gap
- **Limitations / uncertainty:** EDHOC credential structures and ZK-ARCHE's pseudonymous/role-proof architecture differ. ZK-ARCHE need not adopt certificates, CWT, COSE, or EDHOC identifiers. The transferable security principle is exact identity/key/credential-context attribution and consistency, not the external wire format. Current ZK-ARCHE normative trust/reference semantics are not complete enough to choose the exact resolver schema today.
- **ZK-ARCHE inference:** FM-06 can become non-redundant if it targets attribution under mapping substitution rather than raw DH/session-key agreement. R-013's future clearing evidence should distinguish a key identifier from the peer/policy identity to which local trust binds that key.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** potentially zero wire impact if the mapping is purely local and immutable. Multi-authority, aliasing, commissioner, encrypted lookup-hint, or portable-credential designs may require an authenticated namespace/reference field later, but that is separate TD-004 work. Runtime cost is primarily lookup/validation; the security impact is the trust-model binding.
- **Rust/C / vector compatibility impact:** eventual shared fixtures should cover same key under two identity records, stale alias after reprovisioning, credential/reference mismatch across two input paths, correct key with wrong role/policy/audience record, and consistent references that legitimately resolve to the same credential. Rust and C must make the same attribution accept/reject decision.
- **Required next evidence:** a normative resolver relation or bounded design note; one exact non-redundant FM-06 mismatch scenario; Rust/C mapping-substitution negative fixture; traceability from reference → credential → key/commitment → peer/policy identity; formal query/event proving the same mapping relation rather than repeating existing agreement.
- **Recommended disposition:** reproduce

### D20260829-F02 — FM-22 needs an explicit dynamic-corruption matrix and composition/disjointness audit before FS/PCS expansion

- **Novelty:** new
- **Source:** Cremers, Pallas, Peltonen, *Secure Protocol Composition under Dynamic Corruption: Scaling Up Symbolic Analysis for Real-World Security Properties*
- **Primary link:** https://www.usenix.org/conference/usenixsecurity26/presentation/cremers
- **Source type / venue:** peer-reviewed USENIX Security 2026 conference paper
- **Publication / presentation date:** August 2026; CISPA publication record dated August 12, 2026
- **Verified claim:** the work develops a compositional symbolic-analysis result in the Applied pi calculus that supports attackers capable of dynamic corruption when the composed protocols satisfy a disjointness requirement. The authors demonstrate the method on Forward Secrecy for TLS 1.3 with ECH. In their reported evaluation, compositional analyses succeeded where some monolithic analyses failed to return a result, and reduced runtime and memory use on average.
- **Existing owner:** R-004 / R-009 / TD-003 / FM-22
- **Repository fact:** current AUTH-v3 FM-01 secrecy is explicitly scoped to active-network attacker A0 with no endpoint/long-term-secret compromise. The current traceability record explicitly says it does not establish forward secrecy or post-compromise security. The TD-003 closure audit says FM-22 is blocked because compromise/recovery semantics are not yet defined; replay fresh-epoch, rekey/resumption, revocation, and recovery are also split across incomplete lifecycle owners.
- **Problem addressed:** adding a generic `compromise(secret)` fact to the current ProVerif model could create an attractive but ambiguous theorem. Security depends on **what** is compromised, **when**, which state is shared between subprotocols, and what recovery event is supposed to restore guarantees. Without those semantics, a “forward secrecy” or “post-compromise” label could overstate the actual design.
- **Strongest distinct engineering idea:** make the next FM-22 artifact a **dynamic-corruption and composition-readiness matrix**, not a new theorem. At minimum inventory:

  ```text
  object/state                         compromise timing to model
  ----------------------------------------------------------------
  client long-term scalar              before / during / after AUTH
  server long-term scalar              before / during / after AUTH
  role credential / blinding state     before / during / after AUTH
  ephemeral DH secret                  during / after completion
  established session key              after completion
  resumption secret/ticket key         before / after resumption
  replay continuity state              rollback / loss / attacker write
  authorization/epoch state            stale / rollback / attacker write
  future rekey/fresh-epoch material    before / during / after transition
  ```

  For each desired guarantee, state the earliest corruption time it tolerates and the exact authenticated recovery transition. Then audit whether AUTH, replay continuity, resumption, authorization, and future rekey/DATA models satisfy any required disjointness/shared-data conditions before attempting modular proof composition.
- **Evidence maturity:** formal / externally peer-reviewed methodology
- **Limitations / uncertainty:** the USENIX theorem has its own formal assumptions and disjointness conditions; this report has not proven that ZK-ARCHE satisfies them. ZK-ARCHE currently has one synchronized AUTH-v3 ProVerif model plus a separate replay-continuity model, not the paper's exact modeling architecture. The paper is a methodology comparator, not imported assurance.
- **ZK-ARCHE inference:** the immediate gain is claim hygiene and experiment ordering. FM-01 should remain A0/no-compromise until a compromise matrix exists. “Post-compromise recovery” should not be modeled until an authenticated fresh security-context/rekey/reprovisioning transition exists normatively and executable state can be mapped to it.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** research-only; no wire or runtime dependency follows. If future recovery requires durable epoch/rekey state, that cost belongs to R-009/TD-002 measurements, not this formal-method finding.
- **Rust/C / vector compatibility impact:** representable compromise/recovery counterexamples should eventually become deterministic Rust/C negative/state-transition fixtures. No new vector is justified until concrete compromise/recovery semantics exist.
- **Required next evidence:** A3/FM-22 secret/state inventory with corruption timing; guarantee matrix distinguishing PFS/PCS/recovery/non-goals; shared-state and primitive-domain inventory across AUTH/replay/resumption/authz/rekey; disjointness/composability assessment; only then a bounded model prototype and retained results/counterexamples.
- **Recommended disposition:** investigate

## 5. Cross-source synthesis

Today's two findings converge on one assurance rule: **cryptographic success must be interpreted through explicit state attribution**.

For FM-06, the missing state is the resolver relation that says which exact peer/policy identity a credential/reference/key represents. EDHOC's misbinding discipline shows why proving possession without precise attribution can be insufficient. For FM-22, the missing state is the compromise/recovery relation that says which secrets were exposed, when, and which authenticated transition creates a genuinely new security context.

This does not mean ZK-ARCHE should import EDHOC credential formats or adopt a new formal tool immediately. It means the remaining formal work should be driven by explicit repository-owned semantics:

```text
identity/reference relation defined
        -> executable misbinding case
        -> non-redundant FM-06 query

compromise/recovery relation defined
        -> executable recovery state machine
        -> dynamic-corruption model
        -> carefully scoped FS/PCS claim
```

The current repo is correctly ahead of yesterday's parser concern: that specific tested hostile-count allocation hypothesis has been addressed and should not remain an active daily-research blocker.
