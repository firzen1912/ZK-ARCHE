## 2. Executive synthesis

1. ESP-IDF v6.1 makes successful getrandom() return insufficient evidence of cryptographic entropy readiness: the call is non-blocking and ignores flags; the physical entropy source still depends on boot/RF/SAR-ADC phase.
2. Rust value-returning OsRng.fill_bytes helpers and C void randombytes_buf helpers obscure fundamentally different failure propagation. STM32H5 vendor code exposes seed/recovery and timeout errors that an embedded adapter must carry through an operation-atomic security boundary.
3. Libsodium warns VM snapshot/restore may duplicate random output; RNG restart/clone continuity, replay cache restoration, and authorization/resumption lineage are distinct properties. A two-instance synthetic fault experiment is justified.
4. R-005 remains **benchmark**, not promoted. No physical ZK-ARCHE target test, exact-head injected-failure execution, or field-readiness claim was established. No implementation or specification is changed.

### D20261011-F01 — ESP32-S3 getrandom return success is not entropy readiness

- **Novelty/owner:** refines September 24 R-005; TD-002 and zk208/zk216/zk222/zk236.
- **Source/date/type:** Espressif official ESP-IDF v6.1 ESP32-S3 RNG documentation, versioned vendor documentation inspected 2026-10-11 (no publication date listed).
- **Primary link:** https://docs.espressif.com/projects/esp-idf/en/v6.1/esp32s3/api-reference/system/random.html
- **Verified claim:** getrandom() delegates to esp_fill_random(), ignores flags, is non-blocking, and generally returns the requested length even when source strength differs. Vendor true-random prerequisites include active RF, explicitly enabled SAR-ADC entropy, or the second-stage bootloader. After bootloader handoff without a qualified active source output is described only as pseudo-random; active entropy source may conflict with ADC/RF operations.
- **Repository fact / bottleneck:** current Rust/C helper signatures do not express a qualified device entropy-source phase, though spec/implementation-requirements.md §3 mandates fail-closed RNG failures.
- **Distinct engineering idea / inference:** keep **byte-delivery success** and **cryptographic entropy/DRBG readiness** as independent assertions. Qualify UNREADY, READY, and FAULT transitions for cold boot, bootloader handoff, RF off/on, ADC entropy enable/disable, deep sleep/wake, and reseed.
- **Evidence maturity:** vendor constrained-hardware documentation; ZK-ARCHE only concept/benchmark. The documentation does not prove a particular Rust target uses this exact getrandom backend or validate ZK-ARCHE hardware.
- **Wire/CPU/RAM/flash/dependency/trust/privacy impact:** no wire change; provider-state and optional DRBG consume RAM/flash, startup/energy/CPU, and potential ADC/RF scheduling; weak nonce/key entropy endangers authentication and pseudonym privacy.
- **Rust/C/vector/profile impact:** same qualified readiness-negative decision classes must be exercised in both languages; deterministic vector material stays unchanged; iot-core stays non-selectable.
- **Required next evidence:** pinned board, chip revision, SDK, HAL, RNG backend/DRBG; source on/off and fault traces with target memory, energy, and latency data; no crypto output when unready.
- **Disposition:** benchmark; weekly candidate yes.

### D20261011-F02 — Fallible RNG must guard the entire authenticated operation

- **Novelty/owner:** refines R-005 and R-007 proof-randomness review; TD-002, spec/implementation-requirements.md §3.
- **Sources/date/type:** Rust Rand Book Error handling, libsodium Generating random data and Custom RNG (official library documentation inspected 2026-10-11); STMicroelectronics STM32H5 HAL RNG implementation pinned to ba20038d938ecc31399e49d60fa6bcc8e82db5da (official project source inspected 2026-10-11).
- **Primary links:** https://rust-random.github.io/book/guide-err.html ; https://libsodium.gitbook.io/doc/generating_random_data ; https://libsodium.gitbook.io/doc/advanced/custom_rng ; https://github.com/STMicroelectronics/stm32h5xx-hal-driver/blob/ba20038d938ecc31399e49d60fa6bcc8e82db5da/Src/stm32h5xx_hal_rng.c
- **Verified claim:** Rust RngCore::try_fill_bytes permits reporting failure, whereas infallible fill_bytes can panic. Libsodium randombytes_buf has void return and allows custom RNG installation before sodium_init(). The pinned ST HAL source has seed-error, failed recovery, and timeout/error handling paths.
- **Repository fact / bottleneck:** Rust crypto.rs calls OsRng.fill_bytes in value-returning helpers; C crypto.c has void auth_random_bytes32/auth_random_scalar; C proofs.c invokes randombytes_buf before auth_err_t proof generation; C proto.c draws session ID and nonce without checked RNG success. These contracts do not establish how embedded hardware failures reach protocol admission.
- **Distinct engineering idea / inference:** an **operation-atomic fail-closed fault corpus** must inject NOT_READY, short/partial fill, mid-fill failure, seed/clock error, recovery failure, timeout, reseed failure and post-write fault. Assert zero emitted proof/session output, zero trust/replay/lineage/state commit, scratch discard/zeroization and consistent Rust/C reject decisions. A future fallible platform-provider boundary would require human-reviewed implementation work.
- **Evidence maturity:** software/vendor-source evidence only; no ZK-ARCHE injected test executed. Actual target configuration, libsodium backend, STM32 variant and interrupt behavior remain unverified.
- **Wire/CPU/RAM/flash/dependency/trust/privacy impact:** no wire change; checked adapters and scratch buffers add resource cost; suppressing operations affects availability but protects secret integrity; externally distinguishable failure timing would require R-015 analysis.
- **Rust/C/vector/profile impact:** preserve existing deterministic proof known-answer vectors; add shared negative fault fixtures and exact toolchain/lib/backend provenance.
- **Required next evidence:** executable local exact-head Rust/C fault harness, pre/post-operation state snapshots without secrets, scratch wipe evidence, then STM32 seed/timeout physical measurements.
- **Disposition:** reproduce/benchmark, retaining R-005 benchmark; weekly candidate yes.

### D20261011-F03 — Clone/restore changes random-stream uniqueness independently of replay authority

- **Novelty/owner:** refines R-005 clone/rollback requirements; R-009 owns replay/resumption-state coupling.
- **Source/date/type:** libsodium official Generating random data documentation inspected 2026-10-11; NIST SP 800-90C final standard published 2025-09-25.
- **Primary links:** https://libsodium.gitbook.io/doc/generating_random_data ; https://csrc.nist.gov/pubs/sp/800/90/c/final
- **Verified claim:** libsodium warns that a VM snapshot restored later can repeat random output. NIST separates entropy source, DRBG and overall RBG construction, making retained generator state/reseed policy an independent assurance input.
- **Repository fact / bottleneck:** R-005 already lists clone/rollback and root seed handling; R-009 requires restart-safe replay and non-resettable resumption-origin lifetime. No actual two-instance clone-divergence reproduction is retained.
- **Distinct engineering idea / inference:** use synthetic test secrets in two restored instances with identical/changed DRBG state and varied fresh entropy. Independently measure repeated random values, proof/session accept/reject, replay epoch, key-generation and authorization-lineage continuity. Do not treat a freshly drawn nonce as proof that authoritative replay or revocation state is current.
- **Evidence maturity:** official software guidance plus NIST standard; ZK-ARCHE reproduction not executed. VM behavior must not be generalized to physical TRNGs or claimed as proof of a specific nonce reuse today.
- **Wire/CPU/RAM/flash/dependency/trust/privacy impact:** no wire change; secure monotonic continuity anchors, reseed, and key rotation may cost persistent storage, flash wear, boot latency and power. Repeated nonce streams may endanger secrecy and linkability.
- **Rust/C/vector/profile impact:** synthetic replayable clone corpus can exercise Rust/C decision parity separately from live entropy; keep production vectors and profile IDs unchanged.
- **Required next evidence:** twin-instance restore corpus with pinned DRBG/backend, restart generation and replay/lineage state; physical boot/wake repeats with retained artifact hashes.
- **Disposition:** reproduce; weekly candidate yes.

## 6. Cross-source synthesis

A complete API byte return does not imply ready entropy, and ready entropy does not automatically imply an operation safely committed its output. A sound physical-target acceptance claim needs qualified entropy/DRBG state, checked complete sampling, failure-atomic proof and session construction, and independent restart/clone replay/authorization continuity. Espressif, ST, Rust, libsodium and NIST sources support different parts of that composite conclusion; none tests ZK-ARCHE directly.
