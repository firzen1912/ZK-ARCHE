## 2. Executive synthesis

1. **Source date and scope:** `draft-ietf-iotops-iot-dns-guidelines-06` was published **2026-11-02**, superseding the **2026-10-22** `-05` draft. The guidance is an **active Internet-Draft**, not an RFC or a new ZK-ARCHE requirement. Its IoT DNS threat summary and many recommendations were already present in -05; today's novelty is the updated primary-source baseline and its explicit application to ZK-ARCHE's *unmeasured* composed observer experiment, not an assertion that all DNS threats first appeared in -06.
2. **Authentication privacy is stack-relative:** Observable DNS query names, destination resolver, retry/TTL cadence and encrypted-resolver network endpoint may expose device class, boot/restart state and management dependencies even when protocol-level AUTH pseudonyms change. `spec/privacy-considerations.md` already warns about transport/rendezvous metadata; R-015 lacks a DNS-aware matched capture corpus.
3. **Separately verified empirical comparator:** EuroS&P 2026 reports random-forest classification of **DNS frames versus other traffic**, not ZK-ARCHE identity linkage: in its test configuration, accuracy was **86%**, falling to **77%** with additional DNS message compression; its DNS-over-HTTPS comparison was **100%**. These percentages must **not** be presented as ZK-ARCHE anonymity, privacy gain, or same-peer reidentification metrics.
4. **Proposed evidence:** Expand R-015's current first-flight/cross-transport experiments with DNS-silent versus optional-resolver operation, resolver-target and query-timing side channels, combined endpoint/gateway observer traces, and availability/freshness constraints. First reproduce a two-stage attack (DNS-vs-application classification followed by separately evaluated same-peer linkage); do not replace the security contract with cosmetic padding or force DNS into the mandatory core.
5. **Decision:** R-015 stays **P0 / reproduce**. Neither R-005 nor R-014 status changes. No DNS transport, optional feature, new wire format, privacy claim, or external infrastructure dependency is adopted.

## 5. Findings

### D20261103-F01 — DNS resolution and retry cadence form an *optional deployment* privacy/availability side channel

- **Novelty:** refines R-015's observer-model evidence contract; Nov 2 revision is current but many claims precede -06.
- **Source:** *IoT DNS Security and Privacy Guidelines*, `draft-ietf-iotops-iot-dns-guidelines-06` (IETF IOTOPS Working Group active Internet-Draft, **2026-11-02**); comparison `-05` **2026-10-22**.
- **Primary links:** https://datatracker.ietf.org/doc/html/draft-ietf-iotops-iot-dns-guidelines-06 ; https://datatracker.ietf.org/doc/html/draft-ietf-iotops-iot-dns-guidelines-05
- **Verified source-supported claim:** The draft documents resolver hardcoding/policy bypass, predictable DNS query timing when TTL is ignored, source-port and transaction-ID predictability, unbounded retries, and query-data exposure; it recommends configurable resolvers, TTL-respecting cache and bounded failure backoff, unpredictable UDP transaction IDs and source ports, and encrypted DNS when resource-feasible. It advises against padding when fragmentation/energy makes it impractical. The exact DNS standard is *not* a mandatory ZK-ARCHE protocol mechanism.
- **Existing engineering owner / anchor:** R-015; `spec/privacy-considerations.md` §§2–3,7–11, `spec/iot-profiles.md`; TD-002 target measurement and TD-004 privacy/error guidance.
- **Problem/bottleneck:** First-flight ZK-ARCHE privacy evidence currently scopes AUTH packet and transport observation but has no explicit optional DNS query/response and resolver endpoint sequence matched to a peer's boot/attempt/restart timeline. Privacy inferred from PID rotation would be invalid if a separate resolver channel associates sessions.
- **Distinct engineering idea:** For each `DNS-silent local P2P`, `authorized managed resolver`, `unprotected DNS`, and `resource-feasible encrypted resolver` deployment *that is actually applicable*, collect synchronized device/gateway/radio/application DNS+AUTH traces from boot, failed resolution, AUTH retry, normal operation, and restart. Record resolver IP/domain visibility, TTL/revalidation cadence, server-address changes, backoff, retransmission, query-size and response-size metadata, and whether DNS traffic is observable to the selected attacker. Keep independent security labels for server identity, credential authorization, and DNS resolution; a DNS result must not become a trust anchor.
- **Evidence maturity:** **concept** for ZK-ARCHE; *standards-work-in-progress* for the guidance.
- **Limitations:** -06 did not newly demonstrate a ZK-ARCHE leak. It focuses largely on devices using DNS for cloud/management; ZK-ARCHE core P2P AUTH may be DNS-free. DNS encryption reduces exposed query contents but does not inherently hide resolver IP, packet sizes, timing, or the downstream destination. Privacy/availability cost depends on deployed adapter/network.
- **ZK-ARCHE inference:** R-015's threat model must explicitly distinguish an offline/no-DNS profile from a DNS-backed management profile; label linkability as a property of the *whole observable deployment*, not of one AUTH message.
- **Wire / CPU / RAM / flash / dependencies / trust / privacy:** **No ZK-ARCHE wire change.** Optional protected resolver, caches and padding add DNS/external traffic, stack/dependency footprint, host/MCU CPU and RAM, and energy; no numerical claims without measurement. Hardcoded external resolver would add availability and privacy dependence and is not recommended. Trust model unchanged: DNS cannot authorize AUTH/enrollment.
- **Rust/C / vector / profile impact:** No source or production-vector change now. Research vectors/observer-capture manifest should label Rust/C/profile, resolver mode, query/timing, synchronized capture location and restart state. Any future optional DNS behavior needs independent Rust/C/app-adapter compatibility and no-DNS baseline conformance evidence.
- **Required next evidence / disposition:** local exact-head, version-pinned two-mode traces with DNS-vs-no-DNS and failure/backoff controls, held-out devices and observer locations, privacy/DoS/RNG/TTL safety measurements; **reproduce**. Weekly finding candidate **yes**.

### D20261103-F02 — DNS packet obfuscation performance is not same-peer unlinkability

- **Novelty:** new experimental comparator for R-015's two-stage attack metric; refines rather than establishes a ZK-ARCHE vulnerability.
- **Source/date/type:** Lenders, Schmidt, Wählisch, *Secrets Best Not Shared: DNS Privacy Enhancements for the Constrained IoT*, peer-reviewed IEEE EuroS&P **2026-07-06–10**, pp. 1475–1494, plus author-maintained reproducibility artifact **Zenodo v1.0.1 (2026-04-22; accepted 2026-04-14)**. RFC 9953 *DNS over CoAP* (**2026-03**, Proposed Standard) defines DNS over CoAP and its (D)TLS/OSCORE protection options.
- **Primary links:** https://netd.cs.tu-dresden.de/pub/lsw-sbsdp-26.html ; https://zenodo.org/records/19698345 ; https://www.rfc-editor.org/rfc/rfc9953.html
- **Verified source-supported claim:** In the paper's modeled deployment matrix, 58,768 web-derived data objects and 296 deployment scenarios were examined. A Random Forest classified DNS versus non-DNS traffic at **86%** after equalized packet lengths, block transfer and header compression; an additional compressed DNS representation produced **77%**. The paper's DoH case allowed **100%** DNS-frame identification from destination IP information in that study. The author's artifact repository provides experiment code and reproducibility data; an available v1.0.1 data archive is **175.4 GB**, with a smaller **158.2 MB** experiment/code archive. These are published results, *not independently reproduced in this run*.
- **Owner and repository anchor:** R-015; `spec/privacy-considerations.md` §§7–11, `rust/crates/proto/src/proto/auth.rs`, `c/src/crypto/transcript.c`; R-005 as eventual measurement cross-link.
- **Bottleneck:** 'Encrypted' or 'padded' DNS can remain recognizable by metadata, but a classifier labeling *DNS frames* is not a classifier proving two pseudonymous AUTH sessions belong to the same physical device. Conflating these outcomes could falsely strengthen or weaken ZK-ARCHE privacy claims.
- **Distinct engineering idea:** Model the attacker as two explicit stages: **(A)** discover DNS/resolver activity among other device traffic and **(B)** predict the same-peer linkage across full AUTH, resumed AUTH, reboot and transport changes using DNS+AUTH features. Report stage-A and stage-B precision/recall, false positives, top-k, entropy loss, confidence intervals, held-out device and firmware splits, and observer vantage separately. Use the original artifact as an *optional baseline*, not an unbounded 175 GB data import; first reproduce published study metrics with a bounded fixture, then capture ZK-ARCHE-specific traces. Include DNS frame source/destination, cache and TTL changes, encrypted DNS and deliberate DNS silence as ablations.
- **Evidence maturity:** **externally-reviewed** source paper / **software** source artifact; **concept** for ZK-ARCHE-specific claims.
- **Limitations:** The paper evaluates DNS-traffic recognition rather than ZK-ARCHE anonymous role proofs, device reidentification, or authenticated session unlinkability. Results depend on its classifier, datasets, headers, and deployment conditions; the 86/77/100% numbers are not universal security bounds or a basis for production padding settings.
- **ZK-ARCHE inference:** A composed deployment could preserve encrypted AUTH yet leak a stable management resolver relationship. Whether this actually raises same-peer linkage on ZK-ARCHE is a measured research question, not a proven vulnerability.
- **Wire / CPU / RAM / flash / dependency / trust / privacy:** No new protocol bytes or mandatory resolver. Optional DoC/OSCORE/DoH traffic, length bucketing and compression may affect per-link MTU, packet count, CPU, RAM, flash, fragmentation and energy; overhead and any anonymity benefit are **unmeasured** on ZK-ARCHE. Trust/authorization unchanged; privacy effect unknown until stage-B classification.
- **Rust/C / vector / profile impact:** Research-only synthetic/session and network-capture corpus with same Rust/C device labels, stable-versus-rotating PID, profile and DNS-mode annotations; no existing deterministic vectors changed. Any proposed padding/DoC deployment must be profile-gated and measured before human approval.
- **Required next evidence / disposition:** exact-stage evaluation with source artifact version, held-out devices, random/majority baselines, matched observer capture, and measured resource budget; **reproduce**. Weekly candidate **yes**.

## 6. Cross-source synthesis

The Nov 2 IETF WG draft describes observable DNS-client failures, retry and privacy mechanisms; the July peer-reviewed DNS-frame experiment demonstrates *why network-metadata observability may persist even for encrypted/obfuscated resolver traffic*. They support expanding R-015's composite observer manifest, **not** adopting a name resolver, certificate authority, cloud service, DNS-based peer identity, or packet padding in ZK-ARCHE mandatory AUTH. The security invariant for an offline peer with locally authenticated trust must continue to work with no DNS. Preserve replay continuity and authorization freshness even when discovery fails. The evidence gate is a **ZK-ARCHE-specific same-device correlation test**; a DNS-versus-application classifier cannot substitute for it.
