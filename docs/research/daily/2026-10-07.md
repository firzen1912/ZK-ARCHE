## 2. Executive synthesis

1. The current HPKE WG draft is no longer behaviorally identical to RFC 9180: Auth/AuthPSK modes and the AuthEncap/AuthDecap KEM interfaces have been removed. Any ZK-ARCHE lookup-hint prototype must pin the exact HPKE revision and mode rather than merely saying "HPKE".
2. Base-mode HPKE is a suitable confidentiality envelope for a non-authoritative hint, but it provides no sender authentication and no general replay protection. In an exposed datagram profile, return-routability/load validation should therefore occur before HPKE decapsulation, not merely before registry scan or proof verification.
3. With DHKEM(X25519) and the 16-byte-tag AEADs defined by HPKE -05, a one-shot encrypted hint has a cryptographic envelope floor of `H + 48` bytes for an `H`-byte plaintext hint: 32 bytes of `enc` plus `H + 16` bytes of ciphertext. A 16-byte opaque key therefore costs at least 64 bytes and a 32-byte key at least 80 bytes before ZK-ARCHE framing, key/epoch selection, padding, and retry material.
4. RFC 9497 VOPRF remains a different privacy point, not a drop-in one-shot replacement. The Ristretto255 VOPRF request carries a 32-byte blinded element and the response carries a 32-byte evaluated element plus a 64-byte proof before framing; it also requires a request/response interaction. It is relevant only if the threat model requires hiding the lookup input from the verifier/service itself.
5. R-014 remains prototype. No HPKE/VOPRF dependency, wire allocation, profile change, or AUTH_RETRY constant is adopted by this report.

## 3. Findings

### D20261007-F01 — Pin the HPKE generation; do not inherit removed RFC 9180 authentication modes

Source/date/type: `draft-ietf-hpke-hpke-05`, HPKE WG Standards-Track Internet-Draft, 2026-09-26. Primary source: https://datatracker.ietf.org/doc/html/draft-ietf-hpke-hpke-05

Verified claim: the draft says it obsoletes RFC 9180 if approved. It retains Base and PSK variants, removes Auth and AuthPSK modes, and explicitly says the RFC 9180 `AuthEncap()/AuthDecap()` methods have been removed from the KEM interface.

Bottleneck addressed: R-014 currently says "HPKE-style" encrypted hint without an exact algorithm-generation contract. That is now insufficient for reproducible Rust/C/vector evidence because an implementation targeting RFC 9180 can expose a materially different API and mode set from the current WG draft.

Distinct engineering idea / ZK-ARCHE inference: make the prototype manifest identify the HPKE specification revision, KEM ID, KDF ID, AEAD ID, mode, recipient-key identifier/epoch semantics, and vector provenance. For the lookup-hint role, Base mode is enough as an encryption envelope because ZK-ARCHE must not derive peer authentication or authorization from hint decryption in the first place.

Evidence maturity: fresh active IETF WG work; stronger than an individual proposal but still work in progress. Limitation: -05 can still change before RFC publication, so no stable ZK-ARCHE dependency should be declared yet.

Impact: wire impact depends on selected ciphersuite; CPU/RAM/flash/dependency impact remains unmeasured on the target Rust/C stacks. Trust impact is deliberately nil: HPKE success selects candidate state only. Privacy impact is confidentiality against passive observers, not authenticated identity or unlinkability. Rust/C/vector/profile impact: pin revision and algorithms in every comparator vector and reject accidental reliance on removed Auth-mode semantics.

Disposition: retain R-014 as prototype; refine evidence contract.

roadmap_impact: zk220/zk225/zk226; recommendation only, no roadmap/spec/code change without explicit human review.

### D20261007-F02 — Validate return-routability before attacker-triggerable HPKE decapsulation

Sources/date/type: `draft-ietf-hpke-hpke-05` (2026-09-26, IETF WG draft) and RFC 9000 QUIC (2021, IETF Standards Track). Primary sources: https://datatracker.ietf.org/doc/html/draft-ietf-hpke-hpke-05 and https://www.rfc-editor.org/rfc/rfc9000.html

Verified claim: HPKE Base mode does not authenticate a sender; HPKE also defines no general replay protection beyond ordered use inside one context, and its public-key setup operations are more expensive than symmetric encryption/decryption. RFC 9000 uses address validation to prevent amplification and limits responses to unvalidated addresses; a Retry token is intended for immediate use in the connection attempt rather than as a durable identity token.

Repository fact: zk219 already requires stateless/bounded `AUTH_RETRY` source validation before session reservation, registry scan, and expensive proof verification. zk220 says the encrypted hint is only a non-authoritative prefilter.

Distinct engineering idea / ZK-ARCHE inference: on an exposed datagram path, perform bounded parsing and return-routability token validation before HPKE decapsulation; only then perform the O(1) candidate lookup and full PID/proof/possession/transcript/lifecycle validation. An attacker that knows the recipient public key can create Base-mode HPKE ciphertexts and force recipient decapsulation work; therefore "retry before registry scan" is not sufficient if HPKE itself sits before the retry gate. The retry token remains transport/source-reachability evidence, never peer identity, credential validity, or authorization.

Evidence maturity: RFC-backed DoS comparator plus fresh HPKE WG behavior. Limitation: QUIC's exact three-times anti-amplification constant is transport-specific and is not adopted as a ZK-ARCHE constant here.

Impact: likely reduces unauthenticated asymmetric CPU and state pressure at the cost of one retry flight for unvalidated datagram sources. Token bytes, MAC CPU, expiry/replay storage if any, NAT/address-change behavior, and amplification must be measured. Privacy impact includes retry-token linkability and externally distinguishable missing/invalid/expired-token behavior.

Rust/C/vector/profile impact: add counters or retained measurements proving missing/invalid/expired/replayed retry cases do not reach HPKE decapsulation, registry access, session allocation, or proof verification; add valid-token+malformed-HPKE and valid-token+valid-HPKE+unknown-candidate cases with normalized external behavior where privacy policy requires it.

Disposition: prototype/benchmark boundary; no AUTH_RETRY allocation or wire constant promoted.

roadmap_impact: zk219/zk220/zk229; recommendation only, explicit human review required.

### D20261007-F03 — Exact one-shot HPKE hint floor is small but not privacy-neutral

Source/date/type: `draft-ietf-hpke-hpke-05`, 2026-09-26, IETF WG Standards-Track Internet-Draft. Primary source: https://datatracker.ietf.org/doc/html/draft-ietf-hpke-hpke-05

Verified claim: DHKEM(X25519, HKDF-SHA256) has `Nenc = 32` bytes. The AEAD algorithms defined by the draft add `Nt = 16` bytes to the plaintext. The draft explicitly states that HPKE ciphertexts do not hide plaintext length and applications that need length privacy must add a padding policy.

Derived wire fact: Base-mode X25519 HPKE has a lower bound of `32 + H + 16 = H + 48` bytes for an `H`-byte hint. Thus a fixed 16-byte opaque lookup key is at least 64 bytes and a 32-byte key at least 80 bytes before ZK-ARCHE extension framing, recipient/lookup-key selection, epoch/rotation metadata, padding, or retry material.

Repository fact: draft `iot-core` currently declares a 2048-byte maximum datagram. That ceiling is not a license to consume the remaining space without measuring complete AUTH message size, MTU/fragmentation, parser buffers, and target RAM.

Distinct engineering idea / ZK-ARCHE inference: prefer a fixed-size opaque hint plaintext and explicitly budget any recipient-key selector and lookup-key epoch. If multiple hint lengths or key IDs are externally visible, R-015 must treat them as fingerprint/correlation fields. Padding should be justified by measured anonymity-set gain and constrained cost, not added reflexively.

Evidence maturity: exact draft-defined sizes plus repository profile fact. Limitation: this is a cryptographic-envelope lower bound, not a complete ZK-ARCHE packet measurement.

Impact: wire = `H+48` lower bound for this ciphersuite; CPU/RAM/flash remain target/library dependent; dependency = one HPKE-capable implementation per claimed lane; trust = no authority change; privacy = ciphertext confidentiality but remaining length/key-id/timing/failure leakage.

Rust/C/vector/profile impact: deterministic comparator vectors should assert the complete framed byte count, AAD/info binding, recipient-key/epoch selection, malformed `enc`, wrong key, padding class, and cross-epoch behavior while production encapsulation continues to use qualified randomness.

Disposition: prototype; measure before any profile allocation.

roadmap_impact: zk220/zk225 and R-005/R-015 evidence; no roadmap action.

### D20261007-F04 — VOPRF is an interactive verifier-privacy comparator, not the baseline lookup-hint mechanism

Source/date/type: RFC 9497, December 2023, IRTF/CFRG Informational RFC. Primary source: https://www.rfc-editor.org/rfc/rfc9497.html

Verified claim: an OPRF lets the client learn the PRF result while the server learns neither the PRF input nor output; VOPRF adds a proof that the server used the expected private key. For the Ristretto255 ciphersuite, serialized elements and scalars are 32 bytes. A VOPRF request sends one 32-byte blinded element; the response sends one 32-byte evaluated element plus a DLEQ proof consisting of two 32-byte scalars, for a 96-byte response before framing. The protocol is interactive: the client blinds and sends, the server evaluates/proves and returns, then the client finalizes.

Bottleneck addressed: R-014 currently lists VOPRF/POPRF as a comparator without a crisp condition for when its additional machinery buys a distinct privacy property.

Distinct engineering idea / ZK-ARCHE inference: retain VOPRF/POPRF only if the architecture introduces a lookup service/verifier from which the raw lookup input itself must be hidden. That is a different adversary boundary from encrypting a one-shot hint to the peer that already owns the local trust registry. For the mandatory infrastructure-independent Common Contract, an interactive online privacy service must not become required for correctness.

Evidence maturity: CFRG consensus research RFC, not an IETF Standards-Track protocol requirement. Limitation: the 32/96-byte figures are cryptographic-message floors and exclude application framing, server key distribution/configuration, public `info`, retransmission, and transport cost.

Impact: extra flight and group/proof CPU versus one-shot HPKE; potentially stronger privacy against the lookup service; more state/retransmission complexity; additional Rust/C dependency and vector surface. No benefit is assumed unless a concrete verifier-blind threat model exists.

Rust/C/vector/profile impact: if prototyped, pin the RFC 9497 ciphersuite, public-key/configuration provenance, input/info domain separation, deterministic vectors, error normalization, and bounded retransmission behavior separately from the HPKE path.

Disposition: research comparator only; no VOPRF promotion.

roadmap_impact: zk220/R-014 only; explicit human review required.

## 4. Cross-source synthesis

The lowest-risk R-014 experiment is now clearer: a fixed-size opaque registry key can be encrypted with a precisely pinned HPKE Base-mode configuration as a non-authoritative one-shot prefilter, but exposed datagram deployments should validate return-routability/load eligibility before paying the HPKE decapsulation cost. The decrypted candidate still passes through the repository's authoritative attribution relation and full AUTH/lifecycle checks.

The privacy boundary is also sharper. HPKE mainly hides the hint from passive observers; it does not hide ciphertext length and does not authenticate the sender in Base mode. VOPRF addresses a different question—hiding the client's lookup input from the evaluating service itself—and pays for that with interaction, proof work, and additional protocol state. The two mechanisms therefore should not be scored as interchangeable "private lookup" options.
