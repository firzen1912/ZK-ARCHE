## 2. Executive synthesis

1. **The RFC 9266 `tls-exporter` channel binding is NOT interchangeable with an application-specific TLS exporter.** RFC 9266 fixes label `EXPORTER-Channel-Binding`, empty context and 32-byte output and explicitly forbids reuse for multiple upper-layer authentication instances over one TLS connection. The draft ZK-ARCHE profile instead proposes label `EXPORTER-ZK-ARCHE-v1` with unique per-AUTH context. A general ban on multiple AUTH instances cannot automatically be transposed to a distinct application-specific construction, but its cross-instance uniqueness property must be demonstrated independently.
2. **RFC 9846 (July 2026) obsoletes RFC 8446 while retaining TLS 1.3.** Its regular exporter continues to hash the *supplied context* internally and distinguishes regular from early/0-RTT exporter secrets. This corrects the standards citation baseline and sharpens provider-API and exact-handshake-phase testing rather than selecting a new ZK-ARCHE wire mode.
3. **Verified technical erratum EID 9040 (2026-10-12) tightens version negotiation.** Without `supported_versions`, a TLS 1.2 legacy ClientHello may negotiate TLS 1.2; other legacy versions must fail with `protocol_version`. A TLS-1.3-only optional ZK-ARCHE binding must reject TLS 1.2 as well under its stricter local minimum. Test negotiation under an explicit TLS floor; no implicit fallback to weak/unbound mode.
4. No TLS runtime handshake, proof, ZK-ARCHE exploit or device benchmark was executed in this research pass. **R-010 remains P0 / `reproduce`**; R-011 unchanged. No mandatory TLS/PKI/cloud dependency or protocol/implementation promotion.

## 5. Findings

### D20261115-F01 — Do not conflate the standardized `tls-exporter` binding with a per-AUTH application exporter

- **Novelty / owner:** refines R-010 (P0).
- **Primary source/date/type:** IETF Standards Track [RFC 9266](https://www.rfc-editor.org/rfc/rfc9266.html), published **July 2022**, §§2, 4.1; corroborating current [RFC 9846](https://www.rfc-editor.org/rfc/rfc9846.html), **July 2026**, §7.5. Existing standards newly applied to a repository-specific decision, not November publications.
- **Verified external claim:** RFC 9266's standardized `tls-exporter` binding uses `EXPORTER-Channel-Binding`, zero-length context, 32 octets. It identifies the TLS connection, not individual upper-layer authentication instances; §4.1 says an application using this particular binding MUST NOT use it for more than one authentication mechanism instance per connection and MUST close the TLS connection after upper-layer authentication. Its derived binding is not a secret content-encryption key. RFC 9846 supports context-separated application exporters using a supplied label/context, with TLS applying its own context hash.
- **Existing owner / anchor:** R-010, zk228, TD-004, `spec/tls-exporter-channel-binding.md` §§2–7; `c/tests/test_tls_exporter_context.c`.
- **Bottleneck:** A future integration could substitute the standardized connection-level binding for the proposed per-AUTH exporter, falsely assume it isolates multiple AUTH instances, or fail to document the stronger upper-layer-instance uniqueness proof obligation.
- **Distinct idea:** Build a typed `binding_method` / `AUTH_instance_id` acceptance matrix: (A) actual RFC 9266 binding: single AUTH instance per TLS channel and close after use; (B) candidate `EXPORTER-ZK-ARCHE-v1` application-specific binding: distinct authenticated context, actual TLS exporter output, Finished confirmation and no acceptance of mismatched/reused instance material. Include crossed two-AUTH contexts, swapped labels, same-auth-context duplicate, TLS resumption and cross-application mixes. Do not silently exchange method A and B, and do not use a channel binding as an encryption key.
- **Evidence maturity:** externally-reviewed IETF standards for specified constructs; `concept` for ZK-ARCHE's application-specific multi-AUTH extension until executable security/interop evidence exists.
- **Limitations:** The RFC 9266 connection-lifecycle restriction pertains to **its defined binding type**, not automatically every possible TLS exporter protocol. No proof that ZK-ARCHE's distinct proposed label is insecure, nor evidence that distinct contexts alone suffice for the desired compositional guarantee.
- **ZK-ARCHE inference:** Clarify separate semantics for per-channel standardized identity and per-upper-layer AUTH instance, then establish local traceable strict one-to-one binding to the right authorization generation. This does not alter native non-TLS P2P AUTH.
- **Wire/CPU/RAM/flash/dependency/trust/privacy impact:** No current wire/MCU change. Future custom-context validation adds local per-AUTH RAM/state and exporter/Finished CPU, not a new TLS key exchange; standard single-AUTH policy may cost connections/RTT if selected. More transcript/context bytes are within TLS exporter inputs, not new ZK-ARCHE wire fields until human adoption. Trust-domain isolation is the objective; session linkage from TLS addresses/certificates remains a separate privacy limitation.
- **Rust/C/vector/profile:** No modification. Require independent live TLS 1.3 Rust↔C provider EKM oracle and negative matrix, asserting exact binding method, label, context-present semantics and AUTH-instance identity. `0x0001` baseline unchanged; draft AUTH-v3 remains non-advertised.
- **Disposition:** reproduce; weekly candidate yes.

### D20261115-F02 — Adopt the current TLS source and corrected legacy-version interpretation in the qualification oracle

- **Novelty / owner:** refines R-010; R-011 dependency cross-reference only.
- **Primary source/date/type:** IETF Standards Track [RFC 9846](https://www.rfc-editor.org/rfc/rfc9846.html), **July 2026** (obsoletes RFC 8446), §§1.2, 7.5, Appendix E.2; RFC Editor/IESG [verified technical erratum EID 9040](https://mailarchive.ietf.org/arch/msg/tls/64QSoLupbDHGReyyeeWg6F9ihTg/) **October 12, 2026**; [IANA TLS exporter registry](https://www.iana.org/assignments/tls-parameters/tls-parameters.xhtml#exporter-labels) (current registry).
- **Verified external claim:** RFC 9846 obsoletes RFC 8446 without changing the TLS 1.3 wire version. §7.5 says regular `exporter_secret` is the default; separate `early_exporter_secret` is used only with explicit application intent, and the TLS exporter hashes the supplied context. Verified erratum EID 9040 corrects Appendix E.2: `supported_versions` present selects according to that extension; otherwise `legacy_version==TLS1.2` permits TLS 1.2, and other legacy version offers abort with `protocol_version`. RFC 9846 independently forbids TLS 1.0/1.1. A stricter application TLS1.3-only floor remains the application's own policy.
- **Existing owner / anchor:** R-010, zk228 / TD-004; `spec/tls-exporter-channel-binding.md`, `c/tests/test_tls_exporter_context.c`, `spec/transport-association-continuation.md`.
- **Bottleneck:** Stale RFC 8446 text or unverified legacy fallback assumptions may yield inaccurate provider acceptance tests, despite correct deterministic application-context digests.
- **Distinct idea:** Version-pinned negative TLS handshake corpus: TLS1.3 selected via `supported_versions` -> post-Finished regular EKM; missing extension with TLS1.2 legacy version -> TLS1.2 at protocol level **but reject if local binding requires TLS1.3**; missing extension with 1.0/1.1 -> abort; early/0-RTT exporter -> no AUTH completion; wrong-context (including digest-vs-raw or absent/empty substitution) and TLS resumption -> reject, with provider API and observed negotiated version retained. Do not assume RFC 9846's default TLS 1.2 permission authorizes an application binding downgrade.
- **Evidence maturity:** externally-reviewed RFC and verified erratum; `concept` for ZK-ARCHE live interoperability.
- **Limitations:** No actual TLS handshake or Rust/C provider implementation test here. EID 9040 is a TLS version-negotiation correction, not an identified ZK-ARCHE security incident. No new exporter label allocated by this report.
- **ZK-ARCHE inference:** Pin current RFC text and errata in test references; require app-level minimum-version and no-silent-no-binding rules separately from TLS protocol parsing. Keep staged AUTH-v3 Finished dependent on R-011 normative digest decision.
- **Wire/CPU/RAM/flash/dependency/trust/privacy:** No current wire/profile change. Provider-negotiation tests add developer build/runtime/storage artifacts; stricter floor can reduce backward compatibility but prevents unreviewed fallback. Early exporter classification prevents premature trust; no new stable identifier should be sent as a result.
- **Rust/C/vector/profile:** New matched *research-only* TLS-provider test plan; unchanged vectors and Rust/C source. Test exact provider names/versions, EKM outputs, handshake alerts, ALPN, label, context and final Finished in each lane before any claim of interop. No mandatory TLS/DTLS/PKI change.

## 6. Cross-source synthesis

RFC 9266 names and constrains a **particular standardized** connection-level binding; RFC 9846 provides a flexible label/context exporter primitive. ZK-ARCHE's proposed custom per-AUTH construction must not be represented as the RFC 9266 binding or inherit its security properties without showing independent agreement/uniqueness. At the same time, RFC 9846 and verified EID 9040 define the corrected lower-layer negotiation oracle, while ZK-ARCHE's application profile may impose a stricter version minimum. Neither source resolves the outstanding R-011 critical-extension digest contradiction. No external document automatically changes ZK-ARCHE protocol authority.
