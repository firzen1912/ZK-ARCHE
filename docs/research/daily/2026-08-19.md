# ZK-ARCHE Research — 2026-08-19

## Executive synthesis

The current `dev` branch is unchanged since the 2026-08-18 research report: there are no intervening implementation, roadmap, specification, vector, formal-model, or assurance changes. The four registered debts therefore remain the controlling gaps: independent review of the custom role proof, constrained-target measurements, reproducible formal evidence, and completion of the normative specification.

Three findings materially sharpen current work without introducing a new mandatory primitive:

1. **The planned TLS-exporter binding needs upper-layer authentication-instance uniqueness, not merely a TLS-connection binding.** RFC 9266 explicitly distinguishes connection uniqueness from stronger uniqueness across multiple upper-layer authentication instances and warns that the generic `tls-exporter` channel binding alone does not provide the latter. RFC 5705 separately requires applications using exported keying material to securely establish the upper-layer context, including algorithms, endpoints, sessions, and lifetimes. ZK-ARCHE's zk228 candidate already includes a `transcript_context`, but that context needs a normative construction and negative tests before it can be treated as a safe channel-binding profile.
2. **NIST SP 800-133 Rev. 3 turns seed expansion and derived randomness into an explicit key-generation design question.** The April 2026 draft expands asymmetric key generation to cover derived randomness and limited seed-expansion use of SHAKE/DRBGs, aligns RNG text with SP 800-90C, and explicitly asks how root-seed storage and hybrid/PQ implementations map to real systems. For ZK-ARCHE this sharpens R-005: MCU benchmarks should identify whether a target stores private keys directly or stores/derives from a root seed, how derivation domains are separated, and what clone/rollback/reprovisioning behavior follows.
3. **Loss of durable replay state should be treated as a continuity break, not as a recoverable cache miss.** The active individual VTL draft for constrained telemetry requires explicit resynchronization or AEAD-key rotation before further acceptance when replay state is lost, and separates rejection/continuity evidence from accepted committed data. It is not an IETF standard, but the operational pattern directly strengthens R-009 and ZK-ARCHE's future audit/data-sovereignty work.

No evidence reviewed today justifies a mandatory-suite change, wire-format change, maturity promotion, or automatic roadmap/spec modification.

## Findings

### 1. TLS exporter binding must be unique to the ZK-ARCHE authentication instance

- **Sources:** RFC 9266, *Channel Bindings for TLS 1.3*; RFC 5705, *Keying Material Exporters for Transport Layer Security (TLS)*
- **Primary links:** https://datatracker.ietf.org/doc/html/rfc9266 and https://datatracker.ietf.org/doc/html/rfc5705
- **Source type / venue:** IETF Standards Track RFCs
- **Publication dates:** RFC 9266 — July 2022; RFC 5705 — March 2010
- **Verified claim:** RFC 9266 states that `tls-exporter` uniquely identifies the lower-layer TLS connection but does not by itself provide stronger uniqueness among multiple upper-layer authentication protocols or multiple instances of the same authentication protocol on one TLS connection. It notes that stronger uniqueness protects against cross-protocol and cross-instance replay and requires applications using its generic channel binding not to reuse it for more than one authentication mechanism instance on a TLS connection. RFC 5705 requires applications consuming exporter-derived material to securely establish the upper-layer context and identifies algorithms/parameters, endpoint identifiers, session identifiers, and context/key lifetimes as example context elements.
- **Problem addressed:** zk228 currently has the right architectural direction—bind AUTH to TLS exporter material—but an underspecified `transcript_context` could still permit cross-instance ambiguity, especially if a gateway keeps a TLS connection open for repeated authentication, re-authentication, resumption, or multiple logical peers.
- **Strongest distinct engineering idea:** define a ZK-ARCHE-specific exporter-context contract that is unambiguous per upper-layer authentication instance. Candidate inputs for explicit review include protocol/version, suite/profile, deployment/domain, application/ALPN context, endpoint identities or their protocol-safe commitments, a fresh AUTH/session instance identifier, and the relevant ZK-ARCHE transcript hash. Separately specify whether one TLS connection may carry multiple ZK-ARCHE AUTH instances and, if so, how each is made unique.
- **Evidence maturity:** externally-reviewed
- **Limitations / uncertainty:** RFC 9266's one-authentication-instance rule applies to its generic `EXPORTER-Channel-Binding` construction. ZK-ARCHE proposes a separate exporter label and non-empty context, so the correct result is not automatically “close TLS after every AUTH”; the ZK-ARCHE construction needs protocol-specific analysis and tests.
- **ZK-ARCHE inference:** zk228 should not be considered specification-ready until the exporter label/context, upper-layer instance identifier, TLS resumption behavior, TLS termination/proxy assumptions, and cross-instance negative cases are fixed. This also belongs in zk217 transcript coverage and zk221 resumption analysis.
- **Wire / RAM / CPU / dependency impact:** likely small. Most context can be locally constructed and hashed rather than transmitted redundantly, but any fresh AUTH-instance identifier must have an unambiguous source and lifetime. TLS remains optional and therefore must not burden `iot-core` standalone deployments.
- **Rust/C / vector compatibility impact:** no current compatibility change. A future binding profile requires deterministic exporter-context vectors or fixtures plus negative tests for wrong application/ALPN, wrong deployment, wrong endpoint, wrong suite/profile, stale AUTH instance, cross-instance replay, and TLS-resumption context mismatch.
- **Recommended disposition:** reproduce

### 2. NIST SP 800-133 Rev. 3 sharpens constrained-device key-generation and seed-storage requirements

- **Source:** NIST SP 800-133 Rev. 3 Initial Public Draft, *Recommendation for Cryptographic Key Generation*
- **Primary link:** https://csrc.nist.gov/pubs/sp/800/133/r3/ipd
- **Source type / venue:** NIST Special Publication draft
- **Publication date:** 2026-04-17; NIST posted received public comments on 2026-06-30
- **Verified claim:** the revision expands asymmetric key-pair generation to include methods for deriving randomness, introduces limited seed-expansion methods using SHAKE and DRBGs, aligns random-number-generation language with SP 800-90C, and adds KEM/PQC material. NIST specifically requested feedback on systems that store a root seed/secret rather than full keys and on PQ/hybrid implementations.
- **Problem addressed:** R-005 currently asks for entropy-source state, DRBG/reseed behavior, key handling, and target measurements, but does not explicitly distinguish persistent private-key storage from persistent root-seed storage plus deterministic/derived key generation. Those choices change clone risk, rollback behavior, recovery semantics, secure-element/eFuse use, and provisioning evidence.
- **Strongest distinct engineering idea:** make key-generation mode an explicit benchmark/profile field. Record whether each long-term key is generated directly and stored, derived from a protected root seed, or regenerated through a defined seed-expansion process; record the derivation domain/purpose, entropy and DRBG assumptions, seed/key zeroization boundary, reprovisioning behavior, and what prevents accidental cross-purpose or cross-device key reproduction.
- **Evidence maturity:** concept
- **Limitations / uncertainty:** SP 800-133 Rev. 3 is still an initial public draft, not final NIST guidance. ZK-ARCHE uses primitives and device classes that may not map one-to-one to every NIST-approved-module requirement. The document should be used to sharpen assurance questions, not to claim compliance.
- **ZK-ARCHE inference:** R-005 should add root-seed-versus-key-storage and seed-expansion/derivation-domain measurements. R-003 should record the same distinction for any future ML-KEM/hybrid profile because seed-based PQ key storage can materially alter flash and recovery costs.
- **Wire / RAM / CPU / dependency impact:** no wire change. Seed expansion may trade persistent storage for boot/key-generation CPU and RAM; protected root-seed storage may simplify key inventory but raises clone/domain-separation and recovery requirements. These costs need target measurements.
- **Rust/C / vector compatibility impact:** no current vector change. Future target evidence should include deterministic test-only derivation fixtures while keeping production entropy/key generation non-deterministic where required; production seed material must never be checked into vectors/evidence.
- **Recommended disposition:** benchmark

### 3. Replay-state loss should force a visible continuity break before DATA/audit acceptance resumes

- **Source:** `draft-elkhatabi-verifiable-telemetry-ledgers-07`, *Verifiable Telemetry Ledgers for Resource-Constrained Environments*
- **Primary link:** https://datatracker.ietf.org/doc/html/draft-elkhatabi-verifiable-telemetry-ledgers-07
- **Source type / venue:** active individual Internet-Draft / Independent Submission
- **Publication date:** 2026-06-04
- **Verified claim:** the draft defines anti-replay admission relative to durable replay state. When replay state is lost, its operational guidance requires a continuity-break event, prohibits silently re-accepting counters that may already have been accepted, and requires explicit resynchronization or AEAD-key rotation before further affected frames are accepted. It also separates structured rejection evidence from accepted committed telemetry and requires verifiers to distinguish disclosed continuity breaks.
- **Problem addressed:** R-009 already covers AEAD usage accounting, persistence, rollback, rekey, and flash wear, but a generic “persist counters” requirement does not define the fail-closed state after uncertain or lost replay history. zk235 also needs truthful audit semantics when acceptance continuity is broken.
- **Strongest distinct engineering idea:** define a first-class `continuity_unknown/broken` state for LINK/DATA replay windows. If durable replay state cannot be proven current after restart/rollback/storage failure, do not reconstruct an optimistic window and continue; require an authenticated resynchronization or new key epoch, and emit a separate audit/rejection event that cannot be confused with accepted data.
- **Evidence maturity:** concept
- **Limitations / uncertainty:** this is an individual Internet-Draft, explicitly not IETF-endorsed, and its current stream has review issues. Its exact telemetry ledger, counter window, and anchoring design are not ZK-ARCHE requirements. The useful contribution is the fail-closed continuity pattern and separation between accepted records and rejection/continuity evidence.
- **ZK-ARCHE inference:** R-009 should explicitly cover replay-state-loss detection, continuity-break state, authenticated resynchronization/key-rotation recovery, and verifier/audit visibility. For zk235, rejection/continuity artifacts should remain a separate evidence class rather than being inserted into the accepted-data commitment chain as if they were normal data.
- **Wire / RAM / CPU / dependency impact:** small runtime state but potentially significant persistent-storage/flash-wear design. Recovery may incur rekey/resynchronization messages. Audit events add storage but should remain bounded and separate from data commitments.
- **Rust/C / vector compatibility impact:** no current change. Future negative tests should simulate clean restart, torn/rolled-back replay state, missing replay state, stale restored snapshot, key rotation after continuity break, and rejection of post-restart frames until recovery is authenticated.

## Cross-source synthesis

Today's sources converge on a stronger principle for ZK-ARCHE: **cryptographic context must remain unambiguous across both logical boundaries and persistent-state boundaries**.

RFC 9266/RFC 5705 address the logical boundary: lower-layer TLS binding is insufficient unless the upper-layer authentication instance and its application context are unambiguous. NIST SP 800-133r3 addresses key-origin boundaries: a system must know whether key material is directly generated/stored or reproducibly expanded from protected seed material and under what derivation context. The VTL draft addresses persistent-state boundaries: if anti-replay continuity cannot be established after failure, the system must not silently infer a safe state.

For ZK-ARCHE, this suggests a future assurance matrix with three explicit identifiers/epochs: **authentication-instance context, key-generation/key epoch, and durable replay/continuity epoch**. They need not become one wire object, but the specification, implementation, tests, and formal model should make their relationships explicit.
