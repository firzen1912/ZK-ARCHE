## 2. Executive synthesis

1. **The current Rust and C role-membership provers have a witness-index-dependent execution schedule.** Both locate the true role branch from the secret role, execute one path for the real clause and a different path for simulated clauses, and consume different amounts of randomness/work per clause. The August 17, 2026 CFRG Sigma draft now states directly that, for OR composition, which clause is simulated is witness-dependent and real/simulated clauses should follow the same code path with constant-time transcript selection.
2. **ZK-ARCHE currently implements an ordered role sequence, not a canonical mathematical set.** The Fiat–Shamir transcript absorbs roles and commitments by index, no duplicate rejection or canonical sorting is present, and both provers choose the first matching duplicate as the real branch. This is not by itself a demonstrated soundness failure, but it leaves the statement/serialization contract under-specified and can create cross-profile/cross-implementation aliases.
3. **Rust and C do not presently enforce the same acceptance boundary for proof-element encodings.** Rust AUTH_1 decoding validates Ristretto points and canonical scalars before proof verification. C AUTH_1 decoding copies proof fields as raw bytes; the server path validates `eph_c` and `c_prime`, but does not explicitly canonical-check the CDS branch points/scalars before passing them into proof arithmetic. RFC 9496 recommends strict scalar range checks, and libsodium documents scalar inputs as belonging to `[0,L[`. This is a conformance/API-precondition gap, not an established forgery.
4. **The current Fiat–Shamir context deserves an explicit composition proof.** ZK-ARCHE binds `pid`, `nonce_c`, `eph_c`, `c_prime`, role values and branch commitments under `client_role_set_v1`, which is useful domain separation. The August 2026 Fiat–Shamir draft additionally requires a session identifier that uniquely identifies the argument system/codecs/language and an encoded instance that fixes the concrete statement. R-007 should therefore require either explicit binding of version/method/suite/profile proof context or a documented proof that surrounding authenticated context supplies equivalent separation.
5. R-007 remains `reproduce`. The new evidence substantially sharpens the review contract but does not replace the independent cryptographic review required to clear TD-001.

### D20260918-F01 — CDS OR prover schedule depends on the hidden true-role branch

- **Novelty:** new concrete implementation gap.
- **Backlog owner:** R-007; blocking debt TD-001.
- **Sources:** `draft-irtf-cfrg-sigma-protocols-03`; Cramer–Damgård–Schoenmakers, “Proofs of Partial Knowledge and Simplified Design of Witness Hiding Protocols.”
- **Primary links:** https://datatracker.ietf.org/doc/draft-irtf-cfrg-sigma-protocols/03/ ; https://ir.cwi.nl/pub/1456/
- **Source type / venue:** CFRG active Internet-Draft/work in progress; CRYPTO 1994 peer-reviewed paper/original CDS construction.
- **Publication/revision dates:** CFRG draft 2026-08-17, expiring 2027-02-18; CDS paper 1994.
- **Verified source claim:** the current CFRG Sigma draft explicitly notes that in OR composition the choice of simulated clause is determined by the witness and says real and simulated clauses should follow the same code path with constant-time selection of the desired transcript. It also treats the witness, nonces and prover state as secret values and calls for constant-time operations with secret inputs. The CDS work establishes the partial-knowledge/witness-hiding lineage of the OR-composition technique.
- **Repository fact:** Rust finds `true_index` from `allowed_roles.position(role_code)` and branches on `i == true_index`; the real branch samples one scalar and computes `A_i = H*w`, while simulated branches sample two scalars and compute `A_i = H*s_i - Y_i*c_i`. C mirrors that schedule, explicitly consuming 64 random bytes for the real branch and 128 bytes for each simulated branch, with different group-operation paths.
- **Bottleneck addressed:** TD-001 side-channel/privacy review boundary. Transcript-level witness indistinguishability does not by itself show that the implementation hides the true branch from timing, cache/branch, power, or other execution-side observations.
- **Strongest distinct engineering idea:** make real and simulated branch generation follow one witness-independent operation/memory/randomness schedule, with constant-time selection/masking of the real branch transcript; remove early-exit true-index discovery from secret-dependent control flow. If that is not feasible on constrained targets, explicitly narrow the privacy claim and measure the leakage surface rather than implying local side-channel resistance.
- **Evidence maturity:** high for the repository fact; current CFRG guidance is directly relevant but remains work in progress; no local leakage measurement or independent cryptographic review exists yet.
- **Limitations / uncertainty:** no remote exploitability is established. The risk is strongest for local/physical/co-resident or high-resolution timing observers. Constant-time source structure also requires compiler/target validation; source rewriting alone is not proof of constant-time execution.
- **ZK-ARCHE relevance:** role privacy is a central reason to use OR composition. A branch-index leak can reveal the hidden role without breaking the algebraic proof.
- **Wire / CPU / RAM / flash / dependency / trust / privacy impact:** no wire change is required. Equalizing to the worst-case branch path increases prover CPU and RNG work, with small temporary RAM/flash impact depending on implementation strategy. No new online dependency is required. Privacy assurance materially improves if the schedule is actually target-constant-time.
- **Rust/C / vector/profile compatibility impact:** Rust and C need the same branch-selection semantics and leakage contract. Deterministic vectors can prove transcript equivalence but cannot establish constant-time behavior; target measurements/disassembly or a suitable constant-time analysis layer is still required.
- **Required next evidence:** witness-index timing/power or cycle-distribution measurements on at least host plus one constrained target; compiler/disassembly review of branch generation; a constant-time/equalized prototype in both languages; deterministic transcript parity after equalization; independent cryptographic/side-channel review.
- **Recommended disposition:** reproduce.

### D20260918-F02 — Current “role set” is an ordered, duplicate-permitting proof instance rather than a canonical unique set

- **Backlog owner:** R-007.
- **Sources:** `draft-irtf-cfrg-fiat-shamir-03`; `draft-irtf-cfrg-sigma-protocols-03`; CDS94.
- **Primary links:** https://datatracker.ietf.org/doc/draft-irtf-cfrg-fiat-shamir/03/ ; https://datatracker.ietf.org/doc/draft-irtf-cfrg-sigma-protocols/03/ ; https://ir.cwi.nl/pub/1456/
- **Source type / venue:** CFRG active Internet-Drafts/work in progress; peer-reviewed CRYPTO paper.
- **Publication/revision dates:** both CFRG drafts 2026-08-17, expiring 2027-02-18; CDS paper 1994.
- **Verified source claim:** the August 2026 Fiat–Shamir draft requires the application context/session identifier and encoded proof instance to be unambiguous and prefix-free; the encoded instance fixes the concrete statement being proven. The Sigma draft treats the instance as the public relation shared by prover and verifier, while OR composition requires care around which clauses are composed.
- **Repository fact:** the ZK-ARCHE challenge transcript absorbs `r_0..r_n-1` and `A_0..A_n-1` in caller-supplied order. Neither Rust nor C sorts roles or rejects duplicates. Both select the first index whose role value equals the hidden `role_code`.
- **Bottleneck addressed:** mathematical review and deterministic Rust/C/profile interoperability currently lack a normative answer to whether `allowed_roles` means a mathematical set, an ordered list, or a multiset.
- **Strongest distinct engineering idea:** if the intended authorization object is a set, define one canonical representation: non-empty bounded list, unique role codes, strict ascending numeric order, duplicate rejection, and exact max-cardinality behavior before proving/verifying. Prefer validating already-canonical input over sorting silently at verification boundaries so malformed representations cannot acquire aliases. If ordered-list semantics are truly intended, state that explicitly and stop calling the object a set.
- **Evidence maturity:** repository behavior is directly observed; external drafts give a strong serialization/instance-review criterion but do not prescribe ZK-ARCHE's exact role encoding.
- **Limitations / uncertainty:** duplicate/permuted role encodings are not demonstrated here to break CDS soundness. The primary concern is statement ambiguity, aliasing, reviewability, deterministic vectors, policy/profile mismatch, and privacy fingerprinting through representation variability.
- **ZK-ARCHE relevance:** authorization semantics must be identical across Rust, C, vectors and profiles before an external reviewer can analyze “the” relation being proved.
- **Wire / CPU / RAM / flash / dependency / trust / privacy impact:** no extra wire bytes are needed. O(n) canonical-order/duplicate validation is sufficient if callers provide sorted input; RAM/flash cost is negligible. Tightening acceptance may reject previously accepted duplicate/permuted encodings and therefore needs explicit compatibility review. Canonicalization reduces representation aliases/fingerprinting surface.
- **Rust/C / vector/profile compatibility impact:** add governed negative vectors for duplicate role codes, noncanonical order, empty list, maximum count and permutation; require identical error/disposition semantics. Positive vectors should name the canonical role-list representation.
- **Required next evidence:** a written mathematical statement/relation, canonical role-list contract, Rust/C negative corpus, and independent review of completeness/soundness/witness-indistinguishability under that exact statement.

### D20260918-F03 — Rust/C proof-element canonicality checks are not equivalent before CDS verification

- **Novelty:** new concrete conformance gap.
- **Backlog owner:** R-007; adjacent R-004 parser/model-equivalence work.
- **Sources:** RFC 9496, “The ristretto255 and decaf448 Groups”; official libsodium Ristretto documentation.
- **Primary links:** https://www.rfc-editor.org/rfc/rfc9496.html ; https://doc.libsodium.org/advanced/point-arithmetic/ristretto
- **Source type / venue:** CFRG/IETF Informational RFC; original library documentation.
- **Publication/revision date:** RFC 9496, 2023-12; libsodium documentation verified 2026-09-18.
- **Verified source claim:** RFC 9496 defines Ristretto decoding with canonical validation and recommends rejecting noncanonical scalar encodings. Libsodium documents `crypto_scalarmult_ristretto255()` scalar inputs and scalar arithmetic operands as being in `[0,L[`, and provides canonical point validation plus a random-scalar API over `]0,L[`.
- **Repository fact:** Rust AUTH_1 decoding routes each branch point through Ristretto decompression/identity rejection and each branch scalar through `Scalar::from_canonical_bytes`. C AUTH_1 decoding raw-copies branch `A/c/s` bytes. The current C AUTH_1 server path explicitly checks `eph_c` and `c_prime`, but no equivalent pre-verification canonical scalar check or complete branch-point validation is present before CDS arithmetic; `auth_check_scalar()` exists but is not integrated into this path.
- **Bottleneck addressed:** Rust/C differential conformance and the cryptographic library precondition boundary are underspecified for adversarial proof encodings.
- **Strongest distinct engineering idea:** make proof decoding/verification consume one explicit canonical input contract in both implementations: valid non-identity Ristretto points where required, canonical scalar encodings, bounded branch count, and identical malformed-input disposition before group/scalar arithmetic. Build the negative corpus from RFC 9496 invalid encodings plus boundary scalars (`L`, `L+1`, all-`ff`, identity, malformed points) and CDS-specific branch mutations.
- **Evidence maturity:** high for the implementation/API mismatch; no exploit or accepted invalid proof has been reproduced yet.
- **Limitations / uncertainty:** libsodium may reject or transform some malformed inputs in ways that happen to fail verification, but relying on unspecified/out-of-precondition behavior is not a conformance contract. This report therefore does not claim a proof forgery.
- **ZK-ARCHE relevance:** deterministic acceptance/rejection parity is required for cross-language conformance, fuzzing, formal-parser assumptions and external cryptographic review.
- **Wire / CPU / RAM / flash / dependency / trust / privacy impact:** no wire change. Validation adds negligible CPU/flash and no meaningful RAM. It reduces dependence on undocumented library behavior and shrinks parser/proof ambiguity. Privacy impact is indirect through deterministic failure behavior.
- **Rust/C / vector/profile compatibility impact:** create one shared malformed-point/noncanonical-scalar corpus consumed by both Rust and C before proof verification; record the same semantic rejection class even if language/library internals differ.
- **Required next evidence:** local exact-head reproduction of the current Rust/C acceptance matrix; governed negative corpus; C validation boundary; fuzz seeds for mutated branch encodings; parser-to-proof traceability in assurance evidence.

## 6. Cross-source synthesis

The August 17, 2026 revisions of the CFRG Sigma and Fiat–Shamir drafts materially sharpen R-007. The Sigma draft now speaks directly to the exact OR-composition implementation issue present in ZK-ARCHE: the simulated clause is witness-selected, so real and simulated clauses should follow the same code path with constant-time transcript selection. The Fiat–Shamir draft likewise makes the composability boundary more explicit: a 32-byte session identifier names the argument context and must uniquely identify the argument system, message types/codecs, hash suite and language, while the first absorbed instance fixes the concrete statement.

ZK-ARCHE already has useful domain separation: the role proof uses `client_role_set_v1`, and its challenge binds `pid`, `nonce_c`, `eph_c`, `c_prime`, the role sequence and branch commitments. The remaining research obligation is to prove that this is sufficient under the actual version/method/suite/profile composition, or to bind a canonical proof-context digest explicitly. This is an assurance requirement, not an automatic proposal to replace the current transcript construction with the CFRG draft's sponge API.

A smaller conformance point should also be retained for review: Rust and C currently generate scalars by reducing 64 random bytes, which RFC 9496 permits for obtaining a uniformly distributed scalar, but the current Sigma/Fiat–Shamir guidance treats prover randomness/nonces as secret and the Sigma draft's implementation guidance should be checked against the possibility of zero after reduction and against the desired nonzero-scalar contract. The probability is negligible; this is a specification/review item, not an observed failure.
