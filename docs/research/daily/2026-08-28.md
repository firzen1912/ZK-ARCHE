## 1. Executive synthesis

1. **The Rust and C `ZKCTX` parsers do not yet have equivalent hostile-input resource behavior.** Rust constructs `Vec::with_capacity(entry_count)` directly from the attacker-controlled 16-bit entry count before proving that the input contains that many entries or enforcing a selected-profile limit; C parses into caller-owned bounded storage and its hash-only path allocates no entry array. RFC 8949 explicitly warns that hostile length/count fields can drive oversized allocations and resource exhaustion. This is a concrete Rust/C decision-parity and DoS evidence gap under R-011/TD-004, not a reason to change the wire encoding.
2. **The new `iot-core` authorization generations/epochs need an unambiguous authority/provenance namespace.** The schema has holder, audience, role policy, scope, authorization generation, policy epoch, and revocation epoch, but no explicit issuer/authority field. ACE and CWT treat authorization as issued by an authorization authority and provide issuer/audience semantics; the July 2026 ACE EDHOC/OSCORE profile also explicitly binds the client's authentication credential to authorization material. ZK-ARCHE can remain infrastructure-independent, but it must define whether authority identity is immutable implicit profile/deployment state or explicitly authenticated context so that generation/epoch values cannot be confused across authorities or reprovisioning domains.
3. **The unresolved replay fresh-epoch rule should be evaluated as a new authenticated security-context transition, not as a cache reset.** The July 6, 2026 KUDOS -14 draft replaces an old OSCORE Security Context with a newly established one, handles peers with and without nonvolatile storage differently, and requires re-establishing suitable keying material after reboot when latest material was volatile. This strongly corroborates ZK-ARCHE's new fail-closed continuity contract and gives R-009 a concrete comparator for predecessor/new-epoch binding, interrupted transitions, and constrained persistence.
4. No new cryptographic primitive, mandatory infrastructure dependency, production AUTH-v3 enablement, roadmap/spec/ADR/code mutation, debt clearing, formal-verification claim, or release-status change is justified by this report.

## 4. Findings

### D20260828-F01 — Rust parser pre-allocation creates a hostile-count resource asymmetry relative to bounded C parsing

- **Novelty:** new
- **Primary source:** RFC 8949, *Concise Binary Object Representation (CBOR)*, Security Considerations
- **Primary link:** https://www.rfc-editor.org/rfc/rfc8949.html
- **Source type / date:** IETF Standards Track RFC, December 2020
- **Verified source-supported claim:** network-facing decoders must assume hostile input. RFC 8949 specifically warns that attacker-controlled lengths/sizes can trigger very large allocations and resource exhaustion and says decoders need appropriate resource management; validation effort should avoid attacker-amplified or superlinear resource consumption.
- **Existing owner:** R-011 / TD-004 / `spec/auth-v3-context-encoding.md` §9
- **Repository fact:** Rust's generic parser allocates capacity based on the untrusted `u16 entry_count` before proving the bytes are structurally large enough or enforcing a profile maximum. A 9-byte header declaring `entry_count=65535` can therefore request a large vector allocation before the parser returns `Truncated`. C uses caller-owned bounded entry storage and rejects `entry_count > entries_capacity` before capture; its hash-only path performs no entry-array allocation.
- **Problem addressed:** malformed unauthenticated AUTH-v3 context bytes could impose materially different memory pressure in the Rust and C lanes even though both ultimately reject the same malformed input. This weakens the common-contract requirement that the two implementations be decision-compatible and resource-bounded on attacker-controlled pre-authentication data.
- **Strongest distinct engineering idea:** enforce a bound **before allocation**. Options for explicit human review include: (a) pass a selected-profile maximum entry count/total bytes into the parser; (b) derive a safe structural upper bound from `input.len()` before allocation; (c) use a small fixed/stack-backed representation for constrained profile parsing; or (d) parse/hash in a streaming form and only materialize entries after bounded validation. The key invariant is that attacker-declared count alone never controls a large allocation.
- **Evidence maturity:** software
- **Limitations / uncertainty:** this report did not execute a memory benchmark or prove exploitable process failure. Rust allocators may reject or overcommit differently across targets, and the current draft remains non-selectable. The issue is therefore a reproducible resource-asymmetry hypothesis, not a vulnerability claim.
- **Wire / CPU / RAM / flash / dependency / trust impact:** no wire change is required. A pre-allocation bound should reduce worst-case RAM pressure and preserve linear validation cost. Exact MCU/host limits belong to profile evidence.
- **Rust/C / vector compatibility impact:** add shared malformed-count fixtures such as `entry_count=65535` with only the 9-byte header and boundary values around each promoted profile maximum; both lanes should reject before large allocation or unbounded iteration. Record peak allocation/stack behavior for the Rust parser and C caller-capacity path.
- **Required next evidence:** Rust heap-allocation instrumentation for hostile count fields; profile-bound parser API or equivalent pre-allocation guard; shared Rust/C boundary corpus; retained CI demonstrating identical accept/reject classes; constrained target measurements when TD-002 work reaches hardware.
- **Recommended disposition:** reproduce

### D20260828-F02 — Authorization generation/epoch values need an explicit or immutable implicit authority namespace

- **Novelty:** refines
- **Primary sources:** RFC 9200, *Authentication and Authorization for Constrained Environments Using the OAuth 2.0 Framework (ACE-OAuth)*; RFC 8392, *CBOR Web Token (CWT)*; `draft-ietf-ace-edhoc-oscore-profile-11`
- **Primary links:** https://www.rfc-editor.org/rfc/rfc9200.html ; https://www.rfc-editor.org/rfc/rfc8392.html ; https://datatracker.ietf.org/doc/draft-ietf-ace-edhoc-oscore-profile/
- **Source type / dates:** IETF Standards Track RFCs (2018/2022) plus active ACE WG Internet-Draft -11, July 6, 2026
- **Verified source-supported claim:** ACE models authorization permissions as issued by an Authorization Server and consumed by a Resource Server, with audience and proof-of-possession/credential binding as important authorization context. CWT defines an `iss` issuer claim and an `aud` audience claim for contexts that need them. The July 2026 ACE EDHOC/OSCORE profile explicitly binds a client's authentication credential to ACE authorization material.
- **Existing owner:** R-008 / R-012 / R-013 / TD-004
- **Repository fact:** draft `iot-core` authorization v1 includes `holder_binding`, `audience_id`, `role_policy_id`, `scope_bits`, `authorization_generation`, `policy_epoch`, and `revocation_epoch`. It intentionally avoids an online authorization-server dependency, but the encoded context does not identify the authority/issuer namespace under which the three lifecycle integers are interpreted.
- **Problem addressed:** if a deployment can be reprovisioned, federated, migrated between commissioners/authorities, or accept more than one local authorization authority, the same numeric generation/epoch values can have different meanings. `authorization_generation=7` or `revocation_epoch=12` is only meaningful relative to an authority/lineage namespace. Audience alone does not necessarily identify that authority.
- **Strongest distinct engineering idea:** make authority provenance **cryptographically unambiguous without making online infrastructure mandatory**. Two viable design classes deserve explicit review: (1) an immutable implicit authority namespace derived from locally provisioned profile/deployment trust state and included in the holder/policy lookup decision; or (2) a compact explicit `authority_id`/authorization-lineage identifier included in the canonical authorization context. Either way, Rust/C must reject cross-authority generation/epoch substitution and reprovisioning rollback.
- **Evidence maturity:** externally-reviewed concept + software schema
- **Limitations / uncertainty:** ACE/CWT do not require ZK-ARCHE to adopt OAuth, CWT, a CA, or an online AS. A single-authority closed deployment can keep the authority implicit if its namespace is unambiguous and immutable under the profile contract. Adding an explicit field would change the current 148-byte draft authorization encoding and therefore requires versioned human review.
- **Wire / CPU / RAM / flash / dependency / trust impact:** an implicit namespace can cost zero wire bytes but requires precise local-state/versioning rules. An explicit 16/32-byte authority identifier plus the five-byte ZKCTX entry header would add wire/hash input and require a versioned schema update. Neither option requires network reachability.
- **Rust/C / vector compatibility impact:** add cross-authority negative fixtures: same holder/audience/generation under authority A vs B; authority reprovisioning with reused numeric epochs; stale predecessor authority state after migration; and same audience with distinct authority namespaces.
- **Required next evidence:** explicit statement of authority namespace semantics for `iot-core`; proof that generation/policy/revocation values are interpreted only inside that namespace; Rust/C cross-authority substitution tests; migration/reprovisioning rules; byte-budget review if an explicit field is proposed.

### D20260828-F03 — Fresh replay epochs should be tested as authenticated new-security-context transitions with crash/reboot semantics

- **Novelty:** refines
- **Primary source:** `draft-ietf-core-oscore-key-update-14`, *Key Update for OSCORE (KUDOS)*
- **Primary link:** https://datatracker.ietf.org/doc/draft-ietf-core-oscore-key-update/
- **Source type / date:** active CoRE WG Standards Track Internet-Draft -14, July 6, 2026
- **Verified source-supported claim:** KUDOS updates OSCORE by establishing a **new Security Context** that replaces the old one. It distinguishes old, temporary, and new contexts; treats key-use expiration/limits as hard stops; and explicitly handles devices according to nonvolatile-storage capability. If latest security context material was kept only in volatile memory and is lost on reboot, the peer must first establish new suitable keying material before continuing key update operation.
- **Existing owner:** R-009 / TD-003 / TD-004 / `spec/replay-continuity.md` §6
- **Repository fact:** ZK-ARCHE now correctly enters `CONTINUITY_BROKEN` when replay state is missing, stale, unverifiable, or rollback-suspected, and explicitly rejects the idea that a process restart, transport reconnect, address change, or fresh outer `session_id` alone creates a new replay epoch. The remaining unresolved item is the authenticated fresh replay-epoch mechanism.
- **Problem addressed:** a future recovery procedure must make old accepted AUTH material cryptographically inapplicable or unambiguously predecessor-scoped in the new epoch, while surviving interrupted transition and different persistence capabilities. Simply clearing the cache or incrementing an unauthenticated local counter does not establish freshness.
- **Strongest distinct engineering idea:** evaluate fresh replay-epoch designs as **security-context replacement state machines** with explicit predecessor/new-context binding and crash states. Candidate experiments should compare (a) full fresh AUTH/rekey deriving a new epoch-bound security context; (b) an authenticated rekey/epoch transition rooted in already-authorized local trust; and (c) reprovisioning/recommissioning recovery. Do not choose among them from research alone; first require a state/packet/flash-cost matrix and formal/runtime negative tests.
- **Evidence maturity:** software/standards work-in-progress
- **Limitations / uncertainty:** KUDOS is OSCORE-specific and still an Internet-Draft. Its exact wire format, forward-secrecy modes, storage model, and trust assumptions must not be copied blindly into ZK-ARCHE. The relevant lesson is lifecycle structure, not protocol dependency.
- **Wire / CPU / RAM / flash / dependency / trust impact:** a genuine fresh epoch will require authenticated state transition and new context/key material, so it has nonzero cryptographic and persistence cost. The cost depends on whether recovery uses full AUTH, rekey, or reprovisioning. No external service is inherently required.
- **Rust/C / vector compatibility impact:** eventual shared fixtures should cover predecessor epoch replay after transition, simultaneous/divergent transitions, crash before durable commit, crash after durable commit but before acknowledgment, restored-old-state rollback, nonvolatile-capable vs volatile-only targets, and interruption with no silently accepted empty window.
- **Required next evidence:** bounded candidate design matrix; explicit predecessor/new-epoch transcript/key binding; crash-consistency state machine; Rust/C deterministic transition fixtures; formal properties for no AUTH admission during `CONTINUITY_BROKEN` and no predecessor replay acceptance after successful transition; target flash/endurance measurements where persistence is used.

## 5. Cross-source synthesis

Today's three findings converge on one implementation rule: **security-context semantics must be bounded not only cryptographically but operationally**.

```text
untrusted bytes
   -> bounded parse before allocation
   -> canonical context
   -> authorization interpreted inside one authority namespace
   -> accepted AUTH recorded inside one replay/security epoch
   -> state loss fails closed
   -> recovery establishes a newly authenticated security context
```

The canonical byte work added since yesterday materially improves TD-004, but it creates sharper implementation obligations. Deterministic encoding is insufficient if one lane allocates from attacker-declared counts before enforcing profile bounds. Likewise, monotonic authorization epochs are insufficient if their authority namespace is ambiguous. Finally, replay continuity is not restored until the protocol authenticates a genuinely new security context or safely restores trusted predecessor state.
