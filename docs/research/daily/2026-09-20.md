## 2. Executive synthesis

- The strongest new evidence is `draft-ietf-core-oscore-id-update-07`, published **2026-09-07**. It treats a visible identifier update as security-context lifecycle work: in stand-alone mode it derives new traffic keys/Common IV and reinitializes sender sequence and replay state, rather than swapping a label while keeping all security state unchanged.
- The draft also introduces a precise **prepare-versus-activate** privacy boundary for network migration: peers may establish new identifiers in advance, but using the new identifier on the old network—or the old identifier on the new network—can itself create the cross-network correlation the rotation was intended to prevent.
- Most importantly for constrained ZK-ARCHE profiles, the draft makes identifier non-reuse state security-critical. After loss of the latest context or the history of identifiers used under the current master-key tuple, a peer must not perform stand-alone identifier update until a full security-context establishment/renewal occurs.
- ZK-ARCHE already has the right separation to absorb this lesson safely: the 16-byte `session_id` is a correlation value, not identity/authority; transport changes do not create replay epochs; and replay continuity fails closed after unverifiable state loss. The missing piece is an explicit evidence contract for any future **rotatable privacy handle generation** and its relationship to replay/key generations.
- No wire, profile, roadmap, spec, code, formal model, assurance claim, technical-debt state, or release claim changes in this run. R-015 and R-009 remain `reproduce`.

## 5. Findings

### D20260920-F01 — Privacy-handle rotation is a lifecycle transition, not a metadata-only rename

- **Novelty:** new
- **Backlog owner:** R-015 / R-009
- **Source:** Höglund & Tiloca, *Identifier Update for OSCORE*, `draft-ietf-core-oscore-id-update-07`
- **Primary link:** https://datatracker.ietf.org/doc/draft-ietf-core-oscore-id-update/07/
- **Source type / venue:** IETF CoRE Working Group Internet-Draft, Standards Track work in progress
- **Publication or release date:** 2026-09-07
- **Verified claim:** OSCORE Sender/Recipient IDs are plaintext correlation surfaces. In stand-alone identifier update, the peers derive a new Sender Key, Recipient Key, and Common IV and reinitialize Sender Sequence Number and Replay Window. New IDs must not be used with the old security context. The update therefore changes security-context state rather than only a label.
- **Existing engineering owner:** TD-004; R-015 privacy-observability; R-009 replay/key lifecycle; `spec/privacy-considerations.md`; `spec/replay-continuity.md`
- **Repository fact:** ZK-ARCHE v2 has a fixed-width 16-byte `session_id` used for correlation, but its current framing contract explicitly says that changing a `session_id` or transport does not create a fresh replay epoch. The current replay contract has no promoted fresh-epoch mechanism.
- **Problem addressed:** A future attempt to improve unlinkability by merely rotating a visible ZK-ARCHE correlation value could either (a) leave replay/key semantics ambiguous or (b) accidentally reset replay/authority state by treating the new handle as a new security epoch.
- **Strongest distinct engineering idea:** Model three independent objects: `semantic_association`, `visible_handle_generation`, and `security/replay_generation`. A profile that rotates a visible handle must state whether that rotation is purely representational or is cryptographically coupled to a fresh security/replay generation; it must never imply the coupling accidentally.
- **Evidence maturity:** software (IETF design with implementation-oriented protocol state); ZK-ARCHE mapping remains concept/reproduction work
- **Limitations / uncertainty:** OSCORE's identifiers, AEAD nonce construction, and security context are not ZK-ARCHE's wire/session model. The draft is work in progress and cannot be imported as a mandatory dependency. No evidence today shows that the existing ZK-ARCHE `session_id` is unsafe under its current stated claim boundary.
- **ZK-ARCHE inference:** Keep the current rule that `session_id` is non-authoritative. If a future privacy profile rotates a cleartext correlation handle, require an explicit transition contract saying which replay/key generation remains authoritative before, during, and after rotation. A handle change alone must not repair broken replay continuity, stale authorization, revocation, lineage, or channel binding.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** A rotation mechanism could keep the existing fixed-width field and add no per-packet bytes, but it would add state-machine complexity and likely retain current/next generation metadata. If rotation is coupled to key derivation/replay reset, CPU/key-derivation work and persistent lifecycle state increase. No OSCORE dependency is recommended.
- **Rust/C / vector compatibility impact:** Future evidence should include common vectors for same-association/new-handle without replay reset, handle rotation coupled to an authenticated fresh epoch when a profile defines that mode, old-handle use after activation, duplicate/rollback generation, and proof that none of these events revives stale authorization/revocation/lineage state.
- **Required next evidence:** a small transport-neutral state corpus that separates association ID, handle generation, replay generation, and authority generation; equivalent Rust/C decisions; then a formal model that proves handle rotation cannot create AUTH/DATA authority or fresh replay continuity by itself.
- **Recommended disposition:** reproduce
- **Weekly finding candidate:** yes

### D20260920-F02 — Migration privacy needs a staged prepare/activate barrier tied to the path transition

- **Novelty:** refines
- **Backlog owner:** R-015
- **Source:** `draft-ietf-core-oscore-id-update-07`, Section 2.4.2
- **Primary link:** https://www.ietf.org/ietf-ftp/internet-drafts/draft-ietf-core-oscore-id-update-07.html
- **Source type / venue:** IETF CoRE Working Group Internet-Draft
- **Publication or release date:** 2026-09-07
- **Verified claim:** Peers may negotiate/derive new OSCORE identifiers before a network migration, but should not use them on the old network. Using a new ID before migration or continuing to use the old ID after migration can let observers correlate the old and new network activity. The draft therefore permits preparing the new context while delaying activation until the first protected request on the new network; the old context may be retained for migration back.
- **Existing engineering owner:** R-015; `spec/privacy-considerations.md`; `spec/transport-association-continuation.md`
- **Repository fact:** Current ZK-ARCHE continuation semantics correctly separate route change from identity/authority and allow continuation after route/connection replacement only when authenticated context remains current. However, there is no promoted rotatable visible-handle generation or migration-time privacy activation state.
- **Problem addressed:** A rotation policy that is cryptographically correct can still fail its privacy objective if activation timing itself gives the observer a linking event.
- **Strongest distinct engineering idea:** Use an explicit two-stage state for any future migration-aware privacy handle: `NEXT_PREPARED` and `CURRENT_ACTIVE`. Preparation can happen under the old path, but the newly visible handle does not become externally usable until the migration event/profile condition is satisfied. Retained predecessor context is a routing/processability concern, not continuing application authority on the new path.
- **Evidence maturity:** software/concept
- **Limitations / uncertainty:** The IETF draft assumes OSCORE/CoAP and a defined network-migration event. Some ZK-ARCHE transports (serial, CAN, robotics middleware, BLE) may not expose an equivalent path transition, and global traffic analysis can still correlate flows by timing/size even after identifier rotation.
- **ZK-ARCHE inference:** If a future profile promises cross-path unlinkability improvement, the profile must specify the activation event and what an observer can see before/after it. Existing transport-continuation decisions should remain authority decisions; privacy-handle activation should be a separate state machine so a path validation/route change cannot accidentally authenticate a peer or refresh authorization.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** Likely zero additional steady-state bytes if an existing handle field is rotated; temporary RAM/persistent state may hold current and prepared-next handle/context. CPU impact is small for a pure handle transition but higher if tied to fresh key derivation. Trust model is unchanged: transport path remains non-authoritative.
- **Rust/C / vector compatibility impact:** Add future paired vectors for `prepared-before-migration`, `new-handle-on-old-path -> privacy-policy reject/not-active`, `old-handle-on-new-path -> not-current`, `activate-on-migration`, `migration-back`, and path change with unchanged authority. Repeated packet-capture tests should verify correlation surfaces rather than infer unlinkability from state-machine success.
- **Required next evidence:** define the observable attacker model and migration event for at least one concrete profile; capture old-path/new-path traces; measure whether handle timing/size/retry behavior introduces a deterministic linking oracle; preserve Rust/C decision parity.
- **Recommended disposition:** reproduce

### D20260920-F03 — Anti-reuse history and state-loss handling are part of the privacy claim and must be bounded for MCU profiles

- **Novelty:** new
- **Backlog owner:** R-015 / R-009
- **Source:** `draft-ietf-core-oscore-id-update-07` Section 2.4.3; `draft-ietf-core-oscore-key-update-14`; RFC 8613
- **Primary links:** https://datatracker.ietf.org/doc/draft-ietf-core-oscore-id-update/07/ ; https://datatracker.ietf.org/doc/draft-ietf-core-oscore-key-update/ ; https://www.rfc-editor.org/rfc/rfc8613.html
- **Source type / venue:** IETF CoRE Working Group Internet-Drafts plus Standards Track RFC
- **Publication or release date:** ID Update -07: 2026-09-07; KUDOS -14: 2026-07-06; RFC 8613: 2019-07
- **Verified claim:** The ID-update draft requires a stand-alone update to stop after loss of the latest context or the complete set of IDs used with the current `(Master Secret, Master Salt, ID Context)` until a full security-context establishment/renewal occurs. A newly proposed ID must be currently available and must never have been used under that master-key tuple; failed/offered IDs are also retained against reuse. KUDOS separately distinguishes devices able to persist dynamic security state from devices that cannot, and notes the persistent-memory cost of stateful forward-secure updates/counters.
- **Existing engineering owner:** R-009; R-015; TD-002; `spec/replay-continuity.md`
- **Repository fact:** ZK-ARCHE's replay-continuity contract already fails closed when replay state is missing, corrupt, stale, or rollback-suspected, and explicitly refuses to treat a new session identifier as recovery. The current formal replay model preserves that fail-closed property but intentionally lacks a fresh-epoch construction and physical persistence proof.
- **Problem addressed:** Privacy rotation can create its own anti-reuse state. If that state is forgotten or rolled back, the system may reissue a previously observable handle and silently defeat the claimed unlinkability scope; if the history is retained naively forever, it creates unbounded MCU RAM/flash/wear cost.
- **Strongest distinct engineering idea:** Treat privacy-handle non-reuse as an evidence-bearing continuity domain. After unverifiable rollback/state loss, standalone handle rotation must fail closed or require a stronger authenticated rekey/re-auth/reprovisioning transition. Research a bounded generation-derived handle design versus explicit used-handle sets, with the security proof determining whether history can be bounded when key generation changes.
- **Evidence maturity:** software + standards design; constrained-hardware impact remains unmeasured
- **Limitations / uncertainty:** The IETF draft's exact used-ID set is tied to OSCORE nonce/security-context rules. A ZK-ARCHE derivation-based design would need independent cryptographic review; simply hashing a counter is not sufficient evidence of non-reuse or unlinkability. Persistent storage claims remain target-specific.
- **ZK-ARCHE inference:** Extend the R-015/R-009 evidence contract conceptually—not normatively—to include privacy-handle generation persistence, rollback behavior, history bounds, and the event that safely resets/rekeys the non-reuse namespace. This should share the repository's existing fail-closed continuity doctrine rather than invent a privacy-only exception after reboot.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** Explicit history can grow with rotations and cause flash writes/wear. A generation-derived construction could reduce stored history to bounded generation/counter state but adds PRF/KDF work and places stronger requirements on rollback-safe persistence. CPU cost is likely small relative to public-key AUTH, but STM32/ESP32-S3 measurements are still required. No cloud/CA/gateway dependency should be introduced merely to rotate a privacy handle.
- **Rust/C / vector compatibility impact:** Future fixtures should cover handle reuse within a generation, failed-offer reuse, restart with trusted state, restart with missing history, rollback-suspected generation, fresh authenticated generation transition, and predecessor-handle rejection/processability rules. Rust/C should emit the same semantic state, not merely the same bytes.
- **Required next evidence:** derive an explicit maximum rotation count/storage budget for `iot-core`; prototype two approaches (explicit used-handle history vs bounded generation-derived handles) in test-only code; measure RAM/flash writes and restart behavior on ESP32-S3/STM32; independently review the derivation/non-reuse argument before promotion.
- **Recommended disposition:** benchmark / reproduce

## 6. Cross-source synthesis

The fresh IETF evidence makes one decision boundary much sharper: **unlinkability-oriented identifier rotation is not free state**. OSCORE's design couples visible identifiers to security-context derivation, replay state, non-reuse history, migration activation, and reboot recovery. KUDOS shows why that matters on constrained targets: designs that depend on durable dynamic state need an explicit capability/storage contract, and a reboot can force stronger context establishment when that state cannot be trusted.

ZK-ARCHE should not copy OSCORE's wire format or identifier semantics. Instead, the transferable invariants are:

1. a visible privacy/correlation handle is separate from authenticated identity/authorization;
2. rotating the handle does not, by itself, create a fresh replay/key/authorization generation;
3. if a profile deliberately couples rotation to a fresh security generation, that coupling must be authenticated and testable;
4. migration-aware privacy requires a prepare/activate cut, not merely a fresh random value;
5. handle non-reuse state has restart/rollback semantics and a resource cost;
6. loss of that state must not silently improve privacy by forgetting history while weakening replay/security continuity.

This is consistent with current ZK-ARCHE boundaries and exposes a concrete reproduction/benchmark target rather than an immediate architecture rewrite.
