The real clause performs fewer visible scalar-multiplication operations than simulated clauses. C pre-draws a fixed total number of random bytes, but the **per-index arithmetic/control-flow schedule is not uniform**. ## 5. Findings

### D20261106-F01 — Witness-index-dependent prover control flow requires a dedicated leakage oracle

- **Novelty / item:** refines R-007 with exact code-level evidence; R-015 privacy cross-reference.
- **Source:** *Sigma Proofs for Linear Relations*, `draft-irtf-cfrg-sigma-protocols-04`, §7.6; and the preceding -03 §7.6.
- **Primary links:** https://datatracker.ietf.org/doc/draft-irtf-cfrg-sigma-protocols/04/ ; https://datatracker.ietf.org/doc/html/draft-irtf-cfrg-sigma-protocols-03
- **Type / date:** IRTF CFRG informational **Internet-Draft**, 2026-11-02 (not an RFC); -03 pre-existed. Source-backed caution is *not* newly invented by -04.
- **Verified source fact:** For OR composition, the witness selects the simulated/real clause; real and simulated paths **SHOULD** use the same code path and constant-time transcript selection. Secret scalar operations require constant-time implementations. This is a design recommendation, not a proof of ZK-ARCHE leakage.
- **Engineering owner / repository fact:** TD-001 / R-007. `rust/crates/proto/src/crypto.rs::prove_role_set_membership_with_rng` finds `true_index` from the role, then for `i == true_index` draws one scalar `w` and calculates `h*w`; other clauses draw `c_i,s_i` and calculate `h*s_i - y_i*c_i`. `c/src/crypto/proofs.c::auth_prove_role_set_membership_with_bytes` similarly branches on `true_idx`, performs one real-clause scalar multiplication versus two simulated-clause scalar multiplications plus subtraction, and positions per-clause secret/scalar writes differently. C's enclosing helper obtains a fixed `64*(2*n-1)` bytes **per proof**, not constant per-role-index arithmetic. `role_set_membership.json` records the same witness-dependent per-index draw layout.
- **Bottleneck:** A fixed overall byte count or byte-exact Rust/C correctness vector does **not** prove that hidden-role index is unobservable from the prover's CPU/cache/timing/power/EM behavior.
- **Distinct engineering idea:** First record the *same* allowed-role set, public transcript inputs, key/nonce profile and randomized repetitions for **each valid true index**, then instrument per-branch RNG calls, scalar multiplications, buffer writes, instruction traces and high-resolution timing across optimized Rust/C binaries. Test constant-time backends and actual constrained targets separately. A potential uniform-schedule/constant-time-selection remediation must undergo its own mathematical distribution, randomness, memory and wire-compatibility review rather than automatic implementation.
- **Evidence maturity:** software (static source audit of existing code); no new executed benchmark, hardware leakage evidence or exploit.
- **Limitations / uncertainty:** Branching and operation-count differences are visible in source, but compiler optimization, library behavior and measurement noise determine actual observability. This finding does **not** assert remote exploitability, knowledge of a role from network captures, or that OR-proof math is unsound. Fixing control flow without reviewing transcript distributions could itself introduce a flaw.
- **ZK-ARCHE inference:** Treat per-secret-index control/operation parity as a separate gate from deterministic vectors and from mathematical soundness/HVZK. Independently evaluate whole-protocol role privacy.
- **Likely impact:** wire 0 if limited to prover internal scheduling; added CPU work, entropy, stack/RAM, and possibly flash if uniform-path mitigation is selected, all **unmeasured**. Existing Ristretto255/SHA-256 suite and local-trust model remain unchanged; impact on privacy could be material depending on threat model and observer.
- **Rust/C/vector/profile compatibility:** Current `0x0001` deterministic fixture deliberately encodes role-specific DRBG consumption order; a uniform-schedule change would likely change test-vector proof bytes and require explicit versioned vector review. No iot-core MCU result exists. Avoid silently editing code/vectors or changing suite semantics.
- **Required next evidence:** retained per-index trace/timing dataset plus compiler/optimization/backend hash, target identity and leakage statistical analysis; cross-language output/distribution parity; cryptographer review of the CDS OR construction and any proposed mitigation.
- **Recommended disposition:** reproduce. **Weekly finding candidate:** yes.

### D20261106-F02 — Fresh CFRG -04 reference fixtures need a suite-aware, paired-decision conformance ledger

- **Novelty / item:** refines R-007 standards/source baseline; not a new proof system.
- **Sources:** *Fiat–Shamir Transformation*, `draft-irtf-cfrg-fiat-shamir-04`; *Sigma Proofs for Linear Relations*, `draft-irtf-cfrg-sigma-protocols-04`; respective -03 baselines.
- **Primary links:** https://datatracker.ietf.org/doc/draft-irtf-cfrg-fiat-shamir/04/ ; https://datatracker.ietf.org/doc/draft-irtf-cfrg-sigma-protocols/04/
- **Type / date:** IRTF CFRG informational Internet-Drafts, both 2026-11-02; work in progress, not published RFCs.
- **Verified source fact:** Fiat–Shamir -04 specifies transcript/challenge/serialization and reject-on-invalid NARG processing with reference test vectors. Sigma -04 Appendix A identifies *valid* and *adversarial* vectors; each adversarial case names its corresponding valid base so a verifier that rejects everything cannot falsely pass. Its specified examples use P-256 or BLS12-381, and the Sigma document distinguishes the linear-map proof it specifies from externally composable OR proofs.
- **Engineering owner / repository anchor:** R-007 / TD-001; `rust/test-vectors/0x0001/role_set_membership.json`, `rust/crates/proto/src/crypto.rs`, `c/src/crypto/proofs.c`, `spec/implementation-requirements.md`.
- **Bottleneck:** A fixture that merely rejects corrupted `c_prime` cannot establish acceptance of the matching original, replay/statement binding, full proof consumption, or all canonical parse rules across Rust and C.
- **Distinct engineering idea:** Maintain a **paired** (valid proof → accept, one mutation → reject) ledger for identical suite `0x0001` fixtures: altered allowed-role order/content, duplicate/empty role sets, swapped `pid`, `nonce_c`, `eph_c`, `c_prime`, wrong proof domain, extra/truncated proof data, malformed/non-canonical point or scalar, and cross-language behavior. Pin the exact codec and tagged instance. Any external P-256/BLS12-381 fixtures may serve only as *separate* reference-library tests, never claimed as ZK-ARCHE interoperable vectors.
- **Evidence maturity:** concept (standards comparator) plus existing software vectors, **not** newly executed conformance.
- **Limitations / uncertainty:** Some proposed cases require a separate parser/wire-layer oracle; the current fixture's set-size limits and transcript context must be checked against exact v2 encoding. Revisions -03 already contained much of the conformance methodology; do not claim the -04 update invented it. Source correctness and vector passage cannot substitute for independent CDS OR soundness/ZK proof or timing review.
- **ZK-ARCHE inference:** Convert the November 2 primary drafts into a provenance-pinned, suite-aware accept/reject decision table, while explicitly excluding unreviewed protocol and proof-inheritance changes.
- **Likely impact:** no wire change for a test-only ledger; host test/CI artifact storage and harness CPU cost, not runtime RAM/flash/CPU unless adopted later. No new algorithm/dependency/trust model; positive test coverage strengthens assurance only.
- **Rust/C/vector/profile compatibility:** both lanes must independently accept the valid base and reject each mutation; MCU `iot-core` eligibility and measured footprint are unchanged.
- **Required next evidence:** local exact-HEAD corpus execution with retained Rust/C exit statuses and logs, explicit accept/reject trace mapping, and independent cryptographic review.
