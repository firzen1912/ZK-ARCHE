## 1. Executive synthesis

1. **The new `ZK-ARCHE-BIND` classifier needs a future binding-generation/epoch contract if a TLS/DTLS profile ever uses a refreshed exporter.** The active TLS Extended Key Update draft derives cryptographically independent exporter secrets for successive update epochs and expects applications to be notified when a new exporter epoch becomes active. The current Rust/C BIND decision has `binding_fresh` but no explicit exporter-generation identity, prior-epoch retention rule, or transition semantics. This does not require a wire change now; it creates a concrete R-010 reproduction target.
2. **Post-compromise channel refresh and resumption cannot be treated as independent features.** The same current TLS draft requires endpoints enabling Extended Key Update to disable NewSessionTicket PSK resumption under its compromise model because a PSK exposed before recovery can establish another authenticated connection. ZK-ARCHE's current authorization-aware resumption decision already treats a resumption secret as insufficient authorization; a future profile claiming post-compromise recovery must additionally state whether a resumption credential survives, rotates with, or is invalidated by a binding/key epoch transition.
3. **Application/authentication-domain context should remain separate from transport/profile context.** EAP-EDHOC revision 12, now in the RFC Editor queue, makes channel-binding content application/authentication-domain specific and treats consistency failure in the critical binding item as fatal. ZK-ARCHE's current BIND facts explicitly check peer and profile context, while its resumption contract separately checks deployment/domain. The future concrete binding construction should prove a domain/application-context match instead of assuming it is implied by the profile or socket.
4. **Remote attestation freshness is a separate lifecycle axis from channel freshness.** The August 5 TLS attestation draft explicitly notes that attestation Evidence/Results become stale on long-lived connections and discusses reattestation independently from key update. If ZK-ARCHE ever promotes R-006, a `BOUND` channel must not be interpreted as current device-health evidence; attestation freshness, verifier identity, appraisal policy, and privacy need a separate optional state contract.
5. **No new R-* item or status transition is justified.** R-010 owns channel-binding construction, R-009 owns resumption/key lifecycle, and R-006 owns optional attestation. Today's evidence materially refines their future acceptance tests but does not justify changing the research backlog row text or maturity status automatically.

## 4. Findings

### D20260901-F01 — Exporter freshness is an epoch/lifecycle property, not only a boolean

- **Novelty:** new
- **Primary source:** `draft-ietf-tls-extended-key-update-13`, *Extended Key Update for Transport Layer Security (TLS) 1.3*
- **Primary link:** https://datatracker.ietf.org/doc/draft-ietf-tls-extended-key-update/
- **Source type / date:** active TLS WG Internet-Draft, revision 13 published 2026-07-04
- **Source-supported fact:** the draft defines a fresh exporter interface for each successful Extended Key Update. Successive exporter secrets are cryptographically independent; applications are notified when a new epoch becomes active and may request EKM for a specific epoch. TLS and DTLS applications can temporarily retain old/new exporter material under transport-specific retention rules. The draft also states that the ordinary TLS exporter remains static across standard KeyUpdate, so an application has to know which exporter interface/security goal it is using.
- **Existing owner:** R-010 / R-009 / zk221 / zk228 / TD-004
- **Repository fact:** `TransportBindingFacts` currently expresses `binding_fresh` as one boolean and checks AUTH-instance, peer, and profile context. There is no explicit binding/exporter generation, predecessor/current epoch relation, or retention policy. This is appropriate for the current wire-neutral classifier but insufficient to claim a refreshed exporter lifecycle.
- **Problem addressed:** a future TLS/DTLS adapter could call an exporter value “fresh” without proving whether it came from the current exporter generation, a retained predecessor generation, or the legacy static exporter interface. That ambiguity becomes security-relevant if a profile claims post-compromise recovery or invalidates authorization/resumption state on a key epoch change.
- **Strongest distinct engineering idea:** keep the common BIND classifier wire-neutral, but require a future concrete TLS/DTLS binding adapter to normalize at least `binding_generation_current`, `binding_generation_relation` (`current`, `retained-predecessor`, `unknown`), exporter-interface identity, and transition-complete state before mapping to `binding_fresh=true`. Do not compare peer-local epoch counters numerically unless the transport profile proves they share semantics; the TLS draft explicitly allows the local epoch identifier to differ between peers.
- **Evidence maturity:** standards-track work in progress + software decision surface
- **Limitations:** Extended Key Update is an active Internet-Draft, not a final RFC. ZK-ARCHE does not currently implement TLS EKU or a concrete exporter-binding profile. This finding does not require EKU adoption.
- **ZK-ARCHE inference:** if a future profile supports exporter refresh, the BIND/RESUME negative corpus should include stale predecessor exporter, unknown generation, transition-in-progress, peer-local epoch-number mismatch with otherwise matching current exporter, and legacy-static-exporter used where a refreshed exporter is required.
- **Likely impact:** no mandatory wire impact; adapter state and retained-secret cost only for profiles choosing a refreshed channel binding; DTLS may need bounded predecessor retention; PCS-capable profiles add key-exchange CPU/wire cost outside the ZK-ARCHE core.
- **Rust/C/vector/profile impact:** common decision semantics should remain identical. A transport-profile fixture should normalize concrete exporter state into shared Rust/C facts rather than embedding TLS-specific state inside AUTH/TRUST.
- **Required next evidence:** define one concrete `EXPORTER-ZK-ARCHE-*` profile contract with exporter-interface identity, application/context bytes, generation-transition rules, prior-generation retention, and exact negative vectors; test standard KeyUpdate versus Extended Key Update behavior separately.
- **Recommended disposition:** reproduce
- **Weekly finding candidate:** yes

#### Resumption coupling

The same draft materially sharpens the interaction with ZK-ARCHE resumption. Under its stated endpoint-memory compromise model, PSKs issued through TLS NewSessionTicket may have been exposed before an Extended Key Update recovers the active connection; revision 13 therefore requires endpoints enabling EKU to disable such PSK resumption.

ZK-ARCHE should not copy that rule blindly into native resumption. The transferable rule is narrower: **a post-compromise recovery claim must define the compromise/recovery status of every credential capable of creating another association.** A future ZK-ARCHE profile that claims refreshed channel recovery must therefore state whether its resumption credential is independently protected and re-authorized, invalidated on binding/key-generation change, or disallowed.

### D20260901-F02 — Channel-binding semantics belong to the authentication domain, not the socket/profile alone

- **Novelty:** corroborates/refines
- **Primary source:** `draft-ietf-emu-eap-edhoc-12`, *Using the Extensible Authentication Protocol (EAP) with Ephemeral Diffie-Hellman over COSE (EDHOC)*
- **Primary link:** https://datatracker.ietf.org/doc/draft-ietf-emu-eap-edhoc/
- **Source type / date:** IETF EMU WG Standards Track document; revision 12 dated 2026-07-29, in RFC Editor queue as of 2026-08-31
- **Source-supported fact:** EAP-EDHOC transports channel-binding information in protected EAD_3/EAD_4 fields after keying material exists. The document states that the binding content's format and semantics are application-specific and determined by the authentication domain. Multiple occurrences are forbidden, and a consistency error in the critical channel-binding item causes the exchange to fail.
- **Existing owner:** R-010 / R-001 / zk217 / zk228
- **Repository fact:** current ZK-ARCHE BIND facts distinguish peer context and profile context, while the resumption decision separately requires deployment/domain equality. The concrete BIND contract does not yet have a separately named application/authentication-domain match.
- **Problem addressed:** treating profile identity as a proxy for deployment/application domain can permit a valid channel binding to be reused in a semantically different authorization domain even when the same profile and peer are involved.
- **Strongest distinct engineering idea:** in the eventual concrete channel-binding construction, make the upper-layer context explicit and canonical: protocol/version + binding profile + AUTH-instance identifier + peer/holder commitment + deployment/authentication-domain identifier + application/ALPN/service context where applicable. Preserve the existing rule that raw address/routing metadata is not identity or authority.
- **Evidence maturity:** standards-track near-publication work + software design comparator
- **Limitations:** EAP channel binding and ZK-ARCHE are different protocols; the EAD format is not proposed as a ZK-ARCHE dependency. The lesson is semantic separation and fail-closed consistency checking.
- **ZK-ARCHE inference:** add future negative cases where the exporter/channel material is cryptographically valid but the deployment domain, application/service context, or AUTH instance is wrong; these should reject rather than degrade to `UNBOUND_ALLOWED`.
- **Likely impact:** likely only context-hash input bytes, not extra wire bytes when the domain/application context is already locally known; may require a compact explicit domain identifier in profiles where it is otherwise ambiguous.
- **Rust/C/vector/profile impact:** no current classifier change is required by this report; concrete binding adapters need deterministic context construction and same-input/same-decision parity.
- **Required next evidence:** exact domain/application context schema and canonicalization; cross-domain/cross-service replay vectors; prove whether existing `profile_context_match` can safely encompass this or whether a distinct normalized fact is clearer.

### D20260901-F03 — A current channel does not imply current attestation

- **Novelty:** refines
- **Primary source:** `draft-fossati-seat-early-attestation-06`, *Using Attestation in Transport Layer Security (TLS) and Datagram Transport Layer Security (DTLS)*
- **Primary link:** https://datatracker.ietf.org/doc/draft-fossati-seat-early-attestation/
- **Source type / date:** TLS/SEAT-related Standards Track Internet-Draft, revision 06 published 2026-08-05
- **Source-supported fact:** the draft binds attestation to a TLS connection, but explicitly notes that Evidence/Attestation Results become stale over long-lived connections and treats reattestation as a separate lifecycle problem. It discusses post-handshake client reattestation, reconnect-for-freshness, and other options rather than assuming key update refreshes attestation. It also warns that trust decisions should not rely only on the attester trust root and identifies privacy leakage from detailed evidence and online verifier participation.
- **Existing owner:** R-006 / R-010 / TD-002
- **Repository fact:** current `ZK-ARCHE-BIND` is intentionally only channel/context evidence; it explicitly states that a valid binding is not sufficient authentication, authorization, trust mutation, or resumption authorization. This separation is correct and should extend to attestation.
- **Problem addressed:** a future implementation could incorrectly promote `binding_fresh=true` into “peer platform is still trustworthy,” especially on a long-lived TLS/DTLS association.
- **Strongest distinct engineering idea:** if R-006 is ever prototyped, keep an independent optional attestation state with attestation-evidence/result freshness, verifier identity, appraisal-policy version, platform/identity-key binding, privacy class, and expiry/reappraisal trigger. BIND may prove the attestation is attached to the intended channel/AUTH context, but BIND must not manufacture attestation freshness or appraisal success.
- **Evidence maturity:** current Internet-Draft + research-only ZK-ARCHE owner
- **Limitations:** revision 06 itself leaves parts of attestation freshness under discussion; it is not a final standard. Hardware roots of trust, verifier architecture, evidence formats, and MCU costs remain unmeasured for ZK-ARCHE.
- **ZK-ARCHE inference:** a future attestation extension should define behavior for current channel + stale evidence, fresh channel + cached passport result, verifier rotation, reattestation failure, and privacy-preserving/minimized claims. None of these should become mandatory for `iot-core`.
- **Likely impact:** potentially significant wire/CPU/RAM/privacy and external-verifier dependencies; therefore remains optional/research-only.
- **Rust/C/vector/profile impact:** no current baseline change. Any optional profile should expose attestation results to TRUST as separately scoped evidence, not add platform-specific branches to the common BIND classifier.
- **Required next evidence:** bounded attestation state schema; evidence/result size and verifier-latency measurements; freshness/reappraisal policy; relay/cross-session tests; privacy analysis; target root-of-trust inventory.
- **Recommended disposition:** research-only

## 5. Cross-source synthesis

Today's sources converge on a useful separation for the new ZK-ARCHE lifecycle architecture:

```text
transport/channel association
        ↓
concrete exporter / channel binding
        ↓
binding generation + AUTH instance + peer + profile + domain/application
        ↓
BIND disposition
        ↓
AUTH / LINK / RESUME consume BIND as one input

separately:

resumption credential lifecycle
authorization/revocation/lineage lifecycle
attestation evidence/appraisal lifecycle (optional)
```

A key update can refresh channel keying material without refreshing authorization or attestation. A fresh attestation can update platform-health evidence without becoming protocol identity or authorization. A valid resumption secret can remain cryptographically valid while being forbidden by revocation, changed authorization, rollback suspicion, or a stronger post-compromise policy. Keeping these lifecycles separate but explicitly cross-bound is more robust than collapsing them into one generic `fresh` bit.
