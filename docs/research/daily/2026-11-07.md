## 2. Executive synthesis

1. **KUDOS -15**, published 2026-11-02, makes old/new/temporary OSCORE context transition, key confirmation, bounded old-context receive-only retention, and state-loss recovery explicit. This is a comparison model, **not** a ZK-ARCHE wire or security guarantee.
2. KUDOS explicitly distinguishes stateful forward-secret rekey from stateless no-forward-secrecy operation for devices unable to update persistent storage. The latter is **not** a safe shortcut around ZK-ARCHE's `CONTINUITY_BROKEN` or locally authorized `LINEAGE_REPLACE` transition.
3. **TLS Extended Key Update -14**, also dated 2026-11-02, defines a separate *generation-aware* exporter; the ordinary RFC 9846 exporter remains static across standard KeyUpdate, and simply using it provides no EKU-related post-compromise-security claim. That distinction directly sharpens R-010.
4. The EKU draft disables NewSessionTicket PSK resumption when enabled and states that fresh key exchange alone does not necessarily recover authentication after transient connection-state compromise under active MITM. ZK-ARCHE's trust/authorization and resumption gates remain separate.
5. No new local cryptographic test, TLS/OSCORE session, MCU measurement, proof or implementation defect was demonstrated. Keep both P0 questions at `reproduce`.

## 5. Findings

### D20261107-F01 — KUDOS state machine gives a concrete adversarial rekey/restart comparator

- **Novelty / backlog owner:** refines R-009, cross-references R-012; newly examined November revision, not a claim that every rule first appeared in -15.
- **Source:** *Key Update for OSCORE (KUDOS)*, `draft-ietf-core-oscore-key-update-15`, CoRE WG Standards Track Internet-Draft (work in progress), published **2026-11-02**; previous -14 dated 2026-07-06.
- **Primary links:** https://datatracker.ietf.org/doc/draft-ietf-core-oscore-key-update/15/ ; https://www.ietf.org/archive/id/draft-ietf-core-oscore-key-update-15.html ; base OSCORE RFC https://www.rfc-editor.org/rfc/rfc8613 .
- **Verified source-supported facts:** The draft describes OSCORE-protected peer key-update flights with temporary/new/old contexts and subsequent key confirmation (Sections 4.3–4.4). After new-context derivation, ordinary outgoing traffic must use the new context. Optional old-context retention is strictly for late incoming non-update traffic and must end on expiry or recipient key-use limit (Section 4.6). The draft differentiates persistently updated FS-mode key state and no-FS stateless mode for devices unable to perform nonvolatile writes (Section 4.4); following unprepared state loss, application exchanges are restricted pending safe recovery. Cross-context responses need an explicit sender sequence/nonce rule (Section 3). These are OSCORE requirements, not ZK-ARCHE normative requirements.
- **Existing engineering owner / repository anchors:** R-009, R-012, TD-002/TD-004, roadmap zk213/zk221/zk235; `spec/replay-continuity.md`, `spec/replay-epoch-transition-owner.md`, `spec/resumption-lifecycle.md`, Rust/C replay-continuity state machines, `rust/test-vectors/replay/lineage-replace-durable-attempt-v1.txt`.
- **Bottleneck:** A single boolean `rekey complete` cannot encode when successor keys may protect outbound data, when an in-flight predecessor ciphertext may be *decrypted* without obtaining new authorization, or whether persisted replay/key state permits safe restart.
- **Strongest distinct engineering idea:** Define a **two-context transition ledger** mapping `old active → successor derived → confirmation pending → durable verified commit → new active / old receive-only (bounded) → old retired`. Test an independent `authorization generation currently valid?` oracle for any candidate inbound message, even when predecessor decryption succeeds. Include response/request crossing, duplicate rekey flights, simultaneous proposals, crash at every persist step, counter exhaustion, old-context expiry, hard key limit, and restart with missing/stale state. Compare device classes that can/cannot make durable updates; **reject** silent substitution of KUDOS no-FS behavior for ZK-ARCHE replay recovery.
- **Evidence maturity:** concept (WG draft); ZK-ARCHE has existing software state/vectors but no newly executed two-context experiment or physical replay/rekey qualification.
- **Limitations / uncertainty:** This draft is not an RFC or reviewed ZK-ARCHE proof, and its old-context acceptance rules apply to OSCORE packet processing rather than ZK-ARCHE trust. KUDOS FS/no-FS semantics and CoAP observe/Partial-IV machinery do not map automatically to AUTH, DATA, or LINEAGE_REPLACE. No source demonstrates a current ZK-ARCHE bug.
- **ZK-ARCHE inference:** Treat derived-key availability, cryptographic confirmation, durable state transition, replay acceptance, and current authorization as separate predicates. Preserve fail-closed `CONTINUITY_BROKEN`, predecessor retirement and locally authorized transition; retain old decrypt keys *only* if a future approved profile defines safe bounded processing and independently revalidates authorization.
- **Wire / CPU / RAM / flash / dependency / trust / privacy impact:** No proposed baseline wire/dependency change. If a future optional overlap mode is considered, two contexts temporarily consume extra RAM/secure storage and decryption CPU; durable FS incurs flash writes/wear and energy. Tradeoffs unmeasured. Old identifiers/keys may increase metadata/linkability exposure; must not expand local trust.
- **Rust/C/vector/profile compatibility:** Add paired positive/negative decision vectors to existing replay/lineage corpora; independently verify Rust and C across all crash cuts. Profile `iot-core` stays unselectable until authenticated recovery, bounded resource and physical evidence exist. No automatic changes to current vectors/profiles.
- **Required next evidence:** Repo-owned local exact-HEAD trace harness for key-update overlap, restore and revocation-time accept/reject decisions; conserved `q/v` AEAD-key usage; STM32/ESP32-S3 persistent-write, CPU, RAM and energy logs.
- **Recommended disposition:** reproduce. **Weekly finding candidate:** yes.

### D20261107-F02 — EKU generation-aware exporter must not be confused with existing regular TLS exporter binding

- **Novelty / backlog owner:** new-to-R-010 evidence from an updated WG draft; refines separate exporter and post-compromise/rekey boundaries; R-009 cross-reference.
- **Source:** *Extended Key Update for Transport Layer Security (TLS) 1.3*, `draft-ietf-tls-extended-key-update-14`, TLS WG Standards Track Internet-Draft (work in progress), published **2026-11-02**; -13 previously dated July 2026.
- **Primary links:** https://datatracker.ietf.org/doc/draft-ietf-tls-extended-key-update/14/ ; https://www.ietf.org/archive/id/draft-ietf-tls-extended-key-update-14.html ; base TLS 1.3 https://www.rfc-editor.org/rfc/rfc9846 .
- **Verified source-supported facts:** Standard TLS KeyUpdate rotates traffic keys *without* a fresh key exchange; the regular TLS exporter secret remains unchanged over that connection (Sections 1, 11). EKU defines fresh key-exchange-based updates and an independent **generation-aware** exporter initial secret (distinct `exporter_secret_0`) and subsequent secrets `exporter_secret_N`. Applications receive an activation notification after a successful update and can request EKM for a specified generation; DTLS can temporarily retain prior generation secrets for reordered data (Section 11). The draft requires disabling NewSessionTicket PSK resumption when EKU is enabled (Section 8). Following transient connection-state compromise, active man-in-the-middle interference can defeat unauthenticated recovery without appropriate post-update peer authentication (Sections 12, 14). The proposal is not a standardized or implemented ZK-ARCHE exporter profile.
- **Existing engineering owner / repository anchors:** R-010, R-009, TD-004; roadmap zk217/zk221/zk228; `spec/tls-exporter-channel-binding.md`, `spec/resumption-lifecycle.md`, Rust/C `tls_exporter_context` helpers and negative corpora.
- **Bottleneck:** A binding using `EXPORTER-ZK-ARCHE-v1` regular TLS EKM could continue to validate across ordinary KeyUpdate, yet must **not** be reported as newly post-compromise secure. Conversely, a future EKU-aware provider can change exporter generation while one application-level AUTH or in-flight packet is pending, creating stale/mismatched context decisions.
- **Strongest distinct engineering idea:** Establish a **two-by-two TLS update/binding matrix**: ordinary KeyUpdate vs optional EKU, regular/static exporter vs generation-aware EKU exporter. For EKU research also test pre-/post-completion notification, generation 0 vs N vs N+1, stale/absent generation, dropped/late DTLS packet, concurrent AUTH/extended update, retained previous generation expiry, resumed-PSK prohibition, two-sided peer-authentication after transient compromise, and explicit rejection rather than opportunistic exporter switching.
- **Evidence maturity:** concept (IETF draft), with existing canonical-context digest software helpers; no live Rust/C TLS/DTLS EKU exporter provider, post-compromise test or authentication proof demonstrated.
- **Limitations / uncertainty:** EKU -14 is a changeable Internet-Draft and common providers may not expose it. Its PCS claims have explicit transient-compromise/non-MITM preconditions; static exporter binds a channel but does not by itself authorize ZK-ARCHE or recover compromised local trust. Existing R-011 critical-extension encoding conflict and unregistered exporter label remain unresolved.
- **ZK-ARCHE inference:** Keep current candidate regular exporter binding unchanged and expressly **out of scope for EKU PCS**. Before any optional generation-aware profile, require an independent normative decision about generation identity, explicit selection, transcript/Finished placement, resumption policy and whether generation transitions invalidate/reverify ZK-ARCHE binding and authorization. Do not infer that EKU itself upgrades normal AUTH, revocation or replay epochs.
- **Wire / CPU / RAM / flash / dependency / trust / privacy impact:** Today none; potential optional EKU profile adds a key exchange per update (CPU/wire/energy), temporary old+new secret RAM and update/notification state. Per-connection generation signaling may add metadata/linkability and require Rust/C provider support. No MCU or provider costs measured; no mandatory TLS/PKI/cloud requirement.
- **Rust/C/vector/profile compatibility:** Current context-hash fixtures remain relevant only to the regular exporter candidate; they are not live EKM. A future EKU profile would require distinct method/versioned vectors and end-to-end Rust/C TLS provider agreement with wrong-generation/stale-exporter negatives. Do not silently reinterpret the existing 32-byte context digest or regular exporter label.
- **Required next evidence:** Source/provider capability audit and local exact-HEAD TLS1.3/DTLS1.3 tests proving generation-pinned EKM and Finished agreement, unsupported-mode rejection, resumption/authentication boundaries and consistent activation epoch. Prioritize regular-exporter baseline interoperability first; any EKU-specific change needs explicit human approval.
- **Recommended disposition:** reproduce (optional EKU branch remains research-only). **Weekly finding candidate:** yes.

## 6. Cross-source synthesis

The two November 2 drafts both distinguish *cryptographic key derivation* from *safe activation* and previous-generation handling; neither makes stale authorization permissible. KUDOS is a constrained OSCORE context-update reference with an explicit limited no-FS option, while TLS EKU proposes a distinct key-exchange and exporter interface with stricter resumption and post-compromise assumptions. ZK-ARCHE should **not** copy either wire or require either transport: record a precise acceptance ledger under its own local, NO-LEARNING, rollback-resistant lineage and authorization contracts. Existing R-009 multi-key AEAD limits and R-010 standard exporter fixtures remain separate qualification questions.
