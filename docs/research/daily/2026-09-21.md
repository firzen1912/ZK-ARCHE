## 2. Executive synthesis

- **Credential/key references must remain selectors, not authority.** COSE explicitly treats `kid` as a potentially non-unique key-finding hint, and EDHOC uses `ID_CRED_x` to retrieve the actual authentication credential/key. A compact ZK-ARCHE credential reference should therefore be a non-authoritative candidate selector; it must not itself become identity, role, policy, or authorization.
- **Authority must attach to the exact cryptographically verified record.** EDHOC integrity-binds the actual credential and requires application validation of credential parameters, including subject information for misbinding resistance. COSE also constrains algorithm/key operations, while ACE provides a constrained-device example of authorization bound to a proof-of-possession key and audience. ZK-ARCHE should require one exact verified record to supply both key identity and policy attribution.
- **Selector ambiguity is acceptable; authority ambiguity is not.** Multiple local records may share a compact selector, but insertion order, transport metadata, or a caller-supplied role must never choose the authoritative record. Rust and C should agree independent of candidate ordering.
- **Dynamic trust mutation is a profile capability.** The active June 2026 cBRSKI draft combines verify-then-commit trust replacement with explicitly bounded constrained trust-anchor storage and profile classes that may omit re-enrollment entirely. ZK-ARCHE should claim restart-safe in-field ENROLL only on profiles with qualified durable mutation/storage behavior.
- **No status promotion is justified.** R-013 remains `reproduce`. No new wire format, suite, profile, trust primitive, roadmap item, ADR, or implementation request is created.
- **Fresh discovery did not outrank the P0 work.** RFC 10032 (AEGIS, September 2026) is relevant future AEAD research, but it is informational and currently lacks a concrete ZK-ARCHE profile/interop decision; no new backlog item is justified today.

## 5. Findings

### D20260921-F01 — Credential references are non-authoritative, potentially non-unique selectors

- **Novelty:** refines
- **Backlog owner:** R-013
- **Source:** RFC 9052; RFC 9528
- **Primary link:** <https://www.rfc-editor.org/rfc/rfc9052.html>; <https://www.rfc-editor.org/rfc/rfc9528.html>
- **Source type / venue:** IETF Standards Track RFCs / COSE and LAKE
- **Publication or release date:** August 2022; March 2024
- **Verified claim:** RFC 9052 defines `kid` as input for finding a cryptographic key, explicitly says applications must not assume `kid` values are unique, notes that multiple keys can share the same value, and characterizes the identifier as a hint rather than a security-critical field. RFC 9528 applies the same model to EDHOC `ID_CRED_I`/`ID_CRED_R`: these fields facilitate retrieval of the actual authentication credential/key, and more than one key may need to be considered for one `kid`. EDHOC then verifies the actual credential/key through the protocol authentication construction.
- **Existing engineering owner:** R-013; future TRUST/ENROLL specification and assurance; R-014 for lookup/DoS optimization only
- **Repository fact:** R-013 already requires credential/reference binding to the exact public key/commitment and misconfigured-store negatives, but current AUTH-v3 formal evidence receives one preselected trusted public key and current ENROLL-v4 vectors contain no reference-collision dimension.
- **Problem addressed:** treating a compact reference as globally unique or security-authoritative can turn a lookup alias into an identity/role/policy oracle; treating it as unboundedly ambiguous can create nondeterministic policy resolution and CPU/DoS cost.
- **Strongest distinct engineering idea:** split lookup from authority: `reference -> bounded candidate set -> cryptographic verification -> exactly one authoritative record -> policy/lifecycle checks`. Lower-layer metadata may at most prioritize candidate work; it must not confer trust or change the eventual authoritative result.
- **Evidence maturity:** externally-reviewed
- **Limitations / uncertainty:** neither COSE nor EDHOC defines ZK-ARCHE's trust-store schema or role semantics. EDHOC permits contextual information to help lookup; ZK-ARCHE's rule that transport metadata is non-authoritative remains a local architecture constraint.
- **ZK-ARCHE inference:** any future credential reference should be modeled as a non-authoritative selector that may resolve to zero, one, or several records. Authority is unavailable until proof under the exact candidate key succeeds and the associated record is current.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** no mandatory wire growth if an existing compact selector is retained; a stronger digest selector would need separate wire/privacy review. CPU becomes `O(k)` in the number of candidates unless bounded. RAM/flash require a bounded collision bucket/index. No online dependency is implied. Trust semantics improve by removing `reference == identity/authority`. Stable globally unique selectors can worsen linkability, so stronger selectors must also be reviewed under R-015.
- **Rust/C / vector compatibility impact:** shared vectors should cover one selector with two keys; one selector with two role/policy records; reordered candidate storage; zero candidates; candidate count over the profile bound; and lower-layer metadata that changes candidate ordering but not authority. Rust/C terminal semantics must be insertion-order independent.
- **Required next evidence:** wire-neutral multi-candidate resolver model; deterministic Rust/C collision/substitution corpus; bounded candidate policy; DoS measurement; formal mapping relation.
- **Recommended disposition:** reproduce

### D20260921-F02 — Exact cryptographic record selection must precede role/policy attribution

- **Novelty:** refines
- **Backlog owner:** R-013 / R-004
- **Source:** RFC 9528; RFC 9052; RFC 9200; RFC 8747
- **Primary link:** <https://www.rfc-editor.org/rfc/rfc9528.html>; <https://www.rfc-editor.org/rfc/rfc9052.html>; <https://www.rfc-editor.org/rfc/rfc9200.html>; <https://www.rfc-editor.org/rfc/rfc8747.html>
- **Source type / venue:** IETF Standards Track RFCs / LAKE, COSE, ACE
- **Publication or release date:** March 2024; August 2022; August 2022; March 2020
- **Verified claim:** EDHOC authentication credentials carry the public authentication key and may carry other application-validated parameters, particularly subject information used to prevent misbinding; the concrete credential is included in the authenticated/integrity-checked context. COSE requires applications to honor key type/algorithm/key-operation restrictions. ACE/CWT PoP separates key reference/possession from authorization and audience; ACE PoP refresh cannot silently change the proof-of-possession key or audience.
- **Existing engineering owner:** R-013 and R-004; future TRUST/ENROLL spec and assurance
- **Repository fact:** `TrustedAttributionPresent(pkey, peerid, role, authz_core)` in the current AUTH-v3 ProVerif model collapses a pre-resolved mapping into symbolic inputs, and the model expressly excludes alias ambiguity and computational key/credential binding.
- **Problem addressed:** a valid proof under key A must never permit role, policy, audience, deployment, or key-operation metadata to be accidentally sourced from colliding record B.
- **Strongest distinct engineering idea:** define a canonical local `TrustRecord` semantic unit containing the exact key/commitment plus peer/subject attribution, allowed role/policy, audience/deployment/domain, permitted key operations/profile, authorization provenance/generation, and lifecycle/revocation lineage. A wire reference selects candidates only; the proof selects the exact record; only that record can supply authority.
- **Evidence maturity:** externally-reviewed
- **Limitations / uncertainty:** ACE's authorization-server/token topology is not a required ZK-ARCHE architecture. The relevant source fact is the separation of key possession, key reference, audience, and authorization, not the infrastructure model.
- **ZK-ARCHE inference:** accepted attribution should be tied to the exact verified record and record generation, not merely to a public-key lookup followed by an independent role/policy lookup. The record can remain local; no conclusion requires transmitting all policy metadata.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** potentially zero wire cost if the authoritative record remains local. Metadata checks are cheap relative to proof verification. RAM/flash grow with normalized policy/provenance fields and should be measured under R-005. No new mandatory online dependency. This directly reduces key/identity/role misbinding. Keeping policy metadata local avoids unnecessary privacy exposure.
- **Rust/C / vector compatibility impact:** add same-key/different-generation records; same-selector/different-`key_ops` or profile permissions; valid key-A proof with record-B role substitution; valid proof with stale/revoked record generation; correct key with wrong audience/deployment; mapping replacement during in-flight AUTH/ENROLL; and insertion-order permutations. Rust/C must select the same exact semantic record and reason precedence.
- **Required next evidence:** canonical wire-neutral record schema/digest/generation model; shared negative corpus; stateful selector->record relation in formal model with attacker/misconfiguration influence.
- **Recommended disposition:** reproduce

### D20260921-F03 — Durable trust mutation is a bounded profile capability

- **Novelty:** refines
- **Backlog owner:** R-013 / R-005
- **Source:** `draft-ietf-anima-constrained-voucher-31`, *Constrained Bootstrapping Remote Secure Key Infrastructure (cBRSKI)*
- **Primary link:** <https://datatracker.ietf.org/doc/html/draft-ietf-anima-constrained-voucher-31>
- **Source type / venue:** active IETF Standards Track Internet-Draft / ANIMA
- **Publication or release date:** 8 June 2026; current draft expires 10 December 2026
- **Verified claim:** the draft requires a re-enrolling constrained client to verify a new identity against the applicable new trust anchors before accepting replacement state; if validation fails, it must not update either the identity or Explicit Trust Anchor database. The draft also explicitly bounds example constrained trust-anchor storage and defines pledge classes where the minimal class has no explicit TA database and no re-enrollment, while more capable classes support bounded TA storage and re-enrollment.
- **Existing engineering owner:** R-013; R-005 for physical storage evidence; current ENROLL lifecycle for the wire-neutral commit boundary
- **Repository fact:** ZK-ARCHE's current ENROLL state machine already has `ISSUANCE_AUTHORIZED -> COMMITTING -> COMMITTED/RECOVERY_REQUIRED` and warns that host-only tests do not establish flash atomicity or power-loss safety. No current physical MCU evidence establishes restart-safe trust-store mutation.
- **Problem addressed:** a uniform security floor must not be confused with a claim that every constrained target can safely support in-field persistent trust replacement.
- **Strongest distinct engineering idea:** make dynamic trust mutation an explicit profile capability. All profiles retain NO-LEARNING normal AUTH/P2P. An explicit ENROLL path is usable only where the profile has qualified bounded storage, durable atomic/recoverable mutation, and rollback behavior; otherwise ENROLL fails closed or requires an explicit reprovisioning path.
- **Evidence maturity:** concept
- **Limitations / uncertainty:** cBRSKI is still an Internet-Draft, and its PKI/EST architecture and example certificate counts are not ZK-ARCHE requirements. The counts must not be copied as constants.
- **ZK-ARCHE inference:** each constrained profile should eventually declare maximum authoritative records, maximum selector candidates, persistent bytes/record, write amplification, restart recovery, rollback-detection capability, and whether in-field dynamic ENROLL is supported.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** no wire cost for the capability boundary itself. Normal AUTH remains unaffected. Dynamic ENROLL needs bounded RAM/flash and may need journal/dual-slot writes, increasing flash wear. No always-online dependency follows. Trust claims become more precise: a device unable to persist mutations safely does not pretend to provide restart-safe learning. Reprovisioning identifiers need separate privacy review.
- **Rust/C / vector compatibility impact:** add store-full/candidate-bucket-full behavior, interruption before/during/after commit, rollback to older mapping generation, restart after successful commit, failed successor verification preserving predecessor, and a minimal/no-mutation profile receiving ENROLL. Physical STM32/ESP32 evidence is required before any restart-safe claim.
- **Required next evidence:** target-specific trust-record footprint; flash write/amplification/endurance; power-loss/rollback recovery; Rust/C profile behavior parity.
- **Recommended disposition:** reproduce

## 6. Cross-source synthesis

The combined standards evidence supports one compact doctrine:

```text
credential reference
    = lookup hint only
           ↓
bounded candidate records
           ↓
prove possession / verify exact credential
           ↓
select exactly one canonical current TrustRecord
           ↓
check key-ops + method/suite/profile
           ↓
check role/policy/audience/deployment/domain
           ↓
check authz/revocation/lineage/generation
           ↓
AUTH may use existing authority
or explicit ENROLL may attempt a profile-qualified durable mutation
```

This avoids two opposite errors:

1. **over-authoritative selectors** — treating a short reference as globally unique identity/policy authority, creating alias/misbinding and privacy risk; and
2. **unbounded ambiguous selectors** — allowing attacker-influenced collision buckets to trigger arbitrary verification work or policy choice by database order.

The decision boundary is therefore: **selector ambiguity may exist; authority ambiguity must not exist at admission or commit**.

The cBRSKI evidence also corroborates the repository's existing verify-then-commit ENROLL direction, but adds a useful capability boundary: a constrained profile may legitimately omit dynamic trust replacement rather than implementing it unsafely.
