### D20260930-F01 — Canonical Tamarin source plus sound ProVerif generation is now a credible R-004 architecture candidate

- Novelty: new/refines
- Backlog owner: R-004
- Source: Kevin Morio, Yavor Ivanov, Robert Künnemann, A Sound Translation from Tamarin to ProVerif: Enabling Comparative Analysis
- Primary link: https://arxiv.org/abs/2608.06315
- Source type / venue: author preprint / formal-methods research; arXiv cs.CR
- Publication or release date: 2026-08-06
- Verified claim: the work defines a translation from Tamarin multiset-rewrite models to ProVerif, supports a substantial subset including rules, lemmas, and restrictions, and proves soundness within its faithful fragment: a property verified by ProVerif on a faithful translation also holds in the original Tamarin model. For exists-trace properties not involving attacker knowledge it also gives a completeness result. The evaluation covers 562 of 566 lemma tasks from 121 Tamarin models.
- Existing engineering owner: R-004 / TD-003 / zk207
- Repository fact: ZK-ARCHE currently keeps synchronized ProVerif copies and explicitly wants one canonical or mechanically generated formal source; the exact-current tree has no Tamarin source model.
- Problem addressed: byte-synchronizing two .pv copies prevents Rust/C model drift but does not give ZK-ARCHE an independent stateful backend or one canonical source from which multiple verification views are mechanically derived.
- Strongest distinct engineering idea: prototype one representative ZK-ARCHE lifecycle surface as a canonical Tamarin multiset-rewrite source and generate a ProVerif model from that same source, rather than writing a new independent Tamarin model beside the existing ProVerif model. Compare this Tamarin-first strategy with SAPIC+ before choosing an owner.
- Evidence maturity: formal
- Limitations / uncertainty: the source is a preprint; the result applies only to the characterized faithful fragment. Best-effort encodings, explicitly including XOR in the paper, are outside the guarantee. This report did not identify a repository-owned, pinned translator artifact already integrated into ZK-ARCHE, and it does not assume that every privacy/equivalence or state feature ZK-ARCHE needs is faithfully translatable.
- ZK-ARCHE inference: R-004 should stop describing multi-backend work only as “add Tamarin.” The decision is first a canonical-source ownership question: SAPIC+ process source, Tamarin multiset-rewrite source with verified translation, or another mechanically synchronized source. Only one should become authoritative.
- Wire / RAM / CPU / flash / dependency / trust-model impact: no protocol-wire, target RAM, MCU CPU, flash, or deployed trust-model change. Tooling cost increases through an additional formal backend/translator, while assurance drift risk may decrease if a single source is genuinely authoritative.
- Rust/C / vector compatibility impact: no production Rust/C behavior changes. Counterexamples that map to concrete protocol behavior should still become shared Rust/C negative scenarios; generated formal backends are not substitutes for executable cross-language vectors.
- Required next evidence: select one representative model surface; pin the source model, translator implementation/version/commit, Tamarin and ProVerif versions, translation options, generated model hash, and per-lemma property mapping; reproduce both backend results locally; document any feature outside the faithful fragment.
- Recommended disposition: reproduce

### D20260930-F02 — Translation guarantee class must be retained per property; backend agreement alone is not sufficient evidence

- Novelty: refines
- Backlog owner: R-004 / TD-003
- Source: A Sound Translation from Tamarin to ProVerif: Enabling Comparative Analysis; SAPIC+ official documentation
- Primary links: https://arxiv.org/abs/2608.06315 ; https://sapic-plus.github.io/
- Source type / venue: formal-methods research preprint; official formal-verification project documentation
- Publication or release date: 2026-08-06 for the translation paper; SAPIC+ platform documentation current at inspection
- Verified claim: the translation paper explicitly characterizes when faithful translation is not possible and reports best-effort cases outside its formal guarantee. In its evaluation, 246 of 247 non-XOR tasks with definitive results from both tools agree; the remaining result is explicitly associated with an incomplete model. SAPIC+ independently demonstrates the established alternative pattern of one model source targeting ProVerif, Tamarin, and DeepSec, with Tamarin-style lemmas translated to backend queries.
- Existing engineering owner: TD-003 formal model expansion / zk207
- Repository fact: the current ZK-ARCHE formal evidence contract keys results to exact model blobs and tool versions, but the backlog did not yet require a translation-guarantee classification when one canonical model is compiled to another backend.
- Problem addressed: a generated model can be syntactically valid and both backends can appear green while a source feature/property falls outside the translator’s proven semantic fragment. “Both tools passed” is therefore weaker than “this property is covered by a sound translation contract.”
- Strongest distinct engineering idea: add a translation provenance record per property with at least: authoritative source-model hash; translator identity/version/commit; translation options; generated-model hash; backend versions; source property ID; generated query/lemma ID; guarantee class faithful, best-effort, or unsupported; result; and any manually assumed abstraction.
- Evidence maturity: formal / externally-reviewed platform precedent
- Limitations / uncertainty: agreement statistics from a benchmark corpus do not prove correctness for ZK-ARCHE. SAPIC+ and the newer direct Tamarin-to-ProVerif translation start from different modeling formalisms; mixing both as co-equal sources would recreate the ownership problem.
- ZK-ARCHE inference: FORMALLY ANALYZED should be property-scoped to the exact source/model/translation/backend chain. Best-effort or unsupported translation must remain a named evidence gap even if a backend returns a success result. A translator warning or incomplete-model marker should fail closed for promotion.
- Wire / RAM / CPU / flash / dependency / trust-model impact: no deployed protocol cost. Evidence manifests and retained generated artifacts increase repository/storage footprint modestly and add formal-tool dependencies.
- Rust/C / vector compatibility impact: any representable attack/counterexample remains eligible for conversion into one shared Rust/C negative test. No backend verdict should silently change a Rust/C acceptance rule.
- Required next evidence: a repository-neutral schema for translation coverage and result provenance; one bounded reproduction against an existing ZK-ARCHE model; explicit handling of unsupported constructs; evidence that the generated model is derived rather than hand-edited.
- Recommended disposition: reproduce

- Rust/C / vector compatibility impact: no wire/vector changes. Falsified traces should be mapped to existing spec/state owners and, where executable, converted to deterministic Rust/C negative cases.
- Required next evidence: one local exact-head Tamarin recipe for a bounded model, explicit fail/timeout/unterminated handling, retained raw artifacts, and a cache/provenance key covering model/tool/options/repository state.

## 6. Cross-source synthesis

Today’s sources converge on a more precise R-004 design boundary:

~~~text
one authoritative formal source
        |
        +--> native backend analysis
        |
        +--> mechanically generated secondary backend
                    |
                    +--> per-property translation guarantee class
                    +--> generated-model hash
                    +--> exact backend/tool/options identity
        |
        +--> model/spec/code traceability
        +--> executable Rust/C scenarios for representable attacks
~~~

SAPIC+ already demonstrates a process-source/multi-backend architecture. The August 2026 translation work adds a distinct Tamarin-first option with formal guarantees for a characterized subset. ZK-ARCHE should not operate both source strategies simultaneously as independent authorities. The research decision is to prototype one bounded single-source chain and measure semantic coverage, reproducibility, and maintenance burden before selecting the canonical model owner.

The strongest assurance rule is also narrower than “run two provers”: a backend result contributes only to the property and semantic fragment actually represented by the translation. Unsupported/best-effort translation, timeout, incomplete model, missing exact input identity, or manual generated-model edits remain evidence gaps.
