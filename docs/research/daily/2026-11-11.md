## 2. Executive synthesis

1. **Fresh revision-specific ACE security boundary:** ACE WG `draft-ietf-ace-workflow-and-params-09` was published **2026-11-02**. Its -08→-09 changelog explicitly adds group-audience trust-anchor mix-up defenses. A valid anchor signature does **not** prove that a key belongs to the requested audience. ZK-ARCHE should keep authority-domain + audience + subject attribution separately verified, even in infrastructure-free P2P mode.
2. **Lost-predecessor updates are not fresh enrollment:** The same draft distinguishes an authority-delivered replacement of an existing token series from a new series. If the predecessor has been forgotten, the receiver must not silently reinterpret the replacement as a fresh grant. ZK-ARCHE has a stricter locally authorized, monotonic lineage and trust-mutation model, so transplanting ACE's token-series recovery would be inappropriate.
3. **Formal verification tooling can alter a modeled storage machine:** Open Tamarin issues #931, #941 and #942 document state-optimization discrepancies, including unconstrained lookups, stale reads, ignored deletion, and false reachability outcomes. A model's apparent success may be an artifact of translation. ZK-ARCHE currently retains **ProVerif 2.05** models, not a demonstrated SAPIC-optimized Tamarin proof; these are qualification guards for future adoption, not discovered ZK-ARCHE formal failures.
4. **One source-specific conformance trap:** ACE -09 section 3.7 explicitly requires CBOR `true` **0xf5** for `updated_rights`, but Figure 10's caption calls it **0xf6**. RFC 8949 defines 0xf6 as **null**. This is a draft editorial contradiction; follow the explicit semantic text and independent CBOR specification, never the erroneous caption.
5. **No promotion:** No runtime Rust/C tests, ProVerif/Tamarin executions, MCU measurements, new crypto proof, or production/security claim was established. R-013 and R-004 stay P0/`reproduce`. No new mandatory AS/OAuth/COSE/PKI/TLS dependency.

### D20261111-F01 — Group trust-anchor validity must not substitute for authorized audience membership

- **Novelty / backlog owner:** `new` revision-specific source refinement to R-013 (P0); R-008 cross-reference.
- **Primary source/date/type:** IETF ACE WG, *Short Distribution Chain (SDC) Workflow and New OAuth Parameters for ACE*, `draft-ietf-ace-workflow-and-params-09`, Standards Track Internet-Draft, **2026-11-02**, §§3.4–3.5 and Appendix C.1: https://datatracker.ietf.org/doc/html/draft-ietf-ace-workflow-and-params-09 .
- **Verified source-supported claim:** In group-audience responses, `audience2[i]` must identify the RS whose public key is `rs_cnf2[i]`. If `anchor_cnf` accompanies `audience2`, a client verifies that the subject key belongs to an RS listed in `audience2` before using an anchor. Without `audience2`, the relevant anchor must be uniquely associated with that group audience (or itself carry membership constraints), and cannot validate an unrelated RS. Appendix C.1 lists group-audience-mixup protection as new in -09. This is an Internet-Draft, not deployed ZK-ARCHE behavior.
- **Existing owner / repository anchor:** R-013, R-008; `spec/p2p-bounded-delegation-decision.md`, `spec/authorization-generation-lifecycle.md`, `rust/crates/proto/src/enrollment_grant.rs`, `c/src/proto/enrollment_grant.c`.
- **Bottleneck:** A shared trusted issuer/anchor can validate credentials of multiple subjects; cryptographic chain validity alone cannot determine the authorized audience and grant for a particular device. An offline P2P system must avoid cross-domain delegation/credential alias confusion.
- **Distinct engineering idea:** Create an *authority-qualified audience-attribution oracle* with tuple `(local_trust_domain, authorized_issuer, audience, subject_id, subject_public_key, operation, current_generation)`. Positive: explicitly authorized issuer and audience, correct subject key, current scope. Negatives: same-key-valid-but-wrong-audience, swapped group member/key array, duplicated subject identifier under a second issuer, shared anchor for two groups without explicit membership, wrong PoP algorithm, stale generation, and authenticated but unauthorized foreign grant. Verify **no trust mutation** on failed AUTH.
- **Evidence maturity:** `concept` external draft; existing ZK-ARCHE `software` classifiers are not this grouped-mapping test.
- **Limitations:** ACE has centralized AS/token profiles; ZK-ARCHE does not. No new exploit, cryptographic break, or deployed interop evidence is claimed. Group audience policies may legitimately use explicit lists or scoped local authority—implementation is subject to human review.
- **ZK-ARCHE inference:** Reuse audience-binding *discipline*, not ACE's AS, PKI, token schema, anchors or a mandatory group-membership service. Opaque references cannot create new authority.
- **Wire / CPU / RAM / flash / dependency / trust / privacy:** Baseline wire **none**; optional group-attribute encoding could increase bytes/lookup CPU, bounded mapping RAM/flash and stable group-label linkability. Constrained limits unmeasured; no mandatory online dependency. Stronger issuer/audience separation preserves local trust sovereignty.
- **Rust/C/vector/profile compatibility:** No current suite/profile/vector changes. Add aligned positive and negative classifier and identity-mapping fixtures to a later explicit engineering request; retain existing canonical v1 codec and profile semantics unless human-approved.
- **Next evidence:** Local exact-HEAD Rust/C paired authority/audience/group-key collision tests, including restart/rollback and negative foreign-issuer mutation; model owner mapping under TD-003.
- **Disposition:** `reproduce`; weekly finding candidate **yes**.

### D20261111-F02 — Predecessor loss must not silently reclassify a delegated rights update as a fresh grant

- **Novelty / backlog owner:** `refines` R-013, R-012 cross-reference.
- **Primary source/date/type:** Same ACE WG **2026-11-02** -09 Internet-Draft, §§2.1, 3.6–3.7, 11.1; CBOR comparator **RFC 8949 (December 2020)**: https://datatracker.ietf.org/doc/html/draft-ietf-ace-workflow-and-params-09 ; https://www.rfc-editor.org/rfc/rfc8949.html .
- **Verified source-supported claim:** `updated_rights=true` is explicitly conveyed on protected AS→RS replacement uploads, and the RS verifies AS origin and predecessor token series before retaining a current client–RS association. Missing old token causes `missing_old_token` rather than treating a replacement as new. An ACE AS may invoke a specifically defined on-the-fly new-series path: this **is not** general authorization to reset an arbitrary lineage. ACE -09 Figure 10 caption says `0xf6` for true, whereas its normative processing text states `0xf5`; RFC 8949 makes `0xf6=null`. Treat caption as a source discrepancy; do not seed tests with null.
- **Existing owner / anchors:** R-013, R-012 / `spec/lineage-replace-verified-commit-contract.md`, `spec/lineage-replace-convergence-contract.md`, `spec/authorization-generation-lifecycle.md`, `rust/models/proverif/zk_arche_lineage_replace_commit_draft.pv`.
- **Bottleneck:** Constrained storage eviction, crashed predecessor state, stale alias caches and cross-device middleboxes can transform a purported *update* into unauthorized *creation* or restore a retired grant. Correctly authenticated delivery is not sufficient evidence that a predecessor exists and is replaceable.
- **Distinct engineering idea:** Add a *typed intent and predecessor-presence gate* ahead of trust mutation: `FIRST_ISSUANCE` versus `REPLACE_EXISTING` are disjoint authorized operations. A replacement requires matching issuer/domain/audience/subject, explicit predecessor identity, current generation and successful bounded durable commit. If missing, deny and enter a separately authorized recovery path; never infer implicit ENROLL, new series, or fresh authorization from the delivery channel. Test partial group delivery, late retry, missing old record, stale lineage, conflicting authority, and restart with incomplete transaction.
- **Evidence maturity:** `concept` draft comparator, repository `software` policy references; scenario not executed.
- **Limitations:** ACE's `missing_old_token` and token-series behavior are profile-specific. Its on-the-fly restart procedure must **not** be assumed safe under ZK-ARCHE's no-implicit-UNREVOKE lineage semantics; no proof of physical rollback resistance.
- **ZK-ARCHE inference:** Separate token-delivery success, old lineage eligibility, subject authorization, generation freshness, successor confirmation and actual persistent commit. No learning during normal AUTH.
- **Wire / CPU / RAM / flash / dependency / trust / privacy:** No baseline wire change. A future intent indicator could cost bytes if no existing authenticated representation suffices; preserving predecessor tombstones/epoch state costs flash/RAM/writes; extra reject/recovery may affect availability. No token-series or AS dependency introduced; stable lineage IDs require privacy analysis.
- **Rust/C/vector/profile impact:** Add a paired valid replacement plus negative fixtures for missing predecessor, wrong domain, null-vs-true/rejected noncanonical input (only where a CBOR adapter is explicitly evaluated), torn commit and postcommit retry. Do **not** add ACE `updated_rights` to ZK-ARCHE wire by implication.
- **Next evidence:** Exact-head software classifier/persistence fault oracles and authority-preserving lineage invariants, with independently measured constrained flash budget if storage format proposed.
- **Disposition:** `reproduce`; weekly finding candidate **yes**.

### D20261111-F03 — SAPIC optimized mutable-state translation must be qualified before trusting temporal proofs

- **Novelty / owner:** `new` tool-assurance risk for R-004 (P0), TD-003. Different from the November 2/5 proof-output/diff-restriction bugs.
- **Primary sources/date/type:** Tamarin upstream issue reports with executable reproducer models: #931 opened **2026-09-12**, #941 and #942 opened **2026-09-15**, all verified **open** as of 2026-11-11 (updated November 3). https://github.com/tamarin-prover/tamarin-prover/issues/931 ; https://github.com/tamarin-prover/tamarin-prover/issues/941 ; https://github.com/tamarin-prover/tamarin-prover/issues/942 . Primary upstream issue reports (not independently executed or externally peer-reviewed results).
- **Verified source-supported claim:** Issue #931 reports a double-lock exists-trace verdict switching from falsified without `translation-state-optimisation` to verified with it. #941 reports a pure-cell `lookup` outside locks gaining unconstrained `IsIn` values and an else-branch. #942 reports unconsumed old `insert` values, `delete` ignored and a double-insert deadlock causing an unreachable `Done()` and potentially vacuous `no_done` verification. These are issue reporters' model executions on documented tool versions, **not** independently reproduced in this run or proof that every optimized SAPIC model is affected.
- **Existing owner / anchors:** R-004, TD-003; `rust/models/proverif/zk_arche_lineage_replace_commit_draft.pv`, `rust/models/proverif/zk_arche_retained_authority_draft.pv`, `spec/authorization-generation-lifecycle.md`, `spec/lineage-replace-verified-commit-contract.md`, `spec/replay-continuity.md`.
- **Bottleneck:** Nonmonotonic `insert/delete/lookup` storage semantics determine whether a revoked authorization or retired predecessor can reappear. A translator that invents old reads or prunes executable transitions cannot substantiate a state-machine security claim.
- **Distinct engineering idea:** Introduce a *state-translation equivalence canary pack* before selecting SAPIC optimization: pin identical source with optimization on/off, output MSR model hashes, inspect `IsIn` constraints, test overwrite/delete/relookup, nested lock and two inserts per section, then require paired reachable allow and reachable deny plus deliberately insecure mutation expected to falsify the property. Keep loss-of-state recovery and authorization-generation transitions in the model; default to a semantically qualified nonoptimized translation until canaries pass.
- **Evidence maturity:** `software` upstream reproducer reports; ZK-ARCHE-specific evidence **not run**.
- **Limitations:** Current repository retained formal evidence uses ProVerif 2.05, and inspected `.pv` models do **not** enable Tamarin's `translation-state-optimisation`. Do not describe this as a ZK-ARCHE discovered vulnerability, a broken proof, or an automatic ProVerif defect. Requires exact pinned Tamarin/Maude/toolchain and generated-rule inspection; issue status is not a formal fix/absence guarantee.
- **ZK-ARCHE inference:** When migrating mutable authorization/lineage/revocation state to a SAPIC+/Tamarin backend, treat translator settings and executable state-machine non-vacuity as part of the evidence claim, not optional build metadata.
- **Wire / CPU / RAM / flash / dependency / trust / privacy:** **No ZK-ARCHE wire or device-resource change.** Formal tool CPU/time/memory may increase for nonoptimized execution; pinned verification tooling is an offline development dependency, not a runtime trust root. Incorrect verification could overstate authorization safety/privacy but does not change actual runtime behavior.
- **Rust/C/vector/profile impact:** No current code/vector/profile edits. Convert modeled counterexamples to same-state Rust/C tests only after faithfully relating model state to current classifier/storage semantics. Preserve source/model/tool/options/diff hashes and raw trace.
- **Next evidence:** Run upstream #931/#941/#942 minimal reproducers under pinned selected versions with optimization on/off; inspect generated translated multiset rules and warnings; then construct a ZK-ARCHE-specific authorization/revocation state canary and non-vacuous positive and negative mutant tied to exact Rust/C tests.
- **Disposition:** `reproduce`; weekly finding candidate **yes**.

## 6. Cross-source synthesis

An authenticated delivery channel, signed credential and proof outcome each establish a narrower fact than current local authority. In ACE group-token issuance, signer validation and audience qualification differ; for token-series replacement, delivery and predecessor status differ; for formal analysis, parser/proof execution and state-machine semantic preservation differ. ZK-ARCHE should enforce all three separations while keeping P2P, offline, CA-less and NO-LEARNING constraints unchanged. Today established source relevance, not implementational readiness.
