## 1. Executive synthesis

1. **The new logical storage transaction is now precise enough that target qualification should pivot from generic “crash-safe storage” language to an explicit storage-service capability manifest.** PSA Secure Storage already distinguishes storage that provides replay protection from storage that explicitly opts out. TF-M also distinguishes Protected Storage from Internal Trusted Storage, and constrained profiles can ship ITS without rollback protection. For ZK-ARCHE, “uses TF-M/PSA secure storage” is therefore not a sufficient claim; the exact service, flags, backend, and rollback semantics must be recorded.
2. **ESP32-S3 provides a plausible power-loss-tolerant record substrate, but its built-in anti-rollback mechanism does not directly solve per-lineage freshness.** Espressif NVS documents recovery across unexpected power loss and requires `nvs_commit()` for durable changes. NVS encryption protects stored values against unauthorized alteration/addition, while the documented eFuse security-version anti-rollback feature applies to application images. Treating the firmware `secure_version` as a generic lineage counter would therefore conflate two security domains.
3. **STM32H5 provides a qualitatively different hardware option: secure-storage EPOCH counters can invalidate previously encrypted data after regression by changing derived hardware keys.** That is useful anti-rollback evidence, but it is a coarse regression/storage-domain mechanism, not automatically equivalent to ZK-ARCHE's per-lineage `trusted_high_water_generation`. A target adapter must prove the semantic mapping rather than inheriting a claim from the hardware feature name.
4. **No new R-* item or status transition is justified.** R-005 already owns target execution/storage evidence; R-009 and R-012 already own replay/rekey/lineage continuity. Today's evidence sharpens the target adapter qualification matrix rather than creating a new research question.
5. **No workflow, specification, code, roadmap, ADR, assurance, debt, request, finding, release, or `main` content was changed by this research run.**

### D20260831-F01 — PSA/TF-M storage service selection is part of the security contract

- **Novelty:** refines
- **Primary sources:** PSA Certified Secure Storage API 1.0.4; Trusted Firmware-M ITS/Protected Storage documentation and current Profile Small/Medium guidance
- **Primary links:** https://arm-software.github.io/psa-api/storage/1.0/ ; https://trustedfirmware-m.readthedocs.io/en/tf-mv2.2.0/design_docs/services/tfm_its_service.html ; https://trustedfirmware-m.readthedocs.io/en/latest/configuration/profiles/tfm_profile_medium.html ; https://trustedfirmware-m.readthedocs.io/en/tf-mv2.3.0/configuration/profiles/tfm_profile_small.html
- **Source type / date:** Arm/GlobalPlatform-governed PSA API documentation, Secure Storage API 1.0.4 dated 2025-09-23 in its document history; current TF-M project documentation, accessed 2026-08-31
- **Source-supported fact:** PSA Protected Storage defines `PSA_STORAGE_FLAG_NO_REPLAY_PROTECTION` as an explicit opt-out that permits an attacker with physical access to revert an object to an earlier valid version. The architecture states that, absent this opt-out, Protected Storage must detect replacement with a previously valid value. TF-M ITS explicitly does not require rollback protection; TF-M Profile Small uses ITS with no rollback protection, while current Profile Medium enables Protected Storage confidentiality, integrity, and anti-rollback protection by default when PS is selected.
- **Existing owner:** R-005 / R-009 / R-012 / TD-002 / zk213
- **Repository fact:** ZK-ARCHE's new freshness contract requires a target adapter to distinguish record integrity from a trusted high-water generation, and a non-current or unavailable freshness result must fail closed. The storage transaction contract separately requires real target evidence for atomicity/power-loss and anti-rollback behavior.
- **Problem addressed:** a future benchmark could incorrectly record “TF-M secure storage” or “PSA storage” as though that name alone establishes rollback resistance. In reality, ITS vs PS, feature configuration, caller flags, backend support, and profile selection materially change the security property.
- **Strongest distinct engineering idea:** require every target storage benchmark/adapter record to include a **storage capability manifest** with at least: storage API/service (`ITS`, `PS`, vendor NVS, secure element, custom), implementation/version, confidentiality/integrity/replay-protection configuration, relevant creation flags, physical backend, commit/durability semantics, freshness-anchor source, rollback attacker model, and explicit unsupported properties.
- **Evidence maturity:** deployed API/security architecture + target evidence gap
- **Limitations:** PSA/TF-M defines API/service semantics, not proof that a particular board integration correctly realizes them. Platform flash HALs, NV counters, secure elements, and build profiles still need board-specific evidence.
- **ZK-ARCHE inference:** `record_integrity_valid` and `freshness_anchor_current` should be populated from declared adapter capabilities, not inferred from a generic “secure storage enabled” boolean.
- **Likely impact:** no wire impact; small evidence/configuration metadata cost; potential flash/NV-counter cost depends on backend; may exclude constrained configurations that intentionally omit replay protection from claiming rollback-resistant lineage recovery.
- **Rust/C/vector/profile impact:** common Rust/C normalized classifiers can remain unchanged. Target fixtures should exercise the same lineage record under replay-protected and explicitly non-replay-protected adapter modes and require the latter to fail closed for any profile that requires freshness.
- **Required next evidence:** one storage-capability manifest schema; TF-M ITS vs PS target experiments; verify actual `psa_ps_get_support()`/profile configuration; power-cut and old-valid-object restore tests; record exact flags and backend.
- **Recommended disposition:** benchmark
- **Weekly finding candidate:** yes

### D20260831-F02 — ESP32-S3 NVS durability is useful, but firmware anti-rollback is not a lineage counter

- **Novelty:** refines
- **Primary sources:** Espressif ESP-IDF ESP32-S3 NVS, NVS encryption, security overview, OTA anti-rollback, and eFuse Manager documentation
- **Primary links:** https://docs.espressif.com/projects/esp-idf/en/v5.5.3/esp32s3/api-reference/storage/nvs_flash.html ; https://docs.espressif.com/projects/esp-idf/en/latest/esp32/api-reference/storage/nvs_encryption.html ; https://docs.espressif.com/projects/esp-idf/en/latest/esp32s3/security/security.html ; https://docs.espressif.com/projects/esp-idf/en/latest/esp32/api-reference/system/ota.html ; https://docs.espressif.com/projects/esp-idf/en/stable/esp32s3/api-reference/system/efuse.html
- **Source type / date:** official Espressif platform documentation, current/stable docs accessed 2026-08-31
- **Source-supported fact:** Espressif NVS is designed to recover from unexpected power loss, with the in-progress key/value write being the item that may be lost; durable updates require `nvs_commit()`. With NVS encryption, unauthorized alteration/addition cannot be made to appear as a valid pair without the NVS keys, although erasure is not tamper-resistant. ESP32-S3 anti-rollback is documented for application images: the bootloader compares an application `secure_version` against an eFuse-backed version. ESP32-S3 eFuses are one-time programmable; user/key blocks using Reed-Solomon encoding are effectively one-write blocks because the codeword spans the whole block.
- **Existing owner:** R-005 / R-009 / TD-002 / zk213 / zk216
- **Repository fact:** ZK-ARCHE needs two logically separate properties: the ordered lineage transaction must survive interruption conservatively, and a freshness anchor must distinguish the newest authorized lineage record from an older valid snapshot.
- **Problem addressed:** NVS power-loss recovery can satisfy part of the durable-record problem, while firmware security-version eFuse can look superficially like the needed monotonic high-water counter. Reusing it directly for per-lineage transitions would cross security domains and has a finite/irreversible update budget.
- **Strongest distinct engineering idea:** prototype ESP32-S3 as a **two-substrate adapter**: NVS for the ordinary lineage transaction record plus a separately justified freshness mechanism. Do not reuse the bootloader application `secure_version` unless a dedicated architecture review explicitly proves that sharing that firmware lifecycle counter is safe and semantically correct. If custom eFuse state is explored, measure irreversible transition budget, provisioning/write-protection order, block coding constraints, exhaustion behavior, and device replacement/reprovisioning semantics before promotion.
- **Evidence maturity:** deployed platform primitives + constrained-hardware experiment required
- **Limitations:** the current documentation establishes NVS and firmware/eFuse behavior, not a ready-made ZK-ARCHE anti-rollback design. A software high-water journal in ordinary flash may address accidental rollback/power loss but does not automatically resist an attacker who can restore the whole flash image.
- **ZK-ARCHE inference:** NVS `nvs_commit()` success should not be equated with `freshness_anchor_current`. The adapter may be able to report durable record success while still reporting freshness unavailable under a malicious snapshot-restoration threat model.
- **Likely impact:** zero wire impact; NVS adds flash writes/wear; custom eFuse use would consume irreversible hardware state; secure-boot/flash-encryption/eFuse provisioning configuration becomes benchmark metadata.
- **Rust/C/vector/profile impact:** add local target fault injection around every logical storage step and reboot after each cut; restore old complete NVS partitions; vary flash-encryption/NVS-encryption/security configuration; require the normalized Rust/C decision path to remain fail closed when freshness cannot be proven.
- **Required next evidence:** ESP32-S3 exact IDF version/configuration manifest; `nvs_commit()` power-cut harness; old-NVS-snapshot restoration test; NVS encryption/erase behavior test; candidate freshness mechanism with transition/endurance budget; explicit statement that firmware `secure_version` is not reused unless separately approved.
- **Recommended disposition:** benchmark
- **Weekly finding candidate:** yes

### D20260831-F03 — STM32H5 EPOCH-backed secure storage is promising but not automatically a per-lineage high-water counter

- **Novelty:** new
- **Primary sources:** STMicroelectronics STM32H5 Secure Storage and Security Features documentation
- **Primary links:** https://wiki.st.com/stm32mcu/wiki/Security:Secure_Storage_for_STM32H5 ; https://wiki.st.com/stm32mcu/wiki/Security:Security_features_on_STM32H5_MCUs ; https://www.st.com/content/st_com/en/ecosystems/stm32trust.html
- **Source type / date:** official STMicroelectronics platform documentation, pages updated/published in 2026 and accessed 2026-08-31
- **Source-supported fact:** STM32H5 secure storage can derive keys from device-unique hardware material and uses secure/non-secure EPOCH counters. ST documents that a regression increments the relevant EPOCH counter(s), causing new derived hardware keys and preventing previously encrypted secure-storage data from being reused after the regression. ST explicitly describes this as anti-rollback protection for that secure-storage model.
- **Existing owner:** R-005 / R-009 / R-012 / TD-002 / zk213 / zk216
- **Repository fact:** ZK-ARCHE's common freshness classifier expects the adapter to justify an exact `trusted_high_water_generation` bound to the same local security domain and lineage namespace.
- **Problem addressed:** a hardware feature named EPOCH/anti-rollback can be mistaken for direct semantic equivalence with the ZK lineage generation. STM32H5's documented EPOCH is tied to secure-storage regression/domain key derivation, not stated as an application-incremented counter for every trust-lineage replacement.
- **Strongest distinct engineering idea:** evaluate STM32H5 EPOCH as a **coarse storage-domain freshness boundary** and determine whether ZK lineage generation must still live in rollback-protected Protected Storage or another counter. The adapter should explicitly document the mapping: what event advances EPOCH, whether ordinary lineage replacement can advance a protected high-water value without destructive regression, how cloning/reprovisioning behaves, and whether old encrypted lineage records become cryptographically unusable under the tested rollback scenario.
- **Evidence maturity:** vendor-documented hardware security capability + hardware mapping experiment required
- **Limitations:** ST's documents establish platform behavior, not ZK-ARCHE semantics. Treating every lineage replacement as a product regression would be operationally disproportionate and is not recommended by this report.
- **ZK-ARCHE inference:** STM32H5 may support stronger anti-rollback evidence than plain MCU flash, but the common contract should consume normalized facts rather than expose STM32-specific EPOCH semantics to the protocol.
- **Likely impact:** likely zero wire impact; target-specific secure-storage/SAES/DHUK integration and provisioning complexity; possibly lower ordinary flash dependence but additional hardware/platform coupling.
- **Rust/C/vector/profile impact:** common vectors remain storage-neutral. Hardware tests should dump/restore old encrypted storage across regression/EPOCH changes, clone records across devices where feasible, and verify normalized `CURRENT`/`ROLLBACK_DETECTED`/`BINDING_MISMATCH` outcomes.
- **Required next evidence:** representative STM32H5 board; exact part/firmware/security configuration; documented EPOCH transition procedure; old encrypted snapshot restoration before/after regression; device-clone test; mapping from lineage generation to rollback-protected storage without destructive per-replacement regression.
- **Recommended disposition:** investigate

## 5. Cross-source synthesis

The new repository transaction/freshness split is validated by the target literature: **durability, integrity, and freshness are three different properties** and real MCU stacks expose them independently.

```text
logical LINEAGE_REPLACE transaction
        ↓
target durable-record substrate
        ├── power-loss/atomicity semantics
        ├── integrity/confidentiality semantics
        └── wear/failure behavior
        ↓
separate freshness / replay-protection substrate
        ├── Protected Storage replay protection
        ├── rollback-protected high-water state
        ├── secure-element / platform counter
        └── or explicit UNAVAILABLE → CONTINUITY_BROKEN
        ↓
normalized common facts
        ↓
Rust/C shared restart classifier
```

PSA makes the semantic difference explicit with a replay-protection opt-out. ESP32-S3 illustrates why power-loss-tolerant NVS and application-image anti-rollback should not be conflated. STM32H5 illustrates that stronger hardware anti-rollback exists but can operate at a different lifecycle granularity than ZK lineage transitions. The Common Contract should therefore stay storage-neutral while target evidence becomes more specific.
