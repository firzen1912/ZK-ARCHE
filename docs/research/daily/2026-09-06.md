## 1. Executive synthesis

1. **The new resumption privacy precedence is directionally correct, but the privacy state should eventually be scoped to an association/privacy epoch rather than reduced to a reuse counter.** The August 21, 2026 EMU WG EAP-PPT draft explicitly notes that a resumption identifier lets the server detect a peer revisit and therefore restricts session resumption to the current network association. For ZK-ARCHE this supports a future invariant in which a resumption identifier is valid only inside a bounded association/privacy epoch; crossing that boundary requires full AUTH even if cryptographic resumption material has remaining nominal lifetime/reuse budget.
2. **Successful authorization or privacy-token processing must remain subordinate to current channel/association authority.** EAP-PPT performs channel-binding validation after successful token redemption but before EAP-Success, and permits authentication failure if channel-binding data is unsatisfactory. This closely matches current ZK-ARCHE DATA composition: a previously successful AUTH or release authorization cannot authorize a new protected-data release after CORE/LINK/BIND authority becomes unsafe. The useful next evidence is temporal cross-module qualification, not another parallel authorization classifier.
3. **One-time/replay-sensitive privacy objects need two distinct evidence surfaces: internal replay/double-spend state and externally observable failure behavior.** EAP-PPT may detect token double spend and requires recovery with a new token, but its method executes inside a TLS tunnel. ZK-ARCHE's release/resumption decisions expose internal reason precedence in deterministic corpora; future network-facing error behavior should continue to map those reasons through the privacy observability contract rather than automatically exposing fine-grained replay/linkability causes to an unauthenticated observer.
4. **Optional remote attestation should bind the exact operational authentication key through protocol proof of possession.** The August 15, 2026 RATS key-attestation draft addresses key-substitution attacks by carrying the subject public key in EAT evidence and requiring protocol-level proof of possession of the same key, with verifier-provided nonce freshness. For ZK-ARCHE this strengthens R-006 without promoting attestation into the mandatory core: attestation metadata is evidence about a key/platform relation, not peer authority by itself.
5. **No wire, mandatory-suite, profile-selectability, roadmap, ADR, debt status, or maturity claim changes today.** R-006, R-009, R-010, R-012, R-015 and TD-003/TD-004 already own these questions; no backlog edit is required.

### D20260906-F01 — Resumption privacy needs an association/privacy-epoch boundary

- **Novelty:** refines
- **Source:** `draft-ietf-emu-eap-ppt-03`, *Extensible Authentication Protocol (EAP) Using Privacy Pass Token*
- **Primary link:** https://datatracker.ietf.org/doc/draft-ietf-emu-eap-ppt/03/
- **Source type / venue:** IETF EMU Working Group, Standards Track Internet-Draft
- **Publication / update date:** August 21, 2026
- **Verified claim:** the draft states that a TLS session-resumption identifier lets the EAP server detect a peer's revisit. To limit that privacy exposure, it requires a full TLS handshake after each new network association and restricts resumption to the same authenticator/current association. The same document describes Privacy Pass tokens as unlinkable authenticators whose redemption is separated from issuance.
- **Existing owner:** R-009 / R-015 / resumption authorization
- **Repository fact:** current `dev` added deterministic Rust/C cases in `resumption-authorization-v5.txt` where stale privacy-identifier state or a repeated linkable identifier takes precedence over reuse-limit, epoch-stale, binding-mismatch, and profile-mismatch fallback causes.
- **Problem addressed:** a numeric ticket/reuse budget alone does not define the privacy boundary. An identifier can remain cryptographically valid yet become privacy-inappropriate when a peer crosses an association, deployment, mobility, or policy boundary in which correlation should not continue.
- **Strongest distinct engineering idea:** model future resumption privacy validity as a bounded **privacy/association epoch** owned separately from cryptographic secret lifetime. A resumption attempt should require both `(resumption_secret_valid)` and `(identifier_privacy_epoch_current)`. A privacy-epoch transition forces full AUTH even if the credential has unused count/lifetime remaining. The exact epoch trigger remains profile-specific; it must not be inferred from IP/socket address alone.
- **Evidence maturity:** standards-track work-in-progress comparator; ZK-ARCHE current evidence is software/vector level
- **Limitations / uncertainty:** EAP-PPT's "same authenticator/current association" rule is WLAN/EAP-specific and cannot be copied literally into native ZK-ARCHE. ZK-ARCHE must define a transport-neutral privacy boundary appropriate to its P2P/IoT profiles and mobility requirements.
- **ZK-ARCHE inference:** retain current privacy-first fail-closed precedence, but define the normalized fact behind `privacy_identifier_state_current` in terms of a profile-owned privacy epoch plus bounded reuse. Address or transport continuity must not itself become peer identity or authorization.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** potentially one bounded local privacy-generation/epoch value plus identifier rotation state; no mandatory wire change if the epoch is locally derived from authenticated lifecycle state. More frequent full AUTH may increase CPU/wire cost but reduces cross-association correlation.
- **Rust/C / vector compatibility impact:** add future shared vectors for an otherwise valid resumption secret crossing a privacy-epoch boundary, mobility/address change without privacy-epoch change, privacy-epoch change while reuse count remains below limit, and rotation failure/rollback. Reason precedence should remain byte/decision compatible.
- **Required next evidence:** define profile-neutral privacy-epoch semantics; map concrete profile triggers without using address as identity; add Rust/C vectors; measure reconnect/full-AUTH cost on constrained targets; add passive-correlation tests over repeated resumption attempts.

### D20260906-F02 — Authorization success does not supersede channel authority, and internal replay reasons are not automatically public errors

- **Novelty:** corroborates/refines
- **Source:** `draft-ietf-emu-eap-ppt-03`, channel-binding, privacy, and double-spend processing
- **Primary link:** https://datatracker.ietf.org/doc/draft-ietf-emu-eap-ppt/03/
- **Source type / venue:** IETF EMU Working Group, Standards Track Internet-Draft
- **Publication / update date:** August 21, 2026
- **Verified claim:** EAP-PPT can successfully redeem a privacy token and then perform channel-binding validation before EAP-Success; invalid or unsatisfactory channel-binding data can still cause failure. The draft also defines optional double-spend detection for a one-time Privacy Pass token and requires recovery with a new token. EAP-PPT itself runs inside a server-authenticated TLS tunnel.
- **Existing owner:** R-010 / R-012 / R-015 / DATA + BIND
- **Repository fact:** current ZK-ARCHE DATA semantics explicitly state that earlier AUTH, open transport state, retained traffic keys, cached authorization, or an earlier successful DATA release cannot authorize a new release after the authoritative CORE/LINK association decision becomes fail-closed. Current transport-binding classifiers also reject internally inconsistent normalized binding facts. DATA and resumption corpora expose detailed internal reasons for deterministic parity.
- **Problem addressed:** security decisions become unsound when one positive subdecision (token valid, AUTH succeeded earlier, authorization cached, traffic key still resident) is allowed to repair an independent failed authority axis. Separately, deterministic internal reason codes can become privacy oracles if mapped one-for-one onto unauthenticated network-visible errors.
- **Strongest distinct engineering idea:** preserve two layers: **(A) rich internal fail-closed reason precedence for local audit/testing**, and **(B) a separately specified observable failure class** appropriate to the attacker's visibility. In addition, keep the ownership DAG explicit: authorization/release-token success supplies one required fact; current channel/association authority supplies another; neither synthesizes the other.
- **Evidence maturity:** standards-track work-in-progress comparator; current ZK-ARCHE composition is software/spec evidence
- **Limitations / uncertainty:** EAP-PPT protects its detailed method traffic inside TLS, while native ZK-ARCHE deployments may expose different pre-authentication surfaces. Its exact error codes should not be copied. Some authenticated peers may legitimately receive more diagnostic detail than passive/unauthenticated observers.
- **ZK-ARCHE inference:** the new retained-authority composition is the right direction. The next evidence should emphasize temporal cross-module sequences and observable-response equivalence rather than adding another DATA-local copy of replay/revocation/binding state.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** no immediate wire change. Observable-failure normalization may require response bucketing/dummy timing policy with CPU/DoS tradeoffs. Cross-module authority checks reuse existing local state and avoid duplicated classifiers.
- **Rust/C / vector compatibility impact:** retain rich internal reason vectors, then add a separate shared corpus mapping multiple internal causes (release replay, stale privacy identifier, invalid binding, stale authority) to allowed externally observable classes by profile/attacker state. Add temporal Rust/C qualification for AUTH → RELEASE → authority loss → deny.
- **Required next evidence:** complete retained-association temporal test sequence; define observable failure mapping for DATA/resumption/BIND; timing/size/response-class measurement under passive and active attackers; prove no positive authorization subdecision repairs an unsafe channel/association fact.

### D20260906-F03 — Optional attestation must bind the exact operational authentication key

- **Novelty:** new/refines
- **Source:** `draft-reddy-rats-key-binding-02`, *Key Attestation for Entity Attestation Tokens (EAT)*
- **Primary link:** https://datatracker.ietf.org/doc/draft-reddy-rats-key-binding/02/
- **Source type / venue:** IETF RATS Working Group discussion, Standards Track Internet-Draft
- **Publication / update date:** August 15, 2026
- **Verified claim:** the draft carries a Subject Public Key in the EAT `cnf` claim and combines signed attestation evidence with **protocol-level proof of possession of the same operational key**. It explicitly targets key-substitution attacks in which valid attestation for one protected key is presented alongside authentication/enrollment using a different key. It also requires verifier-provided unpredictable nonce freshness and states that time-validity claims do not replace nonce freshness.
- **Existing owner:** R-006 / R-013 / TD-003
- **Repository fact:** ZK-ARCHE treats remote attestation as optional research-only work. Its current Common Contract separately rejects transport metadata as authority and requires explicit holder/credential/authentication context. Existing R-006 already calls for freshness/privacy and cross-session/relay binding analysis; R-013 owns exact credential/reference-to-key binding.
- **Problem addressed:** a verifier can validate genuine attestation evidence and a genuine peer authentication independently yet still be fooled if the evidence refers to a different key than the one the peer actually proves possession of. Freshness alone does not fix this substitution class.
- **Strongest distinct engineering idea:** if an optional ZK-ARCHE attestation profile is ever prototyped, normalize an attested-key fact only after verifying `(fresh attestation evidence → exact subject public key)` **and** `(current ZK-ARCHE AUTH/association → proof of possession of that same key/commitment)`. The attestation result can then constrain policy; it must not create identity, enrollment, or authorization by itself.
- **Evidence maturity:** standards-track work-in-progress; ZK-ARCHE remains research-only for this capability
- **Limitations / uncertainty:** the draft's concrete examples are certificate/TLS/CSR oriented and assume an attestation authority/verifier model. ZK-ARCHE must map the key equality/binding property to its own Ristretto/credential/role model and preserve infrastructure independence for ordinary P2P operation.
- **ZK-ARCHE inference:** R-006 should remain optional. The important transferable invariant is exact-key PoP binding plus fresh evidence, not adoption of PKIX or an online verifier.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** optional EAT evidence can be materially larger and introduces attestation-key/verifier trust plus target root-of-trust dependencies; no impact on the mandatory constrained floor. Verification adds signature/hash and evidence-parsing cost.
- **Rust/C / vector compatibility impact:** an optional future profile needs negative vectors where valid attestation for key A is paired with valid AUTH/PoP for key B, stale/replayed nonce evidence, omitted key-binding claims, and mismatched verifier/session context. Common Contract decisions must remain identical across Rust/C after normalized facts are supplied.
- **Required next evidence:** define ZK-ARCHE-specific subject-key/commitment mapping; prototype key-A/evidence vs key-B/PoP substitution tests; measure evidence bytes/RAM/CPU on edge and constrained targets; analyze verifier privacy and infrastructure failure modes.
- **Recommended disposition:** research-only

## 5. Cross-source synthesis

The strongest combined conclusion is a **non-substitution rule across lifecycle evidence**:

```text
resumption credential / identifier
        ≠ privacy epoch
        ≠ current authorization
        ≠ current channel authority

privacy/authorization token success
        ≠ successful channel binding
        ≠ retained association authority

attestation evidence
        ≠ proof of possession of operational key
        ≠ peer identity / authorization
```

Each source reinforces the same architecture already emerging in ZK-ARCHE: keep independent facts independently owned, bind them cryptographically where one fact asserts something about another, and fail closed rather than allowing a positive result in one layer to repair a stale or missing result in another. The new engineering refinement is mostly **temporal and privacy-scoping evidence**, not new cryptography.
