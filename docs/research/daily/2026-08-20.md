# ZK-ARCHE Research — 2026-08-20

## Executive synthesis

The current `dev` branch remains implementation-stable relative to the 2026-08-19 research cycle: no intervening Rust/C, specification, roadmap, deterministic-vector, formal-model, or assurance changes were found. The active engineering constraints are therefore unchanged: TD-001 independent review of the custom role-membership proof, TD-002 constrained-target measurements, TD-003 reproducible formal evidence, and TD-004 completion of the normative specification.

Three current IETF work items materially sharpen those gaps without justifying a new mandatory primitive:

1. **Extensibility must be continuously tested, not merely documented.** The July 2026 EDHOC GREASE draft reserves unusable cipher suites and non-critical extension values specifically to verify that peers correctly tolerate unknown values without letting those values alter the established security context. ZK-ARCHE already reserves capability/extension registries and says unknown-extension behavior must be tested, but the current Rust negotiation code has only basic common-version/common-suite tests. A GREASE-style conformance lane would expose parser/negotiation ossification before future suites, profiles, and extensions depend on those code paths.
2. **Late enrollment should separate constrained-link authentication from third-party authorization overhead.** The July 2026 ELA draft performs enrollment authorization in parallel with EDHOC authentication, uses a device/domain-authenticator/enrollment-server split, and shifts larger or database-backed work toward the non-constrained side. That directly sharpens zk211/zk212 and R-008: a future ZK-ARCHE `EnrollmentGrant`/commissioner design should specify which authorization evidence must traverse the constrained peer link and which verification or credential-retrieval work can remain behind a gateway/commissioner boundary.
3. **Credential or authorization invalidation must cascade to dependent sessions and derived keys.** The July 2026 EDHOC implementation-considerations draft explicitly treats credential expiration/revocation, invalid application keys, and invalid bound access rights as lifecycle events that can require purging the originating session and derived application keys, then re-establishing fresh security state. ZK-ARCHE currently discusses rekey, revocation epochs, resumption, and authorization separately; future specifications need an explicit dependency/invalidation graph so stale authorization cannot survive through a still-live session or resumed key context.

No source reviewed today warrants changing the baseline Ristretto/HKDF/HMAC construction, promoting BBS/PQ work, or modifying roadmap/spec/code automatically.

## Findings

### 1. GREASE-style conformance testing is a practical defense against ZK-ARCHE extension ossification

- **Sources:** `draft-ietf-lake-edhoc-grease-03`, *Applying Generate Random Extensions And Sustain Extensibility (GREASE) to EDHOC Extensibility*; `draft-iab-protocol-greasing-01`, *Considerations For Maintaining Protocols Using Grease and Variability*
- **Primary links:** https://datatracker.ietf.org/doc/html/draft-ietf-lake-edhoc-grease-03 and https://datatracker.ietf.org/doc/draft-iab-protocol-greasing/
- **Source type / venue:** IETF LAKE WG Internet-Draft in WG Last Call; active IAB Internet-Draft
- **Publication/update dates:** EDHOC GREASE - 2026-07-06; IAB protocol greasing - 2026-07-05/06
- **Verified claim:** EDHOC GREASE defines reserved unusable cipher-suite values and non-critical EAD values that can be sent to ensure peers correctly process unknown values. Recipients must not let random GREASE data alter the resulting security context and should follow normal unknown-value processing. The draft also recommends distinguishing GREASE-related failures operationally and notes that constrained deployments must balance greasing against fragmentation/message-size cost. The IAB draft generalizes the principle: extension points that are not actively exercised tend to ossify and become difficult to use safely later.
- **Problem addressed:** ZK-ARCHE plans registry growth across suites, profiles, extensions, transport bindings, retry, resumption, and channel binding. A registry specification alone does not prove that Rust/C parsers and negotiators will remain tolerant of unknown non-critical values or reject unsupported security-critical selections correctly.
- **Strongest distinct engineering idea:** add a deterministic "extension agility" conformance corpus that regularly injects reserved/unknown capability bits and unsupported suite IDs into HELLO/negotiation paths. Tests should prove that unknown non-critical values do not change the selected security context, unsupported selected security-critical values fail closed, and Rust/C behavior remains byte/decision compatible. Keep network-size GREASE optional; the critical value is exercising the code path in tests and interoperability CI.
- **Evidence maturity:** software
- **Limitations / uncertainty:** EDHOC's EAD semantics are not identical to ZK-ARCHE TLVs/capabilities. ZK-ARCHE must define its own critical-vs-ignorable extension semantics before copying any wire behavior. Random live GREASE may be undesirable on tiny links; deterministic conformance vectors provide most of the engineering value without production bandwidth cost.
- **ZK-ARCHE inference:** this should become an evidence requirement under zk225/zk226 rather than a mandatory runtime feature. `spec/registries.md` should eventually define unknown-value classes, and the Rust/C vector suite should include reserved-value acceptance/rejection fixtures.
- **Wire / RAM / CPU / flash / dependency impact:** no production wire cost if initially test-only. CI/vector corpus grows slightly. A later optional live GREASE profile would add bounded bytes and RNG use and must respect UDP/fragmentation limits.
- **Rust/C / vector compatibility impact:** compatible if test-only. Future registry rules need matched Rust/C vectors for unknown ignorable values, unknown critical values, unsupported suites, vendor capability bits, and extension-order variability where the encoding permits it.
- **Recommended disposition:** reproduce

### 2. ELA provides a concrete constrained-link pattern for authorized late enrollment

- **Source:** `draft-ietf-lake-authz-08`, *Lightweight Authorization using Ephemeral Diffie-Hellman Over COSE (ELA)*
- **Primary link:** https://www.ietf.org/ietf-ftp/internet-drafts/draft-ietf-lake-authz-08.html
- **Source type / venue:** IETF LAKE WG Standards-Track Internet-Draft
- **Publication date:** 2026-07-06
- **Verified claim:** ELA targets authorization of device enrollment over constrained links. It separates the device, domain authenticator, and enrollment server; assumes a pre-existing device-to-enrollment-server trust relation; performs authorization in parallel with the authenticated key exchange; conveys compact authorization information/vouchers over the constrained exchange; and shifts credential/database/backend interactions to a non-constrained path behind the authenticator where possible.
- **Problem addressed:** ZK-ARCHE zk211/zk212 already envision one-time `EnrollmentGrant` objects and delegated commissioner enrollment, but the current roadmap does not yet define the constrained-link/backend split. Without that split, a future enrollment design can accidentally push certificate chains, registry scans, policy engines, or remote authorization dependencies onto `iot-core` peers.
- **Strongest distinct engineering idea:** model late enrollment as three logical roles even if two roles are co-located in simple deployments: joining peer, domain authenticator/commissioner, and enrollment authority. Define a compact grant/voucher that the constrained peer can validate with bounded work while allowing registry lookup, manufacturer/domain policy, revocation checks, and credential retrieval to execute on the gateway/authority side. Preserve offline/local modes by making the remote authority an architectural role, not an always-online dependency.
- **Evidence maturity:** software
- **Limitations / uncertainty:** ELA uses EDHOC EAD/COSE and its own trust assumptions; those formats and exact flows are not ZK-ARCHE requirements. ZK-ARCHE's privacy goals may require less stable device identity exposure than common zero-touch onboarding schemes. The proposed endeavor also requires infrastructure-independent operation, so a commissioner/enrollment authority cannot become mandatory for normal P2P AUTH.
- **ZK-ARCHE inference:** refine R-008 and future zk211/zk212 review around an explicit trust/placement diagram and constrained-wire budget. The `EnrollmentGrant` should bind issuer, domain/audience, device-key commitment where known, authorized role/scope, validity, nonce/replay state, policy epoch, and grant-use channel/session context, while expensive verification remains off the constrained path when possible.
- **Wire / RAM / CPU / flash / dependency impact:** potentially favorable for MCU peers if it moves database/policy work off-device. The grant itself must have a strict byte budget and bounded parser. Remote authority use introduces availability/trust dependencies that require an offline/degraded deployment mode.
- **Rust/C / vector compatibility impact:** no current change. A future enrollment profile requires positive/negative vectors for wrong issuer/domain/device commitment/role/epoch, expired grants, replayed grants, commissioner overreach, and authority-unavailable cases.
- **Recommended disposition:** investigate

### 3. Credential and authorization invalidation must explicitly revoke dependent session/key state

- **Source:** `draft-ietf-lake-edhoc-impl-cons-07`, *Implementation Considerations for Ephemeral Diffie-Hellman Over COSE (EDHOC)*
- **Primary link:** https://www.ietf.org/ietf-ftp/internet-drafts/draft-ietf-lake-edhoc-impl-cons-07.html
- **Source type / venue:** IETF LAKE WG Informational Internet-Draft in WG Last Call
- **Publication date:** 2026-07-06
- **Verified claim:** the draft treats completed authenticated sessions and application keys derived from them as linked lifecycle objects. If an authentication credential expires or is revoked, sessions that relied on that credential become invalid and derived application keys are removed. It separately covers unsafe/expired application keys and cases where application keys or bound access rights become invalid. Fresh protocol execution/key establishment is used to return to valid state when required.
- **Problem addressed:** ZK-ARCHE has separate roadmap items for rekey, resumption, revocation epochs, trust evidence, authorization, and data release. Without a normative dependency graph, an implementation could revoke a role/grant/credential while leaving a resumed session, exported/link key, release token, or cached authorization decision valid longer than intended.
- **Strongest distinct engineering idea:** make invalidation propagation first-class. Each derived security object should carry or reference the credential/registry/policy/key epochs that authorize it. Revoking or changing an upstream object should deterministically identify which sessions, resumption tickets, LINK keys, cached authorization contexts, and DATA release material must be rejected, rekeyed, or reauthenticated. "Rekey" alone must not preserve an authorization state whose source credential or policy epoch is no longer valid.
- **Evidence maturity:** software
- **Limitations / uncertainty:** EDHOC/OSCORE object lifecycles do not map one-to-one onto ZK-ARCHE's future suite decomposition. Immediate deletion versus tombstoning/audit retention is a ZK-ARCHE design choice. Availability-sensitive deployments may need bounded grace or asynchronous revocation propagation, which must be explicit rather than accidental.
- **ZK-ARCHE inference:** create a lifecycle/invalidation matrix spanning enrollment credential, role/policy epoch, authenticated session, LINK/application keys, resumption ticket, authorization context, and DATA release token. This matrix should become input to zk213, zk221, zk230, zk234, and formal-model work under R-004.
- **Wire / RAM / CPU / flash / dependency impact:** likely modest wire impact if epochs/identifiers are already present, but implementation state and persistent metadata may grow. Fast invalidation lookup may require bounded indexing on gateways; MCU peers should retain only the minimal upstream epochs necessary to fail closed.
- **Rust/C / vector compatibility impact:** no current change. Future negative vectors should cover revoked credential with live session, policy-epoch advance with resumption ticket, role removal after key establishment, stale cached authorization, rekey without reauthorization, and release-token use after upstream revocation.
- **Recommended disposition:** reproduce

## Cross-source synthesis

Today's sources point to one common requirement: **future protocol agility and lifecycle changes must be testable as state transitions, not left as registry prose or implementation convention**.

- GREASE makes extension agility observable by intentionally exercising unknown values.
- ELA makes enrollment authorization placement observable by separating constrained and non-constrained roles.
- EDHOC implementation guidance makes revocation observable by explicitly cascading invalidation into dependent sessions and application keys.

For ZK-ARCHE, the corresponding design artifact should eventually be a compact conformance matrix that crosses **registry/extension state**, **authorization/enrollment state**, and **derived-session/key state**. Every transition should have a deterministic outcome and at least one negative vector or formal-model property.
