## 1. Executive synthesis

1. **ZK-ARCHE's new bounded DATA audit hash chain establishes local transition integrity, not global append-only consistency or non-equivocation.** Current Rust state hashes the prior head, sequence, event kind, release-context commitment, authorization generation, revocation epoch, and policy epoch. This detects event/predecessor mutation when the verifier has the expected predecessor/head, but it does not by itself prove that two observers were shown the same history or that an older valid snapshot was not restored.
2. **RFC 9942 gives zk235 a clean architectural boundary for any future transparency bridge: inclusion and consistency are distinct proof types, and append-only assurance requires successful consistency verification, not merely a valid signed receipt.** The RFC also recommends one fail-closed receipt-verification result so a valid signature cannot be mistaken for a valid consistency proof.
3. **Audit evidence is itself a privacy surface.** RFC 9942 explicitly warns that proof structures can reveal log length and that receipt header parameters can reveal information about the transparency service or entries. A future ZK-ARCHE transparency bridge therefore must not export raw local sequence numbers, detailed denial causes, authorization generations, policy epochs, or other stable metadata without a privacy analysis.
4. **Today's new constrained audit-storage manifest is directionally correct because it keeps physical persistence/rollback/power-loss evidence separate from the software hash-chain property.** The manifest remains explicitly `unmeasured`; no physical-target durability, anti-rollback, write-endurance, or latency claim is established.
5. **No wire, mandatory-suite, roadmap, ADR, debt status, or maturity claim changes today.** zk235, TD-002, TD-003, TD-004, R-012 and R-015 already provide adequate ownership; no backlog edit is required.

## 4. Findings

### D20260907-F01 — Local audit integrity is not append-only consistency or non-equivocation

- **Novelty:** refines
- **Source:** RFC 9942, *CBOR Object Signing and Encryption (COSE) Receipts*
- **Primary link:** https://datatracker.ietf.org/doc/rfc9942/
- **Source type / venue:** IETF Standards Track RFC
- **Publication / release date:** June 2026
- **Verified claim:** RFC 9942 separates inclusion proofs from consistency proofs. For its RFC9162_SHA256 profile, consistency verification proves that a newer Merkle-tree state is consistent with an older state; if consistency verification fails, the append-only property is not assured. The RFC recommends exposing a single boolean result for receipt verification to reduce the risk that a valid signature is accepted while the consistency proof is invalid.
- **Existing owner:** zk235 / TD-002 / TD-003 / TD-004
- **Repository fact:** current `DataAuditState` contains only a 32-byte head and `next_sequence`; each digest commits to the previous head, sequence, event kind, `release_context_hash`, authorization generation, revocation epoch, and policy epoch. Current tests demonstrate deterministic first-entry parity and detection of predecessor/sequence/event mutation. Separately, the new constrained-target manifest correctly marks audit persistence, restart, rollback and power-loss testing as unmeasured until physical execution exists.
- **Problem addressed:** a local hash chain can prove that a candidate transition follows a known predecessor, but without an independently trusted checkpoint/freshness anchor or cross-observer consistency mechanism it cannot establish that a device did not restore an older valid chain head, truncate history, or present divergent histories to different observers.
- **Strongest distinct engineering idea:** keep **three evidence layers** explicit: `(1) local transition integrity`, `(2) rollback/freshness-protected durable local head`, and `(3) optional external transparency/non-equivocation proof`. A future transparency bridge should export a privacy-minimized commitment/checkpoint and, if non-equivocation is claimed, support consistency verification between checkpoints. It must remain optional and must not become an authorization dependency for offline P2P/DATA operation.
- **Evidence maturity:** RFC source is externally reviewed; current ZK-ARCHE audit chain is software evidence; physical storage evidence is unmeasured
- **Limitations / uncertainty:** RFC 9942 defines a general COSE-receipt framework and one Merkle-tree VDS profile; ZK-ARCHE currently uses a linear local hash chain, not an RFC9162 Merkle tree. Adopting COSE receipts or a Merkle VDS is not implied. A simple signed/checkpointed linear-chain design may be sufficient for some deployment goals, but its exact non-equivocation/rollback properties must be stated rather than inferred.
- **ZK-ARCHE inference:** do not label the current local chain "tamper-proof", "non-equivocating", or externally transparent. Treat local mutation detection, physical rollback protection, and external consistency as separate claim axes. For zk235, first define what threat requires an external bridge; only then choose a proof structure.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** no mandatory protocol wire impact. A local chain stays approximately constant-state (head + sequence) but durable append/checkpointing consumes flash writes. An optional external consistency mechanism adds proof bytes, hashing, checkpoint state and a transparency-service/monitor trust model; a Merkle design additionally adds tree/proof storage or recomputation costs.
- **Rust/C / vector compatibility impact:** current Rust/C local-chain vectors can remain unchanged. Future evidence should add rollback/truncation/fork scenarios at the storage/checkpoint layer rather than changing the canonical local digest merely to emulate RFC 9942. Any optional bridge requires its own versioned corpus.
- **Required next evidence:** physical append/restart/power-loss/rollback measurements on representative ESP32-S3 and STM32-class targets; explicit local-head freshness mechanism; fork/truncation/old-snapshot negative tests; optional checkpoint/consistency prototype only if the threat model justifies external transparency.
- **Recommended disposition:** reproduce
- **Weekly finding candidate:** yes

### D20260907-F02 — Audit/transparency evidence needs a privacy-minimized export contract

- **Novelty:** refines
- **Source:** RFC 9942, Privacy Considerations
- **Primary link:** https://datatracker.ietf.org/doc/rfc9942/#section-6
- **Source type / venue:** IETF Standards Track RFC
- **Publication / release date:** June 2026
- **Verified claim:** RFC 9942 warns that some proof structures reveal log size at inclusion time, which can disclose sensitive operational information, and requires profiles to perform privacy analysis for mandatory receipt fields because header parameters can reveal information about the service or entries.
- **Existing owner:** zk235 / R-015 / privacy considerations
- **Repository fact:** current local DATA audit events deliberately store only a commitment to the canonical release context rather than protected plaintext, but they also bind sequence, grant/deny kind and authorization/revocation/policy generations into the chain. These values are currently local inputs to a digest, not a defined public receipt format.
- **Problem addressed:** an optional transparency export that naively publishes sequence numbers, denial events, policy generations, revocation epochs, stable device identifiers or richly typed receipt headers can become a correlation/operational-intelligence oracle even when protected DATA itself never leaves the device.
- **Strongest distinct engineering idea:** define a future **audit disclosure boundary** before defining an external receipt: local audit state may retain the minimum information required for forensic verification, while externally exportable evidence should use commitments/pseudonymous domains, coarse or blinded counters where feasible, and purpose-specific disclosure. Inclusion/consistency verification should not require exposing the full local event record.
- **Evidence maturity:** externally reviewed standards guidance; ZK-ARCHE implication remains concept/research level
- **Limitations / uncertainty:** the concrete leakage depends on deployment. A private operator-owned audit channel has a different attacker model from a public transparency service. Hiding sequence/log-size information may complicate simple consistency proofs or reduce operational utility, so privacy and auditability need explicit trade-off measurements.
- **ZK-ARCHE inference:** preserve the current rule that audit evidence never authorizes release. Before any zk235 transparency bridge is promoted, inventory which fields are visible to the device owner, authorized auditor, peer, passive observer, and public service. External receipt verification should collapse internal detailed causes into a bounded verification result where detailed distinctions would create privacy oracles.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** no mandatory core impact. Optional privacy-preserving receipts may add commitments, padding or selective disclosure and therefore extra bytes/CPU; minimizing public metadata can reduce linkability at the cost of more complex audit tooling.
- **Rust/C / vector compatibility impact:** no change to existing local chain. A future export layer needs shared fixtures proving that two different internal event details can map to the same permitted public metadata class while verification still detects invalid commitments/consistency.
- **Required next evidence:** field-level observability matrix for audit events/checkpoints; passive-correlation analysis; proof-size and MCU-cost measurements for candidate optional checkpoint formats; negative tests proving detailed internal denial/revocation causes are not exposed to unauthorized observers.
- **Recommended disposition:** investigate

## 5. Cross-source synthesis

RFC 9942 changes the decision boundary for zk235 in a useful way without requiring a protocol change. The local SHA-256 chain is a valid compact integrity primitive for a known predecessor/history, while rollback-resistant durability and external non-equivocation are separate properties requiring separate evidence. The same standard also prevents treating "more transparency" as automatically "more privacy-preserving": proofs and receipts can leak log-size and service metadata.

The current repository is therefore converging on the right separation:

```text
DATA authorization decision
        ↓
local audit event commitment
        ↓
local hash-chain continuity
        ↓
rollback/freshness-protected durable checkpoint   [not yet physically evidenced]
        ↓
optional privacy-minimized transparency bridge   [research only]
        ↓
optional inclusion/consistency proof + monitor   [only if threat model requires]
```

None of the lower layers should feed authorization authority back upward.
