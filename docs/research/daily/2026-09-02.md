## 1. Executive synthesis

1. **The new enrollment replay fact should eventually prove correlation to one exact authorized enrollment attempt, not only that an operation identifier has not been seen before.** Current `EnrollmentGrantFacts` correctly separates commissioner authorization freshness, one-time enrollment replay state, possession, scope, audience, deployment, epochs, lineage, and rollback. cBRSKI and the current voucher-artifact work sharpen the missing next step: constrained onboarding commonly uses a live nonce for anti-replay, while the signed authorization artifact also pins the intended domain/registrar identity. ZK-ARCHE should therefore test that the consumed nonce/operation ID is cryptographically or canonically bound to the subject, commissioner/authority context, requested grant scope, audience/deployment, and relevant lineage/epoch before an eventual grant wire format is considered complete.
2. **Expiration and nonce freshness are different controls on constrained devices.** cBRSKI explicitly prefers live nonces over expiry times for constrained pledges that may lack accurate clocks. ZK-ARCHE already models both `validity_bounded` and `enrollment_nonce_unused`; this is a strong design direction. Future ENROLL evidence should preserve that separation and must not let a bounded lifetime substitute for one-time replay state where the profile requires single-use enrollment.
3. **Enrollment authorization must remain distinct from later association, network-access, and DATA authorization.** cBRSKI treats its voucher as authorization to establish the intended domain relationship, then separately obtains a domain identity and later network-access credentials. NIST SP 1800-36 likewise treats trusted onboarding as establishing/verifying trust before provisioning credentials and continuing lifecycle controls afterward. This directly supports the new ZK-ARCHE split between ENROLL grant issuance, CORE association admission, and DATA-release authorization. The newest DATA-release v3 surface strengthens the point further by adding current authorization-generation and one-time release-operation replay checks: an issued/accepted enrollment grant should never automatically mean `ESTABLISH` or `RELEASE` without the current local postconditions.
4. **Third-party enrollment assistance can remain optional and below the local authority boundary.** ELA revision 08 uses a device, domain authenticator, and enrollment server, shifting heavier work off the constrained link while the device and authenticator still perform mutual authentication/authorization. ZK-ARCHE can use this as an interoperability/research comparator for commissioner-assisted enrollment, but the common contract should retain its infrastructure-independent rule: external enrollment information may supply verified facts, but local commissioner/admission policy remains authoritative and ordinary P2P must not require an online enrollment service.
5. **No new R-* item or status transition is justified.** R-008 already owns constrained enrollment-authority placement and scoped authorization; R-009 owns replay continuity; R-012/R-013 own authorization lineage and trust mutation. Today’s evidence refines their future conformance contract but does not justify autonomous backlog or roadmap mutation.

### D20260902-F01 — Enrollment nonce freshness must be bound to the exact authorized attempt

- **Novelty:** new/refines
- **Primary sources:** `draft-ietf-anima-constrained-voucher-30` (cBRSKI, February 27, 2026) and `draft-ietf-anima-rfc8366bis-25` (voucher artifact, February 2026)
- **Primary links:** https://datatracker.ietf.org/doc/draft-ietf-anima-constrained-voucher/ ; https://datatracker.ietf.org/doc/draft-ietf-anima-rfc8366bis/
- **Source-supported fact:** cBRSKI uses a signed pledge voucher request and a signed manufacturer voucher; the voucher is an authorization statement identifying the intended owner/Registrar and supports anti-replay. For constrained pledges without reliable time, live nonces are the common anti-replay mechanism. The voucher-artifact work explicitly treats anti-replay information as constraining an artifact to a specific onboarding attempt or validity interval.
- **Existing owner:** R-008 / R-009 / R-012 / zk211/zk212/zk230 / TD-004
- **Repository fact:** the current ZK-ARCHE enrollment classifier consumes `enrollment_nonce_unused` as an authoritative replay fact, plus independent subject-possession, commissioner, scope, audience, deployment, validity, epoch, revocation, lineage, delegation-depth, and rollback facts. The current spec explicitly says it does not yet define a grant wire encoding, signature/MAC, persistence transaction, or replay-store implementation.
- **Problem addressed:** a future implementation could correctly reject reuse of an operation ID but still fail to prove that the fresh ID belongs to the exact subject/request/grant/authority context being issued. Replay-state uniqueness and request/grant semantic binding are related but distinct.
- **Strongest distinct engineering idea:** when an ENROLL wire/grant format is eventually specified, define one canonical `enroll_attempt_context` whose digest or authenticated encoding includes at least: operation/nonce ID, subject key/commitment, commissioner/authority identifier or lineage, requested scope/authority, audience, deployment/domain, policy/revocation/lineage generation, and profile/version. Grant verification must prove that the consumed one-time replay key and the issued grant refer to the same context.
- **Evidence maturity:** standards-track work in progress + implementation-backed ZK-ARCHE decision surface
- **Limitations:** cBRSKI uses manufacturer/Registrar PKI/RPK semantics and is not a ZK-ARCHE dependency. Exact ZK-ARCHE grant encoding remains intentionally undefined. The finding does not prescribe certificates, COSE, CBOR, or a manufacturer service.
- **Likely impact:** potentially one nonce/operation identifier and canonical context bytes/hash in a future ENROLL artifact; bounded replay-state storage; no change to normal AUTH.
- **Rust/C/vector/profile impact:** add future cross-language negative vectors for correct fresh nonce + wrong subject, wrong commissioner/authority lineage, wrong audience/deployment, wrong requested scope, stale epoch/lineage, and nonce copied between two otherwise valid grant attempts.
- **Required next evidence:** specify canonical attempt-context fields; identify who generates the nonce/operation ID per profile; define replay-store key/lifetime and durable-consumption point; prove request→decision→grant correlation in Rust/C and restart/rollback tests.
- **Recommended disposition:** reproduce

### D20260902-F02 — Time-bounded validity is not a substitute for single-use replay state

- **Novelty:** corroborates/refines
- **Primary source:** `draft-ietf-anima-constrained-voucher-30`, cBRSKI
- **Primary link:** https://datatracker.ietf.org/doc/draft-ietf-anima-constrained-voucher/
- **Source-supported fact:** cBRSKI supports time-based vouchers but notes that constrained devices are unlikely to have accurate time; most constrained pledges are expected to use live nonces for anti-replay instead of expiry times.
- **Existing owner:** R-008 / R-009 / TD-002 / TD-004
- **Repository fact:** ZK-ARCHE already has separate `validity_bounded` and `enrollment_nonce_unused` inputs. This is stronger than collapsing freshness into one clock-dependent field.
- **Problem addressed:** future constrained implementations might be tempted to use a short validity interval as the only replay defense because persistent one-time state costs flash writes or requires trusted restart semantics.
- **Strongest distinct engineering idea:** preserve two independent claims: authorization validity/lifetime and attempt uniqueness. Profiles with no trustworthy wall clock may use an authenticated challenge/operation identifier plus replay persistence/high-water state, but should not relabel that as “expiry.” Profiles with trustworthy time may use both.
- **Evidence maturity:** standards-track work in progress + software decision contract
- **Limitations:** the exact nonce length, entropy requirements, persistence scheme, and trusted-time policy remain ZK-ARCHE design questions.
- **Likely impact:** replay persistence and flash/endurance costs on MCUs; possibly no additional wire bytes if an existing operation identifier can be safely bound.
- **Rust/C/vector/profile impact:** profile fixtures should distinguish `clock_validity_current` from `attempt_nonce_unused`; tests should include clock unavailable, clock rollback, fresh time + reused nonce, expired time + fresh nonce, and restart after nonce consumption.
- **Required next evidence:** per-profile trusted-time declaration; replay persistence/high-water behavior; MCU endurance measurement; exact failure precedence under time rollback versus nonce replay.

### D20260902-F03 — Enrollment authority does not automatically authorize later association or data release

- **Novelty:** corroborates/refines
- **Primary sources:** cBRSKI and NIST SP 1800-36 (final November 25, 2025)
- **Primary links:** https://datatracker.ietf.org/doc/draft-ietf-anima-constrained-voucher/ ; https://doi.org/10.6028/NIST.SP.1800-36
- **Source-supported fact:** cBRSKI uses the voucher to establish the intended domain relationship, then separately enrolls a domain identity and subsequently obtains network-access credentials. NIST SP 1800-36 emphasizes establishing trust before provisioning network credentials and continuing lifecycle/posture controls after onboarding.
- **Existing owner:** R-008 / R-012 / CORE association admission / DATA release / TD-004
- **Repository fact:** ZK-ARCHE independently classifies grant issuance (`ISSUE`), secure-association admission (`ESTABLISH`), and DATA release (`RELEASE`). Association admission requires current local trust/authorization/revocation/lineage/replay/binding state. DATA release now additionally requires current authorization generation and an unused release operation, as well as device-local release authority, protected-state and object/purpose scope.
- **Problem addressed:** implementations can accidentally treat “successfully enrolled” as a durable super-permission that bypasses later authorization freshness, revocation, association admission, or per-object release policy.
- **Strongest distinct engineering idea:** create cross-layer lifecycle vectors proving non-implication: `ISSUE`/accepted grant does not imply `ESTABLISH`; `ESTABLISH` does not imply `RELEASE`; prior `RELEASE` does not authorize another release operation/object/purpose; stale/revoked grant-derived authorization forces fresh local evaluation even if cryptographic association keys still exist.
- **Evidence maturity:** final NIST guidance + standards-track comparator + current software decision surfaces
- **Limitations:** network-layer onboarding and ZK-ARCHE’s role/private authorization model differ. This finding supports separation of authority, not adoption of NIST example technologies.
- **Likely impact:** mostly lifecycle-state/test complexity; no mandatory new wire bytes.
- **Rust/C/vector/profile impact:** add a composed deterministic decision corpus or property test over ENROLL→ASSOCIATION→DATA transitions while retaining each subsystem’s own authoritative facts and failure reasons.
- **Required next evidence:** composed Rust/C lifecycle tests; invalidation matrix for grant-derived authorization, association state, resumption, and DATA release; exact spec traceability.

### D20260902-F04 — Enrollment-server assistance should remain an optional evidence source, not common-contract authority

- **Novelty:** corroborates/refines
- **Primary source:** `draft-ietf-lake-authz-08`, *Lightweight Authorization using EDHOC (ELA)*, July 6, 2026
- **Primary link:** https://datatracker.ietf.org/doc/draft-ietf-lake-authz/
- **Source-supported fact:** ELA uses three roles: device, domain authenticator, and enrollment server. The device and authenticator mutually authenticate/authorize, while the enrollment server supplies authorization information and can move heavier work off the constrained link. The document explicitly targets low message/processing overhead on constrained links.
- **Existing owner:** R-008 / R-013 / Common Contract
- **Repository fact:** ZK-ARCHE’s roadmap requires infrastructure-independent ordinary P2P decisions and explicitly allows external infrastructure only as assistance. Current enrollment-grant issuance makes the local commissioner/authorization/revocation/lineage facts authoritative.
- **Problem addressed:** a future zero-touch integration could unintentionally turn an online enrollment service into a mandatory trust oracle for the `iot-core`/`p2p-iot-core` baseline.
- **Strongest distinct engineering idea:** if an ELA-like assisted profile is ever prototyped, normalize server-provided authorization into a locally verified bounded grant/evidence object; the constrained peer must still enforce local scope, freshness, revocation, audience/deployment, lineage, and replay rules. Preserve an offline/degraded path for already-authorized peers.
- **Evidence maturity:** active standards-track draft + architectural comparator

- **Likely impact:** optional backend dependency and possible credential/voucher bytes only for assisted profiles; no mandatory core dependency.
- **Rust/C/vector/profile impact:** any assisted profile should map to the same common decision facts and canonical grant verification, with negative tests proving service availability or transport metadata cannot override local denial.
- **Required next evidence:** explicit assisted-profile trust model, offline behavior, byte budget, server-compromise/misconfiguration tests, and mapping to existing commissioner/grant facts.

## 5. Cross-source synthesis

The repository now has the right high-level separation:

```text
explicit ENROLL request
        ↓
commissioner authority + freshness
        ↓
exact one-time attempt freshness
        ↓
subject possession + bounded grant context
        ↓
ISSUE
        ↓
local trust/authorization state mutation
        ↓
AUTH + CORE association admission
        ↓
ESTABLISH
        ↓
current object/purpose-specific local DATA authority
+ current authorization generation
+ unused release operation
        ↓
RELEASE
```

Today’s external sources sharpen two boundaries inside this flow:

1. `attempt freshness` should eventually be a cryptographically/canonically bound property of one exact enrollment context, not merely a boolean that a nonce was unused; and
2. success at one lifecycle stage must not silently authorize later stages.

The newest DATA-release v3 change independently converges on the same lifecycle discipline by separating authorization-generation freshness and one-time release replay state from authentication and local release authority.

This suggests the next useful research/reproduction artifact is a **composed lifecycle corpus** spanning ENROLL replay/substitution, association admission after grant mutation, and downstream DATA release replay/invalidation—without changing the individual owning classifiers.
