## 1. Executive synthesis

1. **`LINEAGE_REPLACE` now has strong local fail-closed decision/state semantics, but it still lacks a distributed convergence and confirmation contract.** The current Rust/C decision surface can return `REJECT_CONCURRENT`, and the logical state machine prevents two locally active successors, but no wire-neutral peer convergence rule yet states how two authenticated simultaneous attempts, lost final confirmations, reordered messages, or one-sided commit knowledge resolve. Current KUDOS and IKEv2 work show that mature lifecycle protocols explicitly model convergence/key confirmation and simultaneous rekey collisions rather than leaving them to transport behavior.
2. **A stable, integrity-valid restart record is not by itself proof that the record is the newest authorized lineage state.** The current durability classifier intentionally distinguishes structural consistency from physical rollback resistance. RFC 9124's monotonic-sequence rollback discipline provides a useful general security pattern: if an attacker can restore an older authenticated state, freshness needs a trusted monotonic/high-water anchor or the implementation must fail closed and avoid claiming rollback resistance.
3. **The next work should therefore separate two axes of lifecycle assurance:** distributed peer convergence (`proposal → confirmation → exactly one successor`) and local durable freshness (`commit → rollback-resistant high-water evidence → restart classification`). Neither substitutes for the other.
4. **No new backlog item or status change is justified.** R-009 already owns replay/rekey/restart continuity and R-012 owns lineage replacement/invalidation/revocation convergence. Today's evidence makes their next experiments more precise without changing their `reproduce` status.
5. No cryptographic primitive, suite, profile, wire format, roadmap, specification, ADR, implementation, formal model, assurance claim, debt status, or release state is changed by this report.

## 4. Findings

### D20260830-F01 — `LINEAGE_REPLACE` needs an explicit distributed convergence/key-confirmation contract

- **Novelty:** refines
- **Sources:** `draft-ietf-core-oscore-key-update-14` (KUDOS); RFC 7296 (IKEv2)
- **Primary links:** https://datatracker.ietf.org/doc/draft-ietf-core-oscore-key-update/14/ ; https://www.rfc-editor.org/rfc/rfc7296.html
- **Source type / venue:** active IETF CoRE WG Internet-Draft (work in progress) plus IETF Internet Standard
- **Publication or release dates:** KUDOS -14 — 6 July 2026; RFC 7296 — October 2014
- **Verified claim:** KUDOS explicitly models a transition in which peers derive a new OSCORE Security Context and wait for key confirmation before returning to equilibrium; while key update is active, ordinary non-KUDOS traffic is constrained, and the draft defines policies for retaining the old context only for bounded late-message handling. RFC 7296 explicitly addresses simultaneous rekey collisions and defines deterministic collision resolution so redundant new Security Associations converge to one surviving replacement rather than remaining ambiguous.
- **Existing owner:** R-009 / R-012 / TD-004 / zk213 / replay-epoch lineage specifications
- **Repository fact:** ZK-ARCHE now has a local pure decision predicate (`concurrent_free` / `REJECT_CONCURRENT`) and a local storage-neutral state machine that can activate exactly one successor only after a complete accepted plan. It does not yet define a peer-visible or wire-neutral convergence protocol for simultaneous authenticated replacement attempts, confirmation loss, reordered transition messages, or asymmetric knowledge of commit success.
- **Problem addressed:** two peers can each make locally safe decisions yet still disagree about which lineage is current when both initiate replacement, when the final confirmation is lost, or when one peer commits and the other crashes. A local `REJECT_CONCURRENT` boolean does not by itself specify distributed convergence.
- **Strongest distinct engineering idea:** define a **wire-neutral convergence contract before allocating a wire message**. The contract should bind an authenticated replacement-attempt identifier to predecessor generation/epoch, successor binding, recovery challenge, and context. It should then choose one reviewed policy for simultaneous attempts: either (a) a deterministic authenticated winner/tie-break rule, or (b) fail both attempts with `REJECT_CONCURRENT`, apply bounded randomized retry, and preserve an idempotent attempt identifier. In either case, successor AUTH usability and predecessor retirement must have an explicit confirmation/commit boundary, and two successors must never become simultaneously AUTH-usable merely for availability.
- **Evidence maturity:** externally-reviewed standards guidance + software/specification gap
- **Limitations / uncertainty:** KUDOS and IKEv2 have different trust objects and may temporarily retain old/new cryptographic contexts for protocol-specific reasons. ZK-ARCHE should not import their wire formats or temporarily accept two trust lineages. The transferable lesson is explicit convergence, confirmation, collision handling, and idempotence.
- **ZK-ARCHE inference:** the next evidence should target distributed state agreement, not add another local predicate. The current semantic state owner is a good basis, but it needs peer-to-peer attempt/confirmation semantics before a production transition can be considered specified.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** no wire change today. A future attempt identifier/confirmation may add small bounded state and bytes; collision retry policy may add timers/randomness. No new external dependency follows.
- **Rust/C / vector compatibility impact:** shared decision/state corpora should eventually include simultaneous two-successor attempts, one-sided collision detection, lost final confirmation, duplicate confirmation, reordered proposal/confirmation, crash before local durable commit, crash after commit before peer confirmation, stale predecessor retry, and eventual exactly-one-successor convergence or clean fail-closed termination.
- **Required next evidence:** one wire-neutral distributed state/convergence contract; authenticated attempt identity; explicit collision policy; idempotence rule; key/lineage-confirmation boundary; Rust/C transition corpus for loss/reordering/concurrency/crash cases; only then a wire grammar proposal.
- **Recommended disposition:** reproduce

### D20260830-F02 — rollback-safe restart needs a trusted freshness/high-water anchor separate from record integrity

- **Novelty:** refines
- **Source:** RFC 9124, *A Manifest Information Model for Firmware Updates in Internet of Things (IoT) Devices*
- **Primary link:** https://www.rfc-editor.org/rfc/rfc9124.html
- **Source type / venue:** IETF RFC / IoT firmware-update security architecture
- **Publication date:** January 2022
- **Verified claim:** RFC 9124 requires a monotonically increasing sequence number to prevent malicious rollback and requires devices to reject manifests whose sequence number is below the highest onboard sequence. The sequence is a security freshness mechanism distinct from cryptographic authenticity of the manifest.
- **Existing owner:** R-009 / R-012 / R-005 / TD-002 / TD-004 / lineage durability contract
- **Repository fact:** `spec/lineage-replace-durability-contract.md` accepts a restart observation when its logical flags are internally consistent and `record_integrity_valid` is true, but it explicitly states that this does not establish physical rollback resistance. `spec/replay-epoch-recovery.md` separately requires rollback of epoch-transition metadata to be detectable or to cause another fail-closed continuity break. No target storage adapter or trusted freshness anchor is yet defined.
- **Problem addressed:** an attacker who can restore an older, correctly authenticated snapshot may present a record whose integrity is valid and whose internal state is perfectly self-consistent. Integrity answers “was this record authorized?”; it does not answer “is this the newest authorized record?”
- **Strongest distinct engineering idea:** make **freshness provenance a separate normalized storage fact** rather than overloading `record_integrity_valid`. A future target adapter should be able to establish something equivalent to `freshness_anchor_current` from a reviewed mechanism: hardware monotonic counter/secure element, rollback-protected high-water storage, authority-sequenced lineage generation plus a rollback-resistant local high-water mark, or another target-specific primitive. If the target cannot establish freshness under the declared attacker model, restart should map to `CONTINUITY_BROKEN` and the profile must not claim malicious-rollback resistance.
- **Evidence maturity:** externally-reviewed security architecture + constrained-hardware evidence gap
- **Limitations / uncertainty:** RFC 9124 governs firmware manifests, not authentication lineage state. It is used only for the general anti-rollback principle. Some ZK-ARCHE deployment threat models may exclude arbitrary authenticated-flash snapshot restoration; those profiles can use a weaker storage contract if the exclusion is explicit and evidence-backed.
- **ZK-ARCHE inference:** the durability classifier is correctly conservative, but target qualification needs two separate questions: record integrity/atomicity and record freshness/anti-rollback. A MAC or signature over lineage state cannot by itself solve rollback if the adversary can restore an older valid snapshot.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** potentially zero wire impact for local hardware monotonicity; flash/high-water journals add persistent bytes and write endurance; secure-element counters add platform dependencies; an authority-issued generation may become a future authenticated protocol field only after explicit TD-004 review.
- **Rust/C / vector compatibility impact:** the storage-neutral classifier can remain common, but target adapters need fault/snapshot tests: restore an older stable predecessor, restore an older stable successor after a later replacement, tear every write boundary, clone state to another device where relevant, reprovision/reset the freshness anchor, and exhaust/wrap/lose the anchor. Rust/C should agree on fail-closed normalized observations even if platform mechanisms differ.
- **Required next evidence:** storage threat-model matrix distinguishing accidental interruption from malicious rollback; per-target freshness-anchor design; power-loss fault injection; authenticated old-snapshot restoration tests; write-endurance/wear measurements; clone/reprovision semantics; explicit evidence showing when `CONTINUITY_BROKEN` is required.
- **Recommended disposition:** investigate

## 5. Cross-source synthesis

The current repository has made an important step: “fresh replay epoch” is no longer a vague reset operation. It now has an explicit local authority decision, predecessor/successor lineage, plan completeness, fail-closed state machine, and restart classifier. The next assurance boundary is **distributed and durable convergence**:

```text
authenticated replacement intent
        ↓
peer collision / convergence rule
        ↓
key + lineage confirmation
        ↓
exactly one successor logically committed
        ↓
durable commit with trusted freshness/high-water evidence
        ↓
restart classification
        ↓
predecessor permanently non-applicable
```

KUDOS and IKEv2 support the first half of that discipline: explicit transition state, confirmation, simultaneous-rekey handling, and convergence. RFC 9124 supports the second half's anti-rollback principle: authenticity is not enough when old authorized state can be restored. These are complementary controls; neither peer confirmation nor a local monotonic anchor can substitute for the other.
