# ZK-ARCHE Research — 2026-08-22

## Executive synthesis

The current `dev` branch remains implementation-stable relative to the 2026-08-21 research cycle. No intervening Rust/C implementation, deterministic-vector, formal-model, roadmap, specification, or assurance changes were found. The controlling debts therefore remain TD-001 independent review of the custom role-membership proof, TD-002 constrained-target measurement, TD-003 reproducible formal evidence, and TD-004 completion of the normative specification.

Today's highest-value result is architectural rather than cryptographic: **ZK-ARCHE can recover O(1) server-side device lookup without putting a stable cleartext identity on the wire, and it can do so with standard primitives rather than inventing a new private-index protocol.** The current Rust server stores devices in a `HashMap<[u8; 32], DeviceRecord>`, but normal AUTH cannot use that O(1) index because the wire PID is derived from the enrolled public key plus fresh AUTH values. `handle_auth_1()` therefore iterates every registry record, recomputes a PID candidate, and stops on a match. That privacy-preserving scan is correct for the current design but scales O(n).

Three primary-source findings sharpen zk220 and the adjacent authorization/trust work:

1. **HPKE is a practical baseline for an optional encrypted lookup hint.** RFC 9180 explicitly supports encryption to a recipient public key and discusses encrypting identity-bearing metadata. With DHKEM(X25519, HKDF-SHA256), the encapsulated key is 32 bytes; HPKE AEADs defined by the RFC add 16 bytes beyond the plaintext. A 32-byte opaque registry key would therefore cost about 80 bytes before ZK-ARCHE extension framing. The server can decrypt the randomized hint and use the existing `HashMap` for O(1) candidate selection, but the hint must remain a non-authoritative prefilter: full PID, possession, rerandomization, role-membership, transcript, and state-machine verification still decide authentication.
2. **VOPRF/POPRF is a useful privacy comparator, not the default answer.** RFC 9497 provides ristretto255-SHA512 OPRF/VOPRF/POPRF suites, 32-byte group/scalar encodings, deterministic vectors, public-input binding in POPRF, and explicit constant-time requirements. However, ZK-ARCHE's server already owns the enrollment registry and current threat model does not require hiding the enrolled identity from that same server. Online OPRF adds another interaction and state, while a stable OPRF-derived handle remains linkable if sent unchanged. Unless a separate privacy service or stronger server-blindness threat model is introduced, HPKE or an enrollment-issued opaque handle is simpler.
3. **Authorization evidence should be holder-of-key and audience bound, not merely role-valid.** RFCs 8747, 9200, and 9201 bind constrained authorization tokens to proof-of-possession keys through `cnf`, require the authorization server to verify possession when a client requests a specific key, and require recipients to reject incompatible key/profile use. ACE also warns that symmetric PoP keys with a group audience can let one resource server impersonate the client to another. ZK-ARCHE future grants/release tokens should therefore bind scope/purpose and audience to an exact holder key or authenticated session context, and multi-recipient symmetric authorization should not become a default fleet shortcut.

No source reviewed today warrants changing the current Ristretto/HKDF/HMAC baseline, changing current AUTH wire semantics, or promoting VOPRF/HPKE into `iot-core` without measured target evidence. The actionable outcome is a bounded zk220 prototype/benchmark track plus sharper authorization negative tests.

## Findings

### 1. Use HPKE as the first concrete zk220 encrypted-lookup-hint baseline

- **Source:** RFC 9180, *Hybrid Public Key Encryption (HPKE)*
- **Primary link:** https://www.rfc-editor.org/rfc/rfc9180.html
- **Source type / venue:** IRTF CFRG Informational RFC
- **Publication date:** 2022-02
- **Verified claim:** HPKE Base mode encrypts arbitrary plaintext to a recipient public key using a KEM/KDF/AEAD construction. RFC 9180 defines DHKEM(X25519, HKDF-SHA256) with `Nenc = 32` bytes and states that the AEAD algorithms defined by the RFC produce ciphertext 16 bytes longer than the plaintext. The RFC also explicitly notes that applications may encrypt identity-bearing metadata such as a PSK identifier or sender public key with an additional HPKE layer. HPKE uses an explicit `info` input in its key schedule and application-supplied AAD for ciphertext authentication. The RFC warns that Base mode does not authenticate the sender, that bad ephemeral randomness can destroy confidentiality, and that ciphertexts do not hide plaintext length.
- **Problem addressed:** current AUTH performs O(n) privacy-preserving registry scans. Large registries therefore create predictable CPU and latency growth before proof verification, and an attacker can amplify this cost by sending many syntactically valid AUTH_1 messages. The roadmap already proposes encrypted lookup hints but does not define a standard construction.
- **Strongest distinct engineering idea:** add an optional, negotiated HPKE-encrypted opaque registry lookup key that is used only to identify a candidate record. A candidate experimental shape is:

  ```text
  lookup_plaintext = opaque_registry_key[32] || key_epoch
  info = "ZK-ARCHE lookup-hint v1" || deployment/domain || suite || profile || server-key-id
  aad = protocol-version || session_id || seq || selected-extension-set
  lookup_hint = hpke_enc || hpke_ciphertext
  ```

  The server decrypts the hint, performs an O(1) `HashMap` lookup, and then runs the unchanged cryptographic AUTH checks against that selected record. Failure to decrypt, unknown key, wrong epoch/domain/profile, or any mismatch between the selected record and the PID/proofs must fail closed. The hint is never an authentication credential.
- **Evidence maturity:** software
- **Limitations / uncertainty:** HPKE is not currently implemented in ZK-ARCHE and its X25519 suite is not byte-compatible with the existing Ristretto proof group. A separate lookup key pair introduces key lifecycle/rotation/storage work. HPKE decapsulation itself is non-trivial work and should not occur before an exposed UDP endpoint has passed any configured `AUTH_RETRY`/source-validation gate. Base mode does not authenticate the sender; that is acceptable only because the hint is a non-authoritative prefilter and the existing AUTH proof still authenticates the device. Plaintext length is visible unless fixed-length padding is defined.
- **ZK-ARCHE inference:** this is the most direct standards-based construction for zk220 because it preserves the current privacy goal against passive observers while allowing the existing server registry index to be used. It should be compared against a simpler enrollment-issued opaque handle and against the current O(n) scan before being considered for any profile. The lookup key should have an explicit epoch and rotation policy, and old-key acceptance windows must not bypass registry/policy revocation.
- **Wire / RAM / CPU / flash / dependency impact:** for X25519 HPKE and a 32-byte lookup plaintext, the cryptographic payload floor is 32-byte encapsulated key + 32-byte plaintext + 16-byte AEAD expansion = approximately 80 bytes before ZK-ARCHE extension framing and any epoch/key-id fields. Per AUTH there is one HPKE decapsulation plus normal proof verification instead of O(n) PID recomputation. Server memory remains O(n) for the existing map. MCU flash/RAM depends on the chosen HPKE implementation and whether X25519/AEAD code is already available. RNG quality becomes security-critical for client encapsulation.
- **Rust/C / vector compatibility impact:** compatible as an optional extension if current AUTH semantics remain authoritative. Required vectors should cover decrypt success + matching proof, decrypt success + wrong record, wrong server lookup key, stale key epoch, wrong domain/profile/suite/AAD, corrupted `enc`, corrupted ciphertext, duplicate/replayed hint under a fresh AUTH transcript, hint omitted, unsupported extension, and hint accepted only after configured retry/source-validation policy. Rust/C byte-level fixtures should pin `info`, AAD, encoding, and padding.
- **Recommended disposition:** prototype

### 2. Keep VOPRF/POPRF as a comparator unless the threat model requires server-blind derivation

- **Source:** RFC 9497, *Oblivious Pseudorandom Functions (OPRFs) Using Prime-Order Groups*
- **Primary link:** https://www.rfc-editor.org/rfc/rfc9497.html
- **Source type / venue:** IRTF CFRG Informational RFC
- **Publication date:** 2023-12
- **Verified claim:** RFC 9497 defines OPRF, VOPRF, and POPRF. In OPRF, the client learns the PRF output while the server learns neither the client's private input nor the output. VOPRF adds a proof that the server evaluated with the key corresponding to a known public key. POPRF additionally binds public `info` into the PRF evaluation. The RFC includes a `ristretto255-SHA512` suite, deterministic test vectors, 32-byte ristretto element and scalar encodings, application domain-separation guidance, and a requirement that secret-dependent group/proof operations run in constant time.
- **Problem addressed:** an encrypted lookup hint reveals the lookup plaintext to the authenticating server after decryption. A future threat model might want an opaque per-domain or per-epoch pseudonym derived with a server-held secret without exposing the underlying input during derivation, or might place the derivation service across a separate privacy boundary.
- **Strongest distinct engineering idea:** evaluate VOPRF/POPRF only as an alternative handle-issuance mechanism, not as mandatory per-AUTH machinery. For example, during enrollment or a controlled refresh, a device could obtain a pseudorandom handle derived from its device commitment with public input binding the deployment/domain and handle epoch. The server could pre-index the resulting handle for the current epoch. Normal AUTH would then send only the opaque handle plus existing proof material.
- **Evidence maturity:** software
- **Limitations / uncertainty:** ZK-ARCHE's authenticating server already owns the enrolled device registry, so hiding the enrolled identity from that same server during handle derivation usually does not improve the current threat model. If the handle is stable and transmitted directly, it is linkable on the wire unless additionally encrypted or rotated. If evaluated online on every AUTH, OPRF adds another round trip and temporary client state before the existing multi-message AUTH. POPRF/VOPRF adds proof-generation/verification complexity and SHA-512/hash-to-ristretto requirements beyond the current baseline. A simple random opaque handle issued during authorized enrollment may provide equivalent lookup utility with much less machinery.
- **ZK-ARCHE inference:** do not adopt VOPRF merely because it is privacy-preserving and uses ristretto255. First state the precise adversary that HPKE or an enrollment-issued random handle fails against. If no such adversary is in scope, retain VOPRF as a benchmark/reference design. If a separate lookup/privacy service is introduced later, POPRF's public input could cleanly bind deployment and epoch while VOPRF supplies verifiable evaluation.
- **Wire / RAM / CPU / flash / dependency impact:** OPRF uses at least one 32-byte blinded element from client to server and one 32-byte evaluated element back for the ristretto255 suite; VOPRF/POPRF additionally carry proof material. Online use adds a round trip and curve operations before AUTH. Enrollment-time/precomputed use shifts that cost out of the authentication fast path but requires handle-refresh storage and epoch management.
- **Rust/C / vector compatibility impact:** no current compatibility impact. Any experiment should use the RFC 9497 ristretto255 vectors as an external conformance baseline, then add ZK-ARCHE-specific domain/epoch binding fixtures. Negative tests must cover invalid elements, proof failure, wrong public input, wrong server key, stale epoch, and stable-handle linkability measurements.
- **Recommended disposition:** research-only

### 3. Bind future authorization/grant state to an exact holder key and audience

- **Sources:** RFC 8747, *Proof-of-Possession Key Semantics for CBOR Web Tokens (CWTs)*; RFC 9200, *Authentication and Authorization for Constrained Environments Using the OAuth 2.0 Framework (ACE-OAuth)*; RFC 9201, *Additional OAuth Parameters for ACE*; RFC 9203, *OSCORE Profile of ACE*
- **Primary links:** https://www.rfc-editor.org/rfc/rfc8747.html ; https://www.rfc-editor.org/rfc/rfc9200.html ; https://www.rfc-editor.org/rfc/rfc9201.html ; https://www.rfc-editor.org/rfc/rfc9203.html
- **Source type / venue:** IETF Standards-Track RFCs
- **Publication dates:** 2020-03; 2022-08; 2022-08; 2022-08
- **Verified claim:** RFC 8747 defines the CWT `cnf` confirmation claim so an issuer can bind claims to one proof-of-possession key, including by carrying a key identifier when the recipient can resolve that identifier. RFC 9200 uses proof-of-possession access tokens by default in ACE and binds authorization information to a PoP key. RFC 9201 requires an authorization server to verify possession when a client requests that an access token be bound to a particular asymmetric key or key reference, and requires rejection when key algorithm/operations are incompatible with the selected profile or PoP algorithm. RFC 9200 also warns that a symmetric PoP token for a group audience can allow one resource server holding the key to impersonate the client toward other resource servers. RFC 9203 shows an authorization update reusing an existing OSCORE key only after the AS verifies that the key identifier was previously issued to that client.
- **Problem addressed:** ZK-ARCHE currently verifies that a device is enrolled and that its hidden role is in an allowed set, but future ENROLL grants, commissioner authority, DATA release tokens, cached authorization, and multi-peer P2P policy need stronger semantics than "valid role proof". A token/grant that is not bound to the exact holder key/session and intended audience can be copied or replayed into another peer/context even when its signature/MAC is valid.
- **Strongest distinct engineering idea:** future ZK-ARCHE authorization objects should carry or resolve a single holder-key/session confirmation binding and an explicit audience, then bind scope/purpose, deployment/domain, policy/registry epoch, validity, issuer/provenance, and replay nonce/counter around that holder. Key references remain lookup aids; after resolution, the verifier must confirm the resolved key is the exact key/session expected by the authenticated context. For group/multi-peer authorization, do not use one symmetric holder key unless the threat model explicitly accepts every holder's ability to impersonate every other holder.
- **Evidence maturity:** deployed
- **Limitations / uncertainty:** ACE/CWT/OSCORE formats are not requirements for ZK-ARCHE, and importing OAuth/CBOR token machinery wholesale could violate the constrained-profile simplicity goal. The useful lesson is semantic: holder-of-key, audience, scope, and key/profile compatibility must be explicit. ZK-ARCHE can encode these semantics with its own compact grant/release format.
- **ZK-ARCHE inference:** R-008 and R-013 should require proof-of-possession binding for any signed/MACed authorization artifact, while R-012 should require invalidation of those artifacts when the bound key/session/policy epoch is revoked. DATA release material should bind recipient key or channel context in addition to purpose/policy. Commissioner grants should bind the new device's possession key commitment where known and the commissioner's authenticated authorization context.
- **Wire / RAM / CPU / flash / dependency impact:** compact key identifiers/commitments, audience, scope/purpose, epochs, validity, and nonce fields add bounded bytes and persistent authorization metadata. These fields need not require OAuth/CWT libraries. Multi-recipient asymmetric authorization may cost more signatures/encapsulations than a shared symmetric group key but avoids implicit cross-peer impersonation authority.
- **Rust/C / vector compatibility impact:** no current wire change. Future negative vectors should cover valid authorization + wrong holder key, valid holder + wrong audience, key-id mapping to the wrong key, incompatible key operation/profile, stale policy or registry epoch, copied grant across deployment/domain, symmetric group-token misuse, and authorization update attempting to bind a key not previously issued/authorized for that holder.
- **Recommended disposition:** reproduce

## Cross-source synthesis

Today's sources converge on a practical separation of concerns:

```text
lookup privacy/performance
    -> optional encrypted/opaque candidate selector
    -> never authoritative

AUTH
    -> possession + transcript + role-membership + state-machine checks
    -> remains the identity/authentication authority

authorization/grants
    -> exact holder key/session + audience + scope/purpose + epoch
    -> cannot be inferred merely from a role proof or lookup identifier
```

The current O(n) registry scan is therefore not a reason to weaken the PID design or expose stable device IDs. A standard encrypted prefilter can improve lookup asymptotics while preserving the existing verification authority. HPKE is the strongest first prototype because its cost and security boundaries are concrete and it directly supports metadata protection. VOPRF is valuable primarily when the threat model requires oblivious derivation across a distinct server/privacy boundary; otherwise it risks adding cryptographic machinery without removing a real ZK-ARCHE threat.

A second cross-source rule is that **identifier privacy and authorization correctness must stay separate**. An encrypted or OPRF-derived lookup handle can select a record, but only possession/transcript checks authenticate it; a signed/MACed role or grant can authorize action only when it is bound to the exact holder and intended audience/context.

No maturity/evidence status changed today. The findings refine prototype/negative-test targets for existing roadmap phases and add one distinct research question for zk220.
