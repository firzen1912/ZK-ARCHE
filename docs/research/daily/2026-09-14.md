## 2. Executive synthesis

1. **The new stable-v2 framing makes a privacy distinction actionable: semantic association continuity and wire-visible correlation continuity should not be the same fact.** QUIC requires fresh connection IDs across network paths to limit passive cross-path correlation, and RFC 9853 gives the same guidance for DTLS 1.3 mobility. ZK-ARCHE's statement that address changes do not implicitly change the meaning of a protocol session is security-correct, but it should not be interpreted as requiring the same 16-byte cleartext `session_id` on every path.
2. **Path validation is a reachability/anti-amplification property, not peer identity or authorization.** RFC 9853 validates a new DTLS address before updating the CID→address binding and limits application traffic until validation completes; QUIC similarly uses address validation to bound amplification. This maps cleanly to ZK-ARCHE's transport-neutral doctrine: a future datagram adapter can validate a path while CORE/LINK identity, authorization, lineage, revocation, and binding remain independently authoritative.
3. **`FULL_AUTH_REQUIRED` should begin a new authentication/privacy context, not resurrect retained session observables.** RFC 9190 explicitly treats required full handshake after a resumption attempt as a new authentication and ignores the resumption attempt; TLS 1.3 likewise allows a server to decline PSK resumption and perform a non-PSK handshake. ZK-ARCHE's new full-AUTH precedence corpus is directionally aligned, but future qualification should verify fresh session/correlation identifiers and no implicit carry-over of retained authorization/binding bytes.
4. **No backlog status transition is justified.** R-015, R-010, and R-014 remain active because the repository lacks a normative session-handle rotation/migration state machine, Rust/C cross-path correlation corpus, adapter path-validation contract, and measured spoofing/amplification behavior.
5. No wire layout, packet type, suite, profile, roadmap, ADR, technical-debt status, release posture, or hosted-CI policy changes in this report.

## 5. Findings

### D20260914-F01 — Separate semantic association identity from rotatable wire-visible correlation handles

- **Novelty:** new/refines
- **Backlog owner:** R-015
- **Sources:** RFC 9000, *QUIC: A UDP-Based Multiplexed and Secure Transport*; RFC 9853, *Return Routability Check for DTLS 1.2 and 1.3*; RFC 9146, *Connection Identifier for DTLS 1.2*; RFC 6973, *Privacy Considerations for Internet Protocols*
- **Primary links:** https://www.rfc-editor.org/rfc/rfc9000.html ; https://www.rfc-editor.org/rfc/rfc9853.html ; https://www.rfc-editor.org/rfc/rfc9146.html ; https://www.rfc-editor.org/rfc/rfc6973.html
- **Source type / venue:** IETF Standards Track RFCs and IAB privacy guidance
- **Publication dates:** RFC 9000 May 2021; RFC 9146 March 2022; RFC 9853 March 2026; RFC 6973 July 2013
- **Verified claim:** QUIC requires endpoints not to reuse the same connection ID across different local/destination addresses because stable IDs allow passive cross-path correlation. RFC 9853 gives the same privacy recommendation for DTLS 1.3 migration and notes that DTLS 1.3 can obtain fresh CIDs. RFC 9146 explicitly identifies persistent CID linkability, while RFC 6973 identifies persistent/infrequently replaced identifiers as a general correlation risk and recommends replacement/randomization where possible.
- **Existing engineering owner:** R-015 / TD-004 / `spec/wire-framing-v2.md` / `spec/privacy-considerations.md`
- **Repository fact:** v2 exposes a fixed-width 16-byte `session_id` in every packet and currently describes it as a peer-scoped protocol correlation identifier whose meaning is not implicitly changed by transport mobility. The privacy spec already marks session IDs and migration as unresolved correlation surfaces.
- **Problem addressed:** a correct transport-independent session semantic can accidentally become a cross-network tracking handle if the exact same cleartext bytes are required to persist while a peer moves across addresses, radios, gateways, or networks.
- **Strongest distinct engineering idea:** split `association_id` (internal semantic/security state) from `wire_session_handle` (bounded correlation handle). A reviewed mobility mechanism may rotate the wire handle while preserving the same authenticated association and its CORE/LINK authority. Rotation must be authenticated/state-bound and must not reset replay, authorization, revocation, lineage, usage counters, or audit continuity.
- **Evidence maturity:** externally reviewed standards; ZK-ARCHE mapping is concept/spec research
- **Limitations / uncertainty:** QUIC/DTLS CIDs have routing/record-layer semantics that ZK-ARCHE `session_id` does not automatically share. Rotation may be unnecessary in profiles where cross-path unlinkability is explicitly out of scope. A safe rotation protocol could require new state-machine/control semantics even though the 16-byte field width need not change.
- **ZK-ARCHE inference:** the current sentence “address change does not implicitly change session meaning” should remain, but future privacy/conformance work should test whether session meaning can remain stable while the visible handle changes. “same association” must not imply “same observable identifier bytes.”
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** wire width can remain 16 bytes; a rotation mechanism may require one additional control exchange/state mapping and a small bounded set of active/retiring handles. CPU cost is negligible compared with authentication; RAM cost depends on overlap window. Privacy improves only against observers that otherwise rely on the stable handle; lower-layer addresses/radio identifiers may still correlate the peer.
- **Rust/C / vector compatibility impact:** add shared vectors for fresh handle allocation, authenticated rotation, old-handle retirement, replay on retired handle, concurrent old/new overlap bound, restart behavior, and cross-path captures proving expected identifier change without authority reset.
- **Required next evidence:** define the desired privacy scope per profile; specify a transport-neutral semantic/wire-handle separation or explicitly reject it; create Rust/C deterministic state-transition vectors; measure metadata/linkability in UDP/CoAP/BLE-like adapters.
- **Recommended disposition:** reproduce

### D20260914-F02 — Path validation is reachability/anti-amplification evidence, not identity authority

- **Novelty:** refines
- **Backlog owner:** R-014 / R-010
- **Sources:** RFC 9853; RFC 9000
- **Primary links:** https://www.rfc-editor.org/rfc/rfc9853.html ; https://www.rfc-editor.org/rfc/rfc9000.html
- **Source type / venue:** IETF Standards Track RFCs
- **Publication dates:** March 2026; May 2021
- **Verified claim:** RFC 9853 validates a newly observed address before updating the DTLS CID→address binding; while validation is pending, buffered application data is stopped or bounded by an anti-amplification limit. QUIC similarly defines address validation as proof that the peer can receive at a claimed transport address and uses it primarily to control amplification. Neither mechanism turns the address itself into application identity.
- **Existing engineering owner:** R-014 / R-010 / TD-004 / transport-adapter contract
- **Repository fact:** ZK-ARCHE v2 explicitly says transport addresses are not protocol identities and adapters must not rewrite or synthesize security fields. Current retained authority separately gates protected use on authorization, revocation, lineage, replay/restart/usage continuity, and required channel binding.
- **Problem addressed:** mobility on spoofable datagram transports creates a real routing/amplification problem, but solving it by treating the new source address as identity would violate the Common Contract and create UKS/misbinding and privacy problems.
- **Strongest distinct engineering idea:** normalize a transport-adapter fact such as `path_reachability_validated` or `egress_amplification_budget_ok` that controls sending/rebinding only. CORE/LINK must continue to derive peer identity and authorization from authenticated protocol/channel state. A path-validation success cannot repair stale revocation, stale authorization generation, lost binding, rollback suspicion, or other terminal retained-authority failures.
- **Evidence maturity:** externally reviewed/deployed transport design; ZK-ARCHE mapping remains concept/prototype research
- **Limitations / uncertainty:** a transport that already has forgery-resistant authenticated connection migration may not need an extra ZK-ARCHE mechanism. Serial/BLE/CAN-like adapters have different reachability and amplification models. The Common Contract should therefore express capability/evidence rather than hard-code IP/UDP semantics.
- **ZK-ARCHE inference:** R-014's pre-auth source-validation work and post-auth mobility validation should share the principle “prove reachability before allocating/sending too much,” but they are different lifecycle points and must not share identity semantics accidentally.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** can be adapter-local and wire-neutral for transports with native validation; a ZK-ARCHE-owned datagram profile may require challenge/response bytes and transient state. No persistent trust mutation is implied.
- **Rust/C / vector compatibility impact:** future adapter/common-contract fixtures should cover new-address observed, amplification-limited pending state, validated rebinding, validation timeout, forged/raced rebinding, and combinations where path validation succeeds but CORE/LINK authority is stale/revoked.
- **Required next evidence:** map each supported transport class to native vs ZK-ARCHE-owned validation; prototype UDP-like path validation; measure amplification ratio/session-slot cost; add mixed path-validation + retained-authority precedence vectors.

### D20260914-F03 — Full-AUTH fallback after resumption starts a fresh authentication/privacy context

- **Novelty:** refines
- **Backlog owner:** R-010 / R-009 / R-015
- **Sources:** RFC 9190, *EAP-TLS 1.3*; RFC 9846, *TLS 1.3*
- **Primary links:** https://www.rfc-editor.org/rfc/rfc9190.html ; https://www.rfc-editor.org/rfc/rfc9846.html
- **Source type / venue:** IETF Standards Track RFCs
- **Publication dates:** 2022; July 2026
- **Verified claim:** RFC 9190 states that when a full handshake is required instead of resumption, negotiation proceeds as a new authentication and the resumption attempt is ignored; it also notes that ticket reuse permits passive correlation. TLS 1.3 allows a server to decline offered PSK resumption and perform a non-PSK full handshake when possible, and a new connection gets fresh cryptographic state.
- **Existing engineering owner:** R-010 / R-009 / R-015 / TD-004
- **Repository fact:** current `resumption-authorization-v5.txt` distinguishes terminal `REJECT` states from recoverable `FULL_AUTH_REQUIRED` states and gives privacy-identifier failures precedence over ordinary credential fallback. Current research already requires fresh resumed-channel evidence rather than predecessor binding bytes.
- **Problem addressed:** treating full authentication as merely “repairing” a retained session could accidentally preserve stale correlation identifiers, cached authorization, predecessor channel-binding bytes, or lifecycle assumptions that the fallback was supposed to replace.
- **Strongest distinct engineering idea:** define an explicit state boundary: `resumption evaluation -> FULL_AUTH_REQUIRED -> retire/non-authorize retained session state for admission purposes -> run fresh AUTH -> create fresh association/session observables -> re-evaluate current authorization/revocation/lineage/binding before DATA`. Historical lineage may remain auditable, but it is not current authority.
- **Evidence maturity:** externally reviewed standard; ZK-ARCHE mapping remains software/spec research
- **Limitations / uncertainty:** ZK-ARCHE is not EAP-TLS and may intentionally preserve some internal lineage metadata across full authentication. The key distinction is authority/privacy context, not mandatory deletion of all historical records.
- **ZK-ARCHE inference:** `FULL_AUTH_REQUIRED` should have deterministic postcondition tests: fresh AUTH does not inherit predecessor wire `session_id`/privacy identifier merely for convenience, predecessor binding bytes cannot satisfy current binding, and cached authorization is revalidated under current generation/revocation/lineage state.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** no new mandatory wire format implied; cost is the already-expected full AUTH. Fresh identifiers may improve privacy at negligible cost. Persistent lineage/audit storage remains separate.
- **Rust/C / vector compatibility impact:** add end-to-end paired vectors that begin with each recoverable resumption failure and continue through fresh AUTH, asserting new session/correlation identifier, fresh binding evidence, current authorization evaluation, predecessor retained-state non-authority, and equivalent Rust/C outcomes.
- **Required next evidence:** normative fallback postconditions; paired resumption→fresh-AUTH Rust/C vectors; repeated-session capture analysis; restart/rollback behavior of retired retained records.

## 6. Cross-source synthesis

The three findings support one boundary rather than three independent features:

```text
semantic authenticated association / authority
                !=
wire-visible session or connection handle
                !=
transport address / path reachability
```

A peer may remain the same authenticated peer while its route changes; a route may be proven reachable without becoming identity; and a wire correlation handle may need rotation for privacy without resetting security-critical replay/authorization/lifecycle state. Conversely, `FULL_AUTH_REQUIRED` deliberately creates a new authentication authority context and should not keep predecessor observables or cached authority merely to preserve continuity.

This separation is especially important for ZK-ARCHE because the Common Contract is transport-neutral and targets devices that may move between Wi-Fi, cellular, BLE, gateway, or other links. The standards evidence supports capability-normalized transport adapters and explicit privacy state rather than address-derived identity or permanently stable cleartext session handles.
