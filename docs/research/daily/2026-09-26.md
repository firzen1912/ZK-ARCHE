## 2. Executive synthesis

1. `draft-ietf-lake-app-profiles-05` separates an immutable application-profile object from circumstance/session information and excludes session ID, URI path, endpoint role, trust anchors, and exporter output length from the immutable profile. Exact-current ZK-ARCHE already follows this direction through immutable profile IDs plus separately authenticated session/authz/extension/channel-binding context.
2. Supported-profile advertisement is non-prescriptive and order-insensitive in the current draft, while RFC 9528 makes `SUITES_I` preference order security-significant and `SUITES_R` order insignificant. ZK-ARCHE needs explicit set-vs-preference-vs-selected semantics for every negotiation collection.
3. RFC 9528 warns that suite-error feedback can be forged. Retry/support hints may guide a later attempt, but must not delete stronger local preferences, weaken the mandatory floor, or become authorization; final selection still needs local-policy checks and authenticated binding.
4. `exporter_out_len` is prescriptive session information in the current EDHOC work but excluded from immutable profile identity. Future ZK-ARCHE exporter parameters should have one owner: profile-fixed or per-session authenticated, never ambiguous dual ownership.
5. R-001 remains `benchmark`; TD-004 remains open. No wire/profile/suite change is justified.

## 5. Findings

### D20260926-F01 — Immutable profile identity vs session state

- **Source/date/type:** `draft-ietf-lake-app-profiles-05`, 2026-07-06, IETF LAKE active Internet-Draft intended Standards Track.
- **Primary link:** https://datatracker.ietf.org/doc/html/draft-ietf-lake-app-profiles-05
- **Verified claim:** an EDHOC application profile is an established immutable description independent of concrete circumstances. Its profile object excludes `session_id`, URI path, initiator/responder role, trust anchors, and `exporter_out_len`; except for two explicit defaults, missing elements do not imply a value.
- **Bottleneck / engineering idea:** formalize three ownership classes: immutable profile contract, non-authoritative support advertisement, and per-session selected/authenticated context.
- **Evidence maturity / limits:** active standards work plus repository-spec alignment; EDHOC CBOR/registry design is a comparator, not a dependency.
- **ZK-ARCHE relevance/impact:** preserve same-ID immutability; dynamic authorization/revocation generations, routes, AUTH-instance identity, current trust state, and exporter generations should not redefine a stable profile. No current wire change; negligible runtime cost.
- **Rust/C/vector/profile impact:** same-ID fingerprint parity; negative cases for missing/extra fields, semantic drift, and session-state injection.
- **Disposition / next evidence:** benchmark/reproduce; ownership matrix, explicit absence/default rules, drift corpus, exact EDHOC-vs-ZK wire/flash comparison.
- **Roadmap impact:** zk216/217/225/226/227 evidence candidate; explicit human review only.

### D20260926-F02 — Support advertisement, preference ordering, and final selection need distinct semantics

- **Sources:** `draft-ietf-lake-app-profiles-05`; RFC 9528.
- **Primary links:** https://datatracker.ietf.org/doc/html/draft-ietf-lake-app-profiles-05 ; https://www.rfc-editor.org/rfc/rfc9528.html
- **Verified claim:** profile-support advertisement is non-prescriptive and order-insensitive in the draft. RFC 9528 uses preference-significant `SUITES_I`, verifies the first mutually supported selection, transcript-protects it, treats `SUITES_R` order as insignificant, and warns that error feedback may be forged.
- **Bottleneck / engineering idea:** type each negotiated collection as `UNORDERED_SUPPORT_SET`, `ORDERED_PREFERENCE_LIST`, or `FINAL_SELECTED_VALUE`. Retry/support information is candidate data only.
- **Evidence maturity / limits:** Standards Track RFC design plus active draft; exact EDHOC retry mechanics need not be copied.
- **ZK-ARCHE relevance/impact:** set permutations should be semantically invariant where defined as sets; preference reorderings should be policy-significant; final selection must independently satisfy local compatibility and mandatory-floor policy. Small bounded parser/RAM cost only.
- **Rust/C/vector impact:** permutation, preference-reorder, forged/stale hint, capability-strip, incompatible-profile, and no-common-floor fixtures with equal selected tuple/reject class.
- **Disposition / next evidence:** reproduce; normative selection table plus shared downgrade/order/hint corpus.
- **Roadmap impact:** zk217/225/226 candidate; explicit human review only.

### D20260926-F03 — Exporter parameters need exactly one normative owner

- **Sources/date/type:** `draft-ietf-lake-app-profiles-05` and `draft-ietf-ace-edhoc-oscore-profile-11`, both 2026-07-06 active IETF drafts intended Standards Track.
- **Primary links:** https://datatracker.ietf.org/doc/html/draft-ietf-lake-app-profiles-05 ; https://datatracker.ietf.org/doc/html/draft-ietf-ace-edhoc-oscore-profile
- **Verified claim:** EDHOC information distinguishes prescriptive session requirements from non-prescriptive support information. `exporter_out_len` is prescriptive and confirmed through authenticated EDHOC processing while excluded from the immutable profile object.
- **Repository fact / idea:** AUTH-v3 authenticates a channel-binding hash; R-010 still owns future `EXPORTER-ZK-ARCHE-v1` semantics. Each exporter input should be either profile-fixed or per-session selected/authenticated.
- **Evidence maturity / limits:** active standards work and ZK-ARCHE inference; this is not a proposal to add exporter-length negotiation.
- **Impact:** profile-fixed values cost no wire bytes; dynamic values would add bounded context/parser state but negligible crypto cost and no PKI/cloud dependency.
- **Rust/C/vector impact:** fixed values derive identically from the profile; dynamic values need mismatch, duplicate, unknown-label, cross-profile, and transcript-mutation negatives.
- **Disposition / next evidence:** reproduce; exporter ownership table plus cross-instance/cross-profile vectors.
- **Roadmap impact:** zk217/228 candidate; explicit human review only.

## 6. Cross-source synthesis

The reusable lesson is not “adopt EDHOC profiles.” It is to preserve three distinct layers: immutable profile contract; non-authoritative support/retry information; authoritative per-session selected context. The final version/suite/profile/capability/binding tuple becomes authoritative only after local policy, compatibility, and mandatory-floor checks and authenticated transcript binding. Ordering semantics must be explicit.
