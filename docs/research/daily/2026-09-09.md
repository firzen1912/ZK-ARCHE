## 1. Executive synthesis

1. **The newly normative consume-before-verify rule creates a concrete state-deletion DoS question on spoofable transports.** Current `spec/auth-terminal-flight-disposition.md` requires the receiver to remove the pending AUTH session before terminal verification. Current transport-neutral framing places the 16-byte `session_id` in the clear header and explicitly carries the same bytes unchanged over UDP, TCP, CoAP, BLE-L2CAP, or serial transports. An off-path attacker able to observe or guess a live session identifier can therefore potentially inject a forged `AUTH_3` that locates pending state and causes irreversible consumption before its Finished/context authenticator is rejected.
2. **Primary constrained-AKE guidance explicitly recognizes this failure mode.** RFC 9528 notes that a forged `message_2`, `message_3`, `message_4`, or error can trick an endpoint into sending an error and aborting an EDHOC session, and permits implementations to ignore a message likely to be forged rather than abort. RFC 9147 likewise recommends silently discarding invalid DTLS records on easily forged datagram transports to preserve the association, while TLS 1.3's stricter fatal-Finished rule exists inside a connection whose handshake records are already protected at that stage. The transferable lesson is that terminal-state destruction cannot be specified independently of pre-terminal forgery resistance.
3. **ZK-ARCHE should preserve both security goals instead of choosing one globally:** prevent unlimited corrected terminal-verification attempts against retained ephemeral state, while also preventing an unauthenticated datagram from becoming a one-packet session-kill primitive. The next evidence should therefore classify transport/source-validation conditions under which destructive terminal consumption is safe and test adversarial forged `AUTH_3` traffic against those conditions.
4. **No wire, code, spec, roadmap, debt status, profile, or maturity change is made today.** This is a human-review candidate affecting TD-004 and the existing R-015/R-009 assurance boundary. It does not justify autonomously changing the terminal-flight contract or adding hosted Actions on `dev`.

## 4. Findings

### D20260909-F01 — Consume-before-verify can create a forged-flight session-deletion DoS

- **Novelty:** new
- **Sources:** RFC 9528, *Ephemeral Diffie-Hellman Over COSE (EDHOC)*; RFC 9147, *Datagram Transport Layer Security (DTLS) Protocol Version 1.3*; RFC 9846, *The Transport Layer Security (TLS) Protocol Version 1.3*
- **Primary links:** https://www.rfc-editor.org/rfc/rfc9528.html ; https://www.rfc-editor.org/rfc/rfc9147.html ; https://www.rfc-editor.org/rfc/rfc9846.html
- **Source type / venue:** IETF Standards Track RFCs
- **Publication / release date:** RFC 9528 — March 2024; RFC 9147 — April 2022; RFC 9846 — June 2026
- **Verified claim:** RFC 9528 generally aborts and erases EDHOC state after processing failure, but its security considerations explicitly identify forged `message_2`, `message_3`, `message_4`, or error traffic as a way to trick a peer into aborting a live session. It therefore permits implementations to decide that a received message is likely forged and ignore it without sending an error or aborting. RFC 9147 similarly says invalid DTLS records should generally be silently discarded, preserving the association; it specifically warns that fatal-alert behavior on easily forged UDP is highly DoS-susceptible. RFC 9846, in contrast, requires an incorrect Finished to terminate the TLS connection and requires secrets from failed connections to be forgotten. These standards demonstrate that destructive failure behavior depends on whether the terminal input is carried inside a forgery-resistant channel/record context.
- **Existing owner:** TD-004 / R-015 / R-009 / `spec/auth-terminal-flight-disposition.md`
- **Repository fact:** exact-current ZK-ARCHE requires `remove_pending_state(session_id)` before terminal verification for a non-cached `AUTH_3`. Separately, the common wire header exposes `session_id` as 16 clear bytes in every packet and is explicitly transport-neutral, including UDP. AUTH-v3 binds `session_id` into the authenticated transcript, but that authentication is only established when terminal cryptographic verification succeeds; transcript binding does not prevent an invalid forged terminal packet from reaching lookup/destructive disposition first.
- **Problem addressed:** an availability attacker should not gain a one-packet ability to destroy another peer's in-progress AUTH state merely by supplying a visible/captured session identifier, while the receiver still needs to avoid unlimited expensive corrected attempts against one retained handshake state.
- **Strongest distinct engineering idea:** treat **terminal state destruction as a postcondition of a bounded forgery-resistance policy**, not merely of successful session lookup. For each transport/profile, define what evidence is sufficient before an invalid terminal message is allowed to consume state: e.g., an authenticated record layer, a return-routability/source-validation token bound to the AUTH instance, a bounded terminal-attempt budget coupled with timeout/rate limits, or another reviewed mechanism. A raw spoofable datagram carrying only a visible `session_id` should be explicitly tested as the hostile baseline.
- **Evidence maturity:** externally-reviewed standards plus exact-current software/spec repository evidence; ZK-ARCHE exploitability has not yet been locally reproduced
- **Limitations / uncertainty:** an off-path attacker still needs a live `session_id`; a purely random unobserved 128-bit identifier is not practically guessable. However, the field is transmitted in clear and can be observed by passive/on-path attackers, logging/relay components, or local-link adversaries. Transport adapters may provide additional anti-spoofing properties, but current common framing does not make those properties mandatory before destructive terminal disposition.
- **ZK-ARCHE inference:** build a negative harness in which a legitimate `AUTH_1`/`AUTH_2` leaves a pending session, an attacker injects an invalid `AUTH_3` using the observed correct `session_id`, and the legitimate client's valid `AUTH_3` follows. Execute this across the least-forgery-resistant supported profile (UDP-like datagram) and a forgery-resistant/authenticated transport comparator. Record whether one forged packet irreversibly kills the session and the CPU/state-amplification tradeoff of alternative bounded policies.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** no change today. A future mitigation could be wire-neutral if it uses a bounded attempt counter/rate policy, but a cryptographic return-routability token or authenticated pre-terminal wrapper could require extra wire bytes/state and versioned profile semantics. RAM impact is bounded per-session metadata; CPU impact trades one or more failed terminal checks against improved off-path DoS resistance. Trust model impact is explicit transport/source-validation classification, not elevation of address metadata to identity.
- **Rust/C / vector compatibility impact:** current positive vectors need not change. Required next evidence should add cross-language state-transition vectors for forged invalid `AUTH_3` followed by the legitimate terminal flight, repeated forged terminals, cache-hit exact duplicate behavior, and fresh `AUTH_1` retry. Any promoted mitigation must preserve Rust/C decision parity and make profile-specific behavior explicit rather than implicit in transport glue.
- **Required next evidence:** local Rust/C reproduction of the observed-session-id forged `AUTH_3` state-deletion case; attacker model for off-path/on-path/local-link adversaries; per-transport forgery-resistance classification; CPU/session-slot measurements under repeated hostile terminal traffic; reviewed bounded policy that prevents both unlimited verification retries and trivial one-packet state deletion.
- **Recommended disposition:** reproduce

### D20260909-F02 — Terminal disposition must be parameterized by forgery resistance, not transport identity

- **Novelty:** refines
- **Sources:** RFC 9147 DTLS 1.3; RFC 9846 TLS 1.3; RFC 9528 EDHOC
- **Primary links:** https://www.rfc-editor.org/rfc/rfc9147.html ; https://www.rfc-editor.org/rfc/rfc9846.html ; https://www.rfc-editor.org/rfc/rfc9528.html
- **Source type / venue:** IETF Standards Track RFCs
- **Publication / release date:** April 2022 / June 2026 / March 2024
- **Verified claim:** DTLS deliberately keeps an association alive after invalid records in ordinary datagram deployments because spoofing is easy, while TLS treats fatal handshake/Finished failures as connection-ending. EDHOC sits between these models: processing failure normally aborts state, yet its security considerations explicitly allow likely-forged traffic to be ignored to resist attacker-triggered aborts. The standards do not equate `UDP`, `TCP`, or a socket address with authenticated peer identity; rather, their failure behavior follows the protection/forgery properties of the surrounding protocol state.
- **Existing owner:** R-001 / R-015 / TD-004 / Common Contract transport boundary
- **Repository fact:** ZK-ARCHE intentionally uses identical protocol framing across heterogeneous transports and correctly states elsewhere that transport metadata is untrusted unless explicitly authenticated or channel-bound. Therefore it would be architecturally inconsistent to make terminal-destructive authority depend only on `UDP vs TCP`, peer address continuity, or connection identity.
- **Problem addressed:** prevent transport-specific exceptions from fragmenting the Common Contract or accidentally turning lower-layer addressing into authentication authority.
- **Strongest distinct engineering idea:** define a small **forgery-resistance input** beneath the Common Contract rather than a transport-name switch. Conceptually: `terminal_source_status = AUTHENTICATED_RECORD | RETURN_ROUTABLE | SPOOFABLE_OR_UNKNOWN`. The state machine can then specify bounded disposition rules against that security property. The adapter may establish the input only from authenticated/channel-bound evidence defined by its profile; address equality alone is insufficient.
- **Evidence maturity:** externally-reviewed standards guidance; ZK-ARCHE implication is architectural/specification-level
- **Limitations / uncertainty:** the exact normalized input and allowed states are not being proposed normatively here. A return-routability check is weaker than cryptographic endpoint authentication and may still be insufficient against on-path or same-network attackers. Any promoted mechanism needs a precise threat model and resource budget.
- **ZK-ARCHE inference:** keep the common security semantics independent of transport branding, but require each profile/adapter to state whether terminal packets are cryptographically authenticated, merely return-routable, or spoofable before terminal verification. Qualification should prove that an address/connection change alone neither grants authority nor changes the security class without authenticated evidence.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** potentially wire-neutral for authenticated transports; datagram profiles may need bounded cookie/token state or additional authenticated context if simple rate/attempt limits are insufficient. No new mandatory external dependency is implied.
- **Rust/C / vector compatibility impact:** add a shared abstract disposition corpus before transport-specific integration tests. The same normalized forgery-resistance input must produce identical Rust/C outcomes; adapter-specific tests then prove how each transport derives that input.
- **Required next evidence:** transport/profile matrix for UDP, TCP, CoAP, BLE-L2CAP, serial and any authenticated channel binding; proof that source-status derivation does not use unauthenticated address metadata as authority; cross-language decision vectors plus datagram attack reproduction.
- **Recommended disposition:** reproduce

## 5. Cross-source synthesis

The standards point to a security tradeoff that the new terminal-flight contract currently collapses into one rule:

```text
visible/correlatable terminal-flight handle
        +
spoofable or unauthenticated transport
        +
consume pending state before authenticator verification
        ↓
attacker-triggered live-session deletion risk
```

At the same time, simply retaining the session after every invalid terminal authenticator can expose the verifier to repeated online guesses or expensive terminal verification attempts. The correct research target is therefore not `consume` versus `retain` in isolation. It is a bounded state machine that asks **what evidence makes a destructive terminal failure attributable enough to the peer**, how many hostile attempts are tolerated, and when timeout/rate/retry policy forces a fresh AUTH instance.

TLS, DTLS, and EDHOC provide three useful comparators: TLS is aggressively terminal once protected handshake processing fails; DTLS preserves an association across invalid easily forged records; EDHOC explicitly documents forged-message abort as a DoS concern while still maintaining fail-closed session semantics after attributable processing failure. ZK-ARCHE's transport-independent Common Contract should encode the transferable security property rather than copy any one protocol's transport-specific rule.
