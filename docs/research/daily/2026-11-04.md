## 2. Executive synthesis

1. **Source-status novelty, not an algorithm change:** `draft-ietf-lake-edhoc-grease-04` is dated **2026-11-02** and reached publication-requested status **2026-11-03**. Its own -03→-04 changelog is largely name/count/reference/editorial cleanup. The substantive GREASE behavior was present in earlier revisions; do not label it newly invented on November 2.
2. LAKE's successful-path use of *non-critical* ignorable EAD and *unselectable* advertised cipher suites reinforces ZK-ARCHE's separation of normal unknown-value tolerance from **security-critical negative tests**. LAKE's numeric GREASE allocations are **not** ZK-ARCHE allocations.
3. The **2026-11-02 IAB greasing -02** guidance directly warns that special-casing known GREASE values can mask failure on other unknown values. This sharpens an executable Rust/C conformance *oracle*, not a rationale for deploying random live GREASE on resource-limited IoT nodes.
4. **Independent local digest reproduction:** `SHA256(0000) = 96a296d224f285c67bee93c30f8a309157f0daa35dc5b87e410b78630a09cfc7`, whereas `SHA256(5a4b43545801020000) = ef8116870a7dc594749827eae3c9a5346057612b0d93ed3d1f0cea3d6ff0f3ed`. Both repository draft specifications claim to define the same AUTH-v3 `critical_extensions_hash`. GREASE guidance cannot select between them; **human normative resolution remains mandatory before v3 promotion**.
5. LAKE PQ suites -02 separately maintains the method/suite compatibility gate and exact key-exchange placement. This is a **cross-reference** for optional R-003 only. No new PQ suite, wire format, registry allocation, or implementation requirement is adopted.

### D20261104-F01 — GREASE success-path behavior and selection are independent

- **Novelty:** refines; -04 updates primary-source baseline and IESG submission status, but its stated -03→-04 changes are editorial/terminological rather than a new GREASE rule.
- **Backlog owner:** R-011.
- **Source:** *Applying Generate Random Extensions And Sustain Extensibility (GREASE) to LAKE Extensibility*, `draft-ietf-lake-edhoc-grease-04`.
- **Primary link:** https://datatracker.ietf.org/doc/draft-ietf-lake-edhoc-grease/04/ and prior https://datatracker.ietf.org/doc/html/draft-ietf-lake-edhoc-grease-03
- **Source type / date:** LAKE WG Informational Internet-Draft, **2026-11-02**; submission to IESG/publication requested **2026-11-03**; **not an RFC**.
- **Verified source-supported claim:** LAKE reserves noncritical EAD labels `160,41120,43690,44975` and unusable GREASE cipher suites `160,41120,-41121,43690`. Unknown noncritical EAD is handled as ordinary unknown noncritical EAD; a GREASE suite is allowed in an offer but not selected. Unknown critical EAD and a selected GREASE suite are outside successful-path greasing and belong to negative conformance. Optional live GREASE must account for fragmentation, deployment overhead and fingerprinting.
- **Engineering owner / repository anchor:** `spec/registries.md` §§4,9,10; `spec/implementation-requirements.md`; R-011 / TD-004.
- **Problem:** Interoperability tests can falsely pass when implementations recognize only special test values or accidentally accept forbidden selected parameters as though they were ignorable.
- **Distinct idea:** Define a *two-lane oracle*: (A) successful path, legal unassigned **ignorable** point, use ordinary-unknown and reserved-GREASE values interchangeably without affecting selected security context, including non-GREASE adjacent values; (B) negative path, unsupported selected suite, unknown critical, known incompatible, duplicates, noncanonical contexts and profile-forbidden values must reject before authenticated completion. Encode per-point eligibility; prohibit cross-namespace reuse of LAKE numeric allocations.
- **Evidence maturity:** **concept** for ZK-ARCHE; standards-WG draft for comparator.
- **Limitations:** LAKE EAD and COSE cipher-suite encoding are not ZK-ARCHE HELLO TLVs or v3 extension IDs. No live GREASE or conformance execution was performed; no proof the source improves ZK-ARCHE on-wire interoperability.
- **ZK-ARCHE inference:** Continue deterministic local reserved-value testing, with human-gated resource/privacy analysis before any randomized live GREASE; don't let GREASE bypass selected-profile/security validation.
- **Wire/CPU/RAM/flash/dependency/trust/privacy:** Current wire and trust unchanged; test corpus adds only fixture/storage cost. Optional live GREASE would add wire bytes, RNG/CPU, packet and possibly fragmentation/energy costs; privacy may improve or degrade depending on behavioral fingerprint, not measured. No mandatory dependencies.
- **Rust/C/vector/profile impact:** Shared Rust/C expected accept/reject decisions for each extension point, profile, ordering/duplicate/known-invalid/ordinary-unknown/reserved-unknown case; no production vector change, no suite/profile enablement.
- **Next evidence / disposition:** local exact-head fixture and negative-corpus execution in both lanes plus maximum-frame and observer-cost measurements before human live-GREASE review. **reproduce**.
- **Weekly candidate:** yes.

### D20261104-F02 — Grease is not an alternative canonical-hash authority

- **Novelty:** refines / corroborates; new IAB -02 revision and independently reproduced repository contradiction.
- **Backlog owner:** R-011; R-015 privacy cross-reference with no status change.
- **Source / type / date:** IAB-stream *Considerations For Maintaining Protocols Using Grease and Variability*, `draft-iab-protocol-greasing-02`, **2026-11-02**, active Internet-Draft without RFC or formal IETF endorsement; RFC 9170 (2021) and RFC 8701 (2020) earlier comparators.
- **Primary links:** https://datatracker.ietf.org/doc/html/draft-iab-protocol-greasing-02 ; https://www.rfc-editor.org/rfc/rfc9170.html ; https://www.rfc-editor.org/rfc/rfc8701.html
- **Verified source-supported claim:** Explicit reserved values need no special-case bypass; testing only GREASE values cannot establish correct general unknown-value handling. Variation or failure-triggered retry has costs and can create behavior/fingerprinting patterns. GREASE values should not become allocated semantics.
- **Engineering owner / repository anchor:** R-011; `spec/registries.md`, `spec/critical-extension-set-encoding.md`, `spec/auth-v3-context-encoding.md`, `rust/test-vectors/auth-v3/context-encoding-v1.json`; TD-004.
- **Problem:** A receiver can obey ignorable-extension GREASE handling while disagreeing on what security-critical context was authenticated; in ZK-ARCHE two draft specifications prescribe different empty-set bytes for the very same `critical_extensions_hash`.
- **Distinct idea / independent reproduction:** Direct canonical empty set: `0000` (2 B), SHA-256 `96a296d224f285c67bee93c30f8a309157f0daa35dc5b87e410b78630a09cfc7`; ZKCTX critical empty: `5a4b43545801020000` (9 B), SHA-256 `ef8116870a7dc594749827eae3c9a5346057612b0d93ed3d1f0cea3d6ff0f3ed`. Independently recomputed using SHA-256 this run (not new discovery; contradiction first recorded October 25). Both produce a 32-byte field, so discrepancy is transcript interoperability, **not a 7-byte field-size increase**. Build a three-axis acceptance oracle: extension semantic validity, canonical byte construction (after *human* authority decision), and AUTH-v3 Finished/key-confirmation validity. Include positive reordered-but-equivalent selected sets and negative selected-set/hash mutations.
- **Evidence maturity:** **software** for independent empty-digest calculation; **concept** for ZK-ARCHE cryptographic implementation/assurance, no live interop.
- **Limitations:** A digest match doesn't establish selection correctness or equivalent parser/Finished acceptance. External greasing guidance does not resolve which ZK-ARCHE draft specification has normative priority.
- **ZK-ARCHE inference:** Human resolution of the direct-vs-ZKCTX contradiction is required before adding any more GREASE-dependent v3 transcript promotion claims; don't infer that ignored noncritical advertisements change the authenticated selected critical set.
- **Wire/CPU/RAM/flash/dependency/trust/privacy:** Existing wire field is 32 bytes in either encoding. Potential canonicalization scratch/CPU difference and suite/profile migration implications are unmeasured; no dependency or trust change, no privacy gain established.
- **Rust/C/vector/profile compatibility:** Current deterministic ZKCTX fixtures align with one draft but do not resolve competing normative text. Human-selected authority, strict parse/reject-alternative vectors, full paired Rust/C TH-v3/Finished traces, and version/profile migration decision required.
- **Next evidence / disposition:** exact head Rust/C positive/negative independent implementation and Finished test; retain both raw canonical bytes/hashes, unknown handling matrix, no silent override of one draft. **reproduce**, explicit human decision.
- **Weekly candidate:** yes.

### D20261104-F03 — PQ suite revision makes method compatibility an independent gate (cross-reference)

- **Novelty:** refines; updated authoritative version, not a demonstrated cryptographic algorithm change.
- **Backlog owner:** R-003 (cross-reference only; priority P3 and `benchmark` status unchanged).
- **Source / type / date:** LAKE WG Standards Track candidate, *Quantum-Resistant Cipher Suites for LAKE*, `draft-ietf-lake-pqsuites-02`, **2026-11-02**; compares `-01` (**2026-09-19**) and RFC 9528 (**2024-03**).
- **Primary links:** https://datatracker.ietf.org/doc/html/draft-ietf-lake-pqsuites-02 ; https://datatracker.ietf.org/doc/html/draft-ietf-lake-pqsuites-01 ; https://www.rfc-editor.org/rfc/rfc9528.html
- **Verified claim:** Proposed ML-KEM suites have `Supports DH/NIKE = No`; Methods 1–3 require DH/NIKE while signature Method 0 and proposed PSK Method 4 do not. KEM public encapsulation key travels in `G_X` of message_1; ciphertext travels in `G_Y` of message_2. Ciphertext lengths are 768 bytes for ML-KEM-512 and 1568 bytes for ML-KEM-1024. The draft additionally clarifies proposed LAKE registry naming and is **not final IANA allocation**; `TBD` suite identifiers are not assigned IDs. A broad sentence about methods 0–3 must be read with its explicit Method 0/1–3 compatibility table, rather than interpreted to reject signature-only Method 0.
- **Engineering owner / repository anchor:** R-003; `spec/registries.md` §4 (future suite must state key-agreement/method compatibility), `spec/iot-profiles.md` and the nonselectable `iot-core-v1.profile`; TD-002/TD-004.
- **Problem / distinct idea:** A recognized algorithm/suite number is not evidence that a particular method, profile, direction, or cryptographic processing state can run it. Test **known-but-incompatible** independently of **unknown** and **malformed**, with explicit KEM role/key input and failure class; inspect MTU, keygen and side-channel costs separately.
- **Evidence maturity / limitations:** **concept** for ZK-ARCHE; primary IETF draft only. LAKE flow does not define ZK-ARCHE proof or packet layout and cannot be transplanted as an implemented suite.
- **ZK-ARCHE inference:** Keep PQ hybrid optional and unselected; no quantum-resistance claim until complete protocol/key-usage/role-proof/authentication analysis and physical measurements.
- **Wire/CPU/RAM/flash/dependencies/trust/privacy:** 768/1568 bytes are *KEM ciphertext alone*, before LAKE/ZK-ARCHE framing/authentication/padding. These are lower bounds, not measured full flights; plausible large wire, fragmentation, CPU/RAM/flash/entropy costs. No trust or privacy benefit established from changing KEM alone. Core current wire unchanged.
- **Rust/C/vector/profile impact / next evidence:** pinned draft/version/method/suite/profile matrix, correct known-incompatible rejection in both languages, independent keygen/decap failure and fresh-ephemeral tests, full message/MTU/flash/RAM/CPU/energy measurement for any explicitly proposed optional PQ profile. No live test or vector update today; disposition **benchmark (unchanged)**.

## 6. Cross-source synthesis

The new 2026-11-02 LAKE GREASE and IAB guidance reinforce a **three-way** separation: syntactically well-formed unknown ignorable values, forbidden selected/critical semantics, and cryptographically authenticated canonical bytes. ZK-ARCHE already specifies much of the rule; the outstanding hard blocker is not discovering a GREASE constant but proving one authoritative critical-extension representation with both implementations. New LAKE PQ revision similarly distinguishes recognized from compatible cryptographic selections. Treat all external LAKE/IAB draft language as engineering comparators, not automatic ZK-ARCHE requirements.
