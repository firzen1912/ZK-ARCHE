## 1. Executive synthesis

1. **A stable `profile_id` should identify an immutable protocol/security contract, while per-session selected values remain separate authenticated context.** The current EDHOC Application Profiles draft (-05, July 6, 2026, in WG Last Call) explicitly distinguishes an established immutable profile definition from circumstance-specific information and treats prescriptive parameters as fail-closed requirements. This materially refines R-001 now that ZK-ARCHE has concrete draft profile IDs.
2. **The new contiguous high-value “anti-ossification fixture” ranges are useful for deterministic negative tests, but they are not equivalent to live GREASE.** RFC 8701 deliberately uses sparse GREASE values so implementations cannot simply special-case one contiguous range; GREASE values are advertised as unknown but must never be negotiated/selected. ZK-ARCHE should preserve its current ranges as deterministic unknown/reserved fixtures unless a separately specified live-GREASE scheme is introduced. This refines R-011 without requiring a wire change today.
3. **AUTH-v3 currently authenticates three digests whose underlying encodings are still undefined: authorization context, critical extensions, and channel binding.** RFC 8949 and RFC 9052 show why deterministic encoding, unique labels, duplicate rejection, and explicit critical-parameter processing matter. The current ProVerif v3 model abstracts canonical hashing and concrete bytes, so its TRUE results do not cover parser/canonicalization ambiguity. This refines R-004/R-011 and TD-004.
4. **The current registry vocabulary is directionally consistent with RFC 8126’s distinction among Reserved, Experimental, Private Use, and Unassigned.** No new registry category is required from today’s research; the main work is tightening semantics and tests around profile stability, unknown-value fixtures, and canonical hashed contexts.
5. No mandatory-suite change, production AUTH-v3 enablement, roadmap/ADR/spec mutation, debt clearing, maturity claim, or release-status change is justified by this report.

### D20260827-F01 — Profile IDs should name immutable security contracts; selected session context must not redefine them

- **Novelty:** refines
- **Source:** `draft-ietf-lake-app-profiles-05`, *Coordinating the Use of Application Profiles for Ephemeral Diffie-Hellman Over COSE (EDHOC)*
- **Primary link:** https://datatracker.ietf.org/doc/draft-ietf-lake-app-profiles/
- **Source type / venue:** active LAKE Working Group Internet-Draft, intended Proposed Standard; in WG Last Call at inspection time
- **Publication or release date:** July 6, 2026 (-05)
- **Verified claim:** the draft defines an `EDHOC_Application_Profile` as a canonical representation of an established, immutable set of information describing how EDHOC can be run, independent of the concrete circumstance. It separately distinguishes prescriptive parameters, which participants must follow and whose violation causes abort, from non-prescriptive information such as supported options.
- **Existing owner:** R-001 / TD-004 / `spec/registries.md` Profile Registry / AUTH-v3 promotion gate
- **Repository fact:** ZK-ARCHE now has draft numeric profile IDs (`iot-core`, `iot-edge`, `p2p-iot-core`) and separately authenticates `selected_capabilities`, authorization-context hash, critical-extension hash, and channel-binding hash in AUTH v3. The registry currently states that a profile promotion must define mandatory versions/suites, mandatory/forbidden capabilities, allowed/required critical extensions, resource evidence, replay behavior, authorization schema, channel-binding policy, and transport assumptions.
- **Problem addressed:** once a profile ID is stable, silently changing the meaning of that same ID can create cross-version/cross-build ambiguity even when the transcript correctly authenticates the numeric ID. Two peers could agree on the same `profile_id` while holding different local definitions of its prescriptive semantics.
- **Strongest distinct engineering idea:** treat a promoted profile ID as an **immutable semantic contract**. Per-session negotiated/selected values remain separate authenticated fields, but they must be validated against that immutable profile definition. A material change to prescriptive profile semantics should require a new profile allocation or an explicit versioned replacement/deprecation path, not in-place reinterpretation of the same stable ID.
- **Evidence maturity:** concept
- **Limitations / uncertainty:** the EDHOC application-profile draft is work in progress and does not dictate ZK-ARCHE’s encoding or trust model. ZK-ARCHE’s profile composition differs and may intentionally bind more context per session.
- **ZK-ARCHE inference:** before `profile_id=0x0001` or another profile becomes stable, retain a machine-readable or otherwise deterministic profile-definition fingerprint/manifest and Rust/C conformance fixtures proving that the same ID maps to the same prescriptive version/suite/capability/extension/replay/channel/authz rules across implementations and releases. Unknown or incompatible profile semantics must fail closed.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** no additional mandatory wire bytes are implied if the profile ID remains the wire selector; the cost is specification/versioning discipline and small conformance metadata. A definition fingerprint could remain test/evidence metadata rather than a wire field unless later review requires otherwise.
- **Rust/C / vector compatibility impact:** positive/negative negotiation vectors should cover same-ID semantic parity, incompatible-known profile combinations, and profile deprecation/replacement. Existing draft primitive vectors need not change solely for this research conclusion.
- **Required next evidence:** immutable profile-definition contract; prescriptive vs non-prescriptive parameter classification for each draft profile; same-ID Rust/C semantic-parity fixtures; version/replacement/deprecation rule; negative tests for known-but-incompatible profile use.
- **Recommended disposition:** reproduce
- **Weekly finding candidate:** yes

### D20260827-F02 — Deterministic unknown-value fixture ranges and live GREASE require different semantics

- **Novelty:** refines
- **Source:** RFC 8701, *Applying Generate Random Extensions And Sustain Extensibility (GREASE) to TLS Extensibility*
- **Primary link:** https://www.rfc-editor.org/rfc/rfc8701.html
- **Source type / venue:** IETF Informational RFC
- **Publication or release date:** January 2020
- **Verified claim:** RFC 8701 reserves **sparse** values specifically to discourage implementations from conditioning on one recognizable range. GREASE values may be advertised to exercise unknown-value handling, must be treated like unknown values, and must never be selected/negotiated. The RFC also requires protocol-valid advertisements, including no duplicate extension types, and recommends balancing randomized diversity with deterministic placement long enough to expose failures reliably.
- **Existing owner:** R-011 / TD-004 / `spec/registries.md`
- **Repository fact:** ZK-ARCHE now reserves contiguous high regions such as protocol versions `0xF0–0xFE`, suites `0xF000–0xFEFF`, and critical-extension base IDs `0x7800–0x7FFF` for deterministic unknown/anti-ossification fixtures. The registry also correctly says such values must remain unassigned and draft/unknown values must not silently become selectable production semantics.
- **Problem addressed:** a contiguous “special test range” is easy for an implementation to recognize and special-case. It is useful for deterministic negative vectors, but if used as the only live anti-ossification mechanism it can fail to exercise generic unknown-value handling across the real registry space.
- **Strongest distinct engineering idea:** maintain **two distinct concepts**: (1) deterministic reserved fixture ranges for repeatable Rust/C conformance and parser tests; and (2) only if future deployments need live GREASE, a separately reviewed sparse set/pattern of unassigned values distributed through each relevant registry, advertised as ordinary unknown optional values and never allowed into the selected security context. Live GREASE must not use critical extensions whose correct behavior is fail-closed.
- **Evidence maturity:** externally-reviewed
- **Limitations / uncertainty:** live GREASE may add fingerprinting or packet-size variability and may be unnecessary for small closed deployments. ZK-ARCHE can gain substantial value from deterministic unknown-value tests without ever sending GREASE on production networks.
- **ZK-ARCHE inference:** do not rename or reinterpret the current contiguous fixture ranges as live GREASE semantics. First build the deterministic unknown/incompatible corpus. If ossification becomes a deployment concern, define sparse live-GREASE allocations/advertisement rules separately, ensure they are excluded from `selected_capabilities` and authenticated critical-extension selection, and measure privacy/MTU impact.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** deterministic fixtures have zero production cost. Live GREASE would add small optional wire variability and test logic but no new trust authority or cryptographic primitive.
- **Rust/C / vector compatibility impact:** current ranges are suitable for deterministic negative vectors. Future live-GREASE fixtures should verify both lanes ignore/continue for legal unknown optional advertisements, reject if a GREASE value is selected, reject duplicates where prohibited, and never authenticate a GREASE value as an active security feature.
- **Required next evidence:** explicit deterministic-fixture-vs-live-GREASE distinction; unknown/selected/incompatible Rust/C corpus; sparse allocation strategy only if live GREASE is proposed; privacy/MTU/fingerprinting analysis for live use.
- **Recommended disposition:** reproduce

### D20260827-F03 — AUTH-v3 hashed subcontexts need one strict canonicalization and duplicate/criticality contract before formal/runtime claims converge

- **Novelty:** refines
- **Sources:** RFC 8949, *Concise Binary Object Representation (CBOR)*; RFC 9052, *CBOR Object Signing and Encryption (COSE): Structures and Process*
- **Primary links:** https://www.rfc-editor.org/rfc/rfc8949.html ; https://www.rfc-editor.org/rfc/rfc9052.html
- **Source type / venue:** IETF Internet Standards / Standards Track cryptographic encoding guidance
- **Publication or release dates:** RFC 8949 — December 2020; RFC 9052 — August 2022
- **Verified claim:** RFC 8949 defines deterministic encoding rules such as definite lengths and deterministic map-key ordering and warns that duplicate map keys can be handled inconsistently by decoders. RFC 9052 requires labels in each header map to be unique and malformed duplicates to be rejected; its `crit` mechanism requires designated protected parameters to be understood and treats inconsistent critical declarations as fatal. COSE also illustrates an alternative design: authenticate an exact protected serialized byte string, avoiding re-encoding ambiguity for the protected data itself.
- **Existing owner:** R-004 / R-011 / TD-004; secondary relevance R-008/R-010
- **Repository fact:** AUTH v3 binds `authz_context_hash`, `critical_extensions_hash`, and `channel_binding_hash`, but the normative byte encodings and canonical empty representations are intentionally unfinished. The critical-extension registry allows multiplicity only when an extension specification explicitly defines it and requires selected critical values to feed `critical_extensions_hash`. The draft-v3 ProVerif model explicitly abstracts canonical hashing and concrete byte encoding, representing these subcontexts as symbolic bitstrings.
- **Problem addressed:** if Rust and C can parse or canonicalize the same logical context differently—or accept duplicate/alternate encodings differently—the peers can disagree on semantic validity even when the final hash function and transcript code are byte-identical. Formal correspondence over an abstract `bitstring` does not detect parser ambiguity, duplicate collapse, last-one-wins behavior, alternate integer widths, or inconsistent empty-context encoding.
- **Strongest distinct engineering idea:** define one **strict parse → validate → canonical encode → hash** contract for each hashed subcontext. The specification should choose exact type/length/order rules, unique identifiers/keys, allowed multiplicity, duplicate rejection, deterministic empty encoding, and treatment of unknown critical/non-critical values. If a future subcontext instead authenticates exact protected raw bytes, specify that explicitly and do not mix raw-byte and normalized-semantic hashing across implementations.
- **Evidence maturity:** externally-reviewed
- **Limitations / uncertainty:** CBOR/COSE are engineering references, not mandatory dependencies. ZK-ARCHE can retain its existing TLV/custom encoding if it defines equally strict deterministic rules. Switching encodings solely for familiarity would create unnecessary wire/parser churn.
- **ZK-ARCHE inference:** before production v3, add a cross-language canonicalization corpus containing at least: duplicate extension IDs/keys; forbidden multiplicity; legal multiplicity with defined order; alternate integer-width encodings if the chosen format permits them; reordered map/sequence inputs; unknown critical extension; unknown ignorable extension; critical marker referring to missing value; non-canonical empty set/context; and two syntactically different encodings that claim the same semantics. Rust and C must agree on reject/normalize/hash decisions. The formal-model contract should state canonicalization as an external assumption until parser semantics are modeled or proved separately.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** strict canonicalization can be implemented with bounded streaming encoders for constrained profiles. CBOR is not required. Duplicate detection may need a bounded seen-ID set or sorted-order enforcement; exact overhead depends on the final context schema.
- **Rust/C / vector compatibility impact:** this directly requires canonical positive vectors and negative/differential parser vectors. The current AUTH-v3 primitive vector remains useful for the outer transcript but does not clear this subcontext gap because it injects precomputed 32-byte hashes.
- **Required next evidence:** normative canonical encodings and empty representations for all three subcontexts; duplicate/multiplicity rules; Rust/C canonicalization/differential corpus; parser fuzz seeds; formal assumption manifest linking symbolic context terms to exact byte-level constructors.
- **Recommended disposition:** reproduce

## 5. Cross-source synthesis

Today’s sources converge on one specification principle: **a numeric identifier or transcript hash is only as stable as the semantics and encoding underneath it**.

```text
profile ID
   → immutable prescriptive profile definition
   → per-session selections validated against that definition

unknown-value fixture
   → deterministic parser/conformance stress
   ≠ live GREASE unless sparse/ordinary-unknown/non-selectable behavior is specified

AUTH-v3 subcontext hash
   → strict parser acceptance rules
   → unique/multiplicity semantics
   → one canonical byte representation
   → hash
   → transcript binding
```

RFC 8126 also corroborates the repository’s existing category separation: Reserved values are unavailable for assignment, Experimental values are for experimentation, Private Use is deployment-local, and Unassigned remains available through the defined allocation procedure. The new registry document already captures those distinctions closely enough that no new R-* question is needed.

The important gap now sits at the boundary between specification and executable conformance. AUTH-v3’s cryptographic outer binding has useful scoped evidence, but profile-definition stability and subcontext canonicalization need deterministic Rust/C rejection/hash parity before that evidence can support a production Common Contract claim.
