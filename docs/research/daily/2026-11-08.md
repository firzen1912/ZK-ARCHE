## 2. Executive synthesis

1. **New November draft comparator:** Key Transparency architecture -11 (2026-11-01) and protocol -06 (2026-11-02) describe authenticated key-to-label history, monitoring/consistency, portable offline-verifiable responses and fork detection. Crucially, **a single internally valid log proof does not establish that all peers saw the same history**. Security depends on retained consistency state and monitoring assumptions; state loss weakens detection. This sharpens R-013's two-authority/torn-commit negative oracle, but does not justify a central log or external trust.
2. The same draft explicitly requires a freshness policy for offline-presented credentials; the application-defined recent-log criterion **does not replace** ZK-ARCHE's locally authoritative credential, authorization-generation, revocation and replay decisions. A log's identity/key statement is never an ENROLL grant, AUTH admission or DATA authorization in ZK-ARCHE.
3. **New JOSE WG draft status:** `draft-ietf-jose-jwp-modular-bbs-00` (2026-11-02) describes Blind-BBS-based core presentation and modular predicates/holder binding in JWP. It **does not specify concrete sub-proof or device-binding constructions**. It requires nonce/audience freshness, warns that lacking holder binding makes the issued form transferable, and uses fixed layouts/decoys to limit structural correlation.
4. Neither draft was executed against ZK-ARCHE. No Rust/C/fuzz/formal/MCU or cross-implementation result is claimed. R-013 stays `reproduce` and optional R-002 stays `researching`; no normative protocol choice or additional queue item is justified.

## 5. Findings

### D20261108-F01 — Split-view history and lost consistency state require an independent trust-attribution oracle

- **Novelty / backlog:** `refines` R-013; R-012 (freshness) is a cross-reference only.
- **Primary sources / dates / types:** IETF KEYTRANS WG, *Key Transparency Architecture*, `draft-ietf-keytrans-architecture-11`, **2026-11-01**, Informational Internet-Draft: https://datatracker.ietf.org/doc/html/draft-ietf-keytrans-architecture-11 ; *Key Transparency Protocol*, `draft-ietf-keytrans-protocol-06`, **2026-11-02**, Standards Track Internet-Draft: https://datatracker.ietf.org/doc/draft-ietf-keytrans-protocol/06/ .
- **Source-supported facts:** Search/Update/Monitor and per-client consistency are distinct. A log can present different individually verifiable views; peers must compare/monitor histories to detect forks. Offline credential carriers can serialize authenticated lookup responses, but their verifier must apply an explicit recent-distinguished-entry policy. Client state loss reduces detection of historical forks, and draft security depends on local configuration, state and clock assumptions (architecture ``3.2–3.3, 7.2–7.3). These are draft KEYTRANS assumptions, *not* guarantees or requirements for ZK-ARCHE.
- **Existing owner / repository anchors:** R-013 / R-012, TD-004, roadmap zk211/zk212/zk214/zk239; `spec/enroll-lifecycle-state-machine.md`, `spec/authorization-generation-lifecycle.md`, `spec/lifecycle-persistence-freshness.md`; `rust/crates/proto/src/auth_v3_iot_core_authz.rs` and corresponding C resolver.
- **Bottleneck:** A single valid signature or lookup response can be internally consistent while another authorized party received a divergent identity→key binding. Durable recovery that loses an earlier accepted view can silently re-accept a conflicting mapping. Neither local alias resolution nor a log signature should promote new trust by normal AUTH.
- **Distinct idea / proposed executable oracle:** Create two separately scoped authority domains A/B with the same opaque label but different authorized key/role/policy tuples. Feed each side a valid yet mutually inconsistent signed mapping/view, then reorder, duplicate, expire, cross-attribute and roll back one view. Compare four cuts: before authorized ENROLL commit, interrupted alias/identity/persistence commit, completed durable commit, and postcommit cleanup. After simulated state loss, require explicit locally authorized recovery/currentness before any candidate view can affect trust. An optional *consistency-receipt* comparator may be tested offline, but a missing receipt or monitoring outage **must not be reinterpreted as authority to enroll**; the exact local policy for any optional transparency feature needs human review.
- **Evidence maturity:** External **concept** (WG drafts); existing ZK-ARCHE *software* attribution decision paths are read-only context, not today’s reproduced fork defense.
- **Limitations:** KEYTRANS normally assumes a service/log, monitoring, local clocks and possibly third parties; offline credentials may become stale, log operators may withhold evidence, and complete fork detection has deployment assumptions. None of that is a certificate-less decentralized ZK-ARCHE implementation or a demonstrated local vulnerability.
- **ZK-ARCHE inference:** Treat authority-qualified mapping, historical consistency, current authorization, revocation, replay and ENROLL commitment as different predicates. Preserve mandatory disconnected P2P operations between already-authorized peers without DNS/CA/log/cloud dependencies; optional transparency must not acquire root trust.
- **Wire / CPU / RAM / flash / dependency / trust / privacy:** **No mandatory change.** If later explicitly approved, proof/history receipts add wire, validation CPU, retained monotonic state/flash and possible monitoring/network dependencies; exact sizes are unspecified/unmeasured. Labels, log access and monitor cadence may expose device population/activity; comparison must consider privacy and constrained storage cost.
- **Rust/C/vectors/profiles:** Add future *offline fixture* of contradictory signed/mapped records, restored-current versus rolled-back view, and wrong-authority alias under identical identifiers; require identical Rust/C decision codes, deny unauthorized new AUTH/ENROLL/DATA effects, and preserve legitimate pre-invalidation results. No existing vector, protocol profile or implementation is changed.
- **Required next evidence / disposition:** Pin small mock view/receipt data with explicit authority signatures and authenticated epoch provenance, execute exact-HEAD paired Rust/C consistency + state-loss decision corpus, measure persistent writes and bounded cache usage; **reproduce**. Weekly finding: **yes**.

### D20261108-F02 — Modular BBS/JWP specifies serialization, not a complete deployable device-bound credential

- **Novelty / backlog:** Newly **JOSE WG** draft `-00` published 2026-11-02, refining R-002's older individual-draft comparison; R-015 privacy cross-reference, no core-profile priority change.
- **Primary source / date / type:** *BBS and Modular Sub-proofs with JSON Web Proofs*, `draft-ietf-jose-jwp-modular-bbs-00`, **2026-11-02**, JOSE WG Standards Track Internet-Draft (work in progress): https://datatracker.ietf.org/doc/html/draft-ietf-jose-jwp-modular-bbs-00 .
- **Verified facts:** The draft specifies a JWP container with Blind BBS-based core proof, fresh committed-message values feeding optional sub-proofs, and issuer headers. It **does not define concrete predicate sub-proof or holder-device-binding constructions** (abstract). Verifier-supplied unpredictable nonce and `aud` bind each presentation to a transaction/audience; when `kb` is absent the issued credential functions as transferable bearer material. A fixed `cmap` structural layout and decoy slots limit type/shape distinguishability; `alg`/`kb` variation, disclosed values, predicates and transport metadata can still correlate presentations (draft ``2.9–2.10, 6.2–6.3, 7.1–7.3). The draft is not an RFC or a ZK-ARCHE cryptographic review.
- **Existing owner / anchors:** R-002/R-015, TD-001/TD-002/TD-004, roadmap zk217/zk225; `spec/privacy-considerations.md`, `spec/p2p-local-trust-and-delegation.md`, `spec/security-considerations.md`, role-proof implementation in `rust/crates/proto/src/proto/auth.rs` and its C lane. Existing Ristretto255 CDS-OR proof is not a BBS/JOSE proof.
- **Bottleneck:** Accepting a JWP/BBS serialized presentation does not by itself establish holder possession, locally authorized roles or safe issuance/revocation. Optional sub-proof algorithms and device-binding scheme must be separately selected, proven, implemented and interoperably tested; a valid BBS proof does not eliminate stable-header/presentation correlation.
- **Distinct engineering idea:** Create an **optionality and proof-composition ledger** before any prototype: issuance → (optional blind issuance) → signature proof → attribute disclosure → predicate sub-proof → device-binding PoP → nonce/audience → locally authorized role decision → revocation/freshness, with every missing/unknown/incorrect step marked *unsupported*, not assumed. Compare bare BBS, modular predicate, device-bound and absent-device-binding fixtures, plus fixed-layout/decoy versus mixed `cmap`/`alg`/`kb` anonymity cohorts; reject mismatched audience and reused challenge. Benchmark the **complete serialized presentation**, not only a BBS core proof.
- **Evidence maturity:** **concept** (new WG draft); no interoperable suite, formal property, audited library or MCU measurement established for ZK-ARCHE.
- **Limitations:** The selected RFCs and BBS/Blind-BBS dependency drafts may evolve; serialization `-00` deliberately leaves some cryptographic constructions out of scope. BLS12-381 performance and library maturity on specific Rust/C+MCU builds remain unmeasured. A high-entropy nonce cannot compensate for absent holder binding.
- **ZK-ARCHE inference:** Keep all BBS/JOSE modular credentials *optional and research-only* as to integration. Cross-verifier privacy requires end-to-end observable-field/entropy accounting, not a generic “unlinkable credential” claim. No effect on mandatory constrained Ristretto255 profile.
- **Wire / CPU / RAM / flash / dependency / trust / privacy:** Likely larger payload, BLS12-381 pairing CPU and flash, more RAM/scratch, and an additional BBS/JWP + chosen predicate/device-binding implementation dependency than the current compact profile; **no numeric ZK-ARCHE measurements**. Fixed maximum-layout decoys trade metadata privacy for additional bytes and proof work. Local trust and revocation remain independent.
- **Rust/C/vectors/profiles:** Future exact version/cipher-suite/predicate/device-binding pinning and separate positive/negative issuance/presentation fixtures in Rust and C would be required; current CDS-OR vectors and Common Contract profiles must remain untouched. Explicitly test absent `kb` versus verified PoP and audience/nonce alterations before claiming holder-bound presentation.
- **Required next evidence / disposition:** Pin JOSE/CFRG revisions and reference implementations; collect concrete prototype bytes and complete verifier-cost/footprint per optional feature; characterize verifier side-channel/metadata effects and carry out MCU versus edge feasibility comparison before any ADR. **Investigate**, retained `researching`. ## 6. Cross-source synthesis

Both newly revised IETF efforts distinguish **cryptographic validity** from independent authorization/currentness and deployable privacy. A consistent signed label history does not grant local trust; a valid selectively disclosed credential does not prove possession unless a concrete holder mechanism is used. The interoperability/common-contract baseline should not depend on either a transparency service or a high-cost credential format. Any optional use must retain local authority, exact freshness, bounded constrained resources and measured observer privacy.
