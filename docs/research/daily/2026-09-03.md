## 1. Executive synthesis

1. **The new P2P generation checks are necessary but do not yet define the full cryptographic delegation-chain invariant.** The current ZK-ARCHE P2P decision correctly requires locally rooted issuer trust, authenticated holder, integrity-valid grant, bounded scope/audience/deployment/validity, current authorization generation, epoch, revocation and lineage, and bounded redelegation. Current delegated-authorization work sharpens what an eventual wire format should prove between adjacent hops: the parent must authorize the child key, every child permission/audience/lifetime must be no broader than the effective parent, removed permission components must not reappear in descendants, and ambiguous containment must fail closed.
2. **Revocation needs exact grant/link identity plus descendant invalidation semantics in addition to generation freshness.** A coarse authorization-generation advance is useful for invalidating a whole local policy state, but it does not by itself express the narrower case “revoke this delegated link and all descendants, but not its parent or siblings.” The July 2026 delegated-authorization draft requires an unambiguous token identity and invalidates descendants of a revoked link while preserving unrelated siblings/parents. ZK-ARCHE should reproduce this distinction before a P2P grant wire format is promoted.
3. **Replacement/continuation must preserve attenuation and an absolute authority deadline.** The August 2026 delegated-refresh-token draft requires each continuation to re-evaluate current policy, replay/revocation and actor/client binding; replacement must preserve subject/actor chain and resource/scope bounds, prevent concurrent divergent successors, and must not extend the original absolute delegation lifetime. This is directly relevant to ZK-ARCHE's authorization-generation, lineage-replacement, resumption and P2P redelegation lifecycle.
4. **The formal provenance improvement on current `dev` is correctly scoped.** CORE admission now distinguishes `AuthorizationGenerationBound` from `AuthorizationGenerationCurrent` in the synchronized model and test gate, but the repository explicitly does not claim that the cryptographic parsing/persistence path derives those facts. Today's delegation findings are therefore primarily R-008/R-012/R-013 conformance and wire-format research, not evidence that TD-003 is cleared.
5. **No mandatory primitive, suite, wire format, roadmap, ADR, debt status, or maturity claim changes today.** The external sources are active Internet-Drafts and are engineering comparators, not ZK-ARCHE dependencies.

### D20260903-F01 — Delegation needs adjacent-key continuity and monotonic attenuation

- **Novelty:** new/refines
- **Source:** `draft-li-oauth-delegated-authorization-03`, *OAuth 2.0 Delegated Authorization*
- **Primary link:** https://datatracker.ietf.org/doc/draft-li-oauth-delegated-authorization/
- **Source type / venue:** active individual Internet-Draft discussed in OAuth; work in progress
- **Publication or release date:** July 24, 2026
- **Verified claim:** the draft binds each delegated child to a key, requires adjacent parent→child key continuity, requires delegation depth to decrease, requires child scope/authorization details to be contained within the effective parent, prohibits a permission component from reappearing after being omitted, requires audience narrowing, and caps child expiration at the parent's effective expiration. Unsupported or ambiguous containment fails closed.
- **Existing owner:** R-008 / R-013 / `spec/p2p-bounded-delegation.md` / TD-004
- **Repository fact:** ZK-ARCHE's current P2P classifier already enforces locally rooted issuer trust, holder authentication, grant integrity, scope/audience/deployment matching, validity, authorization-generation provenance/currentness, epoch/revocation/lineage freshness, depth, and redelegation permission, but it intentionally does not define a grant wire format or cryptographic chain construction.
- **Problem addressed:** independent booleans such as `scope_match` and `depth_within_limit` do not by themselves specify how a multi-hop verifier proves that each child was actually authorized by the preceding holder, that constraints only narrow, or that a dropped constraint cannot reappear later.
- **Strongest distinct engineering idea:** define a future P2P grant-chain verification contract over ordered links. Each link should cryptographically bind the next holder key/commitment and canonical child authorization, and the verifier should compute effective authority cumulatively. Each child must be a subset of the parent's effective scope/audience/operations and must not extend lifetime or depth. Unknown/ambiguous constraint-comparison semantics must deny rather than widen authority.
- **Evidence maturity:** software/spec comparator
- **Limitations / uncertainty:** the draft uses OAuth/JWT/JWS/DPoP and is not an IETF standard or ZK-ARCHE dependency. ZK-ARCHE can adopt the invariant without adopting those encodings or an online Authorization Server.
- **ZK-ARCHE inference:** generation binding should remain one independent freshness axis within each grant/link; it does not replace parent→child key continuity or attenuation proof.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** an eventual chain format would add per-hop authenticated material and bounded parser/storage cost. MCU profiles need a hard maximum chain depth/bytes and should be able to verify the mandatory floor locally without online infrastructure.
- **Rust/C / vector compatibility impact:** add deterministic multi-hop vectors for valid narrowing, child key substitution, reordered links, depth non-decrease, scope widening, audience widening, lifetime extension, removed-then-reintroduced permission, and unsupported containment. Rust/C must compute the same effective authority and terminal reason.
- **Required next evidence:** canonical grant/link encoding proposal; adjacent key-binding rule; deterministic attenuation algorithm; bounded chain depth/bytes for `p2p-iot-core`; cross-language positive/negative corpus; privacy budget for visible chain metadata.
- **Recommended disposition:** reproduce

### D20260903-F02 — Revocation needs exact-link identity and descendant invalidation

- **Novelty:** refines
- **Source:** `draft-li-oauth-delegated-authorization-03`, revocation sections
- **Primary link:** https://datatracker.ietf.org/doc/draft-li-oauth-delegated-authorization/
- **Source type / venue:** active individual Internet-Draft; work in progress
- **Publication or release date:** July 24, 2026
- **Verified claim:** the draft requires an unambiguous identifier for the revoked delegated token. Revoking a root invalidates every chain rooted in it; revoking an intermediate/leaf token invalidates every chain containing that token and all descendants, while not automatically revoking its parent, siblings, or another token bound to the same key. Offline verifiers cannot learn revocation until status is distributed, so short lifetimes bound exposure where prompt status propagation is unavailable.
- **Existing owner:** R-012 / R-013 / P2P lineage and revocation lifecycle
- **Repository fact:** current ZK-ARCHE P2P delegation requires `revocation_current`, `!explicitly_revoked`, `lineage_current`, and current authorization generation. The authorization-generation lifecycle can invalidate broad local policy state but intentionally remains semantically distinct from revocation and lineage.
- **Problem addressed:** a generation advance is a useful broad invalidation mechanism but cannot express precise branch semantics when one delegated child is compromised or revoked while its parent and sibling grants remain valid.
- **Strongest distinct engineering idea:** future delegated grants should have an exact collision-resistant local/wire identity and an explicit parent/lineage relationship. The local revocation model should support subtree invalidation: target + descendants invalid, parent/siblings unaffected unless a broader authorization-generation or policy transition independently invalidates them.
- **Evidence maturity:** software/spec comparator
- **Limitations / uncertainty:** the draft leaves revocation-status distribution outside its scope. ZK-ARCHE must still solve disconnected-peer convergence and stale-window bounds under its own infrastructure-independent model.
- **ZK-ARCHE inference:** keep three independent controls: authorization generation for broad policy-state freshness, lineage identity for ancestry/replacement, and revocation state for targeted invalidation. Do not collapse them into one counter.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** bounded grant IDs/parent commitments and local revocation metadata; storage scales with active/revoked lineage policy. No mandatory online revocation service should be introduced for the Common Contract.
- **Rust/C / vector compatibility impact:** add root/intermediate/leaf revocation vectors, sibling-survival vectors, same-key/different-grant vectors, stale revocation-view behavior, offline stale-window tests, and restart/rollback persistence cases.
- **Required next evidence:** exact grant-ID derivation; parent/child lineage representation; subtree invalidation algorithm; per-profile stale-revocation bound; bounded storage and restart tests; formal property that revoked-link descendants cannot authorize.

### D20260903-F03 — Continuation/replacement cannot widen or reset delegated authority

- **Novelty:** refines
- **Source:** `draft-zhu-oauth-async-delegation-05`, *Delegated Refresh Tokens for OAuth 2.0 Token Exchange*
- **Primary link:** https://datatracker.ietf.org/doc/draft-zhu-oauth-async-delegation/
- **Source type / venue:** active Internet-Draft; work in progress
- **Publication or release date:** August 3, 2026
- **Verified claim:** every delegated continuation must re-evaluate replay/revocation/current policy and actor/client binding. Replacement must preserve subject/actor chain and resource/scope restrictions, must prevent concurrent requests from creating divergent valid branches, and must preserve the original absolute maximum delegation lifetime; rotation cannot extend that deadline.
- **Existing owner:** R-009 / R-012 / resumption / lineage replacement / P2P delegation
- **Repository fact:** ZK-ARCHE already separates authorization-generation freshness from lineage, replay, resumption and rollback, and its P2P contract limits redelegation/depth. Current decision surfaces do not yet define a cryptographic grant replacement/continuation wire protocol.
- **Problem addressed:** a sequence of individually valid replacements could accidentally extend authority forever, widen authority after policy change, substitute a different holder/actor, or fork into two concurrent valid successors.
- **Strongest distinct engineering idea:** define an immutable root authority envelope for any replaceable delegated grant family: root subject/issuer domain, maximum scope/audience/operations, authentication/holder-binding requirement, maximum depth, and absolute delegation deadline. Each replacement must be exactly one successor, remain within that envelope and current local policy/generation, and invalidate the predecessor atomically/recoverably.
- **Evidence maturity:** software/spec comparator
- **Limitations / uncertainty:** OAuth refresh tokens are not ZK-ARCHE grants; the transferable result is the lifecycle invariant, not the token format or centralized server model.
- **ZK-ARCHE inference:** authorization-generation advancement should force re-evaluation of the current delegated grant but must not silently mint a new root envelope or reset the absolute authority lifetime.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** mainly persistent lineage/family metadata and bounded counters/deadline state; no requirement for additional network round trips unless a future profile chooses them.
- **Rust/C / vector compatibility impact:** add predecessor→successor vectors for same/narrower authority, lifetime extension rejection, actor/holder substitution, concurrent two-successor race, replayed predecessor, policy/generation change during replacement, and restart after partial replacement.
- **Required next evidence:** define root-envelope fields and authoritative time/freshness representation per profile; one-successor commit semantics; concurrency/fault corpus; interaction with resumption and authorization-generation advance; MCU persistence/endurance measurement.

## 5. Cross-source synthesis

The new common theme is that **authorization generation is a freshness gate, not the full delegation proof**. ZK-ARCHE's current direction correctly distinguishes bound/current generation from revocation, lineage and replay. The external delegation work reinforces four additional invariants for any future multi-hop grant wire format: authenticated parent→child holder continuity, monotonic attenuation, exact subtree revocation, and replacement that preserves the original authority envelope and deadline.

There is no reason to import OAuth/JWT/JWS, an online authorization server, or an agent-specific trust model into the constrained Common Contract. The relevant value is the fail-closed lifecycle structure, which can be encoded in a smaller ZK-ARCHE-native representation and validated from locally authorized state.
