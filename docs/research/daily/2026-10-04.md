## 2. Executive synthesis

- Current ZK-ARCHE already separates a monotonic `revocation_epoch` from the profile's still-undefined revocation freshness policy. The resumption path has a fail-closed `revocation_current` predicate, but the repository does not yet define what retained evidence makes that predicate true.
- `draft-ietf-oauth-status-list-21`, now in the RFC Editor publication queue, provides a mature comparator: status is carried in a cryptographically protected JWT/CWT; issuance time is mandatory, expiration and cache TTL are recommended, and a relying party validates the status object and its freshness before relying on it.
- ZK-ARCHE should not copy that draft's wall-clock/HTTP mechanism into `iot-core`. R-012 should instead require a provenance-bearing revocation-view record whose currentness derives from authority identity, view generation/cursor, bounded age or a monotonic no-clock equivalent, and rollback/restart continuity.
- A fresh status view and a valid authorization are separate predicates. A status of VALID cannot revive an expired credential, stale authorization generation, incompatible policy epoch, or invalid lineage.
- Batched status views offer a useful privacy/scalability pattern but introduce compression/decompression, cache, cardinality, stable-reference, and refresh-load costs. Those require measured constrained-target evidence before promotion.
- R-012 remains `reproduce`. No wire field, status-list format, online status provider, new trust root, or roadmap/spec implementation change is authorized.

### D20261004-F01 — Revocation currentness should derive from verified view provenance, not exist only as a Boolean

- **Novelty:** new / refines
- **Backlog owner:** R-012
- **Source:** `draft-ietf-oauth-status-list-21`, *Token Status List (TSL)*
- **Primary link:** https://datatracker.ietf.org/doc/html/draft-ietf-oauth-status-list-21
- **Source type / venue:** IETF OAuth WG Standards Track Internet-Draft; in the RFC Editor publication queue
- **Publication or release date:** revision -21 published 2026-06-21; RFC Editor status advanced to Awaiting First editor on 2026-08-13
- **Verified claim:** a Status List Token is cryptographically protected as JWT or CWT; `iat` is required, `exp` and `ttl` are recommended, and verification includes subject/URI binding, signature/MAC validation, expiration, local freshness policy, and cache refresh behavior. By default, the status statement describes state at the time the Status List Token was issued.
- **Existing engineering owner:** R-012 / zk213/zk214/zk221/zk230/zk234/zk235/zk239 / TD-004
- **Repository fact:** ZK-ARCHE already has a monotonic `revocation_epoch` plus an unresolved separate freshness policy, while the resumption classifier consumes only a derived `revocation_current` Boolean.
- **Problem addressed:** a Boolean current/stale decision is testable control flow but does not prove which authority view, age/generation, restart state, or rollback-safe artifact justified it.
- **Strongest distinct engineering idea:** define a local **revocation-view evidence record** from which `revocation_current` is derived. At minimum it should identify the accepted authority/status source, view generation or cursor, profile freshness bound, age/fetch/issuance evidence or a monotonic no-clock equivalent, and rollback/restart continuity.
- **Evidence maturity:** externally-reviewed
- **Limitations / uncertainty:** TSL is not yet an RFC and assumes JWT/CWT plus a retrieval model that does not map directly onto every ZK-ARCHE deployment. Its wall-clock `iat/exp/ttl` design must not be silently imported into `iot-core`, whose baseline deliberately permits operation without a trusted wall clock.
- **ZK-ARCHE inference:** evaluate two explicit freshness realizations: trusted-time deployments using signed issuance/expiry/cache bounds, and no-trusted-clock deployments using monotonic view generations/cursors plus bounded local refresh/continuity policy. Both fail closed when provenance/currentness cannot be established.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** no AUTH wire change is required to retain local view evidence. A promoted status-distribution mechanism would add signed-object verification, cache metadata and potentially persistent generation/cursor state. No always-online provider or new trust root is justified.
- **Rust/C / vector compatibility impact:** add shared decision fixtures deriving the same `revocation_current` outcome from explicit metadata: fresh, at-boundary, over-bound, wrong authority/domain, rolled-back generation, missing continuity, and unavailable-view cases.
- **Required next evidence:** language-neutral revocation-view record/derivation corpus, Rust/C parity, restart/rollback cases, and exact profile freshness bounds with no-clock behavior.
- **Recommended disposition:** reproduce
- **Weekly finding candidate:** yes

### D20261004-F02 — Status freshness and credential/authorization validity are independent fail-closed axes

- **Novelty:** corroborates / refines
- **Backlog owner:** R-012 / R-009
- **Source:** `draft-ietf-oauth-status-list-21`; RFC 9770 as the existing constrained revocation baseline
- **Primary links:** https://datatracker.ietf.org/doc/html/draft-ietf-oauth-status-list-21 ; https://www.rfc-editor.org/rfc/rfc9770.html
- **Source type / venue:** IETF OAuth WG Standards Track I-D in RFC Editor queue; IETF Standards Track RFC
- **Publication or release date:** 2026-06-21 (-21); RFC 9770 published 2025-06
- **Verified claim:** TSL requires normal referenced-token validation before status evaluation; an expired token does not become valid merely because its status-list entry says VALID. Failure to validate the status object or determine a usable status also leads to rejection. RFC 9770 likewise treats revocation information as invalidating previously usable authorization rather than replacing its other validity conditions.
- **Existing engineering owner:** R-012 / R-009 / `spec/iot-core-authorization-context.md`
- **Repository fact:** ZK-ARCHE checks credential validity/expiry, authorization generation, policy/revocation freshness, lineage, restart continuity and explicit revocation as distinct resumption facts; `iot-core` states that a higher revocation epoch does not itself authorize a peer.
- **Problem addressed:** a future status synchronization implementation could collapse “not revoked” into “authorized/current”, reviving stale or otherwise invalid authority.
- **Strongest distinct engineering idea:** qualify the conjunction explicitly: current status evidence is a **negative invalidation/currentness input**, not an authorization grant.
- **Evidence maturity:** software + externally-reviewed
- **Limitations / uncertainty:** exact failure precedence and recovery remain ZK-ARCHE-specific; the external mechanisms do not define ZK-ARCHE role-proof, lineage, or resumption semantics.
- **ZK-ARCHE inference:** shared negatives should include fresh status + expired credential, fresh status + stale authorization generation, newer revocation view + stale retained attribution, valid credential + unknown/stale status view, and explicitly revoked + otherwise current authorization. Full AUTH fallback must not manufacture fresh authorization if the authoritative revocation view remains unusable.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** test/state impact only; no new dependency or wire bytes are required for the decision decomposition.
- **Rust/C / vector compatibility impact:** extend decision-level coverage around the existing v5 resumption corpus rather than replacing its `revocation_current` predicate.
- **Required next evidence:** deterministic cross-product cases and formal/state-machine properties proving status currentness cannot upgrade stale credential/authorization/lineage state.
- **Recommended disposition:** reproduce

### D20261004-F03 — Batched status distribution trades per-object observability for list/decompression/cache cost and stable-reference privacy risk

- **Novelty:** new / refines
- **Backlog owner:** R-012 / R-015 / R-005
- **Source:** `draft-ietf-oauth-status-list-21`, privacy and operational sections
- **Primary link:** https://datatracker.ietf.org/doc/html/draft-ietf-oauth-status-list-21
- **Source type / venue:** IETF OAuth WG Standards Track I-D in RFC Editor queue
- **Publication or release date:** 2026-06-21
- **Verified claim:** TSL batches statuses for many referenced tokens into a bit-packed array using 1/2/4/8 bits per entry, compresses it with DEFLATE, and defines a CBOR/CWT representation. The draft describes herd privacy: fetching a shared list can reduce issuer visibility into which individual token is being checked. It also warns that unique list URIs/indices and retained status references can be correlatable; larger lists improve herd size while increasing data transfer. Refresh cadence and TTL/expiration bounds also affect provider load.
- **Existing engineering owner:** R-012 / R-015 / R-005
- **Repository fact:** ZK-ARCHE privacy text already treats revocation propagation as a possible membership/policy oracle and has no complete disconnected-revocation privacy claim; physical constrained-target measurements remain TD-002.
- **Problem addressed:** per-credential online status lookup can reveal exactly which credential is active, while a large batched list may reduce that observability but be expensive for an MCU and remain linkable through stable reference metadata.
- **Strongest distinct engineering idea:** if ZK-ARCHE evaluates synchronized status distribution, benchmark at least requester/issuer-scoped full/diff revocation views (RFC 9770-style) against batched status snapshots (TSL-style). Measure privacy cardinality together with wire bytes, decompression RAM/CPU/energy, cache size, refresh traffic, and rollback persistence. The transport provider is not the authority; authenticity must come from the accepted authority's protected status object.
- **Evidence maturity:** externally-reviewed concept
- **Limitations / uncertainty:** DEFLATE, JWT/CWT status lists, HTTP retrieval, and stable token indices are not ZK-ARCHE requirements. On small MCUs, decompression/runtime cost may dominate theoretical bit-level compactness. Herd privacy does not imply unlinkability against colluding parties or network observers.
- **ZK-ARCHE inference:** add a privacy/resource benchmark gate to R-012 and cross-link it to R-015/R-005 rather than selecting a status-list mechanism from standards maturity alone.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** potentially favorable per-status density but new decompression/library, cache and persistent-view costs; stable list/index references can increase correlation. Exact cost is target/profile dependent.
- **Rust/C / vector compatibility impact:** no current protocol vector change. A prototype benchmark should pin cardinality, status density, compressed bytes, decode peak RAM, CPU/energy, cache policy, and observable reference metadata.
- **Required next evidence:** constrained-host and physical-target measurements plus an R-015 observability analysis before promotion.
- **Recommended disposition:** benchmark / reproduce

## 6. Cross-source synthesis

The 2026-08-24 pass already established the RFC 9770 lesson that revocation is a convergence problem with full/diff reconciliation, missed-update recovery, and a measurable vulnerable/stale window. Today's new evidence is narrower and complementary: Token Status List -21 shows how a mature standards design makes **the status view itself** cryptographically verifiable, freshness/cache bounded, and privacy-scalable through batching.

For ZK-ARCHE this sharpens the layer between the existing `revocation_epoch` and `revocation_current` predicate. Qualification needs evidence that the view came from the correct authority/domain, is recent enough under the selected profile, has not rolled back across restart, and remains independent from credential/authorization/lineage validity. The no-trusted-clock baseline means monotonic generation/cursor continuity must remain a first-class alternative to wall-clock expiration.
