## 1. Executive synthesis

1. **A critical extension must be processed according to its registered semantics, not merely recognized by numeric ID.** RFC 9052's `crit` model requires the indicated protected parameter to be understood and processed; RFC 9846 separately requires recognized TLS extensions to be rejected when they appear in a protocol context where their semantics are invalid. For ZK-ARCHE AUTH-v3, a future implementation must therefore fail closed when a registered critical `wire_id` has an unsupported semantic value, invalid context, profile-forbidden use, or unconsumed security effect even if canonical encoding succeeds.
2. **The current `critical-extension-set-encoding.md` is directionally correct because it separates admissibility from canonicalization.** It rejects unknown critical, known-but-incompatible, malformed, duplicate, reserved, draft-not-promoted, and profile-forbidden occurrences before treating them as an acceptable selected set. Today's evidence refines the conformance target: prove the semantic processor was actually invoked and its effect is bound to the authenticated session, not just that Rust and C hash the same bytes.
3. **Canonical sorting is a serialization rule, not permission to erase protocol semantics.** RFC 8949 and the July 2026 CBOR serialization work distinguish deterministic byte ordering from application ordering semantics. TLS 1.3 likewise normally allows different extension types in any order but has an explicit `pre_shared_key` ordering exception and forbids duplicate types. ZK-ARCHE's v1 sorted, duplicate-free extension set is therefore suitable only for extension occurrences whose registry semantics are singleton and order-independent at this layer. Any future ordered or repeated occurrence semantics need a versioned representation rather than silent normalization into the current set.
4. **No backlog row, wire allocation, profile promotion, or maturity claim changes today.** R-011 and TD-004 already own extension agility, criticality, canonical encoding, duplicate/non-canonical behavior, and independently implementable registry semantics. The new evidence changes what their eventual conformance corpus should demonstrate, not their status or destination.

## 4. Findings

### D20260908-F01 — Criticality means semantic processing, not identifier recognition

- **Novelty:** refines
- **Sources:** RFC 9052, *CBOR Object Signing and Encryption (COSE): Structures and Process*; RFC 9846, *The Transport Layer Security (TLS) Protocol Version 1.3*
- **Primary links:** https://www.rfc-editor.org/rfc/rfc9052.html ; https://www.rfc-editor.org/info/rfc9846/
- **Source type / venue:** IETF Standards Track RFCs
- **Publication / release date:** RFC 9052 — August 2022; RFC 9846 — June 2026
- **Verified claim:** RFC 9052 defines `crit` as identifying protected header parameters an application is required to understand, requires those indicated parameters to be present in the protected bucket, and states that the indicated parameters must actually be processed. It also requires duplicate labels in a COSE header map to be rejected as malformed. RFC 9846 requires a recognized TLS extension to abort the handshake if it appears in a message where that extension is not specified, forbids duplicate extension types in one extension block, rejects trailing data left after parsing implemented extension semantics, and emphasizes that extension designs must resist attacker-forced use or non-use through authenticated handshake binding.
- **Existing owner:** R-011 / TD-004 / `spec/critical-extension-set-encoding.md` / `spec/registries.md`
- **Repository fact:** the current AUTH-v3 draft already separates selection/admissibility from canonical encoding. It says unknown critical occurrences fail closed; known-but-incompatible, reserved, draft-not-promoted, malformed, duplicate or profile-forbidden occurrences must not be normalized into an acceptable set; changing selected extension semantics/membership must change the authenticated context. The registry similarly says that a known suite/profile value is not automatically allowed in every context.
- **Problem addressed:** an implementation can superficially pass an "unknown critical extension" test while still being vulnerable to semantic downgrade if it recognizes the numeric ID but ignores, partially parses, mis-contextualizes, or fails to enforce the security effect of the registered value.
- **Strongest distinct engineering idea:** make critical-extension processing a three-stage invariant: `(1) parse + registry/profile admissibility`, `(2) extension-specific semantic validation/application`, `(3) canonical selected-occurrence authentication`. An occurrence may enter the authenticated selected set only after the implementation can prove that its registered security semantics were successfully consumed for the selected version/profile/session context.
- **Evidence maturity:** externally-reviewed standards guidance; ZK-ARCHE current encoding contract is draft specification/software-adjacent evidence
- **Limitations / uncertainty:** COSE and TLS use different extension/header architectures from ZK-ARCHE. Their exact wire formats and registries are not proposed dependencies. The transferable property is the distinction between recognizing a label and correctly processing the semantics that make it critical.
- **ZK-ARCHE inference:** extend the eventual Rust/C conformance corpus beyond `unknown critical -> fail`. Include a registered critical ID carrying an unsupported semantic value, a valid value in a forbidden profile/context, an extension whose parser succeeds but whose mandatory security effect is deliberately not applied, and a mismatch between processed semantics and the canonical selected occurrence. All must fail before AUTH completion.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** no current wire change. Correct semantic processing may require bounded per-extension parser/state code and therefore profile-specific RAM/flash/CPU budgets. No new dependency or trust root is implied.
- **Rust/C / vector compatibility impact:** existing canonical vectors remain valid. Add shared negative decision vectors for known-ID-but-unprocessed, wrong-context, profile-forbidden and trailing/unsupported semantic data; assert both languages reject for the same security class before Finished/completion acceptance.
- **Required next evidence:** independently implementable per-extension semantic contracts in the registry/spec; Rust/C tests proving semantic processor invocation/effect; negative vectors for known-but-unprocessed/wrong-context values; AUTH-v3 mutation tests proving canonical hash plus semantic enforcement are both required.
- **Recommended disposition:** reproduce

### D20260908-F02 — Deterministic ordering must not erase ordered or repeated semantics

- **Novelty:** refines
- **Sources:** RFC 8949, *Concise Binary Object Representation (CBOR)*; `draft-ietf-cbor-serialization-08`, *CBOR Serialization and Determinism*; RFC 9846 TLS 1.3
- **Primary links:** https://www.rfc-editor.org/rfc/rfc8949.html ; https://datatracker.ietf.org/doc/draft-ietf-cbor-serialization/ ; https://www.rfc-editor.org/info/rfc9846/
- **Source type / venue:** IETF Internet Standard / current CBOR Working Group Standards Track Internet-Draft / IETF Standards Track RFC
- **Publication / release date:** RFC 8949 — December 2020; CBOR serialization draft revision 08 — July 2026; RFC 9846 — June 2026
- **Verified claim:** RFC 8949 deterministic CBOR orders map keys to produce reproducible bytes, while duplicate map keys are a validity/interoperability hazard requiring protocol-defined handling. The current CBOR serialization draft explicitly states that deterministic map sorting exists for byte reproducibility and does not create map-order semantics; protocols needing ordered semantics must define them separately. RFC 9846 normally permits different TLS extension types in any order and prohibits duplicate types, but also defines an explicit ordering exception for `pre_shared_key`, which must be last in ClientHello. Thus canonical sorting and protocol semantic ordering are different concerns.
- **Existing owner:** R-011 / TD-004 / `spec/critical-extension-set-encoding.md` / extension registry
- **Repository fact:** ZK-ARCHE's current canonical set sorts occurrences by unsigned numeric `wire_id`, requires strictly increasing IDs, and rejects duplicates. It explicitly states that a future extension registration requiring multiplicity must replace this set format through a versioned rule. Parser arrival order is intentionally not authenticated as semantic order.
- **Problem addressed:** if a future extension's meaning depends on occurrence order, repeated values, or interaction between same-ID occurrences, applying the v1 sort-and-unique transform would collapse semantically distinct inputs into one authenticated representation or reject a feature whose semantics were never representable by the format.
- **Strongest distinct engineering idea:** treat the current AUTH-v3 critical-extension representation as a **singleton, order-independent set contract**. Before allocating an extension into this representation, its registration should state that one selected occurrence is sufficient and that parser/arrival order has no semantics at this layer. If future functionality genuinely needs ordered or repeated occurrences, define a new/versioned authenticated container instead of weakening duplicate rejection or making sorting context-dependent.
- **Evidence maturity:** RFC evidence externally reviewed; current CBOR draft is work in progress; ZK-ARCHE implication is specification/conformance-level
- **Limitations / uncertainty:** ZK-ARCHE's extension set is not CBOR, and TLS's `pre_shared_key` placement rule is protocol-specific. These sources do not prove the exact ZK-ARCHE encoding secure; they demonstrate why deterministic serialization rules and application semantic ordering must be specified separately.
- **ZK-ARCHE inference:** keep current duplicate rejection and order-insensitive hashing for v1. Add an extension-registration invariant covering occurrence cardinality and order sensitivity. Do not introduce a special-case comparator/sort rule for one future extension inside the existing format; version the representation if semantic ordering becomes necessary.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** no current wire/RAM/CPU/flash change. Preserving the singleton/order-independent rule keeps constrained implementations bounded and deterministic. A future ordered/multiplicity container would have separate byte/count/resource limits and a versioning/interoperability cost.
- **Rust/C / vector compatibility impact:** existing empty/sorted/reordered-input vectors remain compatible. Future conformance should prove that parser arrival reordering of the same valid singleton set yields identical canonical bytes/hash, duplicate IDs fail, and no extension registration marked ordered/multi-occurrence can be represented under the v1 set.
- **Required next evidence:** registry-level occurrence-semantics field or equivalent normative prose for promoted extensions; Rust/C registration/conformance checks; a negative fixture demonstrating rejection of a hypothetical ordered/multi-occurrence extension under v1 before any such feature is promoted.
- **Recommended disposition:** reproduce

## 5. Cross-source synthesis

Today's sources sharpen one boundary around the newly indexed AUTH-v3 extension encoding:

```text
raw extension occurrence(s)
        ↓
registry + version/profile/context admissibility
        ↓
extension-specific semantic processing
        ↓
selected singleton/order-independent occurrence set
        ↓
canonical deterministic encoding
        ↓
critical_extensions_hash
        ↓
AUTH-v3 authenticated completion
```

The hash is the end of the semantic-selection pipeline, not a substitute for it. A known numeric ID with ignored or invalid semantics is unsafe even if its bytes are canonical. Conversely, deterministic sorting is for reproducibility; it must not silently redefine future extension order or multiplicity.

This conclusion reinforces the existing draft rather than contradicting it. The current spec already contains the right fail-closed direction and a versioning escape hatch for multiplicity. What is newly actionable is the conformance requirement to prove **semantic consumption** and to keep the v1 representation explicitly restricted to singleton, order-independent semantics.
