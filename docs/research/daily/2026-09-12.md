## 2. Executive synthesis

1. **Failing closed on rollback suspicion is necessary but does not prove rollback detection.** Current Rust/C behavior now maps trusted-state rollback suspicion to broken replay continuity, but the repository correctly records that the symbolic model is not yet synchronized and that physical rollback resistance remains outside that claim. RFC 8613 gives a directly relevant constrained invariant: conservative persistent sequence-number recovery is safe only if the post-reboot value is guaranteed to exceed every value previously used; otherwise that recovery method must not be used. ZK-ARCHE should preserve the same evidence discipline: a `rollback_suspected` input is a security response trigger, not proof that the underlying detector is rollback-resistant.
2. **Current KUDOS work adds a useful transition-isolation rule for R-009.** The July 2026 `draft-ietf-core-oscore-key-update-14` prohibits ordinary application traffic while key update is in progress and requires outstanding interactions to be cleared before proceeding, specifically to avoid old/new security-context ambiguity. ZK-ARCHE should test the analogous invariant at rekey/resumption boundaries: no DATA release may straddle an unresolved key-generation transition unless a reviewed protocol rule explicitly identifies which generation authorizes it.
3. **Fresh authentication or channel binding must not synthesize fresh authorization/revocation authority.** RFC 9200 keeps resource authorization dependent on token scope/audience/current validation in addition to proof of possession; RFC 9770 exists because constrained, intermittently connected devices can hold long-lived authorization whose revocation state changes independently of the cryptographic channel. Current ZK-ARCHE DATA negatives are aligned with that separation: fresh AUTH/rebinding can restore cryptographic liveness only after every independent policy/revocation/lineage/release-authority domain is current.
4. **No backlog status transition is justified today.** R-009 and R-012 remain `reproduce`: the external evidence sharpens executable invariants but does not provide physical rollback evidence, complete Rust/C transition qualification across rekey, or a measured disconnected-revocation stale-window bound.
5. No wire format, suite, profile, roadmap, ADR, technical-debt status, formal-proof claim, hardware-readiness claim, or release posture changes in this report.

## 5. Findings

### D20260912-F01 — Separate rollback response from rollback-detection evidence

- **Novelty:** refines
- **Backlog owner:** R-009
- **Sources:** RFC 8613, *Object Security for Constrained RESTful Environments (OSCORE)*; RFC 9031, *Constrained Join Protocol (CoJP) for 6TiSCH*; NIST SP 800-193, *Platform Firmware Resiliency Guidelines*
- **Primary links:** https://www.rfc-editor.org/rfc/rfc8613.html ; https://www.rfc-editor.org/rfc/rfc9031.html ; https://doi.org/10.6028/NIST.SP.800-193
- **Source type / venue:** IETF Standards Track RFCs; NIST Special Publication
- **Publication / release date:** RFC 8613 — July 2019; RFC 9031 — May 2021; NIST SP 800-193 — May 2018 (NIST page updated February 19, 2025)
- **Verified source-supported claim:** RFC 8613 requires that OSCORE never reuse a sender sequence number under the same AEAD key and gives a nonvolatile-memory recovery construction that intentionally over-advances after reboot. It states that if the implementation cannot guarantee the recovered sequence number is larger than every previously used value, that method must not be used. RFC 9031 strengthens this for its constrained join profile by requiring persistent mutable OSCORE context and replay-window state. NIST SP 800-193 separately treats protection against unauthorized rollback as a platform resilience property rather than something implied by integrity alone.
- **Existing engineering owner:** R-009 / TD-002 / TD-003
- **Repository fact:** current Rust/C replay continuity now fail closed when rollback suspicion occurs from `TRUSTED`, but the assurance addendum explicitly says current formal evidence does not establish the transition and does not establish physical rollback detection, rollback-resistant persistence, power-loss atomicity, or monotonic hardware state.
- **Problem addressed:** conflating `rollback_suspected` being consumed correctly by the classifier with evidence that the platform can reliably detect rollback or that persistent counters cannot undercount prior use.
- **Strongest distinct engineering idea:** model two independent layers: (1) `continuity_evidence_capability` describing whether the platform state is rollback-resistant / monotonic / integrity-only / unavailable, and (2) the protocol reaction to a current continuity signal. A runtime can correctly fail closed on suspicion while still being unable to claim rollback resistance. For constrained counters, a conservative upper-bound scheme is acceptable only when its non-undercount invariant is actually demonstrated under crash/power-loss/restart behavior.
- **Evidence maturity:** externally reviewed standards/guidance; ZK-ARCHE mapping remains software/assurance research
- **Limitations / uncertainty:** OSCORE sequence-number persistence is not ZK-ARCHE's replay format, and NIST SP 800-193 is firmware-resilience guidance rather than a protocol replay specification. Neither source proves a particular ZK-ARCHE storage backend.
- **ZK-ARCHE inference:** `rollback_suspected == false` must never be promoted to “rollback impossible” unless the selected target/backend has evidence for the detector and persistence mechanism. `rollback_suspected == true` should remain fail closed independent of that claim level.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** potentially wire-neutral. Exact persistent counters increase flash writes; conservative monotonic upper bounds can reduce writes but spend counter space and require a proven crash bound. Hardware-backed monotonic state adds platform dependency and must remain a target capability rather than hidden Common Contract infrastructure.
- **Rust/C / vector/profile compatibility impact:** add shared vectors/manifests distinguishing integrity-only restored state, rollback-resistant monotonic state, suspected rollback, missing detector, and safe authenticated fresh-context recovery. Cross-language classifier parity alone is insufficient for a `MEASURED`/deployment claim.
- **Required next evidence:** target-specific persistence capability matrix; power-loss/rollback experiment; exact counter non-undercount proof/measurement; synchronized replay-continuity formal model followed by a fresh exact-model ProVerif run.
- **Recommended disposition:** reproduce
- **Weekly finding candidate:** yes

### D20260912-F02 — Isolate application traffic across unresolved key-generation transitions

- **Novelty:** new
- **Backlog owner:** R-009 / R-012
- **Source:** `draft-ietf-core-oscore-key-update-14`, *Key Update for OSCORE (KUDOS)*
- **Primary link:** https://datatracker.ietf.org/doc/draft-ietf-core-oscore-key-update/14/
- **Source type / venue:** IETF CoRE Working Group Internet-Draft, work in progress
- **Publication / release date:** July 6, 2026; expires January 7, 2027
- **Verified source-supported claim:** KUDOS establishes a new OSCORE Security Context and is designed to avoid `(nonce,key)` reuse across reboot/state loss. Before initiating/continuing key update, a peer must clear outstanding interactions (with defined observation exceptions), and while KUDOS is in progress it must not send ordinary non-KUDOS traffic. The draft explains that this prevents old/new context ambiguity where a response under the new context could otherwise match both a new request and an older request using the old context. It also distinguishes an FS mode that requires preserved nonvolatile state from a no-FS mode for peers that cannot dynamically persist such state.
- **Existing engineering owner:** R-009 / R-012 / TD-004
- **Repository fact:** ZK-ARCHE already tracks key/replay/restart continuity and rejects DATA release when retained association authority becomes unsafe. Current tests also reject new release after rollback or consumed release-operation state. The repository does not yet have complete independently implementable rekey/resumption transition text across all modules.
- **Problem addressed:** mixed-generation application operations during a transition can create ambiguity over which key generation, replay state, authorization generation, and channel binding authorize an operation.
- **Strongest distinct engineering idea:** define a storage-neutral `key_transition_in_progress` / generation-transition barrier in the future lifecycle contract. Until the new generation is fully established and its binding/replay/authorization facts are current, no new DATA release should be admitted under an implicit mixture of predecessor and successor state. Any exception (for retransmission, observations, or transport-specific completion) must be explicit and generation-bound.
- **Evidence maturity:** active WG draft; ZK-ARCHE implication is concept/spec research
- **Limitations / uncertainty:** KUDOS is work in progress and OSCORE-specific. ZK-ARCHE may choose a different rekey protocol and must not inherit KUDOS wire behavior automatically.
- **ZK-ARCHE inference:** the reusable lesson is transition isolation, not the KUDOS packet format. A rekey/resumption operation should have an explicit commit point after which new association/data authority belongs to the successor generation; predecessor and successor state should not be combined implicitly.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** likely no Common Contract wire change if represented as local lifecycle state; may temporarily reduce availability while a key transition is unresolved. Stateful forward-secret modes can require nonvolatile writes; stateless fallback modes may trade away forward secrecy and therefore need explicit profile semantics if ever adopted.
- **Rust/C / vector/profile compatibility impact:** future shared corpus should include DATA attempted before rekey commit (deny), successor generation committed with fresh replay/binding/authorization state (allow if otherwise authorized), aborted transition (well-defined predecessor recovery), and stale predecessor operation arriving after successor commit (deny or explicit idempotent rule).
- **Required next evidence:** normative transition/commit semantics; Rust/C cross-module corpus; reordering/retransmission tests; constrained persistence/latency measurements for any stateful key-update profile.

### D20260912-F03 — Fresh AUTH/rebinding cannot synthesize current authorization or revocation state

- **Novelty:** corroborates/refines
- **Backlog owner:** R-012 / R-008 / R-015
- **Sources:** RFC 9200, *Authentication and Authorization for Constrained Environments Using the OAuth 2.0 Framework*; RFC 9770, *Notification of Revoked Access Tokens in the ACE Framework*; RFC 9700, *Best Current Practice for OAuth 2.0 Security*
- **Primary links:** https://www.rfc-editor.org/rfc/rfc9200.html ; https://www.rfc-editor.org/rfc/rfc9770.html ; https://www.rfc-editor.org/rfc/rfc9700.html
- **Source type / venue:** IETF Standards Track RFCs / BCP
- **Publication / release date:** RFC 9200 — August 2022; RFC 9770 — June 2025; RFC 9700 — January 2025
- **Verified source-supported claim:** ACE separates proof of possession from resource authorization: the resource server still evaluates token parameters such as scope, audience, validity, and current token state. RFC 9770 exists because authorization for constrained/intermittently connected devices can be long-lived while revocation or policy conditions change independently; it provides full/diff revocation-list synchronization and explicitly discusses the vulnerable time window before a resource server learns of revocation. RFC 9700 likewise requires sender-constrained authorization proofs to be replay-protected rather than treating possession alone as sufficient.
- **Existing engineering owner:** R-012 / R-008 / R-015 / TD-004
- **Repository fact:** current Rust retained-association DATA corpus shows that setting `authenticated=true` and restoring `channel_binding_valid=true` does not revive stale authorization generation, explicit revocation, stale lineage, stale device release authority, stale authorization, policy mismatch, consumed release operation, or rollback-suspected state.
- **Problem addressed:** a common lifecycle bug is allowing newly successful cryptographic authentication/rebinding to overwrite or implicitly refresh a separate authorization/revocation domain.
- **Strongest distinct engineering idea:** preserve **independent freshness domains** with a monotonic non-substitution rule: fresh cryptographic liveness can satisfy only the authentication/binding domain. Authorization generation, revocation view, lineage, policy, release-operation replay state, and local data-sovereignty authority must each become current through their own accepted update/reconciliation path before DATA can release.
- **Evidence maturity:** externally reviewed standards plus current software negative tests
- **Limitations / uncertainty:** ACE relies on an authorization server and therefore is only a comparator; ZK-ARCHE's Common Contract must continue to support infrastructure-independent local decisions. Exact stale-window policy for disconnected ZK-ARCHE deployments remains profile/deployment work.
- **ZK-ARCHE inference:** a future reconnect/resumption/rekey API should never expose one generic `refresh_security_state()` operation that silently promotes all domains at once. Each authority domain should carry provenance/currentness, and DATA should compose them fail closed.
- **Wire / RAM / CPU / flash / dependency / trust-model impact:** primarily bounded state and synchronization cost. No online AS is implied. Disconnected operation requires an explicit stale-authority policy; stronger freshness can reduce availability. Privacy improves when revocation synchronization uses opaque/hash identifiers rather than stable public identities, but correlation analysis remains R-015 work.
- **Rust/C / vector/profile compatibility impact:** C must retain parity with the new Rust rebinding-sovereignty negatives. Add reconnect/offline cases where channel freshness succeeds while revocation/policy generation is stale; add full-vs-diff reconciliation tests and explicit stale-window expiry/fail-closed behavior per profile.
- **Required next evidence:** Rust/C parity for all rebinding sovereignty negatives; disconnected full/diff revocation reconciliation corpus; profile-specific maximum stale-authorization bound; formal event mapping proving no AUTH/rebinding event emits authorization/revocation-currentness by implication.

## 6. Cross-source synthesis

The current repository is converging on a useful lifecycle rule: **freshness is typed by authority domain**.

```text
cryptographic freshness
  AUTH / possession / channel binding
              |
              | does not imply
              v
authorization freshness
  generation / scope / audience / policy
              |
              | does not imply
              v
revocation + lineage freshness
              |
              | does not imply
              v
replay / rollback / key-generation continuity
              |
              | all required for
              v
       DATA release authority
```

RFC 8613/9031 show that replay continuity across reboot depends on concrete persistence invariants, not merely classifier logic. KUDOS adds the complementary lesson that old/new key contexts need an explicit transition boundary. ACE/RFC 9770 show that authorization/revocation freshness remains independently mutable even when channel proof is valid. Together, these sources support the current ZK-ARCHE direction without requiring their centralized topology or wire formats.
