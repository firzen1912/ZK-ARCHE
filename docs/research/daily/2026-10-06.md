## 3. Findings

### D20261006-F01 — Directional authorization remains independent

Source: draft-tiloca-ace-bidi-access-control-03 (2026-09-02, active individual Internet-Draft) and RFC 9200. Primary links: https://datatracker.ietf.org/doc/html/draft-tiloca-ace-bidi-access-control-03 and https://www.rfc-editor.org/rfc/rfc9200.html.

Verified claim: the draft uses primary audience/scope for DEV1 accessing DEV2 and reverse audience/scope for DEV2 accessing DEV1. Reverse rights are independently policy-evaluated and either direction may be narrowed from the request.

Repository fact: current P2P text separates authentication and authorization but has no canonical paired A-to-B/B-to-A authorization object.

ZK-ARCHE inference: retain two directional authorization tuples under one authenticated association; never infer reciprocal rights from mutual AUTH or from one accepted direction.

Evidence maturity: standards comparator. Limitation: the bidirectional draft is work in progress and assumes an ACE authorization server. Impact: small state/policy cost; a combined artifact may add wire metadata/linkability but save interactions. Rust/C impact: add symmetric/asymmetric, forward-only/reverse-only, wrong reverse audience, scope narrowing, and one-direction stale/revoked cases. Disposition: reproduce.

roadmap_impact: zk239; no roadmap action; explicit human review required.

### D20261006-F02 — Reverse permission is not grant-mutation authority

Sources: draft-tiloca-ace-bidi-access-control-03, RFC 9200, RFC 9201. Primary links: https://datatracker.ietf.org/doc/html/draft-tiloca-ace-bidi-access-control-03 ; https://www.rfc-editor.org/rfc/rfc9200.html ; https://www.rfc-editor.org/rfc/rfc9201.html.

Verified claim: the draft's token series stays bound to the same PoP key/client/audience/profile and only the original requesting DEV1 can request a successor in that series. RFC 9201 separately defines client PoP and resource-server key binding.

Repository fact: ZK-ARCHE already separates possession/authentication from authorization and has authorization generation/lineage concepts.

ZK-ARCHE inference: any future combined grant needs explicit mutation owner/provenance, predecessor lineage/generation, endpoint key commitments, and both directional audiences/scopes. Reverse permission alone cannot authorize expansion.

Evidence maturity: RFC-backed comparator plus draft. Limitation: ACE's update model is centralized/asymmetric. Impact: small rollback-sensitive state; no heavy dependency. Rust/C impact: wrong-owner, endpoint-swap, stale-predecessor, wrong-direction and unauthorized-update negatives. Disposition: reproduce.

roadmap_impact: zk214/zk230/zk239; no roadmap action; explicit human review required.

### D20261006-F03 — No-clock enrollment needs nonce freshness and authority pinning

Source: draft-ietf-anima-rfc8366bis-36 (ANIMA WG Standards-Track Internet-Draft, 2026-09-09). Primary link: https://datatracker.ietf.org/doc/html/draft-ietf-anima-rfc8366bis-36.

Verified claim: the voucher model supports nonce-bound ephemeral vouchers and nonceless time-bounded vouchers. A device without an accurate clock cannot correctly enforce expires-on. The draft nonce is 8..32 bytes. Registrar identity can be pinned by certificate, raw public key, or SHA-256 public-key representation, and the voucher trust anchor is checked against the registrar actually contacted.

Repository fact: current ENROLL already requires an unused operation identifier, bounded validity, commissioner authority, subject possession and lifecycle currentness; draft iot-core does not require trusted wall-clock time.

ZK-ARCHE inference: make freshness mode profile-specific. No-clock targets use one-time nonce/operation freshness with durable replay/restart/rollback continuity. Clock-qualified profiles may use absolute expiry only with trusted-time evidence. Both cryptographically bind the intended enrollment authority and subject/audience/deployment.

Evidence maturity: current WG draft. Limitation: BRSKI/MASA architecture and exact nonce size are comparator evidence only. Impact: nonce mode costs bounded persistence but no RTC/PKI; stable authority references require R-015 privacy review. Rust/C impact: nonce mismatch/reuse, uncertain restart, expiry-without-time, wrong authority key and wrong audience negatives. Disposition: reproduce.

roadmap_impact: zk211/zk212/zk230/zk234; no roadmap action; explicit human review required.

## 4. Cross-source synthesis
