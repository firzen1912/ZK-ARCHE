## 2. Executive synthesis

- RFC 9846 warns that successor tickets can indefinitely extend keying material rooted in the original full handshake and recommends a separate total-lifetime limit. ZK-ARCHE should qualify both per-credential bounds and a non-resettable origin/full-AUTH lineage budget.
- Standard TLS 1.3 KeyUpdate derives the next traffic secret from the previous traffic secret and does not provide post-compromise security. Traffic-key refresh, fresh key exchange, replay-epoch replacement, authorization/revocation refresh, and resumption-origin replacement must remain distinct state transitions.
- RFC 9846 requires the regular exporter unless an application explicitly requests the early exporter; replayed ClientHello messages reproduce the same early exporter and create channel-binding transplant risk after PSK compromise. ZK-ARCHE's baseline should therefore remain regular-exporter-only.
- The IESG-approved TLS/DTLS IoT profile does not enable 0-RTT for CoAP, MQTT, or other IoT protocols without a protocol-specific profile.
- No wire allocation, suite/profile change, 0-RTT mode, Extended Key Update adoption, or status promotion is justified. R-009 and R-010 remain `reproduce`.

### D20260929-F01 — Cumulative resumption-origin lifetime beyond per-credential bounds

- **Novelty:** refines
- **Backlog owner:** R-009
- **Source:** RFC 9846, Sections 4.7.1 and 7.5
- **Primary link:** https://www.rfc-editor.org/rfc/rfc9846.html
- **Source type / venue:** IETF Proposed Standard
- **Publication date:** July 2026
- **Verified claim:** RFC 9846 caps an individual NewSessionTicket lifetime at seven days, derives a distinct PSK per ticket, and separately warns that repeatedly issuing successor tickets can indefinitely extend keying material from the original non-PSK handshake. It recommends a limit on the total lifetime of that original keying material.
- **Existing engineering owner:** R-009 / zk221 / zk230 / zk235
- **Repository fact:** ZK-ARCHE already bounds individual resumption-credential lifetime/reuse and requires current lifecycle state, but the current decision API lacks an explicit cumulative origin/full-AUTH predicate.
- **Problem addressed:** individually bounded successor credentials can outlive the assurance event that originated the chain.
- **Strongest engineering idea:** keep two independent budgets: credential-local lifetime/reuse and origin/full-AUTH lineage lifetime/generation. Successor credential issuance must not reset the origin budget.
- **Evidence maturity:** externally-reviewed
- **Limitations:** TLS's seven-day limit is TLS-specific and is not proposed as a ZK-ARCHE constant.
- **ZK-ARCHE inference:** reject an otherwise-current successor credential if its originating full-AUTH lineage has exceeded the selected profile's cumulative bound. Only a designated fresh-authority event may establish a new origin.
- **Impact:** likely one bounded origin timestamp/generation/budget plus rollback-protected persistence; negligible wire cost if local-only, but persistent-storage/endurance and trusted-time/monotonic-generation assumptions matter.
- **Rust/C/vector impact:** add successor-chain cases, credential-current/origin-expired cases, restart/rollback of origin state, and origin reset only after the designated fresh-authority event.
- **Required next evidence:** Rust/C origin-lineage state contract/corpus; profile-specific bound; persistence/rollback model; formal trace; constrained storage cost.
- **Recommended disposition:** reproduce
- **Weekly finding candidate:** yes

### D20260929-F02 — Separate traffic-key, fresh-KEX, replay, authority, and resumption generations

- **Novelty:** refines
- **Backlog owner:** R-009 / R-010
- **Sources:** RFC 9846; `draft-ietf-uta-tls13-iot-profile-25`; `draft-ietf-tls-extended-key-update-13`
- **Primary links:** https://www.rfc-editor.org/rfc/rfc9846.html ; https://datatracker.ietf.org/doc/draft-ietf-uta-tls13-iot-profile/25/ ; https://datatracker.ietf.org/doc/draft-ietf-tls-extended-key-update/
- **Source type / venue:** IETF Proposed Standard; IESG-approved Standards-Track I-D; active TLS WG Standards-Track I-D
- **Publication dates:** July 2026; 2026-09-03; 2026-07-04
- **Verified claim:** RFC 9846 standard KeyUpdate derives `application_traffic_secret_N+1` from `application_traffic_secret_N`; the IoT profile says it injects no fresh key-exchange input and does not provide post-compromise security. The active Extended Key Update draft instead performs fresh ephemeral key exchange, defines new exporter secrets, temporarily retains old/current exporter material during transition, and calls out CPU/state DoS from excessive updates.
- **Existing engineering owner:** R-009/R-010; replay/recovery and BIND lifecycle; TD-003/TD-004
- **Repository fact:** ZK-ARCHE already separates replay continuity, resumption authorization, exporter binding, revocation, and lineage. It does not select Extended Key Update.
- **Problem addressed:** a generic "key rotation" event can otherwise acquire authority to reset state it does not actually re-establish.
- **Strongest engineering idea:** maintain independent owners for traffic-key generation, fresh key-establishment/exporter generation, replay epoch, authorization/revocation generation, and resumption-origin lineage.
- **Evidence maturity:** externally-reviewed for standard TLS KeyUpdate; concept/standards-work for Extended Key Update
- **Limitations:** Extended Key Update -13 is an active Internet-Draft, not a published RFC or ZK-ARCHE dependency.
- **ZK-ARCHE inference:** standard KeyUpdate may answer transport AEAD key-usage pressure but must not create a fresh replay epoch, reset cumulative resumption origin, clear revocation, or claim post-compromise recovery. If epoch-changing transport updates are later supported, BIND must consume an explicitly current exporter generation and define safe old/new retirement.
- **Impact:** standard KeyUpdate has little ZK-ARCHE wire impact; fresh-KEX updates add public-key CPU, transient state, concurrency/DoS limits, and possibly dual exporter-generation retention.
- **Rust/C/vector impact:** distinguish `TRAFFIC_KEY_UPDATE`, `FRESH_KEX`, `REPLAY_EPOCH_REPLACE`, and `AUTHORITY_LINEAGE_REPLACE`; prove non-substitution.
- **Required next evidence:** generation-ownership matrix; Rust/C cross-generation negative corpus; formal temporal non-substitution properties; update-load benchmark if a fresh-KEX transport mode is ever prototyped.
- **Recommended disposition:** reproduce

### D20260929-F03 — Early exporter/0-RTT excluded from baseline AUTH binding

- **Novelty:** refines
- **Backlog owner:** R-010 / R-009
- **Sources:** RFC 9846 Sections 7.5 and F.5.1; `draft-ietf-uta-tls13-iot-profile-25` Section 15
- **Primary links:** https://www.rfc-editor.org/rfc/rfc9846.html ; https://datatracker.ietf.org/doc/draft-ietf-uta-tls13-iot-profile/25/
- **Source type / venue:** IETF Proposed Standard; IESG-approved Standards-Track I-D
- **Publication dates:** July 2026; 2026-09-03
- **Verified claim:** RFC 9846 requires the regular `exporter_secret` unless the application explicitly requests the early exporter, recommends separate interfaces, and states that replayed ClientHello messages produce the same early exporter. It warns that after PSK compromise early-exporter authentication channel bindings can be transplanted between connections. RFC 9846 also states that 0-RTT lacks inherent replay protection. The IoT profile requires a protocol-specific 0-RTT profile and does not enable 0-RTT for CoAP/MQTT or other IoT protocols lacking one.
- **Existing engineering owner:** R-010 / zk228; R-009
- **Repository fact:** current ZK-ARCHE BIND defines a normal exporter context and no early-exporter/0-RTT mode. Resumption admission already requires current binding and lifecycle state.
- **Problem addressed:** an implementation could otherwise expose the same label/context through an early-exporter API and silently weaken replay/channel-binding semantics.
- **Strongest engineering idea:** qualify the baseline as regular-exporter-only after the TLS handshake reaches the selected profile's accepted state. Any early-exporter/0-RTT use is a distinct optional profile requiring separate replay, authority, failure, and privacy analysis.
- **Evidence maturity:** externally-reviewed / advanced standards work
- **Limitations:** ZK-ARCHE does not yet define live TLS integration; this is a future integration constraint, not proof of a present flaw.
- **ZK-ARCHE inference:** exporter phase/type must be part of qualification, not just label/context bytes. No 0-RTT application authority is implied by possession of a resumption credential.
- **Impact:** no baseline wire change; avoiding 0-RTT reduces anti-replay state complexity at the cost of one-RTT latency.
- **Rust/C/vector impact:** add mocked/live TLS negative fixtures for early-vs-regular exporter selection, predecessor exporter on resumed connection, and attempted 0-RTT AUTH/DATA.
- **Required next evidence:** TLS integration harness exposing exporter phase/current connection; cross-instance/resumption/early-exporter corpus; explicit baseline 0-RTT non-support.
- **Recommended disposition:** reproduce
