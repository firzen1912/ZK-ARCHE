## 2. Executive synthesis

1. **New November 20 NIST FIPS 140-3 Implementation Guidance D.T and D.U separate validated entropy-source/RBG behavior from the cryptographic module that consumes it.** A successful random-byte API return is insufficient evidence of source readiness, correct operating-environment binding, one-time entropy consumption, and error-state behavior. This improves the concrete R-005 physical-device test design; it does not impose FIPS certification on ZK-ARCHE.
2. **The same November 20 NIST update explicitly recognizes RFC 10024 TLS 1.3 PQ/traditional hybrid group exchange as potentially meeting a defined key-combiner validation scenario.** RFC 10024 itself is **August 2026**, not a November RFC. A standards-based hybrid TLS *transport* comparator is now clearer for optional edge profiles, but does not make the native Ristretto255 device/role proof quantum-resistant.
3. `X25519MLKEM768` requires a **1,216-byte client key share** and **1,120-byte server key share** before full TLS record/handshake overhead. They occur in different TLS flights; summing them and comparing the result to a single 2,048-byte ZK-ARCHE datagram would be erroneous. Constrained MTU, certificate traffic, provider availability and measured resource cost remain unknown.
4. All three selected items retain their original statuses; report/backlog evidence contracts are refined. The existing R-011 authoritative critical-set encoding conflict still blocks complete draft AUTH-v3 Finished interop and requires human review.
5. Nothing here establishes live TLS, physical MCU, entropy-module validation, Rust/C interop, cryptographic proof, PQ-authentication, FIPS certification, or production readiness.

### D20261123-F01 — SP 800-90C RBG validation and module-level entropy use require separately qualified state boundaries

- **Novelty:** `new` for the **November 20, 2026** CMVP D.T/D.U guidance, supplementing already known R-005 entropy/RNG questions.
- **Backlog owner / existing engineering owner:** R-005 (P1 `benchmark`), TD-002, zk208; R-007 and R-009 are cross-references for non-reuse of proof randomness and lifecycle state.
- **Primary source/title/type/date:** NIST and CCCS, *Implementation Guidance for FIPS 140-3 and the CMVP*, updated/effective **2026-11-20**, new ``D.T and D.U. [CMVP dated update](https://csrc.nist.gov/Projects/cryptographic-module-validation-program/fips-140-3-ig-announcements); [official IG PDF](https://csrc.nist.gov/csrc/media/Projects/cryptographic-module-validation-program/documents/fips%20140-3/FIPS%20140-3%20IG.pdf). Regulatory/validation primary text; `D.T ENT.1/ENT.2`, `D.U GenRBG.2/.3/.5/.6`.
- **Source-supported verified claim:** ENT.1 makes qualified entropy-source selection conditional on the **RBG's operating environment** and documented validation/source mappings. ENT.2 prohibits counting or returning a specific source's entropy bits (even a portion) more than once across requests, explicitly including concurrent and predictive paths. D.U requires a *separate* module-level demonstration of RBG operational-environment mapping, boundary/state handling and buffered RBG output single consumption. Under D.U GenRBG.5, an individual entropy-source health-test failure need not automatically put the module in error if the RBG is permitted to continue; failing an RBG health test or terminating RBG operation due to source failures *does* require the applicable module error state. D.T concerns RBG validation; D.U concerns use by modules claiming the relevant validation. These do not establish an automatic requirement on a non-CMVP research prototype.
- **Repository fact:** ZK-ARCHE's existing Rust scalar sampling consumes 64 bytes via `RngCore::fill_bytes` / `OsRng`; C uses libsodium `randombytes_buf`. Their API names alone do not establish ESP32-S3/STM32 entropy readiness, dual-consumer buffer ownership, module health-state recovery, or independently retained physical evidence. TD-002 remains open. The current native profile does not mandate a validated RBG implementation.
- **Bottleneck:** An entropy API that returns a full buffer can still be attached to a source not qualified for the target's startup/sleep state, a stale/shared entropy buffer, or an incorrect failure transition; source-level success cannot be promoted to a device RNG or production security claim.
- **Distinct engineering idea:** Add a **two-boundary entropy provenance and state-transition oracle** to the future local exact-HEAD physical-target manifest: (i) per-device, boot/wake/RF/environment-specific source and readiness/health attribution; (ii) consumer RBG/DRBG/cryptographic-operation buffering, atomic consume-on-read and distinct recoverable-versus-terminal failure handling. Exercise two concurrent consumers, partial buffer, clone, reseed and failed/late readiness with forced faults; assert no repeated seed portions, no partial role proof, no AUTH emission, and no trust/replay state commit on a failed security operation. Record whether the platform/vendor RNG service already enforces these controls rather than inventing a new RNG.
- **Evidence maturity:** `externally-reviewed` for published CMVP guidance; `concept` for ZK-ARCHE adaptation. No local fault injection or physical measurements performed.
- **Limitations / uncertainty:** FIPS CMVP requirements apply to the relevant validation designs/submissions and are **not** universal claims that ZK-ARCHE must seek FIPS 140-3 certification. Operating-environment-dependent source assumptions and the Rust/C platform RNG backends require actual vendor SDK, driver and target-version inspection. Locks and buffers need not exist in every backend. RBG/source error semantics are not interchangeable.
- **ZK-ARCHE inference:** Treat exact target source readiness, unique entropy ownership and complete successful generation as independent evidence obligations. Prefer a fault-aware, operation-atomic platform RNG boundary over accepting arbitrary returned bytes as proof of entropy quality.
- **Likely impact:** **Wire:** none if no protocol change; **CPU/latency:** possibly health/reseed/locking overhead, to measure; **RAM:** scratch/buffer ownership and peak stack, to measure; **flash:** optional metadata/test instrumentation, not quantified; **dependencies:** preserve platform RNG and libsodium/Rust abstractions until target evidence; **trust/privacy:** prevents invalid randomness assumptions that may compromise possession/privacy properties, but does not prove unlinkability or constant time.
- **Rust/C/vector/profile compatibility:** Keep suite `0x0001` and existing valid vector meanings. Introduce conceptual paired Rust/C local **negative** RNG-source and buffered-output fault fixtures, exact target/back-end revision manifest, and no-output/no-commit assertions. No mandatory wire/profile change or selected `iot-core` status change.
- **Required next evidence:** Exact `dev` local builds and source/backend trace; physical STM32H5 and ESP32-S3 boot/wake/RF entropy readiness and fault injections; two-consumer single-consumption, interrupted reseed and state recovery; retained latency/stack/heap/flash/energy traces; match Rust/C error and operation-atomic outcomes; independent review if a stronger claim is proposed.
- **Recommended disposition / weekly finding candidate:** `benchmark`; **yes**, narrowly scoped to source→RBG→module boundary and no FIPS claim.

### D20261123-F02 — Hybrid TLS 1.3 is a qualified *transport* comparator, not a native PQ AUTH replacement

- **Novelty:** `refines`. NIST's **November 20, 2026** D.S update is new; RFC 10024 was published in **August 2026**, not today. The IESG approved the already-reviewed constrained-PQ PQUIP draft -12 as an **Informational** RFC on **November 19**, but it is not yet represented here as a published RFC.
- **Backlog owner / engineering owner:** R-010 P0 `reproduce` and R-003 P3 `benchmark`; zk228 optional exporter/BIND and zk224 optional PQ. R-011 P1 cross-reference.
- **Primary sources/type/date:** NIST/CCCS [CMVP November 20 change summary](https://csrc.nist.gov/Projects/cryptographic-module-validation-program/fips-140-3-ig-announcements), [IG `D.S Additional Comment 8](https://csrc.nist.gov/csrc/media/Projects/cryptographic-module-validation-program/documents/fips%20140-3/FIPS%20140-3%20IG.pdf) (**2026-11-20**); IETF [RFC 10024 ``4–6](https://www.rfc-editor.org/rfc/rfc10024.html), Standards Track (**August 2026**); [IESG PQUIP approval announcement](https://mailarchive.ietf.org/arch/msg/ietf-announce/c60ZO9W8GpnpfDiVMzDTtvoKOI8/) (**2026-11-19**). All primary organizational publications.
- **Source-supported verified claim:** Updated D.S Additional Comment 8 says RFC 10024 TLS 1.3 hybrid key establishment **may** satisfy its Scenario 2 validation conditions using the TLS 1.3 KDF CVL as the approved combiner, not that every implementation is FIPS-validated. RFC 10024 specifies `X25519MLKEM768`, `SecP256r1MLKEM768` and `SecP384r1MLKEM1024`, including key-share/encapsulation checks and TLS failure alerts. For `X25519MLKEM768`, the client's combined share is **1,216 bytes (1,184+32)** and the server's share **1,120 bytes (1,088+32)**; these are separate handshake flights, not entire record sizes. IESG approval of PQUIP -12 gives informational constrained-device deployment guidance stronger process provenance, **not an MCU benchmark or cryptographic certification**.
- **Repository fact:** Current `spec/tls-exporter-channel-binding.md` defines a draft **per-ZK-ARCHE-AUTH-instance** TLS-exporter context; `rust/crates/proto/src/transport/tls_exporter_context.rs` hashes that context but does not negotiate TLS groups or execute live exporters. The native `iot-core` candidate explicitly has `channel_binding=none` and `selectable=0`. ZK-ARCHE authorization is not conferred by TLS. R-011's incompatible critical-set digest preimages remain unresolved.
- **Bottleneck:** A future optional PQ transport could be incorrectly treated as end-to-end PQ device authentication or silently downgraded to classical TLS/no binding; on constrained datagram transports the actual full handshake may exceed the useful packet budget even when its *individual* key shares are below 2,048 bytes.
- **Distinct engineering idea:** Before any optional `BIND`/edge-PQ experiment, define an **authenticated selected-group policy and evidence matrix**, separate from both the RFC 9266 standardized `tls-exporter` channel binding and ZK-ARCHE's application-specific per-instance exporter. For pinned TLS 1.3 Rust/C providers, positively verify the allowed hybrid group, complete handshake, regular exporter with canonical per-AUTH context and final AUTH agreement, plus **negative** classical fallback, unknown/invalid group, bad ML-KEM ciphertext, wrong ALPN/application, reused/crossed AUTH instance, early exporter, old resumed TLS exporter and TLS-terminating proxy. Explicitly distinguish negotiated TLS group authorization from ZK-ARCHE's own role/method/profile authority; an extra field in the exporter context is **not** automatically required by RFC 10024.
- **Evidence maturity:** `externally-reviewed` for the IETF Standards Track RFC and published NIST validation guidance; `concept` for ZK-ARCHE deployment. No live TLS session or Rust/C differential test executed today.
- **Limitations / uncertainty:** The NIST "may meet" statement is conditional; no claim of actual module approval, production provider support, certified X25519 mode, PQ-resistant authentication, nor ciphertext replay resistance beyond the protocol context. Classical TLS certificates or ZK-ARCHE's existing role proofs do not become PQ-resistant merely because the transport key exchange is hybrid. The 1,216/1,120 numbers omit TLS messages, framing, certs, signatures, retry, packet reassembly and energy; actual MCU transport MTUs may be smaller than 2,048 bytes.
- **ZK-ARCHE inference:** An optional TLS 1.3 hybrid *edge* transport may offer a lower-native-wire-churn path to measured session key-establishment migration while preserving the CA-less, infrastructure-independent mandatory baseline. However, end-to-end PQ AUTH/authorization would need a **separate reviewed design and claim**.
- **Likely impact:** **Wire:** separate 1,216-B client and 1,120-B server shares plus full TLS overhead, profile/MTU-dependent fragmentation; **CPU/RAM/flash/energy:** provider- and physical-target-dependent TLS+ML-KEM costs, unknown pending measurements; **dependencies:** optional TLS/ML-KEM libraries only; **trust:** TLS endpoint and proxy termination are distinct from local AUTH/TRUST; **privacy:** hybrid share sizes/fingerprint and TLS metadata remain visible, no anonymity upgrade claimed.
- **Rust/C/vector/profile compatibility:** Do **not** alter native `0x0001`, `iot-core`, existing deterministic vectors, current custom exporter label, or canonical TLS context. Proposed separate *experimental* provider-pinned TLS-hybrid group/ALPN/downgrade corpus and real exporter/Finished Rust/C decision logs; preserve unresolved R-011 canonical critical-set selection as a human gate.
- **Required next evidence:** Official provider supported-group/version inventory, exact-head local pinned TLS 1.3 positive/negative live connection logs on two independent lanes, EKM+per-AUTH checkpoint, TLS resumption/key update and proxy cases; end-to-end handshake bytes/fragmentation/loss/retry and physical MCU/gateway RAM/CPU/flash/energy; authority/downgrade policy mapping; independent review before any optional adoption.
- **Recommended disposition / weekly finding candidate:** R-010 `reproduce`, R-003 `benchmark`; **yes**, with the transport-only, conditional-validation and resource caveats.
