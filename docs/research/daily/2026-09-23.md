## 2. Executive synthesis

- **Return-routability must be a cheap resource gate, never identity or authorization.** CoAP Echo, DTLS 1.3 cookies, and QUIC Retry all use a returned value to establish that a peer can receive at a claimed address and to control amplification/state allocation. QUIC explicitly warns that address-validation tokens are outside the cryptographic handshake and should be used only for information needed for address validation. ZK-ARCHE should preserve the same authority boundary.
- **The gate belongs before every attacker-forced expensive or stateful step on exposed datagram profiles.** R-014 already says “before session reservation, registry scan and expensive proof verification.” HPKE adds a KEM operation at the recipient, so if an encrypted lookup hint is prototyped, source validation should normally precede HPKE decapsulation as well. Otherwise the O(1) lookup optimization can remove registry-scan cost while leaving a public-key CPU oracle reachable by spoofed datagrams.
- **Anti-amplification, anti-state-exhaustion, and anti-CPU-DoS are three different budgets.** A 3x pre-validation byte limit can prevent reflection amplification while still permitting session-slot exhaustion, global/replay-lock contention, registry scans, HPKE decapsulation, or proof work. DTLS 1.3 explicitly states that its cookie mechanism does not protect against DoS from valid source addresses.
- **Current Rust/C behavior gives R-014 a concrete local reproduction target.** The C server reserves a session slot before AUTH_1 candidate scanning and holds `replay_mu` across guarded candidate verification. The Rust server handles UDP under a single shared `ServerState` mutex, performs O(n) PID lookup in `handle_auth_1`, and inserts a retransmit-cache entry after parsed requests, including protocol errors. This report does not claim exploitability; it records resource-ordering and contention surfaces requiring exact-head measurement.
- **HPKE and VOPRF/POPRF answer different privacy questions.** HPKE Base mode can protect lookup metadata from passive observation but does not authenticate the sender and costs an additional KEM operation at each side in the RFC 9180 metadata-protection construction. VOPRF/POPRF can hide the client input from the server but require a two-message public-key protocol and server evaluation/proof work. VOPRF/POPRF should remain research-only unless the threat model specifically requires the registry server not to learn the lookup input.
- **No backlog/status transition is justified.** R-014 remains `prototype`; the existing backlog contract is already directionally correct and should be satisfied with a local exact-head prototype/benchmark before any human promotion request.

## 5. Findings

### D20260923-F01 — Source validation is a non-authoritative reachability/resource gate and should precede HPKE opening

- **Novelty:** refines
- **Backlog owner:** R-014 / R-015
- **Sources:** RFC 9175 (CoAP Echo); RFC 9147 (DTLS 1.3); RFC 9000 (QUIC); RFC 9180 (HPKE)
- **Primary links:** <https://www.rfc-editor.org/rfc/rfc9175.html>; <https://www.rfc-editor.org/rfc/rfc9147.html>; <https://www.rfc-editor.org/rfc/rfc9000.html>; <https://www.rfc-editor.org/rfc/rfc9180.html>
- **Source type / venue:** IETF Standards Track RFCs for CoAP/DTLS/QUIC; CFRG/IRTF Informational RFC for HPKE
- **Publication dates:** February 2022; April 2022; May 2021; February 2022
- **Verified claim:** RFC 9175 Echo can force a client to demonstrate reachability at its claimed network address and is recommended for CoAP amplification mitigation. DTLS 1.3 uses a stateless cookie in HelloRetryRequest to make spoofed-source DoS harder and allows the server to proceed only after cookie validation. QUIC Retry likewise validates a client address, supports stateless encrypted/authenticated tokens, requires token integrity, and warns that tokens are outside the cryptographic handshake and should be used only for address-validation information. RFC 9180's metadata-protection example adds an HPKE Base-mode layer at the cost of one additional KEM operation for both sender and recipient; Base mode provides no remote-party authentication.
- **Repository fact:** exact-current C AUTH_1 processing reserves a session slot before candidate scan/proof verification. Exact-current Rust UDP processing enters the shared state mutex and then invokes O(n) PID lookup without a prior return-routability gate. Neither inspected server entry point exposes an `AUTH_RETRY`/Echo/cookie-style layer before AUTH_1 work.
- **Problem addressed:** an encrypted O(1) registry hint can reduce lookup complexity but still leave spoofed datagrams able to trigger HPKE decapsulation, proof/parsing work, lock contention, error construction, or state allocation unless reachability is established first.
- **Strongest distinct engineering idea:** for exposed datagram profiles, model the pre-auth path as `minimal framing parse -> anti-amplification budget -> stateless return-routability token check -> only then encrypted-hint open / candidate lookup -> cryptographic proof verification -> replay commit / pending-session activation`. The returned token proves only reachability/resource eligibility; it never supplies identity, role, authorization, trust, profile, lineage, or replay authority.
- **Evidence maturity:** externally-reviewed for the reachability/anti-amplification pattern; concept for the ZK-ARCHE ordering.
- **Limitations / uncertainty:** DTLS/QUIC/CoAP mechanisms are comparators, not automatically ZK-ARCHE wire requirements. Source validation mitigates spoofed-source abuse but does not defend against attackers using valid return addresses or on-path attackers. Exact token encoding, rotation, address binding, NAT behavior, privacy, and retransmission rules remain unqualified.
- **ZK-ARCHE inference:** R-014's existing source-validation requirement should encompass HPKE decapsulation itself, not merely session allocation/registry scan/proof verification. A future `AUTH_RETRY` token must remain non-authoritative and short-lived/single-attempt or equivalently privacy-bounded.
- **Wire / CPU / RAM / flash / dependency / trust / privacy impact:** likely one extra datagram round trip for an unvalidated source; a compact retry response/token; cheap symmetric MAC/AEAD verification before public-key work; zero pending-session allocation before validation; no persistent per-client state if token generation is stateless; only rotating server token-secret state is needed. Token reuse/lifetime/address binding can create correlation or NAT/mobility failures and requires R-015 analysis. No new trust authority is created.
- **Rust/C / vector / profile compatibility impact:** add shared deterministic valid/invalid/expired/wrong-address/wrong-port/replayed-token vectors; prove that pre-validation traffic creates no pending AUTH session and cannot reach HPKE/registry/proof code paths; profile-specific behavior for UDP vs TCP; cross-language agreement on ERROR-vs-silence and token expiry/rotation semantics.
- **Required next evidence:** exact `AUTH_RETRY` wire-neutral state model; token construction threat model; Rust/C state-allocation instrumentation; datagram amplification accounting; HPKE-before/after-gate CPU comparison; privacy/linkability review; local exact-head adversarial test corpus.
- **Recommended disposition:** prototype
- **Weekly finding candidate:** yes

### D20260923-F02 — Anti-amplification, anti-state-exhaustion, and anti-CPU-DoS are independent budgets

- **Novelty:** refines
- **Backlog owner:** R-014
- **Sources:** RFC 9000; RFC 9147; RFC 9175; `draft-ietf-core-corr-clar-04` as work-in-progress corroboration only
- **Primary links:** <https://www.rfc-editor.org/rfc/rfc9000.html>; <https://www.rfc-editor.org/rfc/rfc9147.html>; <https://www.rfc-editor.org/rfc/rfc9175.html>; <https://datatracker.ietf.org/doc/draft-ietf-core-corr-clar/>
- **Source type / venue:** IETF Standards Track RFCs plus an active CoRE WG Internet-Draft whose published revision expired 20 September 2026 and therefore is treated only as work in progress
- **Publication dates:** May 2021; April 2022; February 2022; draft revision 19 March 2026
- **Verified claim:** QUIC requires an endpoint to limit data sent to an unvalidated address to three times the amount received. CoAP Echo is designed to establish return reachability and mitigate amplification; current CoRE WG work continues to use a factor-of-three model while explicitly remaining work in progress. DTLS 1.3's cookie mechanism makes spoofed-source DoS harder but explicitly provides no defense against DoS from valid IP addresses.
- **Repository fact:** C can consume a reserved session slot while candidate work is outstanding and can hold its replay mutex during verification. Rust serializes packet dispatch through one global shared-state mutex and performs O(n) lookup inside that critical section. Both paths can therefore have state/CPU/lock costs that are not captured by response-byte amplification alone.
- **Problem addressed:** a server can satisfy a network anti-amplification limit while still being vulnerable to CPU saturation, lock convoying, session-slot exhaustion, retransmit-cache growth, or valid-source flooding.
- **Strongest distinct engineering idea:** qualify three independent pre-auth budgets: `(1) bytes_out / bytes_in before reachability validation`, `(2) persistent or bounded state allocated before validation`, and `(3) CPU/critical-section work before validation`. Add a fourth valid-source budget for work after return-routability succeeds but before authentication succeeds.
- **Evidence maturity:** externally-reviewed for amplification/source-validation limits; software evidence for current local resource ordering; benchmark evidence not yet present.
- **Limitations / uncertainty:** the three-times limit is a transport/protocol comparator, not automatically a ZK-ARCHE normative constant. TCP has different spoofing/amplification properties but remains exposed to connection/resource exhaustion. No claim of exploitability or specific request rate is made without measurement.
- **ZK-ARCHE inference:** R-014 should not accept a single “retry enabled” checkbox as evidence. Promotion needs separate quantitative pass/fail criteria for network amplification, state allocation, CPU/lock time, and valid-source abuse.
- **Wire / CPU / RAM / flash / dependency / trust / privacy impact:** no additional mandatory wire mechanism beyond F01; this mainly changes qualification metrics. Instrumentation cost is local. RAM accounting must include pending sessions and retransmit/error caches. CPU accounting must include parsing, token verification, HPKE, registry lookup, proof verification, replay-cache work, and mutex wait/hold time. No trust-model elevation is introduced.
- **Rust/C / vector / profile compatibility impact:** benchmark both implementations at 10/100/1k/10k registry records with spoofed/unvalidated, validated-but-unauthenticated, replayed, and legitimate traffic; measure mixed UDP/TCP contention; assert zero/explicitly bounded pending state before validation; verify exactly one accepted transition under duplicate races.
- **Required next evidence:** instrumented local exact-head load harness with per-stage CPU cycles/time, mutex wait/hold time, session/retransmit-cache occupancy, packet byte ratios, and accepted-state-transition counts.
- **Recommended disposition:** prototype / benchmark

### D20260923-F03 — HPKE encrypted hints and VOPRF/POPRF protect different observers and impose different DoS costs

- **Novelty:** corroborates / refines
- **Backlog owner:** R-014
- **Sources:** RFC 9180; RFC 9497
- **Primary links:** <https://www.rfc-editor.org/rfc/rfc9180.html>; <https://www.rfc-editor.org/rfc/rfc9497.html>
- **Source type / venue:** CFRG/IRTF Informational RFCs
- **Publication dates:** February 2022; December 2023
- **Verified claim:** RFC 9180 describes metadata protection by wrapping identifying metadata in an additional HPKE Base-mode layer, with an extra KEM operation for sender and recipient; Base mode does not authenticate the remote party. RFC 9497 defines OPRF/VOPRF/POPRF as two-message protocols where the server learns neither the client's private input nor the PRF output; VOPRF/POPRF add verifiability and public-input capability, respectively. RFC 9497 is an IRTF/CFRG Informational RFC, not an Internet Standards Track specification, and notes limits in the available analysis for some multi-key/batching settings.
- **Repository fact:** R-014 already names HPKE encrypted hints as the prototype path and VOPRF/POPRF as a comparator requiring a threat model before promotion. No implementation or vector for either lookup mechanism exists in exact-current Rust/C trees.
- **Problem addressed:** “privacy-preserving O(1) lookup” is underspecified unless the protected observer is named. Passive-link privacy, registry-server input privacy, and sender authentication are different properties and lead to very different cost/round-trip tradeoffs.
- **Strongest distinct engineering idea:** keep the near-term prototype focused on an opaque, non-authoritative registry key carried inside a padded HPKE envelope after source validation. Consider VOPRF/POPRF only if the explicit threat model requires the registry server itself not to learn the lookup input; place any such public-key interaction after return-routability validation and budget its proof/evaluation cost separately.
- **Evidence maturity:** externally-reviewed primitives; concept for ZK-ARCHE composition.
- **Limitations / uncertainty:** HPKE does not by itself solve replay, sender authentication, linkability from stable ciphertext length/timing, or authoritative record binding. VOPRF/POPRF does not by itself solve authorization or source validation and adds interaction/public-key work. Neither option is promoted by this report.
- **ZK-ARCHE inference:** the correct prototype comparison is not “which primitive is more private?” but “which observer must be blinded, under what lookup-key rotation and revocation model, and at what pre-authentication CPU/wire cost?” An enrollment-issued opaque handle is the cheapest comparator but needs rotation/non-reuse analysis to avoid becoming a stable correlator.
- **Wire / CPU / RAM / flash / dependency / trust / privacy impact:** HPKE adds ciphertext/KEM encapsulation bytes and one recipient KEM operation but can retain a one-request AUTH shape after retry validation. VOPRF/POPRF adds at least a two-message interaction plus server group evaluation/proof work and additional transcript/state complexity. Both require key-rotation semantics; neither grants authorization. Padding/epoch rotation affect wire overhead and linkability.
- **Rust/C / vector / profile compatibility impact:** prototype one exact encoding for opaque lookup key, HPKE `info`, AAD, padding class, key epoch, and invalid/rotated/revoked key handling; deterministic cross-language vectors before performance claims. VOPRF remains comparison-only unless an explicit server-oblivious threat requirement is approved.
- **Required next evidence:** HPKE hint deterministic vectors and lookup-key lifecycle model; 10/100/1k/10k benchmark; passive-linkability analysis; side-by-side resource/wire model versus plaintext opaque handle and VOPRF/POPRF; explicit threat-model decision.
- **Recommended disposition:** prototype for HPKE; research-only for VOPRF/POPRF

## 6. Cross-source synthesis

The external standards converge on a narrow but strong rule: **return-routability is a resource-control predicate, not a security-authority predicate**. CoAP Echo, DTLS cookies, and QUIC Retry differ in wire format, but each makes a responder demand evidence that a peer can receive at a claimed address before it fully commits resources or sends a large response. QUIC's explicit restriction that tokens carry only address-validation information is especially aligned with ZK-ARCHE's existing separation of transport metadata from identity/authorization.

The exact-current repository then exposes why ordering matters. C spends a bounded session-table slot before the registry/proof path has completed. Rust avoids that exact reservation pattern but serializes the whole dispatcher under one mutex and performs O(n) PID lookup there. An HPKE lookup hint can improve asymptotic registry work, but RFC 9180 makes clear that it adds a KEM operation. Consequently, **source validation should be cheaper than the work it gates and should sit ahead of both the lookup accelerator and the original O(n) path** on exposed datagram profiles.

The standards also show why one DoS metric is insufficient. A three-times response limit constrains reflection bandwidth; it does not cap server CPU, mutex occupancy, registry scans, session slots, retransmit caches, or a flood sourced from real addresses. ZK-ARCHE therefore needs a staged resource contract rather than a generic “anti-DoS” claim.
