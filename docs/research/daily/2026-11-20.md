## 2. Executive synthesis

1. **New primary standards:** RFC 10021 (*Group OSCORE*) and companion RFC 10020 (*Group Communication for CoAP*) were published as Standards Track RFCs in **November 2026**; the IETF Datatracker entries were updated **2026-11-19**. These are materially stronger publication evidence than their earlier drafts. Their security rules apply to Group OSCORE/CoAP, not automatically to ZK-ARCHE.
2. **Authenticated source is not authenticated intended recipient:** RFC 10021 warns that a group-mode request directed at one member can be redirected to other members because the individual destination is not protected. This concretizes R-008's audience/target binding negative tests without imposing Group OSCORE or a Group Manager on ZK-ARCHE.
3. **A lost replay window must not become an empty trusted window:** RFC 10021 requires invalidation of recreated receiver contexts after relevant state loss and uses a specific CoAP Echo freshness challenge or new security context; ZK-ARCHE's authentic fresh-epoch owner remains unresolved. R-009 needs a *local exact-head* counterexample-driven test, not a protocol shortcut.
4. **Group membership revocation requires complete, authenticated rekey reconciliation:** RFC 10021 specifies generation increments, removal of stale sender credentials/recipient contexts, and a safe fallback when missed generations cannot be reconciled exactly. R-012 already has related FULL/DIFF and tombstone requirements; the new standard refines a group-membership test matrix, not a central service requirement.
5. No implementation execution, new formal proof, measured MCU cost, optional multicast/profile adoption, wire change, roadmap promotion, or improved assurance/field-readiness claim occurred.

### D20261120-F01 — Group sender authentication cannot substitute for authenticated recipient targeting

- **Novelty:** new Standards Track finalization; **refines** existing R-008.
- **Backlog owner / engineering owner:** R-008; zk214 / zk240, TD-004.
- **Source/title/date/type:** IETF **RFC 10021**, *Group Object Security for Constrained RESTful Environments (Group OSCORE)*, Standards Track, **November 2026**, sections 13.8–13.9; companion **RFC 10020**, *Group Communication for CoAP*, Standards Track, **November 2026**, sections 3.6 and 6.3. Datatracker record for RFC 10021 updated 2026-11-19.
- **Primary links:** https://www.rfc-editor.org/rfc/rfc10021.html#section-13.9 ; https://www.rfc-editor.org/rfc/rfc10021.html#section-13.8 ; https://www.rfc-editor.org/rfc/rfc10020.html#section-6.3 .
- **Verified source claim:** In Group OSCORE's *group mode*, an attacker can redirect a unicast request intended for one group member to other group members because the intended recipient's network address is not cryptographically protected; RFC 10021 identifies potentially destructive side effects for non-safe methods and recommends pairwise mode for one-recipient unicast. The Group Manager credential is separately included in authenticated associated data to resist a cross-group-clone attack; this **does not** fix the specific intra-group intended-recipient redirection problem. RFC 10020 discusses multicast fanout/response amplification and congestion-control obligations.
- **Repository fact / anchor:** `spec/p2p-bounded-delegation-decision.md` already requires independently authenticated holder/issuer, explicit audience/scope/generation and local authority; `spec/zk-arche-protocol.md` keeps authentication separate from authorization. The current repository does not define a mandatory Group OSCORE group mode or a multicast-operation protocol.
- **Bottleneck:** cryptographically valid **sender authentication** is insufficient to establish which **receiver(s)** are authorized to execute a received protected effect.
- **Strongest distinct engineering idea:** Add an exact-audience/recipient/operation effect-frontier oracle: same valid cryptographic holder/source proof delivered to target A versus target B; unicast directed to A but forwarded to B; multi-destination versus explicitly single-target operation; and authentication valid while local grant or generation is invalid. Verify `DENY` at the target before side effects, across Rust/C and packet/transport adapters. Include one valid positive execution, and a deliberate negative mutant showing that omitting the target field would allow unintended action.
- **Evidence maturity:** **externally-reviewed** for the standardized Group OSCORE threat and mitigation; **concept** for applying the analogy to ZK-ARCHE. No test execution.
- **Limitations:** Group OSCORE is a different protocol. Its redirect attack does **not** establish the same vulnerability in current ZK-ARCHE. Pairwise Group OSCORE keys do not automatically solve ZK-ARCHE authorization. Ordinary P2P peers may operate without group communications or CoAP.
- **ZK-ARCHE inference:** Keep receiver binding and scope as authorization inputs even if transport-layer authenticated-source checks pass; require target-specific local proof/decision for any proposed multicast or remote-effect extension. Retain offline P2P Common Contract without a Group Manager dependency.
- **Likely impact:** *wire* none for baseline; optional group extensions might need authenticated recipient-set/operation fields and extra bytes; *CPU/RAM* canonical target-set parsing and per-recipient decisions; *flash* no current change; *dependencies* none mandatory; *trust* group possession is not per-operation permission; *privacy* group membership, target sets and response fanout may expose topology; resource and correlation costs unmeasured.
- **Rust/C / vectors / profiles:** paired valid-A/redirected-B/cross-domain/audience mismatch/unknown target/multi-target/unsafe action vectors and local target-policy currentness; no changes to suite `0x0001`, current v2, or draft `iot-core` registry. Additional multicast profile is human-gated and separately benchmarked.
- **Next evidence / disposition:** reproduce receiver-binding negatives at current authorization/operation frontiers, then human review any normative recipient-set encoding. **reproduce**; weekly candidate **yes**.

### D20261120-F02 — Replay-state loss and sender sequence exhaustion require non-vacuous recovery

- **Novelty:** new Standards Track finalization; **refines** R-009.
- **Backlog / engineering owner:** R-009, cross-reference R-012; zk213/zk218, TD-003/TD-004.
- **Source/title/date/type:** IETF RFC 10021, *Group OSCORE*, Standards Track, **November 2026**, sections 2.6.1, 2.6.2, 5.3, and 9.
- **Primary links:** https://www.rfc-editor.org/rfc/rfc10021.html#section-2.6.1 ; https://www.rfc-editor.org/rfc/rfc10021.html#section-2.6.2 ; https://www.rfc-editor.org/rfc/rfc10021.html#section-5.3 ; https://www.rfc-editor.org/rfc/rfc10021.html#section-9 .
- **Verified source claim:** RFC 10021 requires a newly recreated Recipient Context's replay window to be **invalid** under specified prior-state-loss conditions and forbids delivering application messages under invalid replay windows. It specifies discard, CoAP Echo challenge-response, or obtaining new security context parameters as recovery routes. Partial-IV validation/replay-window update is atomic. Sequence-number exhaustion must be detected and further message protection under the exhausted context must stop. Its CoAP Echo method uses explicit per-client challenge/freshness handling and is not a generic clockless recovery proof.
- **Repository fact / anchor:** `spec/replay-continuity.md` defines `CONTINUITY_BROKEN` fail closed; `spec/replay-epoch-recovery.md` expressly leaves the authenticated successor wire/owner implementation blocked. The `iot-core` draft lists a minimum 64-entry accepted-AUTH1 FIFO window but `replay_epoch_rule=unresolved`; Rust/C replay tests and ProVerif model cover bounded abstract continuity, not transport-specific Echo or a proven exact durable transition.
- **Bottleneck / engineering idea:** Exercise an explicit **three-way distinction** in Rust/C and formal-state tests: (a) trusted restored replay state may continue, (b) lost/corrupt/rolled-back state cannot accept by resetting to empty, (c) only an authenticated, locally authorized **lineage-replacement epoch** may allow successor-domain traffic. Include responder challenge duplicates/forgeries as research comparators, not a new required Echo protocol. Count sender nonce/sequence exhaustion separately from verifier replay acceptance and authorization generation.
- **Evidence maturity:** **externally-reviewed** Group OSCORE normative rules; **concept** for ZK-ARCHE-specific recovery and persistence. No local execution/measurement.
- **Limitations:** ZK-ARCHE uses distinct replay structures and identities; CoAP Echo can rely on conditions (including protected security context and optional freshness/timing rules) that do not transfer to a clockless device automatically. A new authenticated replay epoch is still unimplemented; this source alone cannot make `iot-core` selectable.
- **ZK-ARCHE inference:** An authenticated packet with an accepted signature does not repair lost receiver replay continuity, and a fresh transport session is not a fresh security epoch.
- **Likely impact:** *wire* no baseline change; any future recovery handshake needs measured bytes and flight counts; *CPU* challenge/check/KDF work; *RAM* retained per-peer replay windows/challenge state; *flash* durable generation/rollback anchors and wear budget; *dependencies* no mandatory CoAP/OSCORE; *trust* fresh epoch must be locally authorized; *privacy* challenges/retries and state-loss behavior may identify rebooted peers.
- **Rust/C / vector / profiles:** shared positive trusted-restore and authenticated-successor (only when specified) plus negative missing/corrupt/rollback/reuse/out-of-order/replayed challenge/partial-write cases; preserve current v2 and draft profile claims, no fabricated passing tests.
- **Next evidence / disposition:** exact-head Rust/C state-transition and crash-cut corpus, retained proofs/counterexamples and physical MCU restart/flash-wear measurements before any profile promotion. **reproduce**; weekly candidate **yes**.

### D20261120-F03 — Group rekey generations and stale-member history must be reconciled before trust reuse

- **Novelty:** new Standards Track finalization; **refines** existing R-012 (corroborates prior RFC 9770 history-gap research with a distinct group-key angle).
- **Backlog / engineering owner:** R-012, R-008/R-009 cross-references; zk213/zk214/zk240, TD-004.
- **Source/title/date/type:** IETF RFC 10021, *Group OSCORE*, Standards Track, **November 2026**, sections 12.1–12.2 and 13.4; companion RFC 10020, *Group Communication for CoAP*, Standards Track, **November 2026**, section 6.2.1.
- **Primary links:** https://www.rfc-editor.org/rfc/rfc10021.html#section-12.2 ; https://www.rfc-editor.org/rfc/rfc10021.html#section-13.4 ; https://www.rfc-editor.org/rfc/rfc10020.html#section-6.2.1 .
- **Verified source claim:** Group OSCORE requires rekeying when a member leaves, advances a **Key Generation Number**, and communicates new keying material together with stale Sender IDs. Members remove affected authentication credentials and Recipient Contexts. When rekey generations are missed, members must recover exact stale-ID history or remove their existing group credential/recipient contexts rather than retain possibly stale members. The Group Manager owns these functions in **Group OSCORE**.
- **Repository fact / anchor:** `spec/revocation-convergence-and-stale-authorization.md` separates revocation-view freshness and local authorization; `spec/authorization-generation-lifecycle.md` separates local authorization generation from replay epoch and key lineage; R-012 already requires FULL/DIFF history-gap and durable REVOKE-only tombstone testing. Those two independent concepts must not be collapsed into the Group OSCORE Key Generation Number.
- **Bottleneck / strongest distinct idea:** For any future group-credential or multi-peer local-authority use, keep `authority/domain`, authenticated update generation, exact predecessor, stale member set, current authorized roles, receiver context and session key generation **separately attributable**. Test missed generation N→N+2, forged/incomplete revoked-member list, stale recipient context retained after rekey, offline restart, and crash between old-key retirement and successor commit. If complete proof of update continuity is absent, fail closed rather than treating the latest group key alone as sufficient current authorization.
- **Evidence maturity:** **externally-reviewed** for the RFC group scheme; **concept** for ZK-ARCHE adaptation.
- **Limitations:** The RFC's Group Manager is an explicit key-management authority specific to Group OSCORE. ZK-ARCHE requires offline-capable, locally controlled P2P trust; it must **not** import a mandatory centralized group manager, token service, or PKI. Exact global revocation convergence cannot be assumed for disconnected peers. RFC deletion rules for old contexts do not justify deleting ZK-ARCHE's persistent REVOKE-only lineage tombstones.
- **ZK-ARCHE inference:** Separate cryptographic membership rekey from authorization-grant revocation and replay-epoch renewal; annotate stale-peer invalidation at the local protected-operation effect frontier.
- **Likely impact:** *wire* no baseline change, optional authenticated FULL/DIFF/generation updates add bytes; *CPU* verification and key derivation; *RAM* reconciliation buffers/current and pending contexts; *flash* rollback/tombstone metadata and writes; *dependencies* none mandatory; *trust* only accepted local authority can change authorized membership; *privacy* member lists and change cadence leak group structure unless explicitly protected/assessed.
- **Rust/C / vectors / profiles:** paired FULL/DIFF complete/incomplete/foreign-authority/missed-generation stale-peer/drop-old-context/restart and mutation-negative corpora, with consistent allow/deny at P2P and DATA frontiers; no current suite/profile or wire change.
- **Next evidence / disposition:** authoritative local update-provenance definition plus Rust/C exact-head history-gap and stale-group-member denial traces, then constrained RAM/flash/latency measurement and human review of any new group extension. **reproduce**; weekly candidate **yes**.

## 6. Cross-source synthesis

RFC 10021 separates **sender authentication**, **intended-recipient binding**, **per-receiver replay continuity**, **group-membership key generation**, and **authorization to act**; RFC 10020 adds group-request amplification/congestion considerations. A verified sender or current encryption key is not sufficient to prove an action was intended for this receiver, that receiver replay state is current, or locally authorized rights remain valid. ZK-ARCHE already mandates these as distinct decision surfaces; newly published standards sharpen the negative tests but do not replace its Common Contract or authorize a centralized/group protocol. Current evidence remains design-level until reproduced against actual Rust/C implementation and retained formal models.
