## 2. Executive synthesis

1. **Cross-language invalid-input asymmetry is visible at the public CDS-OR prover entry points.** The Rust prover locates a true-role index via `.expect(...)` and allocates branch vectors from the supplied list length without an explicit bound in that function. The C prover returns typed errors for zero or greater-than-`AUTH_MAX_ROLES` counts and for a missing role. That is a source-level API-contract discrepancy, not a demonstrated network exploit. Ingress validation and runtime behavior require exact-head testing.
2. **Constrained PQ key size cannot be judged solely by retained flash size.** Seed-only storage, expanded-key caching, import consistency, protected backup, restart and secure erasure require separate CPU/RAM/flash/trust/energy measurements. The PQUIP WG -12 draft and RFCs 9881/9935 provide source-backed comparators; no PQ profile is adopted.
3. **ML-DSA signing has a measurable latency distribution, not just one throughput number.** PQUIP -12 estimates ML-DSA-65 at 5.137 iterations on average and 22 iterations for 99% completion, under its model. This is a benchmark design requirement for *optional* signing workloads, not proof of actual ZK-ARCHE MCU timing.
4. No executable Rust/C test, cryptographic proof, formal result, device benchmark, revised wire format, suite, default trust policy or production claim was established today. R-007/R-005/R-003 remain unpromoted.

Rust verifier does not apply the same explicit 8-branch maximum. Positive vector parity does not test this behavior. Whether public protocol ingress is fully prevalidated is not established by this function-level read.

Create one *API → framing → authenticated effect* decision oracle with zero branches, 1/8/9 branches, role absent, duplicate/out-of-order roles, count/length mismatch, and malformed points/scalars. Record Rust panic/unwind/abort behavior separately from typed C errors. Check that malformed public inputs cannot induce unbounded allocation, partial proof emission, or trust/session mutation. Also retain paired valid proof/one-mutation reject tests; do not make every negative test pass by rendering valid AUTH unreachable.

- **Limitations:** An external caller could validate the role list before these exported functions; no ingress reachability, panic propagation, allocation exhaustion, compiled side channel, or field exploit has been shown. The scalar challenge/transcript structure and role witness-dependent operation asymmetry identified on November 6 remain separately open.
- **ZK-ARCHE inference:** Establish the same bounded, canonical, fail-closed role-set semantics in both implementation lanes without silently altering the mandatory suite or normal AUTH. Do not interpret a source discrepancy as evidence of production exploitability.
- **Likely impact:** *Wire* no justified immediate change; *RAM* Rust O(n) vector allocation versus C fixed maximum; *CPU* attacker-influenced invalid-list work can vary if exposed; *flash/dependencies* no proposed new dependency; *trust* failed proof must not establish role authorization; *privacy* error and timing-class differences could form an oracle if externally observable (unmeasured). ### D20261119-F02 — PQ seed storage is a custody and import-consistency decision, not a free RAM optimization

- **Novelty / backlog:** refines R-005 P1, R-003 P3 cross-reference (no duplicate question).
- **Primary sources, dates and types:** IETF PQUIP WG, *Adapting Constrained Devices for Post-Quantum Cryptography*, `draft-ietf-pquip-pqc-hsm-constrained-12`, **2026-11-15**, Informational Internet-Draft, https://datatracker.ietf.org/doc/html/draft-ietf-pquip-pqc-hsm-constrained-12 ; IETF RFC **9881** (ML-DSA key representations, 2025), https://www.rfc-editor.org/rfc/rfc9881.html ; RFC **9935** (ML-KEM key representations, March 2026), https://www.rfc-editor.org/rfc/rfc9935.html .
- **Verified source claim:** PQUIP distinguishes storing a protected seed versus a full expanded key; seed-only saves *persistent* storage at the price of regeneration CPU, latency and potentially transient RAM. Seeds need private-key-grade protection. RFC 9881 describes ML-DSA's 32-byte seed representation; RFC 9935 describes ML-KEM's **64-byte** internal seed material (`d,z`) and consistent expanded-key import tests. These formats are X.509/ASN.1 interoperability references, not requirements to introduce X.509 into ZK-ARCHE.
- **Repository fact / owner:** R-005, R-003; `spec/iot-profiles.md` remains unselectable and target measurements remain missing under TD-002; current suite `0x0001` is classical Ristretto255/SHA-256, not ML-KEM/ML-DSA.
- **Bottleneck / distinct engineering idea:** Qualify **three separate device storage profiles** for one explicitly optional PQ candidate: (A) retained seed/ephemeral expanded secret, (B) protected cached expanded key, (C) externally provisioned seed+key with exact keypair consistency validation. Each must declare trust boundary, key export/backup/recovery, mismatch rejection, secure erasure and restart behavior. Measure flash footprint *and* peak transient stack/heap, key-generation/derivation cycles, energy, and flash write/endurance. Protect against rollback of credential generation and reuse of erased provisional material.
- **Evidence maturity:** **concept** for ZK-ARCHE; WG draft and RFC are primary normative/background evidence, not local physical-target measurements.
- **Limitations:** Seed derivation cost, secure-element capacities and support for importing/exporting seeds are implementation-specific. The draft does not supply ZK-ARCHE Rust/C performance measurements. Do not infer that any generic seed mode is sufficient for recovery or hardware protection.
- **ZK-ARCHE inference:** Optional PQ profile selection must account for peak key expansion and opaque-module import/consistency semantics, not just public-key and ciphertext size. Seed export may conflict with a non-exportable-key threat model; require explicit human review rather than inventing a mandatory security module.
- **Likely impact:** *Wire* no baseline change, optional profile transport unmeasured; *CPU/energy* increased on-demand expansion; *RAM/stack* transient expanded key and caches; *flash* seed-only may reduce retained size, caches enlarge it; *dependencies* optional PQ provider/HSM; *trust/privacy* seed compromise exposes derived keys, backup/transfer changes trust assumptions; no direct privacy improvement.
- **Rust/C/vectors/profiles:** Paired seed→keypair deterministic/independent reference vectors, inconsistent seed+expanded-key negative imports, module API failure/partial-generation tests, restart/zeroization and provider-version manifests; separate physical STM32/ESP32-S3 profiles before any optional promotion. Existing `0x0001`, v2/v3 and profile vectors unchanged.
- **Next evidence / disposition:** one provider-pinned ML-KEM-768 optional gateway/edge candidate and storage-mode microbenchmark with precise device HSM/RNG boundary. **benchmark**; weekly candidate **yes**.

### D20261119-F03 — ML-DSA signing needs quantile and failure-iteration benchmarks rather than one average

- **Novelty / backlog:** refines R-003 P3 and R-005 cross-reference; the research question is optional signature-bearing PQ authentication, not a claim about current Ristretto CDS-OR.
- **Primary sources / date / type:** PQUIP WG `draft-ietf-pquip-pqc-hsm-constrained-12`, **2026-11-15**, active Informational Internet-Draft, https://datatracker.ietf.org/doc/html/draft-ietf-pquip-pqc-hsm-constrained-12#section-5.1 ; NIST **FIPS 204**, issued **2024-08-13**, with a **2026-07-31** note pointing to potential errata, https://csrc.nist.gov/pubs/fips/204/final .
- **Verified source claim:** Under the draft's geometric model of ML-DSA rejection sampling, expected loop counts are 4.361 (ML-DSA-44), 5.137 (ML-DSA-65), and 3.905 (ML-DSA-87). Its 99%-completion counts are 18, **22**, and 16 respectively. The draft discusses an 814-versus-820/821 iteration-tail calculation; this is a potential-update analysis, **not** an already adopted ZK-ARCHE or FIPS amendment. Signature *verification* does not run this signing-rejection loop.
- **Repository fact / owner:** R-003 includes comparison of PQ signature-based versus KEM-based authentication; R-005 requires real device CPU/energy manifests; TD-002 physical measurements remain absent. No optional ML-DSA signer is implemented as a required ZK-ARCHE suite.
- **Bottleneck / distinct engineering idea:** A candidate PQ-authenticated profile can look feasible from mean MCU signing latency yet exceed mission energy or request-deadline budgets at the tail. Measure per-iteration fixed/variable cost; median, p95, p99 and high-iteration timeout behavior; bounded queue/backpressure and retry semantics; report signing separate from verification, KEM encapsulation/decapsulation, and general AUTH. Use repeatable benchmark seeds while separately qualifying production RNG, and test failures do not partially publish an authentication effect.
- **Evidence maturity:** **concept** for ZK-ARCHE; WG draft model is not an actual Rust/C/MCU measurement.
- **Limitations:** Probabilistic model and per-parameter probabilities are not direct target timing distributions. Secret-dependent side-channel security and NIST conformance require separate analysis; do not change standardized iteration limits from a research draft.
- **ZK-ARCHE inference:** Optional PQ signing may fit gateway tiers but requires worst-tail, denial-of-service and energy measurements before influencing resource profiles. Mandatory constrained-suite `0x0001` remains unchanged.
- **Likely impact:** *Wire* optional signature size not assessed here, current zero; *CPU/energy* variable due to rejection iterations; *RAM* buffers/NTT intermediates; *flash* optional PQ library; *dependencies* optional provider; *trust/privacy* timing and response divergence could form an observation channel if correlated, unmeasured.
- **Rust/C/vectors/profiles:** Same input workload and profile-capped timeout across pinned Rust/C provider builds; retained loop-count distribution, negative timeout/failed-signature tests and complete wire sizes, then hardware manifest. No changes to existing vectors or mandatory profiles.

## 6. Cross-source synthesis

The CFRG proof-validation comparator and the PQUIP resource advice highlight separate hidden assumptions: a mathematically meaningful proof still needs bounded, consistent library/parser input behavior, while a small stored PQ seed does not imply a small, constant-time or low-energy authentication operation. ZK-ARCHE must preserve three independent gates: accepted cryptographic statement and authorization, resource-bounded exact Rust/C behavior, and reproducible physical/evidence qualification. Optional PQ work cannot repair TD-001 or R-011; likewise no draft's recommendation replaces local tests, external review or actual constrained measurements.
