## 2. Executive synthesis

1. Constant-time assurance is a property of a concrete compiled artifact on a concrete target, not merely of source code or a library API. Libsodium 1.0.21 reports introducing optimization blockers in critical paths after specific RISC-V compiler/options combinations produced unwanted conditional jumps. Version 1.0.22 includes those 1.0.21-stable changes. Current ZK-ARCHE C uses the environment's libsodium through pkg-config and generic -O2, so a side-channel claim needs exact library/compiler/flags/target provenance rather than "uses libsodium."

2. The Rust lane has the same qualification boundary. Exact-current ZK-ARCHE locks curve25519-dalek 4.1.3 and subtle 2.6.1. Dalek says its operations are written with constant-time logic but scopes its assembly-level confidence to at least x86_64; subtle calls its protection best-effort and warns that debug builds contain secret-dependent invariant branches. Those statements do not automatically qualify ESP32-S3, STM32, or another non-x86 target.

3. Source-level equalization of the CDS prover remains necessary but is not sufficient. Rust and C still select the hidden true-role branch and execute a different random/arithmetic schedule for that branch than for simulated branches. Equalizing those paths should precede strong privacy claims, after which the compiled artifact still needs target-specific leakage evidence.

4. The repository already has much of the right provenance vocabulary. The constrained-target manifest records compiler, flags, backend/version, architecture, build profile, and firmware hash. The general qualification record captures compiler versions but not the linked libsodium build or complete compiler-flag/backend tuple. R-007 should explicitly require dependency/backend provenance, artifact identity, generated-code review, and retained leakage evidence.

5. No status promotion is justified. R-007 remains reproduce and TD-001 remains open. The backlog evidence contract is refined because the fresh sources materially change what counts as sufficient side-channel evidence.

### D20260925-F01 — Compiler and target transformations are part of the constant-time trust boundary

- Novelty: new/refines.
- Backlog owner: R-007; supporting execution-context owner R-005/zk208.
- Sources: libsodium 1.0.21 and 1.0.22 official release notes; CFRG Sigma Protocols draft.
- Primary links: https://github.com/jedisct1/libsodium/releases/tag/1.0.21-RELEASE ; https://github.com/jedisct1/libsodium/releases/tag/1.0.22-RELEASE ; https://datatracker.ietf.org/doc/draft-irtf-cfrg-sigma-protocols/
- Source type / venue: official cryptographic-library releases; IRTF/CFRG Internet-Draft.
- Publication/release date: libsodium 1.0.21 on 2026-01-06; 1.0.22 on 2026-04-09; Sigma Protocols draft-03 updated 2026-08-16.
- Verified claim: libsodium 1.0.21 states that optimization blockers were added in critical code paths because unwanted conditional jumps had been observed on RISC-V under specific compilers and options. Version 1.0.22 includes 1.0.21-stable changes. The current CFRG Sigma draft treats witnesses, nonces, and prover state as secret, says secret-dependent group/field work should execute in constant time, and specifically recommends that real and simulated OR clauses follow the same code path with constant-time selection.
- Existing engineering owner: TD-001; zk208 side-channel/execution-context evidence; zk209 independent proof review.
- Repository fact: ZK-ARCHE C compiles with generic cc, default -O2, and libsodium found by pkg-config. Its CDS prover still has a source-level true-index branch with different random consumption and arithmetic.
- Bottleneck addressed: source review can miss compiler-introduced conditional control flow, while a library name/version alone cannot establish constant-time behavior for a different target/compiler/options tuple.
- Distinct engineering idea: define side-channel evidence against a compiled-artifact identity: repository commit, dependency source/package and version, compiler and version, optimization/LTO flags, target triple/ISA/features, crypto backend, binary/firmware hash, and relevant function disassembly or equivalent generated-code record. Treat a material tuple change as a new qualification identity.
- Evidence maturity: upstream implementation evidence plus CFRG guidance.
- Limitations: the libsodium release note does not establish that its Ristretto255 path used by ZK-ARCHE was affected, nor that ZK-ARCHE is exploitable on RISC-V or another target. It establishes a compiler/target risk class that raises the evidence threshold.
- ZK-ARCHE relevance / inference: R-007 should not be considered side-channel reproduced merely because source branches are later equalized or because libsodium is intended for constant-time cryptography. Exact generated code and target observations remain in scope.
- Likely wire/CPU/RAM/flash/dependency/trust/privacy impact: no wire change; small or no steady-state RAM impact; path equalization/optimization barriers can alter CPU latency and code size; provenance collection adds build/evidence complexity but no runtime authority or online dependency; privacy confidence becomes artifact/target-scoped.
- Rust/C/vector/profile compatibility impact: canonical proof bytes can remain unchanged. C evidence must bind the linked libsodium build and compiler configuration; Rust needs analogous dependency/backend/toolchain identity. Vector parity remains necessary for semantics but orthogonal to leakage.
- Disposition: reproduce.
- Required next evidence: equalize witness-dependent source scheduling; retain generated-code/disassembly evidence; execute target-specific timing and, where physical attackers are in scope, power/EM leakage tests across hidden-role classes; repeat after compiler/dependency/backend changes.

## 6. Cross-source synthesis

Today's evidence changes the R-007 assurance model from a source-only question into a layered artifact qualification problem:

    witness-independent source schedule
                  +
    constant-time primitive/backend contract
                  +
    exact dependency + compiler + flags + target provenance
                  +
    generated-code / artifact identity review
                  +
    target timing leakage test
                  +
    power/EM evidence where physical attacker is in scope
                  ↓
    scoped side-channel evidence for one build/target

None of these layers substitutes for mathematical proof review. Equalizing the real/simulated CDS clauses addresses a known source-level privacy concern. Library/toolchain evidence addresses whether supposedly constant-time operations remain so after compilation. Statistical testing looks for observable leakage in the concrete artifact but cannot prove its absence.

Claim separation remains:

- vector parity is not side-channel parity;
- source constant-time is not compiled-artifact constant-time;
- library constant-time is not protocol-glue constant-time;
- one-target evidence is not cross-target evidence.
